The host firewall

The network redesign of 2026-10-27 changes this page. hopbox leaves the vRack and the OVHcloud API, and the servers talk over their public addresses (Q90). This page describes the code after milestone N31, which removes the vRack zone.

The host firewall is the nftables table inet hopbox_host of every server of an install. It makes the edge servers the bastion of the install (rules 2 and 5). Only an edge server takes traffic from the whole internet. On its public address, a control server or a node takes only the traffic of the install, from the peer addresses of the servers (Sets). A peer address is the public IPv4 address at which the other servers reach a server (Enrollment and the install PKI). On the mesh, each server takes only the ports of its roles. Operators reach a server that is not an edge server by SSH only through an edge server as a jump host. On an edge server, the table also forwards and translates the egress of the machines (The egress of the machines).

The firewall is in internal/hostfw. hopboxd run starts it on every server, right after the metrics listener and before the units of the roles (hopboxd). The provider block of the Terraform provider names the jump host in ssh_jump_host (hopbox Terraform provider).

In the examples, the edge servers have the peer addresses 203.0.113.21 and 203.0.113.22.

Zones

Section titled “Zones”

The table sorts each new connection by the interface that takes it. A zone is the set of interfaces that share one list of open ports.

Zone Interfaces Sources that a port takes
Loopback lo Every source. The table takes every packet of loopback.
Mesh hbm0 The mesh range 10.239.0.0/16.
Tap devices The tap devices of the machines on a node, hbt* The table takes them, and leaves them to the table inet hopbox_node (the node network), which owns all traffic of the machines.
Public Each other interface, such as the uplink or a private network of the provider. The egress tunnels hbe* are in it too, so a machine reaches the public ports of an edge server through its tunnel. Every source for the ports of the roles edge and dns. Each port of the traffic of the install takes only its set (Sets).

A machine behind an egress tunnel reaches the public ports of its edge server at the floating addresses, as the internet does. It reaches no port at a peer address of the install. Its own edge server is no exception (The egress of the machines). Each zone ends with a drop, so a port that no role opens takes nothing. The replies of the connections of the server pass in every zone, and so do the ICMP messages of ICMP and DHCPv6.

Ports

Section titled “Ports”

Each role opens its ports. A server with more than one role opens the ports of each role.

Role Zone Port Source Use
A server without the role edge Public TCP 22 The set jump_hosts. While the server never knew an edge server, every source (Never a lockout). The SSH of the operators and of the provider through an edge server (The jump hosts).
A server that enrolls: node, dns, or edge Public UDP 51820 The set peers The WireGuard packets of the mesh, which runs on the peer addresses (the mesh).
edge, on a server that enrolls public UDP 51821 The set peers The egress tunnel hbe0, which takes the egress of the nodes (the egress of the machines).
node without edge, on a server that enrolls public UDP 51821 to 51836 The set peers The egress tunnels hbe0 to hbe15 of the node (the egress of the machines).
control Public TCP 7443, the port of control.internal_listen The sets peers and registered The internal listener on the peer address of the control server: the enrollment, the control channels, and the API and the console that the edge servers forward (the internal listener).
node Mesh TCP 7444 The mesh range The disk listener of the cold moves (Cold move).
edge Public TCP 22 Every source The sshd of the operators. The edge server is the jump host.
edge Public TCP 80 and 443 Every source The HTTP and HTTPS listeners (the edge role).
edge Public TCP 2222, the port of edge.ssh_listen, only for connections that a redirect sent there Every source The SSH ports of the machines, TCP 10000 to 30000. The table inet hopbox_edge sends them to edge.ssh_listen (the SSH front door), so the input hook sees port 2222. When conntrack records the redirect (ct status dnat), the rule takes the connection there. Any redirect or destination NAT to that port passes, also one that an operator with edge.ssh_redirect = false writes. A connection straight to port 2222 takes nothing.
dns Public TCP and UDP 53 Every source The DNS role (the DNS role).

The edge servers of an install run the DNS role. Port 53 follows the role dns, not the role edge, as the owner decided on 2026-10-27 (plan question Q74). So a server with the DNS role alone, as in Serve the domain of an install with the DNS role, opens port 53 and no edge port. An edge server without the DNS role keeps port 53 closed. The table opens the same ports whatever the listen addresses of the config say, as the owner decided on 2026-10-27 (plan question Q80). A listener on another port, such as edge.https_listen = ":8443", takes no connection from outside the server. So at its start, hopboxd logs the host firewall opens no public port for this listener, so it takes no connection from outside the server at level warn, for each such listener of edge.https_listen, edge.http_listen, and dns.listen. A listener on loopback gets no warning.

The other listeners of hopboxd take nothing from outside the server: the API listener on 127.0.0.1:7080, the metrics listener on 127.0.0.1:9464, and the listener of the SSH front door on port 2222.

The ports follow the roles of the bootstrap config at the start of hopboxd. So when a removal takes a role from a running server, the restart at its end closes the ports of that role: 80, 443, and the SSH ports of the machines for edge, 53 for dns, and 7444 for node (the admin API). Port 22 of a server that is no longer an edge takes only the set jump_hosts, which the server knew as an edge already. The other servers get the new edge set and the new jump_hosts within one heartbeat (the mesh).

Sets

Section titled “Sets”

The table holds up to four sets of IPv4 addresses. A port of the traffic of the install takes only the addresses of its set.

Set Holds Ports that take it
peers The peer addresses of the servers of the install that are not decommissioned (Control store tables). A server without a peer address is not in it. It also holds the address of the internal listener of each live control process on a peer address (Control store tables). A server with the control role alone has no row in servers, so this address lets the control servers reach the internal listeners of each other. This is a build default of N28, not an owner decision. Public UDP 51820, the UDP ports of the egress tunnels, and TCP 7443 of a control server.
jump_hosts The peer addresses of the edge servers among them. Public TCP 22 of a server without the role edge.
registered The peer addresses of the enrollment tokens that are not used and not expired (Enrollment and the install PKI). Only a server with the control role has this set. Public TCP 7443 of a control server.
known_peers Every peer address that the install knows, and each address of peers. These are the peer addresses of the servers that are not decommissioned, and the address of the internal listener of each row of control_processes, live or not. An address leaves only with the decommission of its server or with the sweep of its row, 24 hours after the last renewal, never with a missed heartbeat. Only a server with the egress of the machines, an edge server, has this set. A control role of an older release sends no known peers, and the set then holds peers alone. This is a build default of N28, not an owner decision. None. The egress of the machines reaches none of its addresses (The egress of the machines).

A registered address reaches the internal listener only while its token works. So a new server enrolls from its peer address, and its later control channel comes from the same address, which peers then holds. hopboxd binds the control channel to the peer address once the server has its sets (the edge role). A peer address stays in peers until its server is decommissioned. Providers reuse addresses, so a stranger can get the address of a decommissioned server.

The sets come from two places:

Server Where the sets come from
A server with the control role The control role reads peers, jump_hosts, known_peers, and registered from the store every second (Control store tables). So a new enrollment token reaches registered within 2 s, and the Terraform provider waits for that before it enrolls a server. The control role hands the sets to the firewall only after a change.
A server without the control role Each mesh that the control role sends holds peers, jump_hosts, and known_peers in its field firewall (the control channel). A change reaches the server within one heartbeat, 5 s. The agent hands the sets to the firewall before the mesh device takes the mesh. A mesh of a control role of an older release has no firewall, and the server keeps the sets that it has.

Each server keeps its last peers, jump_hosts, and known peers in the file <data_dir>/hostfw/peers (Server layout), and writes it after each change, through a temp file and a rename. The start of hopboxd loads the file before the control channel comes back. So a restart without a control server keeps the mesh port and the way in through the jump hosts. Without the file, the start takes the sets of the table before it. It never takes registered from the file or the table: the control role reads it within a second, and each registration ends with its token.

The file has one address on each line, after its kind. The kinds are peer, jump_host, and known_peer. Two more lines stand alone, without an address. The line knew_edge records that the server knew an edge server (Never a lockout). The line known_peers_whole records that the known peers came from the control role (The egress of the machines). A line that starts with # is a comment:

Each check compares the elements of each set with the sets of the firewall. So a flush of a set alone comes back within 2 s, and so does a delete of an element. Each new set from the control role or from a mesh checks the table again, also the same sets.

The jump hosts

Section titled “The jump hosts”

Port 22 of the public interface of a server without the role edge takes the peer addresses of the edge servers alone, the set jump_hosts. An edge server reaches a peer address straight over the internet. So the SSH of an operator through an edge server comes from the peer address of the edge server. That SSH leaves from the source that the kernel picks, so the default route of the edge server must carry its peer address as the source. hopboxd sets that source again when the route loses it (the edge role). The Terraform provider dials the peer address of a server through the jump host too.

An edge list that turns empty keeps the last jump_hosts, as the owner decided on 2026-10-27 (plan question Q93). So the last edge server that leaves stays a jump host of each server, and hopboxd logs the install has no edge server now, so port 22 of the public interface keeps the last jump hosts at level warn. A new edge server replaces the list. The kept address has the risk of reuse of the peers (Sets): a stranger who gets the address of the last edge server that left reaches port 22 of each server, but still needs an SSH key.

Never a lockout

Section titled “Never a lockout”

A change of the table never closes the way of an operator into a server in a way that this section does not name. The owner decided the ways of SSH on 2026-10-27 (plan question Q93, which replaces Q75):

  • A server that never knew an edge server keeps port 22 open on its public interface, to every source. No jump host reaches it. This covers a new server before its first control channel, and a first server without the edge role, such as ks. A server knew an edge server once its set jump_hosts had an address. While port 22 of its public interface takes every source, hopboxd logs this server never knew an edge server, so no jump host reaches it, and its public interface keeps port 22 open at level warn, at each install of the table. An edge server opens port 22 to every source anyway.
  • A server that knew an edge server keeps port 22 of its public interface closed to every address outside jump_hosts, also while that set is empty. This holds after a restart, through the file <data_dir>/hostfw/peers, and after the last edge server left (The jump hosts). The way back after a lockout is the rescue mode or the console of the provider. A computer that the operator owns has no such provider tools, so its way back is its own console.
  • A server that had a vRack address under a release before N31 counts as a server that knew an edge server. So port 22 of its public interface stays closed, also before it knew an edge server. The owner decided this on 2026-10-27 (plan question Q75, and question Q10 of the review of N16). Such a release kept the file <data_dir>/hostfw/vrack-interface. At its start, hopboxd writes the line knew_edge to the file peers, and then removes the file vrack-interface. If the write fails, the file stays, and the next start tries again.
  • One netlink batch replaces the whole table. If the kernel refuses the batch, the table before it stays as it was.
  • The table outlives hopboxd. A stop, a crash, or an upgrade of hopboxd keeps the table, so SSH through the jump host goes on.
  • A destroy of the Terraform provider stops hopboxd, and then removes the table. Its public address then takes SSH again (The Terraform provider).

To let a server that left its install for good take SSH from every source again, run these commands on it:

While the server is still in an install, the next sets of the control role close port 22 again.

A release from before the host firewall keeps the table of a later release, and never changes its jump hosts. So the Terraform provider removes the table after it moves a server to such a release (hopbox Terraform provider). The owner decided it on 2026-10-27 (plan question Q79). It reads the release from hopboxd version --json: from N16 on, the field features names host-firewall (the version command). After a move by hand, run sudo nft delete table inet hopbox_host on the server through the jump host.

If a server stays closed, the rescue mode of its provider boots it into another system, which runs no table.

The Terraform provider

Section titled “The Terraform provider”

The provider reaches a server without the role edge through the jump host of ssh_jump_host, which dials the peer address of the server (hopbox Terraform provider). If the provider block has no ssh_jump_host, a create or an update of such a server fails before any step. The owner decided two more rules of the provider on 2026-10-27:

  • An import takes the peer address of the server alone, such as 203.0.113.21. The import of a server without the role edge dials that address through the jump host. The install must know a server with that peer address, or the import fails (plan question Q96, hopbox Terraform provider).
  • A destroy removes the table once hopboxd stopped. It also removes the files peers and vrack-interface of <data_dir>/hostfw. A server of this release has no file vrack-interface, but a test server of a build before N31 can keep one. So a later hopboxd on the server never starts with the jump hosts of the old install. So its public address takes SSH again (plan question Q77, hopbox Terraform provider). A server without nft gets the package nftables first. The login, the stop of hopboxd, or the removal of the table can fail. On a server without the role edge, the table then keeps port 22 closed to every address but the edge servers. The jump host still reaches the server. So the destroy fails with an error that names the commands to run, and keeps the resource. The next destroy goes on.

The egress of the machines

Section titled “The egress of the machines”

An edge server that enrolls takes the egress of the machines of the nodes from its egress tunnel hbe0 (the egress of the machines). Its table then has six more chains:

Chain Hook and priority What it does
egress_mark prerouting, mangle Puts the conntrack mark bit 0x20000000 on each new connection from a tunnel. Puts the packet mark 0x68620100 on each reply of such a connection. The rule of that mark routes the reply back into the tunnel, and not over the mesh (the egress of the machines).
egress_output output, mangle, of the type route Puts the same mark on each reply of the server itself. A machine reaches a public port of its own edge server, and the reply goes back through the tunnel (plan question Q52).
forward forward, filter Sends each packet from a tunnel to the chain egress. Lets the replies into a tunnel, and drops each other packet into a tunnel. On a server with the node role, it takes the local exit too. It drops each packet from a tap device that conntrack marks invalid, and each packet from a tap device to an address of the set known_peers. It refuses each IPv6 packet from a tap device to 2000::/3 that leaves through another interface than the uplink. Drops the forwarded traffic of the other interfaces, as The forward guard says.
egress none, the chain forward jumps to it Drops each packet that conntrack marks invalid. Drops each destination in the set known_peers. Drops the private ranges of the node table, which hold the mesh range. Drops each IPv6 destination outside 2000::/3. Accepts IPv4 to the public zone. Accepts IPv6 from fd65:1c74:e769::/48 only to the uplink, and only while the uplink has a global IPv6 address. Refuses the rest: TCP with a reset, and other packets with ICMP administratively prohibited.
egress_nat postrouting, srcnat, of the type nat Translates the source of the egress. IPv4 from a tunnel to the public zone gets edge.public_ipv4, or the masquerade without that key. IPv6 of every machine to the uplink gets the global IPv6 address of the uplink (NAT66). This holds for the tunnel and for the local exit.
egress_guard postrouting, srcnat + 10 Drops each packet with a source in 10.240.0.0/12 or fd65:1c74:e769::/48 that leaves through an interface other than lo, hbm0, a tunnel, or a tap device. It comes after the source NAT, so it sees the translated source.

The table of the node network translates the IPv4 egress of the machines of a node with the edge role. So the rule of IPv4 in egress_nat takes the egress of a tunnel alone (the node network). The rule of IPv6 takes the machines of the tunnel and of the local exit alike.

The egress of a machine reaches no peer address of the install, through a tunnel or through the local exit. An edge server without edge.public_ipv4 translates the IPv4 egress to the address of its uplink, which is its peer address. Without the drop, a machine reaches the ports that the other servers open to the set peers, such as the internal listener of a control server. The drop holds also when the edge server is a control server. It also holds for a server with the control role alone that stopped: such a server has no row in servers, so it leaves peers 20 s after its stop, but its own table keeps its sets and still takes this edge. It stays in known_peers until the sweep of its row. This is a known limit: a control server that stays down for more than 24 hours leaves known_peers. At its return, its start writes its row again, and the edges drop its address again within seconds.

The drop needs the whole set known_peers. The start of hopboxd knows the whole set when the file <data_dir>/hostfw/peers has the line known_peers_whole and no line that the start skips. The firewall writes that line once the sets come from the control role or from a mesh. So an empty set counts as whole too, such as on a server without a peer address. The table before the start never counts, because a start with a closed egress installs a partial set too. Until then, the chain egress drops each packet, and the chain input drops each packet from a tunnel. On a server with the node role, the chain forward also drops each packet from a tap device to the public zone. So no machine reaches a public address before the first sets of the control role or of a mesh, and no machine reaches a peer that the set lacks. This covers these starts:

  • A start with a file of a later release that has a line that this hopboxd skips.
  • A start with a file that it cannot read.
  • A start with a file of a release before N28, without the line known_peers_whole.
  • A start after a reboot, without the file.
  • A start without the file that adopts the table before it.
  • A second start before the first sets, after a start with a closed egress. The first start writes the file again without known_peers_whole.

At such a start, hopboxd logs the host firewall does not know every peer address of the install yet, so the egress of the machines reaches no public address until the first sets of the control plane at level warn. The first sets open the egress again. This is a build default of N28, not an owner decision.

A connection of a machine to the peer address of its own edge server never passes the forward hook. The input hook takes it, with the address of the machine as its source. The chain input drops each packet from a tunnel to an address of the set known_peers, before the jump to the zones. So a machine behind the tunnel reaches no port at the peer address of its edge server. It still reaches the public ports at the floating addresses, as the internet does. On the local exit, the node table drops a connection of a machine to its own server (the node network). Peer addresses are IPv4 only (plan question Q91), so these drops have no rule of IPv6.

NAT never runs for a packet that conntrack cannot place, such as a TCP segment with SYN and FIN, or one without flags. Without a rule, such a packet leaves the uplink with the address of the machine. Two rules stop it. The chains egress and forward drop each such packet from a tunnel or a tap device, before any accept. The chain egress_guard drops each packet that still has the source of a machine on the way out. Each rule holds alone.

The uplink and the NAT66

Section titled “The uplink and the NAT66”

The IPv4 egress leaves through the public zone. The IPv6 egress leaves only through the uplink. The uplink is the device of the IPv6 default route of the main table, with the lowest metric. Without edge.public_ipv4, hopboxd logs this edge server has no edge.public_ipv4, so the egress of the machines leaves from the address of its output interface at level warn, at each start.

The NAT66 gives the IPv6 egress one global IPv6 address of the uplink. The firewall picks it in this order:

  1. If the uplink holds the preferred source (src) of the IPv6 default route, that address.
  2. Else the lowest permanent address, such as a static address of the network config of the host.
  3. Else the lowest other address, such as an address of a router advertisement.

The pick skips an address in duplicate address detection, an address that failed it, a deprecated address, and a temporary address. It also skips unique local addresses, link-local addresses, and the floating address of edge.public_ipv6 (the bootstrap config of hopboxd). The AAAA records name that floating address, and the egress never leaves from it.

With a multipath IPv6 default route, the uplink is the device of its first next hop. The kernel can send a flow to another next hop, and the table refuses the IPv6 egress there. So such a flow gets a reset or ICMPv6 administratively prohibited. Give an edge server one IPv6 default route.

Each check of the table reads the uplink again, every 2 s (The table must stay). A new uplink or a new address installs the table again. A failed read keeps the uplink of the last check.

Without an IPv6 default route, or without a global IPv6 address on the uplink, the edge server has no NAT66. The chain egress then refuses the IPv6 egress of the tunnel. The chain forward refuses the IPv6 egress of the local exit to 2000::/3. TCP gets a reset, and other packets get ICMPv6 administratively prohibited (plan question Q85). hopboxd logs a warning at the start and at each change (Logs).

The other tables

Section titled “The other tables”

A server can have three tables of hopboxd. Each table sees each packet of its hooks. An accept of one table does not stop the next table, and a drop of any table drops the packet.

Table Server Its part
inet hopbox_host Every server What reaches the server.
inet hopbox_node A node What the machines reach, and what reaches a machine (the node network).
inet hopbox_edge An edge server The redirect of the SSH ports to the SSH front door (the SSH front door).

On a server that is not an edge server, the table inet hopbox_host filters only the input hook. So it does not touch the traffic that a node forwards between the mesh, its machines, and its egress tunnels. On an edge server that enrolls, it also has the chains of The egress of the machines.

At the start and at the stop of hopboxd

Section titled “At the start and at the stop of hopboxd”

The unit host firewall of hopboxd run takes these steps at its start:

  1. It reads the sets of the table that an earlier hopboxd installed. Without such a table, the sets start empty.
  2. It reads <data_dir>/hostfw/peers, which gives peers, jump_hosts, and known_peers (Sets). On an edge server, the egress stays closed until the start knows the whole set known_peers. Only a file with known_peers_whole and no skipped line gives the whole set, never the table of step 1 (The egress of the machines). Without the file, it keeps those of step 1. A file or a line of it that the start cannot read never stops the start, because after a reboot no table is left. The start logs the error, skips each such line, and counts the server as one that knew an edge server, so port 22 of the public interface stays closed. Without a readable file, it keeps the sets of step 1. The next sets write the file again.
  3. It reads the file <data_dir>/hostfw/vrack-interface of a release before N31. If the file exists, the server counts as one that knew an edge server. Once the file peers keeps the line knew_edge, the start removes the file vrack-interface (Never a lockout).
  4. On an edge server that enrolls, it reads net.ipv4.ip_forward and the file of the forward guard. It finds the uplink and the address of the NAT66 (The uplink and the NAT66).
  5. It replaces the table with the rules of the roles and the sets, in one netlink batch. No packet sees a table that is half made. If the batch fails, the start of hopboxd fails, and the table before it stays.
  6. On an edge server that enrolls, it turns on the IPv4 forwarding that step 4 found off. Then it turns on IPv6 forwarding (the egress of the machines).
  7. It starts to watch the table.

The stop of hopboxd ends the watch, and keeps the table.

The table must stay

Section titled “The table must stay”

Do not flush the nftables ruleset of a server: no nft flush ruleset, and no restart of nftables.service of Debian, whose start flushes the ruleset.

The unit watches nftables. After each change in nftables, and every 2 s in case the watch fails, it checks the table: its sets, its chains, the expressions of each rule, and the elements of each set. So a flush, a delete of a part, and a replace of a rule each show. When a part differs, it installs the whole table again. It logs this error at most once a minute, with the count of repairs in the field repairs:

Each nftables request of hopboxd ends after 10 s, so a kernel answer that never comes fails the request with i/o timeout and does not block the unit. A check that times out counts as a broken table: the unit logs the error above with the i/o timeout in err, adds 1 to hopbox_host_firewall_repairs_total, and installs the table again. The 10 s also cover the batch of an install, which the kernel applies in the send of the request. The largest batch that fits in one netlink message took under 30 ms on a host with every CPU busy.

The bound of the repair is 2 s, the time between two checks. In the test fleet, the table was back 22 to 48 ms after a flush. A change in nftables within 2 s of a repair waits for the next check. So two writers of the table take turns every 2 s, not at the speed of the events. Two hopboxd processes or another tool can be such writers. In the gap, the server has no host firewall. A connection that opened in the gap stays open after the repair, because the table takes the packets of each connection that conntrack knows. While hopboxd does not run, nothing repairs the table, and the next start installs it.

On an edge server, each check also finds the uplink of the NAT66 again. A check installs the table again after a new uplink or uplink address, and after new sets.
