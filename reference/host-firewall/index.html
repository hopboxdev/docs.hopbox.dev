The host firewall

The network redesign of 2026-10-27 changes this page. hopbox leaves the vRack and the OVHcloud API, and the servers talk over their public addresses (Q90). This page describes the code after milestone N27, which opens the public interface to the peer addresses of the install. The rules of the vRack zone stay until N31. Milestones N28 to N32 change the code and this page again. Before you set up a fleet on the vRack or with an IPv6 /56, read Q90.

The host firewall is the nftables table inet hopbox_host of every server of an install. It makes the edge servers the bastion of the install (rules 2 and 5). Only an edge server takes traffic from the whole internet. On its public address, a control server or a node takes only the traffic of the install, from the peer addresses of the servers (Sets). A peer address is the public IPv4 address at which the other servers reach a server (Enrollment and the install PKI). On the vRack and on the mesh, each server takes only the ports of its roles. Operators reach a server that is not an edge server by SSH only through an edge server as a jump host. On an edge server, the table also forwards and translates the egress of the machines (The egress of the machines).

The firewall is in internal/hostfw. hopboxd run starts it on every server, right after the metrics listener and before the units of the roles (hopboxd). The provider block of the Terraform provider names the jump host in ssh_jump_host (hopbox Terraform provider).

In the examples, the vRack interface is enp3s0f1. The edge servers have the peer addresses 203.0.113.21 and 203.0.113.22, and the vRack addresses 172.31.0.21 and 172.31.0.22.

Zones

Section titled “Zones”

The table sorts each new connection by the interface that takes it. A zone is the set of interfaces that share one list of open ports.

Zone Interfaces Sources that a port takes
Loopback lo Every source. The table takes every packet of loopback.
vRack The interface that holds the one vRack address of the server, as the mesh finds it (the mesh) The vRack range 172.31.0.0/16, or the vRack jump hosts for port 22. The /56 of the install is not part of the vRack range.
Mesh hbm0 The mesh range 10.239.0.0/16.
Tap devices The tap devices of the machines on a node, hbt* The table takes them, and leaves them to the table inet hopbox_node (the node network), which owns all traffic of the machines.
Public Each other interface, such as the uplink. The egress tunnels hbe* are in it too, so a machine reaches the public ports of an edge server through its tunnel. Every source for the ports of the roles edge and dns. Each port of the traffic of the install takes only its set (Sets).

On an edge server, the address of the /56 on the vRack interface is in the public zone too (The address of the /56). Each zone ends with a drop, so a port that no role opens takes nothing. The replies of the connections of the server pass in every zone, and so do the ICMP messages of ICMP and DHCPv6.

Ports

Section titled “Ports”

Each role opens its ports. A server with more than one role opens the ports of each role.

Role Zone Port Source Use
A server without the role edge Public TCP 22 The set jump_hosts. While the server never knew an edge server and never had a vRack address, every source (Never a lockout). The SSH of the operators and of the provider through an edge server (The jump hosts).
Every server vRack TCP 22 The set vrack_jump_hosts. While it is empty, the vRack range. The SSH through an edge server on the vRack.
A server that enrolls: node, dns, or edge vRack UDP 51820 The vRack range The WireGuard packets of the mesh (the mesh).
A server that enrolls Public UDP 51820 The set peers The same. N28 moves the mesh to the peer addresses.
edge, on a server that enrolls vRack and public UDP 51821 The vRack range, and the set peers The egress tunnel hbe0, which takes the egress of the nodes (the egress of the machines).
node without edge, on a server that enrolls vRack and public UDP 51821 to 51836 The vRack range, and the set peers The egress tunnels hbe0 to hbe15 of the node (the egress of the machines).
control vRack TCP 7443, the port of control.internal_listen The vRack range The internal listener: the enrollment, the control channels, and the API and the console that the edge servers forward (the internal listener).
control Public TCP 7443, the port of control.internal_listen The sets peers and registered The same, on the public address of the control server.
node Mesh TCP 7444 The mesh range The disk listener of the cold moves (Cold move).
edge Public TCP 22 Every source The sshd of the operators. The edge server is the jump host.
edge Public TCP 80 and 443 Every source The HTTP and HTTPS listeners (the edge role).
edge Public TCP 2222, the port of edge.ssh_listen, only for connections that a redirect sent there Every source The SSH ports of the machines, TCP 10000 to 30000. The table inet hopbox_edge sends them to edge.ssh_listen (the SSH front door), so the input hook sees port 2222. When conntrack records the redirect (ct status dnat), the rule takes the connection there. Any redirect or destination NAT to that port passes, also one that an operator with edge.ssh_redirect = false writes. A connection straight to port 2222 takes nothing.
dns Public TCP and UDP 53 Every source The DNS role (the DNS role).

An edge server takes no new connection on the vRack other than its ports of the vRack zone. The edge servers of an install run the DNS role. Port 53 follows the role dns, not the role edge, as the owner decided on 2026-10-27 (plan question Q74). So a server with the DNS role alone, as in Serve the domain of an install with the DNS role, opens port 53 and no edge port. An edge server without the DNS role keeps port 53 closed. The table opens the same ports whatever the listen addresses of the config say, as the owner decided on 2026-10-27 (plan question Q80). A listener on another port, such as edge.https_listen = ":8443", takes no connection from outside the server. So at its start, hopboxd logs the host firewall opens no public port for this listener, so it takes no connection from outside the server at level warn, for each such listener of edge.https_listen, edge.http_listen, and dns.listen. A listener on loopback gets no warning.

The other listeners of hopboxd take nothing from outside the server: the API listener on 127.0.0.1:7080, the metrics listener on 127.0.0.1:9464, and the listener of the SSH front door on port 2222.

Sets

Section titled “Sets”

The table holds four sets of IPv4 addresses. A port of the traffic of the install takes only the addresses of its set.

Set Holds Ports that take it
peers The peer addresses of the servers of the install that are not decommissioned (Control store tables). A server without a peer address is not in it. Public UDP 51820, the UDP ports of the egress tunnels, and TCP 7443 of a control server.
jump_hosts The peer addresses of the edge servers among them. Public TCP 22 of a server without the role edge.
registered The peer addresses of the enrollment tokens that are not used and not expired (Enrollment and the install PKI). Only a server with the control role has this set. Public TCP 7443 of a control server.
vrack_jump_hosts The vRack addresses of the edge servers. N31 removes it with the vRack zone. TCP 22 of the vRack interface.

A registered address reaches the internal listener only while its token works. So a new server enrolls from its peer address, and its later control channel comes from the same address, which peers then holds. A peer address stays in peers until its server is decommissioned. Providers reuse addresses, so a stranger can get the address of a decommissioned server.

The sets come from two places:

Server Where the sets come from
A server with the control role The control role reads peers, jump_hosts, and registered from the store every second (Control store tables). So a new enrollment token reaches registered within 2 s, and the Terraform provider waits for that before it enrolls a server. The control role hands the sets to the firewall only after a change.
A server without the control role Each mesh that the control role sends holds peers and jump_hosts in its field firewall (the control channel). A change reaches the server within one heartbeat, 5 s. The agent hands the sets to the firewall before the mesh device takes the mesh. A mesh of a control role of an older release has no firewall, and the server keeps the sets that it has.

The sets of vrack_jump_hosts come from each mesh, and on a server without the mesh from the control role (The jump hosts).

Each server keeps its last peers and jump_hosts in the file <data_dir>/hostfw/peers (Server layout), and writes it after each change, through a temp file and a rename. The start of hopboxd loads the file before the control channel comes back. So a restart without a control server keeps the mesh port and the way in through the jump hosts. Without the file, the start takes the sets of the table before it. It never takes registered from the file or the table: the control role reads it within a second, and each registration ends with its token.

The file has one address on each line, after its kind. The line knew_edge records that the server knew an edge server (Never a lockout). A line that starts with # is a comment:

Each check compares the elements of each set with the sets of the firewall. So a flush of a set alone comes back within 2 s, and so does a delete of an element. Each new set from the control role or from a mesh checks the table again, also the same sets.

The jump hosts

Section titled “The jump hosts”

Port 22 of the public interface of a server without the role edge takes the peer addresses of the edge servers alone, the set jump_hosts. An edge server reaches a peer address straight over the internet. So the SSH of an operator through an edge server comes from the peer address of the edge server. From N30 on, the provider dials the peer address of a server through the jump host too.

An edge list that turns empty keeps the last jump_hosts, as the owner decided on 2026-10-27 (plan question Q93). So the last edge server that leaves stays a jump host of each server, and hopboxd logs the install has no edge server now, so port 22 of the public interface keeps the last jump hosts at level warn. A new edge server replaces the list. The kept address has the risk of reuse of the peers (Sets): a stranger who gets the address of the last edge server that left reaches port 22 of each server, but still needs an SSH key.

Port 22 of the vRack zone takes the vRack addresses of the edge servers alone, the set vrack_jump_hosts. Until N30, the provider reaches a server through the jump host at its vRack address (The Terraform provider).

Server Where the vRack jump hosts come from
A server that enrolls Each mesh that the control role sends. The vRack jump hosts are the vRack addresses of the peers with the role edge (the mesh). A new edge server reaches the firewall of each server within about two heartbeats.
A server with the control role alone The control role reads the vRack addresses of the edge servers from the table mesh_members every 5 s (Control store tables).

While the server knows no vRack address of an edge server, port 22 of the vRack zone takes the whole vRack range. This holds before the first mesh after a reboot, and in an install without an edge server on the vRack. A restart of hopboxd keeps the set of the table before it, so a restart while no control server answers keeps the vRack jump hosts. A table of a release before N27 holds the vRack addresses in jump_hosts, and the start takes them as the vRack jump hosts.

Never a lockout

Section titled “Never a lockout”

A change of the table never closes the way of an operator into a server in a way that this section does not name. The owner decided the ways of SSH on 2026-10-27 (plan question Q93, which replaces Q75):

  • A server that never knew an edge server and never had a vRack address keeps port 22 open on its public interface, to every source. No jump host reaches it. This covers a new server before its first control channel, and a first server without the edge role, such as ks. A server knew an edge server once its set jump_hosts or its set vrack_jump_hosts had an address.
  • A server that has a vRack address, or had one, keeps port 22 of its public interface closed to every address outside jump_hosts, also before it knew an edge server. A jump host reaches it over the vRack, where port 22 takes the whole vRack range until the first mesh. The owner decided this on 2026-10-27 (plan question Q75, and question Q10 of the review of N16): a short outage of the vRack never opens public SSH. So a server on the vRack whose edge servers have no peer address keeps port 22 of its public interface closed, as before N27. While port 22 of its public interface takes every source, hopboxd logs this server never knew an edge server, so no jump host reaches it, and its public interface keeps port 22 open at level warn, at each install of the table. An edge server opens port 22 to every source anyway.
  • A server that knew an edge server keeps port 22 of its public interface closed to every address outside jump_hosts, also while that set is empty. This holds after a restart, through the file <data_dir>/hostfw/peers, and after the last edge server left (The jump hosts). The way back after a lockout is the rescue mode or the console of the provider. A computer that the operator owns has no such provider tools, so its way back is its own console.
  • While the server knows no vRack address of an edge server, port 22 of the vRack zone takes the whole vRack range (The jump hosts).
  • One netlink batch replaces the whole table. If the kernel refuses the batch, the table before it stays as it was.
  • A host with two vRack addresses keeps the vRack interface of the last check, so a mistake on the host never closes the vRack zone.
  • A server that had a vRack address and lost it keeps the rules of its vRack interface. The address comes back with the network setup of the provider, or a restart of the network service. The file <data_dir>/hostfw/vrack-interface names the interface, so a restart or a reboot without the address keeps it too. hopboxd logs this server lost its vRack address, so the host firewall keeps the rules of its vRack interface at level error. Its public interface keeps its own rules, so the jump hosts reach it there. To let a server that left the vRack for good drop the rules of the vRack interface, remove the file and restart hopboxd.
  • The table outlives hopboxd. A stop, a crash, or an upgrade of hopboxd keeps the table, so SSH through the jump host goes on.
  • A destroy of the Terraform provider stops hopboxd, and then removes the table, before the server leaves the vRack. Its public address then takes SSH again (The Terraform provider).

To let a server that left its install for good take SSH from every source again, run these commands on it:

While the server is still in an install, the next sets of the control role close port 22 again.

A release from before the host firewall keeps the table of a later release, and never changes its jump hosts. So the Terraform provider removes the table after it moves a server to such a release (hopbox Terraform provider). The owner decided it on 2026-10-27 (plan question Q79). It reads the release from hopboxd version --json: from N16 on, the field features names host-firewall (the version command). After a move by hand, run sudo nft delete table inet hopbox_host on the server through the jump host.

If a server stays closed, the rescue mode of its provider boots it into another system, which runs no table.

The Terraform provider

Section titled “The Terraform provider”

The provider reaches a server without the role edge through the jump host of ssh_jump_host, at its vRack address (hopbox Terraform provider). If the provider block has no ssh_jump_host, a create or an update of such a server with vrack_address fails before any step. The owner decided two more rules of the provider on 2026-10-27:

  • An import of such a server names its vRack address after a comma in the import ID: <service name>,<vRack address>, such as ns1234568.ip-198-51-100.eu,172.31.0.21. The import dials that address through the jump host. The server there must hold the public address of the service name, or the import fails. An edge server imports with the service name alone (plan question Q76, hopbox Terraform provider).
  • A destroy removes the table once hopboxd stopped, before the server leaves the vRack. It also removes the files vrack-interface and peers of <data_dir>/hostfw, so a later hopboxd on the server never starts with the jump hosts of the old install. So its public address takes SSH again (plan question Q77, hopbox Terraform provider). A server without nft gets the package nftables first. The login, the stop of hopboxd, or the removal of the table can fail. Then the destroy keeps the server in the vRack, where the jump host reaches it. It fails with an error that names the commands to run, and the next destroy goes on.

The address of the /56

Section titled “The address of the /56”

An edge server holds one address of the /56 of the install on its vRack interface (the edge role). The vRack carries the public IPv6 traffic of that address. So the address takes the public ports of the server from every source, as the uplink does. The other addresses of the vRack interface keep the rules of the vRack zone.

The provider of the uplink does not route the /56. So on an edge server with edge.public_ipv6, the chain postrouting drops some packets. It drops each packet with a source in the /56 that leaves through another interface than these: the vRack interface, loopback, the egress tunnels, and the tap devices. If the rule or the route of the table hopbox_egress6 is gone, a reply of the /56 still never leaves through the uplink. A reply from another address of the /56 to a machine leaves through a tunnel or a tap device, so it passes. The gateway of the /56 and another edge server can send such a reply.

The chain runs at the priority srcnat + 10, after the source NAT at srcnat. So it also drops a packet that a source NAT gives an address of the /56. The NAT66 of the egress is such a source NAT, at srcnat (The egress of the machines). A rule that changes the source of a packet must run at srcnat or before, never after the guard.

The egress of the machines

Section titled “The egress of the machines”

An edge server that enrolls takes the egress of the machines of the nodes from its egress tunnel hbe0 (the egress of the machines). Its table then has five more chains:

Chain Hook and priority What it does
egress_mark prerouting, mangle Puts the conntrack mark bit 0x20000000 on each new connection from a tunnel. Puts the packet mark 0x68620100 on each reply of such a connection. The rule of that mark routes the reply back into the tunnel, and not over the mesh (the egress of the machines).
egress_output output, mangle, of the type route Puts the same mark on each reply of the server itself. A machine reaches a public port of its own edge server, and the reply goes back through the tunnel (plan question Q52).
forward forward, filter Sends each packet from a tunnel to the chain egress. Lets the replies into a tunnel, and drops each other packet into a tunnel. Drops the forwarded traffic of the other interfaces, as The forward guard says.
egress none, the chain forward jumps to it Drops the private ranges of the node table, which hold the mesh range and the vRack range. Drops each IPv6 destination outside 2000::/3. Accepts IPv4 to the public zone. Accepts IPv6 only to the vRack interface, and only with edge.public_ipv6. Refuses the rest: TCP with a reset, and other packets with ICMP administratively prohibited.
egress_nat postrouting, srcnat, of the type nat Translates the source of the egress from a tunnel. IPv4 to the public zone gets edge.public_ipv4, or the masquerade without that key. IPv6 to the vRack interface gets the address of edge.public_ipv6.

The table of the node network translates the egress of the machines of a node with the edge role. So the chain egress_nat takes the egress of a tunnel alone (the node network).

The IPv4 egress leaves through the uplink, and the IPv6 egress through the vRack interface, where the /56 lives. Without edge.public_ipv4, hopboxd logs this edge server has no edge.public_ipv4, so the egress of the machines leaves from the address of its output interface at level warn, at each start.

The forward guard

Section titled “The forward guard”

At the start of an edge server that enrolls, the host firewall reads net.ipv4.ip_forward. When it is 0, the firewall turns it on for the egress, after the install of the table. Then the chain forward drops each forwarded IPv4 packet that touches neither a tunnel nor a tap device:

On a server with the node role, the rule also names the tap devices: iifname != "hbt*" oifname != "hbt*". The file <data_dir>/hostfw/forward-guard records that hopboxd turned forwarding on (Server layout). Each later start finds forwarding on, reads the file, and keeps the guard. Something else can turn forwarding on before the first start of hopboxd, such as Docker. The table then has no guard for IPv4, and the forwarding of that host stays as it was. IPv6 forwarding is one switch for the whole host. The firewall turns it on at each start of an edge server that enrolls, also after the install of the table (the egress of the machines). So the chain forward always drops each forwarded IPv6 packet that touches neither a tunnel nor a tap device.

ICMP and DHCPv6

Section titled “ICMP and DHCPv6”

Each interface takes these packets, also without a connection, as the owner decided on 2026-10-27 (plan question Q78 rule 2):

Packets Why
ICMP echo request, and ICMPv6 echo request The monitoring of OVHcloud pings each server. A server that does not answer can get an intervention.
ICMP destination unreachable, time exceeded, and parameter problem. ICMPv6 destination unreachable, packet too big, time exceeded, and parameter problem. Path MTU discovery and the errors of the routes.
ICMPv6 router advertisement, neighbor solicitation, neighbor advertisement, and multicast listener query IPv6 on the link stops without them.
UDP to port 546 from a link-local address The answers of a DHCPv6 server. The request goes to a multicast address, so the answer does not count as a reply.

The table

Section titled “The table”

The other tables

Section titled “The other tables”

A server can have three tables of hopboxd. Each table sees each packet of its hooks. An accept of one table does not stop the next table, and a drop of any table drops the packet.

Table Server Its part
inet hopbox_host Every server What reaches the server.
inet hopbox_node A node What the machines reach, and what reaches a machine (the node network).
inet hopbox_edge An edge server The redirect of the SSH ports to the SSH front door (the SSH front door).

On a server that is not an edge server, the table inet hopbox_host filters only the input hook. So it does not touch the traffic that a node forwards between the mesh, its machines, and its egress tunnels. On an edge server with a /56 address, it also filters the postrouting hook. On an edge server that enrolls, it also has the chains of The egress of the machines.

At the start and at the stop of hopboxd

Section titled “At the start and at the stop of hopboxd”

The unit host firewall of hopboxd run takes these steps at its start:

  1. It reads the sets of the table that an earlier hopboxd installed. Without such a table, the sets start empty.
  2. It reads <data_dir>/hostfw/peers, which gives peers and jump_hosts (Sets). Without the file, it keeps those of step 1. A file or a line of it that the start cannot read never stops the start, because after a reboot no table is left. The start logs the error, skips each such line, and counts the server as one that knew an edge server, so port 22 of the public interface stays closed. Without a readable file, it keeps the sets of step 1. The next sets write the file again.
  3. It finds the vRack interface.
  4. On an edge server that enrolls, it reads net.ipv4.ip_forward and the file of the forward guard.
  5. It replaces the table with the rules of the roles and the sets, in one netlink batch. No packet sees a table that is half made. If the batch fails, the start of hopboxd fails, and the table before it stays.
  6. On an edge server that enrolls, it turns on the IPv4 forwarding that step 4 found off. Then it turns on IPv6 forwarding (the egress of the machines).
  7. It starts to watch the table.

The stop of hopboxd ends the watch, and keeps the table.

The table must stay

Section titled “The table must stay”

Do not flush the nftables ruleset of a server: no nft flush ruleset, and no restart of nftables.service of Debian, whose start flushes the ruleset.

The unit watches nftables. After each change in nftables, and every 2 s in case the watch fails, it checks the table: its sets, its chains, the expressions of each rule, and the elements of each set. So a flush, a delete of a part, and a replace of a rule each show. When a part differs, it installs the whole table again. It logs this error at most once a minute, with the count of repairs in the field repairs:

The bound of the repair is 2 s, the time between two checks. In the test fleet, the table was back 22 to 48 ms after a flush. A change in nftables within 2 s of a repair waits for the next check. So two writers of the table take turns every 2 s, not at the speed of the events. Two hopboxd processes or another tool can be such writers. In the gap, the server has no host firewall. A connection that opened in the gap stays open after the repair, because the table takes the packets of each connection that conntrack knows. While hopboxd does not run, nothing repairs the table, and the next start installs it.

Each check also finds the vRack interface again. A check installs the table again after a new vRack interface and after new sets. A lost vRack address keeps the interface (Never a lockout).
