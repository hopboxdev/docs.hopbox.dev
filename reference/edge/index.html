The edge role

The network redesign of 2026-10-27 changes this page. hopbox leaves the vRack and the OVHcloud API, and the servers talk over their public addresses (Q90). This page still describes the current code. Milestones N26 to N32 change the code and this page. Before you set up a fleet on the vRack, read Q90.

The edge role is the HTTPS front of an install. It takes the HTTPS traffic of every client, and it routes each request by its host name. The domain of the install goes to the control role, which serves the API and the console. A machine URL, such as box1.example.com, goes to its machine. A private machine URL needs a sign-in first. This page covers the listeners, TLS, the routing, and the forwarded requests. It also covers the machine URLs, the sign-in of a private machine URL, the public IPv6 address of an edge server, EdgeService, the metrics, and the logs. The edge role also runs the SSH front door of the machines, which the SSH front door covers.

The edge role is in internal/edge. The pushes of the control role are in internal/control/channel/edge.go. The routes and the sign-in are in internal/service/edge.go. EdgeService, /auth/machine, and the forwarded requests are in internal/api/edge.go.

In the examples, the domain of the install is example.com.

Listeners

Section titled “Listeners”

The edge role has two HTTP listeners, and the listener of the SSH front door (the SSH front door). Their addresses are in the section [edge] of the bootstrap config (the bootstrap config of hopboxd).

Item Value
HTTPS listener edge.https_listen. Default: :443, port 443 on every address.
HTTP listener edge.http_listen. Default: :80. It only sends each request to HTTPS (HTTP to HTTPS).
Protocols HTTPS: HTTP/2 and HTTP/1.1, by ALPN. HTTP: HTTP/1.1.
Open connections At most 16,384 on the HTTPS listener, and 65,536 on the HTTP listener, of the 1,048,576 file descriptors that hopboxd.service allows. The bound of the HTTPS listener keeps the memory of its connections under 4 GiB (Memory of stalled requests). A connection past the bound of the listener gets no refusal. It waits in the backlog of the kernel until another one closes. So a full HTTPS listener stops new console sessions and new CLI connections, with no error page. The open connections go on. hopbox_edge_open_connections and hopbox_edge_connection_limit show how full each listener is (Metrics).
Open connections of one client At most 256 on each listener. A client is an IPv4 address, or the /64 of an IPv6 address. The edge role closes a connection past this bound at once, so one client cannot hold every slot of a listener. Each one counts in hopbox_edge_client_connection_refusals_total{bound="client"}.
Open connections of one IPv6 network At most 1,024 on each listener, for all /64s of one IPv6 /48 together. The holder of a /48 has 65,536 /64s, enough to fill a listener alone. The edge role closes a connection past this bound at once. The count of its /64 does not matter. Each one counts in hopbox_edge_client_connection_refusals_total{bound="network"}. An IPv4 address has no such bound (Clients behind one network).
Request header At most 64 KiB, also on HTTP/2. A larger header gets 431 Request Header Fields Too Large.
Header timeout 10 s for the header of a request. A slow client then loses its connection.
Idle timeout 2 min without a request closes a connection.
HTTP/2 streams At most 250 at once on one connection.
HTTP/2 receive buffer 256 KiB for each stream, and 250 times that for the connection. So a stream whose target reads nothing, such as an exec with unread input, stalls alone. The other streams of the connection go on.
Open requests At most 16,384 at once on the HTTPS listener, streams and WebSockets included. A request past the bound gets 503 Service Unavailable with Retry-After: 1 and Hopbox-Not-Run: 1.
Open requests of one client At most 1,024 at once. A request past the bound gets 429 Too Many Requests with Retry-After: 1 and Hopbox-Not-Run: 1, so one client cannot take every slot of the 16,384. A client is an IPv4 address or the /64 of an IPv6 address.
Open requests of one IPv6 network At most 4,096 at once, for all /64s of one IPv6 /48 together. A request past the bound gets 429 Too Many Requests with Retry-After: 1 and Hopbox-Not-Run: 1. The count of its /64 does not matter. So one /48 can take at most a quarter of the 16,384. Watch hopbox_edge_requests_total{to="refused"} for the refusals of both bounds.
HTTP/2 frames At most 16 KiB for each frame that a client sends.
Request body on HTTP/1.1 A body that sends nothing for 1 minute while its target reads it ends. The edge role then answers, and closes the connection. A body that keeps sending has no time limit. If an answer ends before the whole body was read, the edge role sends the whole answer at once, reads no more of the body, and closes the connection. That holds for the answers of a target and for the answers that the edge role makes itself, such as a refusal of the bounds, a sign-in, or the 502 Bad Gateway when no control server or machine takes the request. It holds for a body with a Content-Length and for a chunked body, and for an answer of every status. So a client that still sends its body gets the whole answer and its end. If the forward fails after the target took the request, the 502 Bad Gateway comes only once the body ends, or once it sends nothing for 1 minute.
Answer, HTTP/2 streams, and WebSockets No timeout, so streams, downloads, and WebSockets can last.

Clients behind one network

Section titled “Clients behind one network”

The bounds of a client and of an IPv6 network count by address. So all people behind one address share its slots, also with their long streams, such as an office or a carrier with one NAT.

Network What it shares
One IPv4 address 256 connections on each listener, and 1,024 open requests. A carrier NAT can put thousands of people behind one address. IPv4 has no bound of a wider network, because the next addresses often belong to other people.
One IPv6 /64 256 connections on each listener, and 1,024 open requests. One host usually holds a whole /64.
One IPv6 /48 1,024 connections on each listener, and 4,096 open requests, for all its /64s together. One site, such as an office or a server of a hosting provider, usually holds a /48. A carrier or a hosting provider can also give many customers a /64 each in one /48. These customers then share the bounds of the /48.

Without the bound of a /48, 64 /64s of one /48 fill the 16,384 connections of the HTTPS listener. With it, a client needs 16 /48s. A lower bound for each /48 keeps the listener open for more networks, but it stops more users of a shared /48. The bound is 1,024 connections for each /48. If the users of a large network reach the bound, hopbox_edge_client_connection_refusals_total{bound="network"} and hopbox_edge_requests_total{to="refused"} grow.

Memory of stalled requests

Section titled “Memory of stalled requests”

A request can stall in two ways. Its target reads none of its body, or its client reads none of the answer. A stalled request holds memory in the edge until it ends, because no timeout ends an HTTP/2 stream. The bounds of open requests cap that memory. At the end of each request, the edge closes its body. So an HTTP/2 stream whose answer waits for the window of the client holds no body:

Buffer of one request Size
The request header At most 64 KiB.
The body on HTTP/2 At most 256 KiB, the receive buffer of the stream.
The answer of the control role At most 64 KiB, the receive buffer of the stream to the control role.
The frame buffer of the body to the control role 64 KiB, the largest frame that the internal listener reads (the internal listener).
The copy buffers of the proxy 32 KiB in each direction.

So one request holds at most 512 KiB. A connection also holds memory without a request:

Buffer of one HTTPS connection Size
The read buffer of the HTTP/2 framer At most 16 KiB, the largest frame.
The write buffer of the HTTP/2 framer About 16 KiB.
The TLS records About 17 KiB in each direction.
The HPACK tables 4 KiB in each direction.
The save buffer of the HPACK decoder Up to about 64 KiB, for a header in CONTINUATION frames.
The stacks of its goroutines 16 KiB to 32 KiB each after the TLS handshake.
The structs of the connection Some KiB.

The edge counts 256 KiB for one HTTPS connection. A connection of the HTTP listener holds a read buffer and a write buffer of 4 KiB. It also holds a stack, its structs, and the wrappers of the listeners. An idle one takes about 20 KiB. The edge counts 32 KiB for it. So the bounds are these:

Who Most memory
One client 584 MiB: 256 HTTPS connections of 256 KiB, 256 HTTP connections of 32 KiB, and 1,024 requests of 512 KiB.
One IPv6 /48 2.3 GiB: 1,024 HTTPS connections of 256 KiB, 1,024 HTTP connections of 32 KiB, and 4,096 requests of 512 KiB.
The HTTPS listener 12 GiB: 16,384 connections of 256 KiB, and 16,384 requests of 512 KiB.
The HTTP listener 2 GiB: 65,536 connections of 32 KiB.

A test of internal/edge checks these bounds against the defaults.

The answer of a machine and the body of a request on HTTP/1.1 wait in the socket buffers of the kernel, not in hopboxd. The kernel parameters net.ipv4.tcp_rmem, net.ipv4.tcp_wmem, and net.ipv4.tcp_mem bound them. Each HTTP/1.1 connection to a machine also holds a read buffer and a write buffer of 4 KiB in the edge.

The unit edge of hopboxd run opens the listeners at its start (hopboxd). If another program holds a port, the start fails, and hopboxd exits with status 1. The error names the address, such as edge: listen on :443: bind: address already in use. Ports 443 and 80 need root, and hopboxd.service runs hopboxd as root (Server layout).

At a stop, the unit ends the SSH connections, closes the listeners, gives the open requests 2 s, and then ends the rest: streams, WebSockets, and long calls. The whole stop takes at most 5 s.

TLS

Section titled “TLS”

The edge role serves one certificate: the wildcard certificate of the install, for the domain and *.<domain> (the certificate of the install). The control role pushes the certificate with its key over the control channel (the control channel). The edge role keeps it only in memory.

Rule Value
TLS versions 1.2 and 1.3. The cipher suites are the defaults of Go.
Server name (SNI) Required. A handshake without a server name fails.
Host names The domain, and each name under it. A handshake for another name fails.
Before the first certificate Every handshake fails.
Certificate of another domain When the domain of the install changes, the edge role refuses every handshake until the certificate of the new domain arrives. It never serves the certificate of the old domain.

When the role edge leaves a running server, the end of the removal restarts hopboxd without the role (the admin API). The new process has no copy of the certificate of the install, of its key, or of the SSH host key of the install. The edge role keeps them only in memory, and writes none of them to the disk (hopboxd). The control store keeps them for the other edge servers. hopboxd install drops the table edge from the config with the role, edge.public_ipv4, edge.floating_addresses, and edge.public_ipv6 among its keys. So the check of the uplink, which runs only with the edge role, puts no floating address back. The host firewall closes ports 80, 443, and the SSH ports of the machines, and port 22 takes only jump_hosts from then on (the host firewall). The Terraform provider then takes the floating addresses off the uplink (hopbox Terraform provider).

The edge role checks each certificate that the control role pushes before it serves it. It refuses a certificate in each of these cases, and keeps the certificate that it has:

  • The domain of the message is not a domain in lowercase without a final dot.
  • The leaf does not cover the domain, or a name under it.
  • The leaf is not valid now.
  • The key is not a PKCS #8 key, or it does not match the leaf.

A handshake that fails counts in hopbox_edge_tls_refusals_total (Metrics).

Routing

Section titled “Routing”

The edge role routes each HTTPS request by its host. The host is the Host header, or the :authority of HTTP/2, in lowercase, without a port and without a final dot.

Request Answer
The host is not the server name of the TLS connection, and one of the two is not a name of the certificate: the domain, or one label under it 421 Misdirected Request. A browser sends the requests of every name of a certificate on one HTTP/2 connection, so those pass. A host outside the certificate does not, also in a request in the absolute form, such as GET https://other.example/.
Method CONNECT 405 Method Not Allowed. The edge role is not a proxy.
Host example.com, path under /hopbox.cluster.v1. 404 Not Found. The cluster API is only for the servers of the install, on the internal listener.
Host example.com Forwarded to the control role (Forwarded requests).
Host grafana.example.com, while no machine holds the name grafana Forwarded to the control role with Hopbox-Forward-Target: grafana (The Grafana host).
Host <name>.example.com The machine <name> (Machine URLs).
Any other host under the domain, such as sub.box1.example.com 404 Not Found. Subdomain routes come in phase 4.

Each HTTPS answer carries the header Strict-Transport-Security: max-age=31536000; includeSubDomains (HSTS). A browser then reaches the domain and every machine URL only over HTTPS for a year.

An HTTP/1.1 request with the body encoding chunked gets Connection: close on its answer, also on a refusal of the bounds of open requests. Such a request can also have had a Content-Length header, which the server drops. Two such headers can hide a second request behind the first one, so the connection ends after the answer (RFC 9112, section 6.1). The server of Go refuses the other ambiguous requests. Two different Content-Length values, and a space before the colon of a header name, get 400 Bad Request. A Transfer-Encoding other than chunked gets 501 Not Implemented. A header line that continues on the next line reaches a machine as one line. The edge role builds a new request for each request that it forwards, so a forwarded request never carries the framing of the client.

The pages of the edge role are plain text, with Cache-Control: no-store and X-Content-Type-Options: nosniff. They also carry Content-Security-Policy: default-src 'none'; frame-ancestors 'none' and X-Frame-Options: DENY, so no page shows them in a frame. So do the redirects of the sign-in, and the pages of /auth/machine.

HTTP to HTTPS

Section titled “HTTP to HTTPS”

The HTTP listener answers each request for the domain or a name under it with 301 Moved Permanently to the same host and path over HTTPS. For example, http://box1.example.com/a?b=1 goes to https://box1.example.com/a?b=1. A request for another host, or before the edge role knows the domain, gets 404 Not Found.

Forwarded requests

Section titled “Forwarded requests”

The edge role forwards each request of the domain and of the Grafana host to the internal listeners of the control servers (the internal listener). It uses the dial order of the control channel: the URLs of the live control servers that the control role sent and the server keeps, then the URLs of channel.control_urls of the bootstrap config that are not among them (the control channel). Each new list of the control role replaces the order at once. A control server that stays in the order keeps its skip. It sends the requests to the live control servers in turn, one request after the other. It tries the other URLs of channel.control_urls in order after them, as fallbacks. Without a list from the control role, it sends the requests to the URLs of channel.control_urls in turn. Its EdgeService calls, such as the machine URL sign-in and the checks of the SSH front door, go the same way. A request that got no connection, because a dial or the TLS handshake failed, goes to the next control server with its body unread. The edge role then skips that control server for 10 s, so the next requests try the others first. A request that reached a control server and failed before its answer came does not go again, but the edge skips that control server for 10 s too. The HTTP/2 transport of the edge sends a request again on a new connection to the same control server when that server ended the old connection with GOAWAY before it took the request. A request with a body goes again too, while no try read its body. A request whose client went away, or whose deadline ended, marks no control server and goes to no other one. A short deadline of a caller says nothing of the control server. A dead control server still gets skipped: its connection fails the ping within 10 s, and a new dial to it fails within 3 s. A new connection to a control server has 3 s for its dial and 3 s for its TLS handshake: a dial to the peer address of a control server takes a few round trips of the internet, so a slower one is gone, and the request goes on to the next control server well within the deadline of its call. A control server that died hard leaves its HTTP/2 connection half open. So the edge pings a connection to a control server that sent nothing for 5 s, and closes it when the answer does not come within 5 s. The requests on it then fail, and the next requests go to the others. This covers Connect, gRPC, gRPC-Web, streams in both directions, trailers, the sign-in pages under /auth/, and the WebSocket of exec (/api/ws/exec). The end of the answer of the control server that took the request also ends the body of the request. So a stream whose answer ended, such as an exec at the exit of its command, ends while its client still holds its side of the stream open. The admin API is public behind the edge too, for admin API keys.

Item Value
Transport Mutual TLS 1.3 with the server certificate of the edge server, against the install CA. HTTP/2 for every request but a WebSocket upgrade, which uses HTTP/1.1, because HTTP/2 cannot carry it.
Host The host of the client request, such as example.com.
Hopbox-Client-Addr The address of the client, IP:port. The edge role sets it over any value that the client sent.
Hopbox-Forward-Target grafana on a request of the Grafana host (The Grafana host). On any other host, the request does not carry it. The edge role deletes any value that the client sent.
X-Forwarded-For The IP address of the client alone. The edge role drops the value that the client sent.
X-Forwarded-Host, X-Forwarded-Proto The host of the request, and https.
Forwarded Dropped.
Flush Each write of the control role goes to the client at once, so streams do not wait.
HTTP/2 receive buffer 64 KiB for each stream, and 1 GiB for the connection, which holds the buffers of all 16,384 open requests. So an answer that one client does not read never stalls the answers of other clients.
Failure 502 Bad Gateway with a page that says that the control plane did not answer. If the request got no connection to the control role, because of a dial or TLS error to every control server, the answer also carries Hopbox-Not-Run: 1. After a connection, the control role can have run the call, so the answer has no such header.

The header Hopbox-Not-Run: 1 tells a client that the call changed nothing, so the client can retry it (the API server). The refusals of the bounds of open requests carry it too (Listeners).

The control role trusts Hopbox-Client-Addr and Hopbox-Forward-Target only on a connection whose certificate proves a server with the edge role (the internal listener). The rate limits of sign-in then count each client by its own address (Sessions, cookies, and sign-in links).

Machine URLs

Section titled “Machine URLs”

The control role pushes the routes of the machine URLs over the control channel (the control channel). A route names a machine that holds its name and is not on its way out. A running machine has a target: the address of the machine on its node, its URL port, and its lease (Control store tables).

Case Answer

Wake on connect

Section titled “Wake on connect”

A sleeping machine is a machine in standby or hibernated. The edge role resumes or wakes it only after the check of access of the request:

  • A request for a public URL passes the check.
  • A request for a private URL passes it with a valid sign-in of an account with access to the machine. A request without one gets the sign-in, and wakes nothing.

The edge role then holds the request, and calls EdgeService.WakeForConnection (EdgeService.WakeForConnection). The control role sets the target of the machine to running. Once the routes give the machine a target, the request goes on to the machine. So a client sees only a slower first answer. The requests that wait for one machine share one call.

The URL can turn private, or the access of a token can end, during the hold. So once the machine runs, the request takes the check of access again on the new route. A request of a URL that turned private gets the sign-in, and a token without access gets 403 Forbidden. Neither reaches the machine.

Private machine URLs

Section titled “Private machine URLs”

The URL of each machine is private by default. Only an account that uses the machine opens it: its creator, and every member of its org once the creator shares it. An org admin cannot open the private URL of a private machine of another member, as with a shell. The rule is the policy action machine.open_url (the API server). The creator makes the URL public with SetMachineURLVisibility (the machine API), if the limit public_urls of the org allows it. The personal org of a limited account does not allow it (the org API). A public URL needs no sign-in.

The sign-in of a private URL takes these steps. The machine is box1.

  1. A browser asks for https://box1.example.com/page?x=1 without a machine cookie. The edge role answers 303 See Other to https://example.com/auth/machine?machine=box1&path=%2Fpage%3Fx%3D1. A path longer than 512 characters becomes /.
  2. The control role reads the session cookie of the console at /auth/machine. With a live session of an account that uses the machine, it makes a one-time code, and answers 303 See Other to https://box1.example.com/__hopbox/auth?code=<code>&path=%2Fpage%3Fx%3D1. Without a session, it answers 401 Unauthorized with a page that says to sign in to the console first.
  3. The edge role takes the code at /__hopbox/auth, and trades it for a token with EdgeService.ExchangeMachineCode. It sets the token in the cookie __Host-hopbox_machine, and answers 303 See Other to the path. A path that is not a plain path on the host, such as //other.example, becomes /.
  4. The browser asks for https://box1.example.com/page?x=1 with the machine cookie. The edge role checks the token with EdgeService.AuthorizeMachineRequest, takes the cookie out of the request, and forwards the request to the machine.

The code never reaches the machine. The answers of steps 2 and 3 carry Cache-Control: no-store and Referrer-Policy: no-referrer.

An account without the role cannot get a code. A fix needs a state cookie on the host, and it does not cover a link straight to /auth/grafana, so this limit stays.

Each refusal goes to the log as grafana refused, with the reason, the method, the path, the client address, the request ID, and the account and the session when a token named them. A refusal writes no audit entry. A file that holds a wrong key logs the key of the identity toward Grafana does not work. The log and the audit log never hold the cookie, the code, the signed token, the key, the query string, or the body. The audit entry holds the path without its query, or / for a path that looks like a credential.

What Grafana gets

Section titled “What Grafana gets”

The handler deletes Cookie and Authorization from the request, and sets X-Hopbox-Identity over any value that a client sent. The header holds a signed Ed25519 token with the claims iss (hopboxd), sub (hopbox), iat, and exp, which is 120 s later. The handler reuses a token for 60 s. The private key is the file grafana-identity.key next to the bootstrap config, and Grafana holds only the public key (hopboxd). hopboxd refuses a key file that its group or others can read.

All instance admins share one Grafana user, hopbox, which is always a Viewer. A Viewer can run any PromQL through /api/ds/query, so a stolen cookie reads all metrics and can send heavy queries. It reaches nothing else in Grafana.

The handler removes each Set-Cookie of Grafana, because a Grafana bug must not set a cookie on the whole domain. It adds these headers to each answer of Grafana. Cache-Control: no-store applies outside /public/.

The public IPv6 address

Section titled “The public IPv6 address”

An edge server can hold one floating IPv6 address on its uplink, as the owner decided on 2026-10-27 (rule 4 of the bastion architecture, plan question Q94). The bootstrap config names it in edge.public_ipv6, without a prefix length (the bootstrap config of hopboxd):

The zone names this address in its AAAA records, through the public addresses of the install (the DNS role, hopbox Terraform provider). Without a floating IPv6 address, the zone has no AAAA record, and the install takes IPv4 only.

The operator routes the address to the server at its provider. The network setup of the Terraform provider puts it on the uplink as a /128 (hopbox Terraform provider). Without the Terraform provider, put it there by hand. hopboxd puts it on the uplink whenever no interface of the server holds it, also at its first start when the address was never there (The check of the uplink). The host firewall has no rule of its own for it. The uplink is in the public zone, so the address takes the public ports of the edge server from every source (the host firewall). The NAT66 of the machines never takes it (the host firewall).

The egress of the machines

Section titled “The egress of the machines”

Each edge server that enrolls takes the egress of the machines of the nodes through its egress tunnel hbe0 (the egress of the machines). Its host firewall forwards the IPv4 egress to the public zone, and the IPv6 egress to the uplink alone (the host firewall). The IPv4 egress gets the source edge.public_ipv4, the floating address of the edge server (the bootstrap config of hopboxd). The IPv6 egress gets a global IPv6 address of the uplink (NAT66), never the floating address of edge.public_ipv6. Without such an uplink address, the edge server refuses the IPv6 egress (the egress of the machines). An edge server with the node role is the local exit of its own machines (the egress of the machines). While its uplink has no IPv4 default route on a device with a carrier, the edge server takes no egress of the nodes (the egress of the machines).

The source of the own connections

Section titled “The source of the own connections”

The other servers of an install take the traffic of the install only from the peer addresses (the host firewall). An edge server also holds floating addresses on its uplink. A connection of the edge server from a floating address reaches no port of another server. So hopboxd binds these connections of each server to its peer address:

  • the control channel and its data streams, to the internal listener of a control server (the control channel),
  • the enrollment of hopboxd enroll and hopboxd install --enroll-token (Enrollment and the install PKI),
  • the requests that the edge role forwards to the internal listeners (Forwarded requests),
  • the data streams that a control process forwards to another control process (the control channel).

The peer address is the one address of the set peers of the host firewall that an interface of the server holds. hopboxd run takes the set of its host firewall. hopboxd enroll and hopboxd install take the last sets in <data_dir>/hostfw/peers (the host firewall). In these cases, a connection leaves from the source that the kernel picks:

  • The server has no sets yet, such as at its first enrollment. The network setup of the Terraform provider runs before that enrollment, and sets the source of the default route, so the enrollment still leaves from the peer address.
  • No interface of the server holds an address of peers, or more than one interface address is in peers.
  • The destination is not a peer address, such as loopback, a vRack address, or a host name.

The other connections of the server leave from the source that the kernel picks. These include the SSH of an operator from the edge server to a node (the host firewall), the mesh, and the egress tunnels. The kernel takes the preferred source (src) of the default route. Without it, on an uplink with /32 addresses and an onlink gateway, the kernel takes the first address of the uplink, and that can be a floating address. So the network setup of an edge server with floating addresses sets src <peer address> on the default route of the uplink.

This is a build default of the fix of docket item 137, not an owner decision.

The check of the uplink

Section titled “The check of the uplink”

A DHCP renew, networkctl reconfigure, or ifdown and ifup of the uplink can drop the source of the default route and the floating addresses. On an edge server with edge.public_ipv4, edge.floating_addresses, or edge.public_ipv6 (the bootstrap config of hopboxd), the unit channel of hopboxd run checks the uplink at its start, after each change of an address or a route of the server, and every 2 s. The uplink is the device of the IPv4 default route of the main table with the lowest metric. A check repairs these gaps:

  1. If the default route has another preferred source or none, the check sets the peer address as its source. It keeps the gateway, the metric, the protocol, the flags, and the MTU of the route. This also works while the uplink has no carrier.
  2. If no interface of the server holds an address of edge.public_ipv4, edge.floating_addresses, or edge.public_ipv6, the check puts that address on the uplink, as a /32 or a /128. The first check after a start also puts on an address that the uplink never held.

The check logs each repair at level warn (the egress of the machines). It never removes an address or a route. It does not know a floating address that the bootstrap config does not name, so it does not put such an address back. Before the first sets of the control plane, the check does not know the peer address, so it does not change the route. An edge server without the three keys gets no check.

The Terraform provider puts the floating addresses on the uplink at each boot and at each apply. It writes edge.floating_addresses only to a release whose version names the feature floating-addresses (the version command). When an update drops a floating address, the provider first writes the new keys and waits for the restart of hopboxd, and only then removes the address from the uplink. Otherwise the check puts the address back at once (hopbox Terraform provider).

EdgeService.WakeForConnection

Section titled “EdgeService.WakeForConnection”

hopbox.cluster.v1.EdgeService.WakeForConnection resumes a machine in standby, or wakes a hibernated machine, for a connection that passed its check of access at the edge (Wake on connect). It needs the certificate of a server with the edge role. The edge role calls it only after the check of access of the connection, so it carries no credential of the client. It sets the target running with the actor system, and does not wait. The edge role waits for the target in the routes.

Request field Type Meaning
machine_id string The ID of the machine of the route, a UUID.
channel WakeChannel The kind of the connection: WAKE_CHANNEL_SSH for an SSH key that the front door accepted, WAKE_CHANNEL_PRIVATE_URL for a signed-in request of a private URL, or WAKE_CHANNEL_PUBLIC_URL for a request of a public URL. The audit entry records it in its detail channel, as ssh, private_url, or public_url.
Response field Type Meaning
current_state string The state of the machine at the call, such as hibernated.

A machine with the target standby resumes, with the checks of ResumeMachine. A machine with the target hibernated wakes, with the checks of WakeMachine: the limits of the org, the room of its node, and a node whose heartbeats name the feature and the capability (the machine API). Each change writes the audit entry machine.resume or machine.wake with the actor system, and counts as a use of the machine. A machine whose target is running already gives no change, no audit entry, and no error. A private machine whose creator is suspended never resumes or wakes, because a route knows only the suspension of the org.

No machine has the ID not_found
