The admin API

The admin API is the API service hopbox.admin.v1. Instance admins and root on a control server use it to operate the whole install. The hopbox CLI and the SDKs never include it. This page lists its calls and the admin socket. The API server covers the parts that every call shares: the request gate, the policy check, the idempotency keys, and the error codes. The generated reference is Admin API.

Where the admin API is served

Section titled “Where the admin API is served”
Listener Callers that the policy allows Use
The admin socket, <run_dir>/admin.sock local_root hopboxd admin on the server (hopboxd)
The API listener, control.api_listen admin_key, except for the calls of KeyringService, MailService, LoginLinkService, and AdminKeyService. An admin session, for the calls of the Admin area. The hopbox Terraform provider and scripts, with an admin API key in the header Authorization: Bearer hbxadm_... (CLI tokens, API keys, admin API keys, and SSH keys). The Admin area of the console, with the session cookie (Console).
The domain of the install, through the edge servers, which forward it to the internal listener (the edge role) as on the API listener The same callers from outside the server, such as https://example.com/hopbox.admin.v1.ServerService/ListServers. The admin API is public behind the edge, for admin API keys and admin sessions.

Admin sessions

Section titled “Admin sessions”

An admin session is the console session of an instance admin whose sign-in is at most 10 minutes old (Sessions, cookies, and sign-in links). The Admin area of the console calls the admin API with it (Console). The cookie rules of the public API hold for these calls too. Each call must carry the Origin header of the install and the header Connect-Protocol-Version: 1 (Sessions, cookies, and sign-in links). So a page of another site cannot make an admin call with the cookie of a browser.

An admin session can make these calls, and no other call of the admin API:

Service Calls
hopbox.admin.v1.InstallConfigService GetInstallConfig, UpdateInstallConfig, GetSMTPConfig, SetSMTPConfig, ClearSMTPConfig, GetOAuthConfig, SetOAuthClient, ClearOAuthClient
hopbox.admin.v1.InstanceAdminService ListInstanceAdmins, GrantInstanceAdmin, RevokeInstanceAdmin, ListAdminNotices, DismissAdminNotices
hopbox.admin.v1.AdminKeyService CreateAdminKey, ListAdminKeys, RevokeAdminKey
hopbox.admin.v1.ServerService ListServers, GetServer, CordonServer, UncordonServer, SetServerLabels, DrainServer (only of a server that hosts no control process), CancelDrain
hopbox.admin.v1.PoolService CreatePool, GetPool, ListPools, DeletePool
hopbox.admin.v1.SizeService CreateSize, GetSize, ListSizes, RetireSize
hopbox.admin.v1.AccountService ListAccounts, SuspendAccount, UnsuspendAccount
hopbox.admin.v1.OrgService ListOrgs, SuspendOrg, UnsuspendOrg, SetOrgLimits, GetDefaultOrgLimits, SetDefaultOrgLimits
hopbox.admin.v1.MachineService ListMachines, StopMachine, DeleteMachine
hopbox.admin.v1.ImageService ListImages

The Admin area also reads the audit log of the whole install with ListAuditEntries of the public API, under the same rule. The same rule holds for the audit log of an org in which the instance admin is not an owner or an admin (the sign-in, account, and audit API).

The other calls hand out a secret, or change what only root on a control server or the hopbox Terraform provider changes:

Calls Reason
SetMaintenance, CreateLoginLink, RegisterAdminKey, and the calls of KeyringService and MailService Only root on a control server makes them (The admin socket).
CreateEnrollmentToken and DecommissionServer The hopbox Terraform provider adds and removes servers. An enrollment token is a secret.
RegisterImage, GetCertificate, ListControlProcesses, ListAccountSignInMethods, RemoveAccountSignInMethod, and DeleteAccount No page of the Admin area uses them. They stay with root on a control server and with admin API keys.

The policy check of the service layer decides each call, the reads too (the API server). The console only hides the pages of the Admin area from other accounts. It is not the check.

Caller Result
The session of an instance admin, at most 10 minutes after its sign-in, on a call of the table The call runs. Its audit entry has the actor kind session, the account, and the session.
The session of an instance admin, more than 10 minutes after its sign-in, on a call of the table permission_denied with the message permission denied: this action needs a sign-in within the last 10 minutes. Sign in again, then retry, and the detail hopbox.v1.RecentSignInRequired (the sign-in, account, and audit API). The call writes no audit entry.
The session of an instance admin, on any other call permission_denied without the detail. A new sign-in does not change it.
The session of an account that is not an instance admin permission_denied without the detail, on every call.
The CLI token of an instance admin permission_denied. The hopbox CLI never calls the admin API.
A session cookie without the Origin of the install, or without the Connect protocol unauthenticated with the message the credential is not valid (Sessions, cookies, and sign-in links)

The gate reads the instance admin role and the age of the sign-in with the session on each call. So a revoke of the role closes the admin API to the sessions of the account at once.

The internal listener does not serve the admin API (the internal listener).

In maintenance mode, the admin API takes only SetMaintenance (the API server). Each other call, also each Get and List call of this page, writes an audit entry, so maintenance mode refuses it with unavailable before it changes anything. The reads keep the option (hopbox.v1.read_only) all the same, because a retry of them does no harm (API definitions).

Every call of the admin API writes an audit entry in the transaction of the call, also a call that only reads. The entry has the action of the call, the actor kind of the caller, and the request ID. An entry of local_root also has the details peer_uid and peer_pid: the user and the process that called through the socket. A refused call writes no entry.

The admin socket

Section titled “The admin socket”

The admin socket is a unix socket that only root can use. With it, whoever controls a control server can always act, even without web access. The code is in internal/adminsock.

Item Value
Path <run_dir>/admin.sock, by default /run/hopbox/admin.sock (the bootstrap config of hopboxd)
Owner the user of hopboxd, root on a server
Mode 0600
Protocols Connect, gRPC, and gRPC-Web, over HTTP/1.1 or HTTP/2 with prior knowledge
Services every service of the admin API, gRPC reflection, and gRPC health
Caller local_root

The socket checks each connection in two ways:

  1. File mode. The socket file has mode 0600, so only its owner can connect. hopboxd makes the socket under a temp name, admin.sock.<6 random characters>.tmp, sets the mode, and then renames it to admin.sock. So the final name never has a looser mode.
  2. Peer check. For each new connection, hopboxd asks the kernel for the user and the process of the peer: SO_PEERCRED on Linux, LOCAL_PEERCRED and LOCAL_PEERPID on macOS. It accepts only root (uid 0) and the user that runs hopboxd. It closes any other connection at once and logs admin socket refused a peer. On a server, hopboxd runs as root, so only root is accepted. On a laptop, hopboxd runs as you, so you can call it without sudo.

The second check holds also after a change of the mode of the file. The request gate of the socket turns the peer into the caller local_root, with its user ID and its process ID. Then the policy check and the audit log see that caller (the API server).

When it starts, hopboxd does these checks on the socket:

Check Error
The socket dir must not be a symlink. adminsock: the socket dir <dir> is a symlink
The socket dir must be a dir. adminsock: the socket dir <dir> is not a dir
Group and others must not be able to write in the socket dir. Such a user can swap the socket for one of their own. adminsock: the socket dir <dir> has mode <mode>, which lets group or others change it
The socket dir must belong to the user of hopboxd. adminsock: the socket dir <dir> must belong to the user of hopboxd
A file at the path must be a socket. adminsock: <path> exists and is not a socket, so hopboxd will not replace it
Another process must not serve a socket at the path. A socket that no process serves, for example after a crash, is removed. adminsock: another process serves <path>. Stop it first
The path plus its 11-byte temp suffix must fit in the 103 bytes of a unix socket path. adminsock: the socket path <path> has <n> bytes, and with its temp suffix it must fit in 92

A missing socket dir is created with mode 0755. When hopboxd stops, it removes the socket file, if the file is still its own socket.

Logs of the socket

Section titled “Logs of the socket”

The socket writes these records with component=adminsock:

Message Level Fields
admin socket refused a peer warn uid, pid
admin socket failed to read the peer warn err

Each call through the socket also gets the access log record api call with caller=local_root (the API server). The HTTP server of the socket writes its own errors at level warn with component=http, as the API listener does. These records have no component=adminsock.

hopboxd admin is the client of the socket. Other gRPC or Connect clients work too. For example, with curl and the Connect protocol:

InstallConfigService

Section titled “InstallConfigService”

hopbox.admin.v1.InstallConfigService reads and changes the config of the whole install. The config lives in the table install_config (Control store tables).

The message InstallConfig holds the general config:

Field Type Description
domain string The domain of the install, for example example.com. It is empty until an instance admin sets it.
version int64 The version of the install config. It starts at 1 and grows by 1 with each change.
update_time google.protobuf.Timestamp The time of the last change.
public_addresses repeated string The IPv4 and IPv6 addresses at which the edge servers take traffic, in their order. The DNS role points the domain, ns1, ns2, and every machine name at them (the DNS role). It is empty until an instance admin sets it.
acme_directory_url string The ACME directory of the CA that issues the wildcard certificate of the install (the certificate of the install). The default is https://acme-v02.api.letsencrypt.org/directory, the production CA of Let’s Encrypt.
acme_email string The contact email of the ACME account of the install. For an account without a contact, it is empty.
acme_terms_agreed bool true once an instance admin agreed to the terms of the CA of acme_directory_url. The install asks for no certificate before that. The default is false.
mail_transport MailTransport How the install delivers its mail (Mail). The default is MAIL_TRANSPORT_SMTP.
maintenance bool true while the install is in maintenance mode (the API server). Only SetMaintenance changes it. The default is false.

The enum MailTransport has these values:

Value Number Meaning
MAIL_TRANSPORT_UNSPECIFIED 0 Never in a response. A request must not use it.
MAIL_TRANSPORT_SMTP 1 Sends each mail through the SMTP server of the install (SMTP config).
MAIL_TRANSPORT_FILE 2 Writes each mail to a file on the control server that sends it, and sends nothing. It is for a dev or test install. MailService reads the files (MailService).

UpdateInstallConfig

Section titled “UpdateInstallConfig”

Changes the fields that the request sets, and keeps the others. It returns the config after the change.

Item Value
Procedure /hopbox.admin.v1.InstallConfigService/UpdateInstallConfig
Policy action install_config.update: local_root, admin_key, and an admin session
Idempotent option no. A second call with the same request sets the same values again.
Audit entry action install_config.update, no target, details domain (the new domain), old_domain, public_addresses (the new addresses, joined by commas), and old_public_addresses. Also acme_directory_url, acme_email, acme_terms_agreed (true or false), and mail_transport (smtp or file), each with its old_ detail. A change of the domain, of an ACME setting, or of the mail transport tells the instance admins (Notices to instance admins).

The request UpdateInstallConfigRequest has these fields:

Field Type Description
domain optional string The new domain. It must follow the rules in Domain rules. Leave the field out to keep the domain.
public_addresses PublicAddresses The new public addresses. The list replaces every public address of the install. An empty list removes them. Leave the field out to keep them.
acme_directory_url optional string The new ACME directory: an https URL of a host, with at most 2048 characters, and without user info or a fragment. It holds no whitespace and no control character. A new directory also sets acme_terms_agreed to false, unless the request sets acme_terms_agreed too. Leave the field out to keep the directory.
acme_email optional string The new contact email of the ACME account. It must be one plain email address, such as ops@example.org, without whitespace or a control character. The install keeps it in lowercase. An empty string removes the contact. Leave the field out to keep the email.
acme_terms_agreed optional bool true records that the caller agrees to the terms of the CA of the directory. A new agreement covers the terms that the next attempt reads from the directory. false stops new certificates. Leave the field out to keep it.
mail_transport optional MailTransport The new mail transport. The SMTP config stays, so a switch back to MAIL_TRANSPORT_SMTP needs no new config. Leave the field out to keep the transport.
expected_version optional int64 The version of the install config that the caller read. If the config has another version now, the call fails with aborted and changes nothing. Leave the field out to change the config at any version.

The message PublicAddresses has one field, addresses, a repeated string. Each address must follow the rules in Domain rules: at most 16 IPv4 or IPv6 addresses, none twice. The install keeps them in the text form of Go netip, in their order. So 2001:DB8::10 becomes 2001:db8::10, and an IPv4 address in IPv6 form, such as ::ffff:203.0.113.10, becomes 203.0.113.10.

With expected_version, two admins that change the config at the same time cannot overwrite each other: the second one gets aborted with the message conflict: the install config is at version <n>, not <m>. Read it again. The call locks the row until it commits, so the version check and the change happen as one step.

A request that sets no field gets invalid_argument with the message invalid argument: the update sets no setting. expected_version alone sets no field. A bad domain gets invalid_argument with the rule that it breaks, for example invalid argument: invalid name: the install domain "localhost" must have at least two labels, such as hop.example.org. A bad address gets invalid_argument with the rule that it breaks, for example invalid argument: invalid public address: "0.0.0.0" is not an address that a client on another host can reach. A bad ACME setting gets invalid_argument too, for example invalid argument: invalid ACME setting: "http://acme.example.org/directory" is not an https URL of a host without user info or a fragment, such as https://acme-v02.api.letsencrypt.org/directory. Whitespace or a control character gets, for example, invalid argument: invalid ACME setting: the directory URL holds the character ' '. It can hold no whitespace and no control character. MAIL_TRANSPORT_UNSPECIFIED or an unknown transport gets invalid_argument with the message invalid argument: the mail transport <n> is not smtp or file.

While the transport is MAIL_TRANSPORT_FILE, each update logs mail goes to files, not to recipients at level warn (Mail).

Field Type Description

A change sets the column maintenance of install_config, adds 1 to the version, and publishes the change event install.maintenance_changed in one transaction (Control store tables). Then the control process turns its own maintenance mode on or off. Maintenance mode lets this call through also while it is on, so the admin socket always takes it.

A call that turns maintenance mode on, also one for the state that the install has already, returns only after the calls, the control channels, and the leader jobs that ran in this process ended. If they do not end before the deadline of the call, it fails with unavailable and the message unavailable: <n> calls, control channels, or leader jobs still run: context deadline exceeded, and maintenance mode stays on. Call it again. If maintenance mode turns off before the wait ends, the call fails with unavailable and the message unavailable: maintenance mode turned off while it waited for the calls, control channels, and leader jobs to end, because the work runs again. So a success means that maintenance mode was on and the work had ended.

The turn to on also covers the other control processes of the install, which record themselves in control_processes (Control store tables). It runs these steps:

  1. Before it changes anything, it checks the live rows. If a live control process knows fewer than 44 migrations, the call fails with failed_precondition and the message the control process <id> on <host> (hopboxd <rel>) knows the migrations up to <n>, and only a hopboxd that knows migration 44 honors maintenance mode. Upgrade it first. Maintenance mode stays off. Only releases from migration 0045 on write rows, so this check guards the rows of a future release, not an older one.
  2. It drains its own process, as the paragraph above says.
  3. It waits until every other live control process reports maintenance mode on and drained, with a maintenance_version at least the version of install_config that the turn wrote. It reads the rows every 250 ms. Each process reports in its row the version at which it read maintenance mode, so the wait compares versions, not times. A process that applies the change renews its row at once, and once more at the end of its drain. A process that ended without its stop counts as gone only 35 s after its last renewal (store.ControlProcessGone: the live window of 20 s and the dead peer timeout of 15 s), because a COMMIT that it sent before its fence can still land until the store ends its session. A process that stopped cleanly counts as gone at once. So a turn to on beside a control server that died can wait up to 35 s, longer than the deadline of the call: then it fails with unavailable, and you call it again.

If a process does not report before the deadline of the call, the call fails with unavailable and the message maintenance mode is on, but the control process <id> on <host> (hopboxd <rel>) did not report that its calls, control channels, and leader jobs ended: .... The rest of the message is the cause, such as context deadline exceeded. The flag stays on then. Call it again. A control process of a release before migration 0045 writes no row, so the call does not see it, and neither does any check that reads the rows: the migration guard, the KEK promote, the decommission check, and the rolling upgrade order. Upgrade every control server before you rely on them.

The control process logs maintenance mode is on: the API takes only reads, and the control role serves no control channel at level warn after a change to on, and maintenance mode is off at level info after a change to off, with component=service.

A change of the domain or of the public addresses raises the serial of the DNS zones (Control store tables). The same transaction publishes the change event dns.zone_changed. The control role then pushes the new zones to each server with the DNS role (the DNS role). An update that sets the same domain and the same addresses again changes neither, and pushes nothing.

RotateKEK

Section titled “RotateKEK”

Adds a new KEK to the file keyring in <data_dir>/kek and makes it the current one. The old KEKs stay, so the values that they sealed still open (Sealing). Use it only with one control server. With more than one, use StageKEK and PromoteKEK.

Item Value
Procedure /hopbox.admin.v1.KeyringService/RotateKEK
Policy action keyring.rotate: local_root only. The key files live on one control server, so only root on that server rotates them.
Idempotent option yes. A call must have an Idempotency-Key header (the API server).
Audit entries keyring.rotate.start before the key file exists, then keyring.rotate after it. Both have target kind kek, target ID the ID of the new KEK, and the detail idempotency: the SHA-256, in hex, of the caller scope and the idempotency key.

The request RotateKEKRequest has no fields. The response RotateKEKResponse has these fields:

Field Type Description
key_id string The ID of the new current KEK, for example file:2.

The call refuses while the install has a row of a control process on another host in control_processes, live or not (Control store tables). A control server that stopped cleanly, or that ended without its stop, keeps its row for 24 hours, so it counts too. The call fails with failed_precondition and the message the install has a control server on <host> too, and a rotation makes the new key current only on this server. Run hopboxd admin kek stage, copy the staged file to every control server, then run hopboxd admin kek promote. The new key gets the next ID of the install: one after the newest key of this keyring and of kek_fingerprints, so a key that another control server made, or a stage that an operator gave up, never shares its ID (Sealing). The check comes after the policy check and before the steps below. The call takes these steps. The audit entries of steps 4 and 6 commit in transactions of their own, apart from the transaction of the call. A key file is live as soon as it exists. Each entry commits also after the client gave up. A failed entry is tried 3 times, with waits of 0.1 s and 0.4 s, and each try waits at most 10 s.

  1. The policy check.
  2. It looks in the audit log for a rotation (keyring.rotate) of the last 24 hours with the same idempotency key. If it finds one, it returns the ID of that key and stops.
  3. It looks for a start (keyring.rotate.start) of the last 24 hours with the same idempotency key. The start names a key. If that key exists as <n>.key or <n>.staged, and no rotation entry names it, an earlier try made the key and stopped before step 6. The call then takes that key. If the key is still staged, the call records its fingerprint, as step 5 does, and promotes the file to <n>.key. Then it goes to step 6.
  4. It writes the start entry keyring.rotate.start. The entry has the ID of the next key and the hash of the idempotency key.
  5. It writes the new key as the staged file <n>.staged, and records its fingerprint. If the install has another key of that ID, the call fails with failed_precondition, removes the staged file, and the current KEK stays. Then it promotes the file to <n>.key. From this moment, the new KEK is current.
  6. It writes the rotation entry keyring.rotate.
  7. It logs rotated the key-encryption key at level info, with component=service, key_id, and caller.

So a retry with the same idempotency key never makes a second key, wherever the first try stopped:

The first try stopped A retry
before step 4, or at step 4 makes the key, as a first try does
after step 4, before the key file existed finds the start, sees no key file, and makes the key
in step 5, after the staged file existed and before its promote finds the start and the staged file, records its fingerprint, promotes it, and records that key. No staged file stays behind.
after step 5, before step 6 committed finds the start and the key file, and records that key
after step 6, for example after a failed commit of the idempotency key finds the rotation entry and returns its key

Steps 2 and 3 matter because a call that fails leaves no idempotency response, so a retry runs the call again (the API server). Without an idempotency key, for example from a test of the service layer, the call skips steps 2 to 4.

One hopboxd runs one rotation at a time, so two calls at the same time get two keys in turn. The keyring can refuse the rotation, for example because others can read the keyring dir. Then the call gets failed_precondition with the message of the keyring (Sealing). Any other failure of the key file, such as an I/O error, gets internal.

If the rotation entry still fails after its tries, the new KEK stays current without its rotation entry. Then hopboxd logs rotated the key-encryption key, but the audit entry failed at level error, with key_id and err, and the call fails with internal. Each failed try of an entry logs audit entry failed at level warn, with action, try, and err. A retry of the call with the same idempotency key records the key at step 3.

A rotation does not rewrap the sealed values. They keep their old KEK until RewrapSealedValues moves them. The rewrap also moves the key of the install CA (Control store tables).

Notices to instance admins

Section titled “Notices to instance admins”

Some calls leave something that lasts after the session that made them. For example, a stolen admin session of 10 minutes can make an admin key that works for 365 days. So these calls tell the instance admins, in the console and by email (plan question Q103):

Call When it tells the instance admins
CreateAdminKey Always.
RegisterAdminKey When it makes a key, with registered set to true.
GrantInstanceAdmin When the account was not an instance admin.
The sign-in of a login link (the sign-in, account, and audit API) When it makes the account an instance admin.
A new sign-in method of an account: a link from a session (Sessions, cookies, and sign-in links), or a sign-in that joins the account through a verified email When the account is an instance admin (plan question Q106). A stolen session can link the email or the GitHub user of an attacker, and so keep the role after the session ends. The audit entry account.link_sign_in_method then has the detail instance_admin set to true. The method of a login link never joins an existing account, because it proves no email.
RevokeInstanceAdmin Always. Otherwise a stolen session can revoke the other admins first, so that nobody hears of its later actions. The notice comes before the revoke, so the revoked account gets the email and a notice too. Its notice shows only if it gets the role again.
The admin DeleteAccount (DeleteAccount) When the account is an instance admin, as for the self-delete in the next row. The audit entry admin_account.delete then has the detail instance_admin set to true. The actor is root or an admin API key, so no account gets the copy of the actor. Each email of the deleted account gets the notice as an instance admin.
SuspendAccount and UnsuspendAccount (SuspendAccount) When the account is an instance admin, and the call changes its state. Otherwise a stolen session can suspend the other admins first, so that nobody hears of its later actions, as with a revoke. The audit entry then has the detail instance_admin set to true. A call with already set to true tells nobody.
DeleteAccount (the sign-in, account, and audit API) When the account is an instance admin (Q106). Otherwise a stolen session can remove an admin in silence, as with a revoke. The notice comes before the delete, so each email of the deleted account gets the copy of the actor. The audit entry account.delete then has the detail instance_admin set to true.
SetSMTPConfig and ClearSMTPConfig Always.
SetOAuthClient and ClearOAuthClient Always.
UpdateInstallConfig When it changes domain, acme_directory_url, acme_email, acme_terms_agreed, or mail_transport. The transport decides whether the install uses the SMTP server. The domain decides where the console and every link of the install go, and the ACME settings decide which CA issues the certificate of the install (Q106). A change of public_addresses alone tells nobody. hopboxd admin config set and hopboxd install --domain call UpdateInstallConfig, so their changes tell the instance admins too.

A notice is the audit entry of the call. In the transaction of the call, each instance admin other than the actor gets an open notice in the table admin_notices (Control store tables). The banner of the console and the Admin area show the open notices (Console), and ListAdminNotices returns them. hopboxd admin has no command for them, because root has no account and so no notices.

After the commit, hopbox sends an email to each email of each of these instance admins. When the actor is a session, its account gets a copy too. For a link from a session, the copy also goes to the email of the new method, unless another account holds that email as verified. A method that joins at a sign-in through a verified email is different, because whoever proved the email acted, and that person is maybe not the owner of the account. So the account gets an open notice in the console like each other instance admin, and its email says that a new sign-in method joined the account. The person whose session someone stole is the person who knows best that the action was not theirs. The sign-in of a login link had no session before the grant, so its account gets no copy. An email that no sign-in method verified gets the notice too, because only root adds such an email to an account, in a login link.

The email has these parts:

  • What changed, with the facts of the audit entry, such as the name, the ID, and the end of a new key.
  • Who did it: the session and its account, the CLI token and its account, the admin API key, or root on a control server with its user and process.
  • The time and the ID of the audit entry.
  • How to undo it: the page of the Admin area and the hopboxd admin command. For an action of a session, also how to revoke the role of its account, which closes the admin API to each session of the account at once. For a new sign-in method, the command hopboxd admin account sign-in-method remove with the IDs of the account and of the method. A method that joined at a sign-in through a verified email had no session before, so its advice says to revoke the role first, because the holder of that email can sign in again. Each value in a command of the advice is in POSIX single quotes, and each ' in it is written as '\''. So a POSIX shell, such as sh, bash, or zsh, reads each value as one word, also a value with shell code in it, such as an ACME directory URL with $(...) in its query. In another shell, such as tcsh, these quotes are not safe, so run the command in sh, bash, or zsh. A delete is final, so its advice says to read the audit log for the other actions of the deleted account. The advice of an admin delete by an admin API key gives the command that revokes the key. The advice of a suspend gives the page Accounts of the Admin area and hopboxd admin account unsuspend. The advice of an unsuspend gives the same page and hopboxd admin account suspend.
  • The link to /admin/notices, or for the copy of the actor, a line that says why the actor gets it. A change of the domain names both domains in place of the link.

The email and the notice never hold a secret: no admin key, no client secret, and no SMTP password. They hold only the facts of the audit entry, which never holds a secret value either.

A change of the mail config sends its email the way that the install sent mail before the change, and the new way only when that fails. The changes of the mail config are SetSMTPConfig, ClearSMTPConfig, and a change of mail_transport. So a new SMTP server that an attacker sets does not swallow the notice of its own change. A change of domain also sends its email the old way first. Each email of the change names the old domain in its first line and its subject, also when it goes the new way after the old way failed. The email of a first domain names the new domain there, because the install had no domain before. It has no link to /admin/notices, because the console at the old domain no longer answers, and a link to the new domain can lead to a domain that an attacker set. In place of the link, it says that the console moved from the old domain to the new one. It tells the reader to check the change first, and then to type the new domain in the browser. Some mail clients make the name of the new domain clickable, so the email asks for the check before the reader opens it. A domain set on an install without one gets the same line with none as the old domain, so no email links to a domain that the actor just set. It has no old value to set back. So its advice gives sudo hopboxd admin config set --domain=DOMAIN, with the domain of the install in place of DOMAIN.

A failed email never fails the call. The emails of one notice share one limit of 20 s. For each address that fails, hopbox logs the email of an admin notice failed at level error, with audit_entry, account, and err. It also writes the audit entry admin_notice.mail_failed, with the actor kind system, the target kind audit_entry and the ID of the entry of the call, and the details account, email, and error. The error is the reply of the mail server. If that text looks like a credential, the audit log refuses it, so error holds a fixed text instead, and only the log has the reply. An address can also look like a credential, for example hbx_ops@example.org stored before the audit log refused such values. Then the entry goes without email, and account still names the recipient. The detail email_sha256 holds the first 16 hex digits of the SHA-256 of the address, so you can tell apart the addresses of one account. So one such value never costs the entries of the other addresses. The notice stays in the Admin area. An install without an SMTP config fails each email this way. With the file transport, the email goes to the mail folder (Mail). After the sends, hopbox logs sent the emails of an admin notice at level info, with audit_entry, action, sent, and failed. If it cannot write the audit entries of the failures, it logs the audit entries of the failed emails of an admin notice failed at level error.

SuspendAccount

Section titled “SuspendAccount”

Suspends an account, for example to handle abuse. The call deletes nothing. In its transaction, it does these steps:

  1. It sets the state of the account to suspended, with the reason and the time.
  2. It deletes every session and every CLI sign-in of the account (Sessions, cookies, and sign-in links, CLI tokens, API keys, admin API keys, and SSH keys). So the private machine URLs of those sessions stop too (Control store tables).
  3. It suspends the personal org of the account, and each org in which the account is the only owner, with the same reason. An org that is suspended already keeps its suspension and its reason. Each org that the call suspends stops its machines, as for SuspendOrg. The column suspended_with_account of the org names the account (Control store tables).
  4. In each other org of the account, it sets the target stopped on each private machine of the account. A shared machine keeps running, because the org uses it. A hibernated machine stays hibernated.

While the account is suspended, these rules hold:

What Result
A sign-in with a magic link, a login link, GitHub, or Google It fails with permission_denied and the message permission denied: an instance admin suspended this account, so it cannot sign in. The reason: <reason>. No session starts (Sessions, cookies, and sign-in links).
The poll of a device sign-in that a person approved before the suspend It fails with the same error, and uses up the device code (CLI tokens, API keys, admin API keys, and SSH keys).
The member API keys and the SSH keys of the account They stay in the store, but they do not work. They work again after the unsuspend (CLI tokens, API keys, admin API keys, and SSH keys, the SSH front door).
An open stream, such as WatchMachines, of a credential of the account It ends at its next check of the credential (the API server).
An open SSH connection with a key of the account It ends at the next check (the SSH front door).
Any call with a credential of the account that the request gate let in before the suspend No change lands after the commit of the suspend. In each org, the account has no role from that commit, so a call in an org, also a read, fails as for an account that is not a member (Control store tables). For a machine, that is not_found. DecommissionServer

Section titled “DecommissionServer”

Takes a server out of the install for good. The state turns decommissioned, and no call changes it again. The install refuses the certificates, the heartbeats, and the renewals of the server from then on. If the control channel of the server runs in the same control process, that process ends it after the commit. A channel in another control process ends at its next heartbeat (the control channel).

The call works from every state but decommissioned. A draining or shutting_down server must be empty. The drain runs this call itself at its third empty check (Cold move).

The call refuses a server that still holds machines. The control store counts each machine on the server that its executor has not deleted yet, stopped machines included. The last heartbeat of the server counts its allocations. The call refuses a server that a move runs from or to. It also refuses a server that keeps the copy of a disk which a failed move left, while the machine lives on another node.

The decommission drops the old copies that the server still had to remove. It clears cleanup_server_id of those moves, so that a new move of those machines does not wait. The row of the drain goes too, and so does a pending removal of roles, with its stranded machines. removed_roles stays.

The call also refuses a server that shares its host with the last live control process, while another server is not decommissioned. The other servers need that control role. The check reads the live rows of control_processes (Control store tables). A live process hosts the server when its row names the server ID, or when it is the process that takes the call and its own host has that identity in <data_dir>/server (Enrollment and the install PKI). The call refuses only while no live control process runs on another host, and other servers still belong to the install. A process on another host counts only when its row names no server, or names a server that is not decommissioned. A process on a decommissioned server goes with its server, so it keeps no control plane for the others. A control process of a release before migration 0045 records no row, so the check does not see it: upgrade every control server before a decommission relies on it. So an install with a second control server decommissions the first server in any order, and the server of the last control process goes last. The check takes a transaction lock before it reads, and so does each enrollment. So two decommissions at the same time, such as in one parallel terraform apply, see each other, and a server that enrolls during the check counts. If the control role cannot read that identity, the call fails with failed_precondition. The message names the file: cannot read the server on the host of this control role: read <data_dir>/server/identity.pem: .... A decommission of a decommissioned server changes nothing, and its row version stays. When Terraform destroys a server, the hopbox Terraform provider drains it, and the drain calls it (hopbox Terraform provider). The provider never removes the first server from its state after a decommission outside Terraform.

DrainServer

Section titled “DrainServer”

Moves every machine of a server cold to other nodes, then decommissions the server (Cold move, Drain a node). The call cordons the server and sets its state to draining, then returns at once. A leader job moves the machines, at most 2 at once. A machine that cannot move stays on the server with its disk: a running machine with no room keeps running, a machine whose move failed stays stopped. The drain of the Server names it. Once the server is empty, 3 empty checks in a row, one minute apart, decommission it. A drain never deletes a machine.

A second call starts the drain again, as a retry. It clears the stranded list, restarts start_time, and counts the empty checks from zero. The drain records whether the server was cordoned at its first start, and a retry keeps that record. CordonServer during the drain sets it too. CancelDrain ends the drain. A server that drains stays cordoned, so UncordonServer refuses it with failed precondition: the server <id> drains, and stays cordoned until the drain decommissions it. To keep the server, cancel the drain with hopboxd admin server cancel-drain <id>. An unresponsive server keeps that state with the flag set, and turns draining at its next heartbeat.

RemoveServerRoles

Section titled “RemoveServerRoles”

Starts the removal of the roles edge, dns, node, or more than one from a running server, the first server too (plan questions Q97 and Q100). The server keeps its ID and the data of its other roles. The call returns at once. hopboxd admin server remove-role calls it (hopboxd), and the Terraform provider calls it when a plan drops a role (hopbox Terraform provider).

The call refuses the role control with unimplemented. The control role never enrolls, and it goes from a server only through a second control server on the external Postgres. It refuses a removal that leaves the server no role that enrolls (node, dns, or edge), because its certificate needs one. A drain takes a whole server out (DrainServer). The role dns runs only on edge servers, so the removal of edge from a server with dns must name dns too.

These checks run in the transaction of the call. Each refusal gives failed_precondition with the reason:

  1. The server runs a release whose heartbeats name the feature remove-role (the control channel). The control role takes the features only from the heartbeats of the release that the server runs now.
  2. Another server keeps each role that goes. That server is ready, or cordoned for edge and dns, and has no pending removal of the role. For edge, that server holds at least one floating address: its heartbeats report edge.public_ipv4, edge.floating_addresses, or edge.public_ipv6.
  3. For node, another ready node exists. A machine without room elsewhere does not fail the call. It stays on the server, as in a drain.
  4. For edge and dns, the public addresses of the install, which the zone names, hold no address of the server: its peer address, the floating addresses of its heartbeats, and the public addresses on its interfaces (the API server). Set the public addresses first with hopboxd admin config set --public-address.
  5. No live control process runs a release of the schema version below 56.

The call takes the advisory lock of the server registry, so two removals run one after the other, and each sees the other. It records the removal on the server row (removal_roles, removal_cordoned_before, removal_started_at), and writes the audit entry server.remove_roles_start. The registry keeps every role until the end of the removal, so the certificate of the server stays valid and its control channel goes on (Enrollment and the install PKI).

For node, the call cordons the server first. A leader job then moves each machine of the server cold to another node, as the drain does, at most 2 at once (Cold move). No decommission comes at the end. A machine that cannot move stays on the server with its disk, the removal waits, and removal.stranded names the machine. The removal records whether the server was cordoned before it. Its end and its cancel lift only a cordon that it set, so a cordon of the operator stays.

A removal without node is ready at once. A removal of node is ready once the server holds nothing for a move (removal.ready). An enrollment of the server with the roles that stay then ends the removal (Enrollment and the install PKI). The end adds the roles that went to removed_roles.

One removal runs at a time on a server. A second call for a server with a pending removal returns that removal when it names the same roles, in any order. So a retry of the Terraform provider goes on with it. A call with other roles fails. DrainServer refuses a server with a pending removal, and this call refuses a server that drains.

SizeService

Section titled “SizeService”

hopbox.admin.v1.SizeService manages the sizes of machines. A fresh install has only the size default (Domain rules). An instance admin adds bigger sizes with this service. A user picks a size at the create of a machine, and never a pool (the machine API). The sizes live in the table sizes (Control store tables).

A size can name a pool and labels. They become the placement filters 4 and 5 of each machine of the size (Placement), so its machines land only on the nodes of that pool that have each label (plan question Q60). A size that names no pool takes any pool.

A size never changes. A machine copies the vCPUs, the RAM, and the disk of its size at its create. To change a size, add a size with a new name and retire the old one. A retired size takes no new machine. Its machines keep it, and its name stays taken, because the machines name it. The size default cannot retire, because a create without a size takes it.

CancelMove

Section titled “CancelMove”

Ends the cold move of a machine that runs (Cold move). The move ends in the state failed, with the error an instance admin canceled the move. A machine in stopping gets its own target back on its node. A machine in pulling goes back to its source node with its disk, stopped, and the target node removes what it pulled. A machine that is no longer in moving on the target node stays there (Cold move).

With give_back, the call also asks the target node to give such a machine back to its source node, also after its move failed (plan question Q102, Cold move). The target node answers through its control channel. It gives the machine back only when it never proved the pull of the move. Otherwise it keeps the machine, and the source removes its copy. The call returns at once with give_back MOVE_GIVE_BACK_REQUESTED. Read the answer in give_back of the move with ListMoves. A give_back on a move whose machine stays on its source, or goes back there, only cancels the move.
