hopboxd

hopboxd is the server binary of hopbox. It runs on every server of an install.

Usage

Section titled “Usage”

When you run hopboxd without a command, it prints its help and an error, and exits with status 80.

Global flags

Section titled “Global flags”

A global flag goes before or after the command.

Flag Type Default Description
--log-level level info The lowest level of the log records that hopboxd writes. The values are debug, info, warn, and error. Case does not matter. A value can also carry an offset, for example info+2, as in Go’s log/slog.
-h, --help bool false Prints the help of hopboxd, or of the command that it follows, and exits.

run

Section titled “run”

run reads the bootstrap config, starts the roles that the config lists, and runs until it gets SIGINT or SIGTERM. Then it stops the roles and exits with status 0. The bootstrap config of hopboxd lists the keys of the bootstrap config.

Flag Type Default Description
--config path /etc/hopbox/hopboxd.toml The bootstrap config file.

First, run starts the metrics listener and the host firewall. Then it starts the units of the control role, the DNS role, the edge role, and the node role, in this order. Then it starts the unit of the control channel. A role that the config does not list has no units. Each unit starts after the unit before it is ready.

Order Unit What it does Stop timeout
0 metrics Serves the Prometheus metrics on metrics.listen (Metrics). 5 s
1 host firewall Replaces the nftables table inet hopbox_host with the rules of the roles of the server, in one netlink batch (the host firewall). The table is in place before any role opens a listener. If the batch fails, the start fails, and the table before it stays. Until its stop, it watches the table. It installs the table again after a flush, and after a change of the vRack interface or of its sets. Its stop keeps the table, so the firewall holds while hopboxd is down. It keeps the vRack interface and its last peers, jump hosts, and known peers in <data_dir>/hostfw (the host firewall). After the install of the table, an edge server that enrolls turns on forwarding for the egress (the host firewall). 0.1 s
2 postgres Starts the bundled Postgres (the bundled Postgres). The cluster is in <data_dir>/pg, and the socket is in <run_dir>/pg. With postgres.url, it starts no Postgres. It reads the CA file and the password file of the external Postgres, and the next units connect to it over TLS (the bundled Postgres). 30 s
3 store Opens the connection pool of the control store and runs the migrations (the bundled Postgres). Then it checks the key files. It first applies a promote of a key-encryption key that happened while this process was down, and then opens the install CA of the control store with the key files of this server. It makes the CA when none exists. If the key files cannot open it, the start fails with control: the key files in <dir> do not open the install CA of the control store: <error>. Copy the key files of a running control server there. A keyring without any key passes this check (Sealing). Then it imports the bootstrap admin API key from the file that hopboxd install can leave (Server layout). Then it registers the default image of the release (The default image of the release). Until its stop, it reads the schema of the store every 10 s. If a newer hopboxd applied a migration that does not run with this one, if the store lost its schema, or if 12 reads in a row fail, it stops hopboxd. 12 reads take about 2 minutes, which outlasts the failover of a managed PostgreSQL (the bundled Postgres). The limit is safe only because of the fence below: a process that cannot reach the store fences itself within 15 s, long before the schema watch stops it, so it never writes while the other control processes no longer count it. The migration runner writes the first row of this control process in the table control_processes while it still holds the migration lock, right after the migrations and with the same check of the schema, so no newer hopboxd applies a migration that does not allow this one before the first row exists (the bundled Postgres). At the end of the unit, it writes the full row and keeps it up to date until its stop (Control store tables). The row holds a new random ID for each start, the ID of the enrolled server of the same hopboxd or none, the host name, the URL of the internal listener, the release, the schema version, the key files and the staged key files that it can open, the key with which it seals, and the maintenance and drained flags. While its key dir has a staged file, or while it misses the promoted key, each renewal first applies the promote of the install (Sealing), as does each change event keyring.kek_promoted. The unit renews the row on a fixed ticker every 5 s. Each try takes at most 2 s, so a slow store never moves the next renewal. It also renews at once after a turn of maintenance mode, after the internal listener starts, at a change event of a promote of a KEK, and once at the end of a drain, when no call, control channel, or leader job of the process runs any more in maintenance mode. A row renewed in the last 20 s is live. Each renewal reads the schema of the store in the same transaction, and fails when the store no longer runs with this hopboxd, so a renewal that works means both (the bundled Postgres). A renewal that fails this way fences the process and stops hopboxd at once. When no renewal worked for 15 s (the 20 s of the live window less a margin of 5 s, counted from the start of the last renewal that worked), the process fences itself before its row stops being live. While it is fenced, every listener of the API refuses every call, reads too, with unavailable, the header Hopbox-Not-Run: 1, the header Retry-After: 30, and the message this control server lost the control store for a while, so it takes no call until it reaches the store again. Retry later, or through another control server. Only gRPC health and reflection pass. The plain HTTP routes that maintenance mode refuses, such as the starts of the GitHub and Google sign-in, answer 503 with that message. No control channel and no leader job runs. A leader that stays fenced for 15 s gives up its lease, and a fenced process does not try for the leader lock (Leader jobs). The fence lifts at the next renewal that works. admin control list shows the rows. 5 s
4 events Reads the change events of the control store from the head (Control store tables). It feeds them to the watches and the lifecycle waits of the machine API in this process (the machine API). So they see each change, also one of another control process or of a node. If the reader stops by itself, hopboxd stops. 2 s
5 leader election Takes part in the leader election (Control store tables). The leader runs the leader jobs. 15 s
6 api Serves the API on control.api_listen (the API server). 10 s
7 internal listener Serves the cluster API over TLS on control.internal_listen: enrollment, the control channels of the servers, and EdgeService. It also serves the API and the console to the edge servers, for the clients that they forward (the internal listener). 5 s
8 admin socket Serves the admin API on <run_dir>/admin.sock (the admin API). 10 s
9 dns The DNS role (the DNS role). At its start, it reads the zones on its disk, and serves them if they pass every check (the DNS role). Then it opens a UDP socket and a TCP socket at each address of dns.listen. So a port that another program holds fails the start. Without zones on its disk, it answers SERVFAIL to each query until the first zones arrive over the control channel. 1 s
10 edge The edge role (the edge role). At its start, it opens the HTTPS listener at edge.https_listen and the HTTP listener at edge.http_listen. So a port that another program holds fails the start. It refuses each TLS handshake until the first certificate arrives over the control channel. At its stop, it closes the listeners, gives the open requests 2 s, and then ends the rest, also the streams and the WebSockets. 5 s
11 machines The node role. It first sets up the node network: it replaces the nftables table inet hopbox_node with one that holds the tap devices of the machines that run, and turns on IPv4 and IPv6 forwarding (the node network). Until its stop, it watches the table, and installs it again after a flush. It adds the guest kernel of vmm.kernel to the kernel cache. It starts the executors of the machines with the Firecracker driver (the node executor, the Firecracker driver). It also starts the store of the machine logs (Machine logs). Once the server has a mesh address, it serves the disks of the cold moves on port 7444 of that address (Cold move). At its start, the executors attach to the microVMs that run. At its stop, the executors end their actions at once. Every microVM keeps running, because it runs in a systemd unit of its own. The unit of each machine runs stop-guest at its stop, and is ordered before hopboxd.service. 10 s
12 channel Keeps the control channel of this server to one of the live control servers that the control role sent, kept in <data_dir>/server/control-urls, or to one of channel.control_urls, over mutual TLS. After a lost or refused channel, it dials the next URL (the control channel). If the control role runs in the same hopboxd, the channel still goes over TLS (the control channel). It hands the zones that the control role sends to the dns unit. It hands the certificate, the routes, and the access changes to the edge unit. It hands the specs of the machines to the executors of the machines unit, and the machine streams to its handlers. It also keeps the mesh device hbm0 (the mesh). It checks the device at its start, before the first heartbeat, and then every 2 s. It hands the device the mesh that the control role sends. At its start, it removes what the IPv6 block of a release before N29 left on the server, and tries again every 2 s until nothing is left (the egress of the machines). It also keeps the egress tunnels hbe*, with a check at its start and then every 2 s (the egress of the machines). It hands them each mesh. An edge server tells in each heartbeat that its tunnel is ready. On an edge server with edge.public_ipv4, edge.floating_addresses, or edge.public_ipv6, it keeps the floating addresses on the uplink and the peer address as the source of the default route, with a check at its start, after each change of an address or a route, and every 2 s (the edge role). Its start returns after these first checks. Before the enrollment of the server, it waits for the identity in <data_dir>/server. So run can start before enroll. 5 s

Unit 1 runs for every role. Units 2 to 8 belong to the control role and unit 9 to the DNS role. Unit 10 belongs to the edge role and unit 11 to the node role. Unit 12 runs on a server that enrolls: one with a role other than control. Unit 13, systemd notify, runs for every role:

Order Unit What it does Stop timeout
13 systemd notify Sends READY=1 to the socket of NOTIFY_SOCKET at its start, and STOPPING=1 at its stop (sd_notify(3)). Without NOTIFY_SOCKET, it does nothing. It starts last. So the unit hopboxd.service of Type=notify becomes active only after every other unit is ready (Server layout). If it cannot send, the start fails. 1 s

On a server with only the node role, run starts the metrics listener and the host firewall unit. Then it starts the machines unit, the channel unit, and the systemd notify unit. On a server with only the DNS role, it starts the dns unit in place of the machines unit. On a server with the edge role, it starts the edge unit before the channel unit. So what the channel gets for these roles always has a server.

run stops the units in the reverse order. First it stops systemd notify, then channel, machines, edge, and dns. Then it stops the units of the control role, from the admin socket to Postgres, then the host firewall, and last the metrics listener. So no unit stops before a unit that needs it. A server can have the control role and a role that enrolls. Then the control role sees the channel of its own server close before its listeners stop. Each stop has the timeout in the table:

  • The channel unit closes the control channel and waits for its loop and its checks to end. It keeps the device hbm0 and the egress tunnels. So their traffic goes on while hopboxd is down.
  • The machines unit ends the actions of the executors, closes the guest links, and closes the files of the machine logs. It stops no microVM, and keeps the node network.
  • The edge unit closes its listeners and gives the open requests 2 s. Then it cancels the rest: the streams, the WebSockets, and the long calls. At the timeout, it closes every connection (the edge role).
  • The dns unit closes its sockets and waits for the queries in flight.
  • The api, internal listener, and admin socket units stop taking new connections and wait for the running unary calls. They end every open stream at once, because a stream has no natural end. They cancel the stream and end every read of its request body. So a stream that waits for the client, such as a reflection stream, ends too. A unary call that still reads its request body gets 2 s more. So a stalled upload cannot hold the stop. At the timeout, they close the rest (the API server).
  • The leader election unit ends the term of the leader and releases the leader lease.
  • The events unit stops its reader of change events and closes its connection.
  • The store unit stops the renewals of the row of this control process, and marks the row stopped, so no check waits for this process. The row stays until the sweep. Then it stops the schema watch and closes its connections.
  • The host firewall unit ends its watch of the table, and keeps the table.
  • The postgres unit asks for a fast shutdown. After 20 s, it asks for an immediate shutdown, and 5 s later it kills Postgres. With an external Postgres, it does nothing.

Only the units of the roles of the server run, so the sum of their timeouts depends on the roles. The unit hopboxd.service gives hopboxd 105 s to stop (TimeoutStopSec=105s, Server layout).

Roles Sum of the stop timeouts
control 83.1 s
control, dns 89.1 s
control, edge 93.1 s
control, dns, edge 94.1 s
control, node 98.1 s
control, node, dns 99.1 s
control, node, edge 103.1 s
control, node, dns, edge 104.1 s
dns 12.1 s
edge 16.1 s

Leader jobs

Section titled “Leader jobs”

The leader of the control role runs these jobs. In maintenance mode, the leader pauses every job, and keeps its lease (the API server). It logs maintenance mode paused the leader jobs at level info, with component=leader. A fence of the process also pauses every job (Run). If the fence lasts longer than one lease TTL (15 s), the leader gives up its lease, so another control process can lead. It logs this process stays fenced, so it gives up the leader lease to a process that can run the leader jobs. While it is fenced, the process does not try for the leader lock. When maintenance mode ends, the jobs start again as at the start of a term, with the sweep first and 20 s without a check of silent servers. The sweep runs once at the start of each term of the leader, and then every 10 minutes. The check of silent servers runs every 5 s. The auto-delete of idle machines and the return of SSH host keys run every minute. The check of silent servers skips the first 20 s of each term. In that time, the servers can dial again after a stop of the control role, before the leader marks any of them.

enroll

Section titled “enroll”

enroll makes this server a part of an install (Enrollment and the install PKI). It takes these steps:

  1. It reads the bootstrap config. The config must list a role that enrolls: every role but control. Today that is node, dns, edge, or more than one.
  2. It checks the form of the token.
  3. If the config lists node, it runs the preflight check and prints each result to standard error. A failed check of severity fail stops the enrollment, before any call. A failed check of severity warn only prints.
  4. It reads the hardware of the server: the CPU model, the CPU threads, the RAM, and the whole disks (Enrollment and the install PKI).
  5. It makes its own ECDSA P-256 key and a certificate request. The private key never leaves the server.
  6. It dials the first URL of channel.control_urls. The TLS handshake checks that the control listener has a certificate of the CA whose hash the token holds, before the token leaves the server. Only if a dial fails does it go on to the next URL, in the order of the list. The token works once, so a call that reached a control server is never sent again.
  7. It calls EnrollmentService.Enroll with the token, the request, the host name, the roles, and the hardware. The roles are the roles of the config without control.
  8. It checks the answer and writes the identity to <data_dir>/server.

The whole command has 60 s. A running hopboxd run with a role other than control finds the new identity within 2 s and opens the control channel.

install

Section titled “install”

install installs the release of the hopboxd that runs it. That release is the dir of the binary, with its manifest.json (Release bundle). For a first install, run the hopboxd of an unpacked bundle. After that, sudo hopboxd install runs the current release. install must run as root on Linux. The Terraform provider runs it on each new server. Install hopbox on a Debian 13 server by hand runs it by hand.

An install is idempotent: a second run with the same flags changes nothing and does not restart hopboxd. A run from a new release is the last step of an upgrade. Server layout lists every path, user, unit, and setting that it makes.

It takes these steps, in order:

  1. It checks the flags. It takes the lock /opt/hopbox/.lock, or the lock that an upgrade passes to it. If another install or upgrade holds the lock, the install stops. It checks the release dir against its manifest.
  2. If the bootstrap config /etc/hopbox/hopboxd.toml exists, it reads the file with the owner and mode checks of hopboxd run (the bootstrap config of hopboxd). Then it applies the flags. With --internal-listen on a server with a role that enrolls, the URL of the new listener takes the place of each loopback URL of channel.control_urls (the internal listener).
  3. With the control role and no Postgres cluster yet, the install makes the control store of this server, so it needs --domain. With postgres.url, the install connects to the external Postgres instead. If its database has no table schema_migrations, the install counts as the first one, and it needs --domain. An external Postgres that the install cannot reach, for example because of a wrong CA, stops the install here (the bundled Postgres).
  4. With the node role, it checks that data_dir is on XFS with reflinks. The DNS role needs no XFS.
  5. It checks that /usr/local/bin/hopboxd is a symlink or does not exist.
  6. It makes the users: hopbox-pg for the control role without postgres.url, and hopbox-jail with the IDs of the jailer for the node role. It refuses IDs of the jailer that another entry of /etc/subuid, /etc/subgid, /etc/passwd, or /etc/group uses (Server layout).
  7. It makes the dirs of the roles: <data_dir>/server for a role that enrolls, and the dirs of the machines for the node role. It refuses a dir that is a symlink or that another user owns, and it sets the mode of each dir (Server layout).
  8. With the node role, it runs the preflight check and prints each result to standard error. A failed check of severity fail stops the install.
  9. If /opt/hopbox/releases/<version> does not exist, it copies the release there, and checks that the copy has the manifest of the source.
  10. With the control role, it checks that the Postgres of the release has the major version of the cluster in PG_VERSION (the bundled Postgres). With postgres.url, it skips that check. It also makes the schema check of upgrade with the migrations that this hopboxd knows, on the external Postgres when the config names one. So a hopboxd install of an older release dir, run by hand, cannot switch into a schema that does not run with it.
  11. With the node role, it puts the default image of the release into the image cache. It removes the disk of the image from the release dir. If the cache has a dir of that image without artifact.json, it adds the file of the release. A node that downloads the disk of an image leaves such a dir (the Firecracker driver).
  12. With the control role, it does three things. If the keyring has no key, it makes the first key-encryption key. On the install of step 3, it writes the hash of --bootstrap-admin-key-hash to a file. A later run ignores the flag and logs a warning. If no cluster exists and the config has no postgres.url, it runs initdb.
  13. With the node role, it reserves the SSH ports 10000 to 30000.
  14. If the release, the config, or a unit is about to change, it writes the marker /opt/hopbox/.restart-pending. If the bootstrap config changed, it then writes the file.
  15. It points /opt/hopbox/previous to the release that ran before, and then /opt/hopbox/current to the release. In this order, a crash between the two renames never loses the release of a rollback. It points /usr/local/bin/hopboxd to /opt/hopbox/current/hopboxd.
  16. It writes each unit that changed. If a unit changed, or the marker was there before this run, it runs systemctl daemon-reload. Then it runs systemctl enable hopboxd.service.
  17. If the release, the config, or a unit changed, or the marker was there before this run, it runs systemctl restart hopboxd.service. Otherwise it runs systemctl start hopboxd.service. If hopboxd runs, that start does nothing. Both wait until hopboxd is ready. After a good start, it removes the marker.
  18. It removes the releases other than the current and the previous one.
  19. With the control role, it reads the domain of the install through the admin socket. If --domain names another domain, it sets it. Without --domain, an install without a domain fails.
  20. If the server has a role other than control and no identity yet, it enrolls with the enrollment token, as enroll does.
  21. With --peer-address, it reads the server of the identity through the admin socket. If the server has another peer address or none, it sets the address with SetServerPeerAddress (the admin API).

Steps 1 to 13 make every check that can refuse. They change nothing that a running hopboxd reads: the config, the current release, and the units stay the same until step 14. So a refused install leaves the running hopboxd as it was. If a run stops after step 14 and before the restart, the marker stays. The next run then restarts hopboxd, also without another change. The install never removes data.

upgrade

Section titled “upgrade”

upgrade moves this server to the release of a bundle file. upgrade --rollback moves it back to the previous release. It must run as root on Linux, on a server with an install. If the bundle of a server changes, the Terraform provider runs it.

With --bundle, it takes these steps:

  1. It reads the bootstrap config and /opt/hopbox/current, so it fails on a server without an install.
  2. It takes the lock /opt/hopbox/.lock. It holds the lock until the install of step 6 ends. It passes the lock to that install as the file descriptor 3, which the environment variable HOPBOX_INSTALL_LOCK_FD names. So no other run can prune the new release in between.
  3. It checks the sha256 of the bundle file against --sha256. The manifest proves only that the bundle is whole. The sha256 from a trusted place, such as the .sha256 file of the build, proves that it is the bundle that you built.
  4. It unpacks the bundle to a temp dir /opt/hopbox/releases/.incoming-<random>, and checks the release against its manifest and its owner (Release bundle). It renames the temp dir to /opt/hopbox/releases/<version>. If that dir exists with the same manifest, it keeps it. If it exists with another manifest, the upgrade stops.
  5. With the control role, it reads the newest schema migration of the control store and the oldest schema version that runs with it. It compares that version with schema_version of the new release (Release bundle). If the schema_version of the release is lower than that oldest schema version, the upgrade stops (the bundled Postgres). It reads through the socket of the running Postgres. If no Postgres answers, it starts the Postgres of the current release for the read, and stops it again. If that Postgres does not start, it uses the Postgres of the new release. After the guard of the install, both have the same major version. Each read has 30 s, and each start has the 60 s of pgsup on top.
  6. It runs /opt/hopbox/releases/<version>/hopboxd install --roles=<roles>, with the roles of the config. The install of the new release does the rest: the Postgres guard, the image cache, the switch of current and previous, the units, and the restart.

With --rollback, it takes the same lock and checks the release of /opt/hopbox/previous and its owner. It makes the schema check of step 5, and runs the hopboxd install --roles=<roles> of that release. The install then points current to the previous release, and previous to the release that ran.

The old hopboxd only unpacks and checks. The new release runs its own install. So each release brings the steps that it needs. The CLI of install is the contract between two releases. Until the install of step 6 switches the release, the running hopboxd keeps running, and nothing that it reads changes.

The microVMs of the machines run in their own units in hopbox-machines.slice, not in hopboxd.service. So they keep running through the restart of an upgrade or a rollback (Server layout).

Flag Type Default Description
--bundle path none The bundle file, such as hopbox-v0.2.0-linux-amd64.tar.gz.

A rollback runs an older hopboxd on the control store of the newer one. A schema migration of the newer release can allow the older release, with its line -- oldest_schema_version. Then the rollback goes on, and the older hopboxd runs on the newer store (the bundled Postgres). A migration that does not allow it makes the older hopboxd refuse the database at its start, with store: the database has a migration that does not run with this hopboxd. So the schema check of step 5 refuses such a rollback before the switch, and the current release keeps running. Upgrade to a release that knows the migrations instead. v0.1.0 refuses every store with a migration that it does not know, so no rollback from a later release to v0.1.0 passes the check.

After a rollback to a release without stop-guest, some units run the older hopboxd at their stop: the units of the machines that the later release booted. That hopboxd exits with status 80, unexpected argument stop-guest. The journal of the unit then shows the usage text of the older hopboxd at each stop. You can ignore it. The unit ignores the status, so a shutdown or a reboot in the guest still counts as a shutdown, not as a crash.   • If forward-guard-ipv6 exists, run sudo sysctl -w net.ipv6.conf.all.forwarding=0, then remove the file.
  • On a server without the role node, if forward-guard exists, run sudo sysctl -w net.ipv4.ip_forward=0, then remove the file.

Run the second line only on a server without the role node. An edge server that ran a build of main with the egress from before forward-guard-ipv6 has no such file. After the rollback of such a server, run sudo sysctl -w net.ipv6.conf.all.forwarding=0 by hand, unless another tool on the server needs IPv6 forwarding.

Section titled “admin”

admin calls the admin API of the hopboxd that runs on this server, through its admin socket (the admin API). The socket accepts only root and the user that runs hopboxd. On a server, hopboxd runs as root, so run admin with sudo. The audit log records each call, with the actor local_root (Control store tables).

Flag Type Default Description

--socket path none The admin socket. It overrides --config, and admin then reads no config.

  1. The path of --socket.

The default image of the release

Section titled “The default image of the release”

Each release ships its own default image, because the image holds hopbox-guest of the same commit (Release bundle). So at each start, the control role registers the image of control.release_image, by default /opt/hopbox/current/image/artifact.json (the bootstrap config of hopboxd). New machines of the name default then take the guest agent of the release. Machines that exist keep their image.

The rules are simple:

  • The start registers the image by its digest. If the install has the digest already, the start changes nothing and writes no audit entry. So a restart of the same release changes nothing. When two control servers start at once, one of them adds the image, and the other one finds it.
  • A new image gets the audit entry image.register with the actor local_root and the detail already false, as admin image register as root does.
  • The start registers only the image of the release, under its own name. It never changes or removes an image of another name.
  • New machines take the image of a name that the install registered last. So an image that an operator registers after the start wins, also an older build. It wins until a release brings an image that the install does not have yet. To keep an image of your own across releases, give it another name, and create machines with that image name.
  • A rollback does not bring its image back. hopboxd upgrade --rollback starts the older release, whose image the install has already. So new machines keep the image of the newer release, with its guest agent. A register of the older image changes nothing either, because the install has its digest. Each guest agent takes the versions of the guest link that its node speaks (Guest link).
  • In phase 2, an install can have control servers on two releases, for example during an upgrade. At its start, the control role skips the register when the install has an image of the same name that a newer release registered. It compares the releases as semver versions. So a control server on the older release never makes its image the newest. The start logs the install has the default image of a newer release, so the control role registers none, and changes nothing. The control role records its release on the images that it registers. An operator image has no release, and so has an image that a release before migration 0045 registered. Neither makes the control role skip. A version that is not semver, such as a build for development, skips nothing. The start does not compare the build times, because a reproducible build of the image has a fixed build time. The check and the register run in one transaction under the lock LockKeyReleaseImages, so two control servers of two releases that start at once never both register (the bundled Postgres). After a full rollback of every control server to the older release, the image of the newer release stays the newest of its name, because the older release skips its own. Register the older image by hand with admin image register if you want it back.

Only a server with the control role registers the image. The nodes still need the disk of the image: the install of a release puts it into the image cache of a node (the Firecracker driver).

Their URLs and the SSH front door answer no client until maintenance mode ends, because the edge servers lose their channels too. An open SSH session to a machine ends in the window, because its edge server cannot check its access again.

The command succeeds once the writes, the control channels, and the leader jobs that ran have ended while maintenance mode stayed on. This holds for every live control process of the install, not only for the one that takes the call. Each other live control process must report maintenance mode on and drained in a renewal of its row after the turn, and the call polls the rows every 250 ms. A control process that stops renewing its row counts as ended. The wait compares versions, not times. Each control process reports in its row the version of install_config at which it read maintenance mode (maintenance_version), and the call waits until every other live process reports maintenance mode on, drained, and a maintenance_version at least the version that the turn wrote. A control process of a release before migration 0045 records no row, so the command does not see it, and neither does the migration guard, the KEK promote, the decommission check, or the rolling upgrade order. Upgrade every control server before you rely on these checks. So after a success, no change of the API or of a server reaches the control store. hopboxd admin db export runs it first. On an install that is in maintenance mode already, it changes nothing, and waits the same way. Since every admin read is refused in maintenance mode, a second admin maintenance on is the harmless way to print the settings, maintenance among them, in that window.

It prints the settings of the install as admin config get does, with maintenance set to true.

Section titled “admin db export”

Copies the control store of this server from the bundled Postgres to an external Postgres, such as managed PostgreSQL. An install with one server uses it once, to move to the external Postgres that several control servers share. Run the control store on an external Postgres has the whole move. The code is in internal/dbexport.

Flag Type Default Description

Run it as the user of hopboxd, root on a server. It reads the bootstrap config of --config for the paths. The server must have the control role, and no postgres.url. The export takes these steps:

  1. It connects to the bundled Postgres over its socket, and to the target with TLS and sslmode=verify-full, with the CA file and the password file. It checks the files as hopboxd run checks them.
  2. It checks the target. The target must run the major version of the bundled Postgres or a newer one (plan question Q68), so Postgres 18 or later. Its user must be able to create tables in the schema public. Its database must hold no table, view, or sequence outside the catalogs, except those of an extension. A refusal of steps 1 and 2 changes nothing.
  3. It turns maintenance mode on through the admin socket, and waits until the writes and the control channels of the install ended (admin maintenance on).
  4. It opens a read-only transaction on the bundled Postgres, and exports its snapshot. In that snapshot, it checks that the flag of maintenance mode is on, reads the last migration, and counts the rows of each table of the schema public. A store out of maintenance mode, for example after admin maintenance off during the export, is refused, because it can still change. Then pg_dump dumps the bundled Postgres in that snapshot, in the custom format, to <data_dir>/export/hopbox-<time>.dump. The export makes the dir <data_dir>/export with mode 0700, and sets that mode also on a dir that exists. It makes the dump file first, empty, with mode 0600, and pg_dump writes into it and keeps that mode, whatever the umask. The dump holds the sealed secrets of the install, so no other user may read it. So the counts describe the dump exactly.
  5. pg_restore restores the dump into the target in one transaction, and stops at the first error. Every object gets the user of --to as its owner, and keeps no grant of the bundled Postgres. A failed restore leaves the target empty.
  6. It checks the copy: the same last migration in schema_migrations, the same tables, and the same row count in each table.
  7. It deletes the rows of control_processes on the copy, and clears servers.channel_process there. They name the processes of the source, which never run on the copy, and a row that still looks live would hold back the checks of the new control servers (Control store tables).
  8. It removes the dump, prints the config lines, and tells the operator to stop hopboxd on this server.

stop-guest

Section titled “stop-guest”

The unit of each machine runs stop-guest as its ExecStop (the Firecracker driver). So a reboot of the server, or a systemctl stop of the unit, shuts the guest down cleanly. You do not run it yourself. The help of hopboxd does not list it.

Flag Type Default Description
--api-socket path none, required The API socket of the Firecracker of the machine.
--timeout duration 30s How long to wait for the end of Firecracker.

stop-guest reads the process ID of Firecracker from the env var MAINPID, which systemd sets for ExecStop. Without MAINPID, Firecracker ended already, and stop-guest exits with status 0 at once. Otherwise it sends SendCtrlAltDel through the API socket, and waits for the end of the process. If Firecracker ends within the timeout, it exits with status 0. If Firecracker does not end in time, it exits with status 1. If the call fails, and Firecracker does not end within 2 s, it exits with status 1 too. The unit ignores the status, and systemd then ends Firecracker with SIGTERM. It logs to the journal of the unit, at level info. Without MAINPID, it logs Firecracker ended before the stop, so the guest needs no shutdown. Otherwise it logs asking the guest to shut down, with pid and timeout, and after the end of Firecracker the guest shut down, with duration.

The flags of stop-guest stay the same in each release. A unit keeps the command line of the release that booted the machine, and runs the hopboxd of the current release.

The DNS role writes its records with component=dns (the DNS role). The edge role writes its records with component=edge (the edge role).

Status Meaning
