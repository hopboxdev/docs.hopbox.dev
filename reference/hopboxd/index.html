hopboxd

hopboxd is the server binary of hopbox. It runs on every server of an install.

Usage

Section titled “Usage”

When you run hopboxd without a command, it prints its help and an error, and exits with status 80.

Global flags

Section titled “Global flags”

A global flag goes before or after the command.

Flag Type Default Description
--log-level level info The lowest level of the log records that hopboxd writes. The values are debug, info, warn, and error. Case does not matter. A value can also carry an offset, for example info+2, as in Go’s log/slog.
-h, --help bool false Prints the help of hopboxd, or of the command that it follows, and exits.

run

Section titled “run”

run reads the bootstrap config, starts the roles that the config lists, and runs until it gets SIGINT or SIGTERM. Then it stops the roles and exits with status 0. hopboxd-config.md lists the keys of the bootstrap config.

Flag Type Default Description
--config path /etc/hopbox/hopboxd.toml The bootstrap config file.

First, run starts the metrics listener. Then it starts the units of the control role, the DNS role, the edge role, and the node role, in this order. Then it starts the unit of the control channel. A role that the config does not list has no units. Each unit starts after the unit before it is ready.

Order Unit What it does Stop timeout
0 metrics Serves the Prometheus metrics on metrics.listen (metrics.md). 5 s
1 postgres Starts the bundled Postgres (postgres.md). The cluster is in <data_dir>/pg, and the socket is in <run_dir>/pg. 30 s
2 store Opens the connection pool of the control store and runs the migrations (postgres.md). Then it imports the bootstrap admin API key from the file that hopboxd install can leave (server-layout.md). Then it registers the default image of the release (The default image of the release). 5 s
3 events Reads the change events of the control store from the head (control-store.md). It feeds them to the watches and the lifecycle waits of the machine API in this process (machine-api.md). So they see each change, also one of another control process or of a node. If the reader stops by itself, hopboxd stops. 2 s
4 leader election Takes part in the leader election (control-store.md). The leader runs the leader jobs. 15 s
5 api Serves the API on control.api_listen (api.md). 10 s
6 internal listener Serves the cluster API over TLS on control.internal_listen: enrollment, the control channels of the servers, and EdgeService. It also serves the API and the console to the edge servers, for the clients that they forward (internal-listener.md). 5 s
7 admin socket Serves the admin API on <run_dir>/admin.sock (admin-api.md). 10 s
8 dns The DNS role (dns.md). At its start, it opens a UDP socket and a TCP socket at each address of dns.listen. So a port that another program holds fails the start. It answers SERVFAIL to each query until the first zones arrive over the control channel. 1 s
9 edge The edge role (edge.md). At its start, it opens the HTTPS listener at edge.https_listen and the HTTP listener at edge.http_listen. So a port that another program holds fails the start. It refuses each TLS handshake until the first certificate arrives over the control channel. At its stop, it closes the listeners, gives the open requests 2 s, and then ends the rest, also the streams and the WebSockets. 5 s
10 machines The node role. It first sets up the node network: it replaces the nftables table inet hopbox_node with one that holds the tap devices of the machines that run, and turns on IPv4 forwarding (node-network.md). Until its stop, it watches the table, and installs it again after a flush. It adds the guest kernel of vmm.kernel to the kernel cache. It starts the executors of the machines with the Firecracker driver (executor.md, firecracker-driver.md). It also starts the store of the machine logs (machine-logs.md). At its start, the executors attach to the microVMs that run. At its stop, the executors end their actions at once. Every microVM keeps running, because it runs in a systemd unit of its own. The unit of each machine runs stop-guest at its stop, and is ordered before hopboxd.service. 10 s
11 channel Keeps the control channel of this server to channel.control_url, over mutual TLS. If the control role runs in the same hopboxd, the channel still goes over TLS (control-channel.md). It hands the zones that the control role sends to the dns unit. It hands the certificate, the routes, and the access changes to the edge unit. It hands the specs of the machines to the executors of the machines unit, and the machine streams to its handlers. Its start returns at once. Before the enrollment of the server, it waits for the identity in <data_dir>/server. So run can start before enroll. 5 s

Units 1 to 7 belong to the control role and unit 8 to the DNS role. Unit 9 belongs to the edge role and unit 10 to the node role. Unit 11 runs on a server that enrolls: one with a role other than control. Unit 12, systemd notify, runs for every role:

Order Unit What it does Stop timeout
12 systemd notify Sends READY=1 to the socket of NOTIFY_SOCKET at its start, and STOPPING=1 at its stop (sd_notify(3)). Without NOTIFY_SOCKET, it does nothing. It starts last. So the unit hopboxd.service of Type=notify becomes active only after every other unit is ready (server-layout.md). If it cannot send, the start fails. 1 s

On a server with only the node role, run starts the metrics listener, the machines unit, the channel unit, and the systemd notify unit. On a server with only the DNS role, it starts the dns unit in place of the machines unit. On a server with the edge role, it starts the edge unit before the channel unit. So what the channel gets for these roles always has a server.

run stops the units in the reverse order. First it stops systemd notify, then channel, machines, edge, and dns. Then it stops the units of the control role, from the admin socket to Postgres, and last the metrics listener. So no unit stops before a unit that needs it. A server can have the control role and a role that enrolls. Then the control role sees the channel of its own server close before its listeners stop. Each stop has the timeout in the table:

  • The channel unit closes the control channel and waits for its loop to end.
  • The machines unit ends the actions of the executors, closes the guest links, and closes the files of the machine logs. It stops no microVM, and keeps the node network.
  • The edge unit closes its listeners and gives the open requests 2 s. Then it cancels the rest: the streams, the WebSockets, and the long calls. At the timeout, it closes every connection (edge.md).
  • The dns unit closes its sockets and waits for the queries in flight.
  • The api, internal listener, and admin socket units stop taking new connections and wait for the running unary calls. They end every open stream at once, because a stream has no natural end. They cancel the stream and end every read of its request body. So a stream that waits for the client, such as a reflection stream, ends too. A unary call that still reads its request body gets 2 s more. So a stalled upload cannot hold the stop. At the timeout, they close the rest (api.md).
  • The leader election unit ends the term of the leader and releases the leader lease.
  • The events unit stops its reader of change events and closes its connection.
  • The postgres unit asks for a fast shutdown. After 20 s, it asks for an immediate shutdown, and 5 s later it kills Postgres.

Only the units of the roles of the server run, so the sum of their timeouts depends on the roles. The unit hopboxd.service gives hopboxd 105 s to stop (TimeoutStopSec=105s, server-layout.md).

Roles Sum of the stop timeouts
control 83 s
control, dns 89 s
control, edge 93 s
control, dns, edge 94 s
control, node 98 s
control, node, dns 99 s
control, node, edge 103 s
control, node, dns, edge 104 s
dns 12 s
edge 16 s
dns, edge 17 s
node 21 s
node, dns 22 s
node, edge 26 s
node, dns, edge 27 s

Each sum is under the 105 s of hopboxd.service.

If the install has no key-encryption key yet, the internal listener starts all the same. It then has no certificate, and logs the internal listener has no certificate yet. Until root makes the first key with admin kek rotate, it fails each TLS handshake (internal-listener.md).

If run gets SIGINT or SIGTERM while a unit starts, it stops the units that started, in the reverse order, and exits with status 0.

If a unit fails to start, run stops the units that started, in the reverse order, and exits with status 1. If a unit fails while it runs, for example when the API listener stops, run stops every unit and exits with status 1. A supervisor such as systemd then restarts hopboxd. A crash of Postgres alone does not stop hopboxd, because the supervisor of Postgres restarts it (postgres.md).

Leader jobs

Section titled “Leader jobs”

The leader of the control role runs these jobs. The sweep runs once at the start of each term of the leader, and then every 10 minutes. The check of silent servers runs every 5 s. The auto-delete of idle machines and the return of SSH host keys run every minute. The check of silent servers skips the first 20 s of each term. In that time, the servers can dial again after a stop of the control role, before the leader marks any of them.

Job Every What it does
Sweep of idempotency keys 10 min Deletes the expired idempotency keys (control-store.md).
Sweep of sign-ins 10 min Deletes the ended sessions, and the magic links, login links, and OAuth flows that are older than 24 hours (sessions.md). Deletes the expired CLI tokens, the ended CLI sign-ins, and the device sign-ins and failed device approvals that are older than 24 hours. Deletes the API keys and admin API keys that expired more than 30 days ago (credentials.md).
Sweep of the fleet 10 min Deletes the enrollment tokens that expired more than 1 day ago, and the server certificates that expired more than 1 day ago. It keeps the newest certificate of each server (control-store.md).
Check of silent servers 5 s Marks unresponsive each ready or cordoned server whose last heartbeat is 20 s old or older: 4 missed heartbeats. The write checks the leader lease, so a leader that lost its lease writes nothing. Each server that it marks gets an audit entry server.mark_unresponsive with the actor system (control-store.md). The next heartbeat of the server makes it ready again, or cordoned (control-channel.md).
Sweep of invitations 10 min Deletes the invitations to orgs that ended more than 24 hours ago, by a use, a revoke, or the expiry. It also deletes the records of their rate limits that are older than 24 hours (org-api.md).
Sweep of machines 10 min Frees the machine names and the SSH ports whose reservation of 7 days ended (domain-rules.md). Drops the row of each machine that its executor deleted, 7 days after its delete request. Then deletes the machine lease of each machine whose row is gone (control-store.md). Each of these four steps runs in a transaction of its own that checks the leader lease. So a leader that lost its lease frees nothing more.
Prune of change events 10 min Deletes the change events that are older than 24 hours. Every reader of the events starts from the head, so an older event serves nobody (control-store.md).
Certificate of the install when due Gets the wildcard certificate of the install from the ACME CA, and renews it after two thirds of its lifetime. It starts at the start of each term, and plans again after each change of an input of the ACME job (acme.md). Every write checks the leader lease.
Auto-delete of idle machines 1 min Deletes each machine whose last recorded use is older than its auto-delete timeout plus 1 minute. A use is recorded at most once a minute (machine-api.md). It takes at most 100 machines per run, the oldest last use first. The next run takes the rest. It skips the machines of a suspended org. Each machine goes in a transaction of its own, which checks the leader lease, so a leader that lost its lease deletes nothing. The delete reserves the name and the SSH port, as DeleteMachine does. Each delete gets an audit entry machine.delete with the actor system and the detail reason (auto-delete), and the log record deleted an idle machine. A machine whose delete fails gets the log record deleting an idle machine failed, and the job goes on with the next one. Only a lost leader lease stops the run.
Return of SSH host keys 1 min Gives each SSH host key that a route record claims, and that no record lists, to the oldest record that claims it. A report that lets a key go gives it at once, but it skips a record that another transaction locks, and a hopboxd of v0.1.0 gives no key. It takes at most 100 keys per run, and each key goes in a transaction of its own. The write needs no leader lease, because a report makes the same write. Each key gets the log record a machine got an SSH host key that no other machine holds at level info, with machine (control-store.md).

Example

Section titled “Example”

guide/run-hopboxd.md runs the control role on a laptop. guide/enroll-node.md enrolls the node role of a server with the control role of the same server. guide/dns-role.md runs the DNS role.

enroll

Section titled “enroll”

enroll makes this server a part of an install (enrollment.md). It takes these steps:

  1. It reads the bootstrap config. The config must list a role that enrolls: every role but control. Today that is node, dns, edge, or more than one.
  2. It checks the form of the token.
  3. If the config lists node, it runs the preflight check and prints each result to standard error. A failed check of severity fail stops the enrollment, before any call. A failed check of severity warn only prints.
  4. It makes its own ECDSA P-256 key and a certificate request. The private key never leaves the server.
  5. It dials channel.control_url. The TLS handshake checks that the control listener has a certificate of the CA whose hash the token holds, before the token leaves the server.
  6. It calls EnrollmentService.Enroll with the token, the request, the host name, and the roles. The roles are the roles of the config without control.
  7. It checks the answer and writes the identity to <data_dir>/server.

The whole command has 60 s. A running hopboxd run with a role other than control finds the new identity within 2 s and opens the control channel.

Flag Type Default Description
--token string none, required The enrollment token, hbxe_<id>_<secret>_<cahash>, from admin enrollment-token create. The environment variable HOPBOX_ENROLLMENT_TOKEN gives it too, so the token stays out of the process list. The flag wins over the variable.
--config path /etc/hopbox/hopboxd.toml The bootstrap config file.
--json bool false Prints one JSON object with the identity of the server instead of its ID.

On success, enroll prints the server ID to standard output, and the line hopboxd: enrolled as the server <id>. hopboxd run connects it to the control plane. to standard error. With --json, it prints one object with these keys:

Key Description
server_id The ID of the new server.
roles The roles in its certificate, for example ["node"] or ["node","dns"].
ca_hash The SHA-256, in hex, of the certificate of the install CA.
certificate_expire_time The end of the server certificate, 30 days after the enrollment, in UTC.
dir The dir of the identity, <data_dir>/server.

Example:

A server that is enrolled already, and whose config lists a role beyond those of its identity, adds the new roles in place (enrollment.md). The token must allow each new role. The server keeps its ID. enroll then prints hopboxd: the server <id> has the roles <roles> now. Restart hopboxd to use them: systemctl restart hopboxd. hopboxd install restarts it on its own.

Error Cause
the config <path> lists no role that enrolls. Add "node", "dns", "edge", or more than one to roles The config lists only control.
the token does not have the form hbxe_<id>_<secret>_<cahash>. Make one with hopboxd admin enrollment-token create The token is not an enrollment token.
the preflight check failed, so this server cannot run machines: and one line for each failed check A check of severity fail failed (preflight.md). On a Mac, every check fails, as it must.
this server is enrolled already as the server <id> with the roles <roles>. To enroll it again, remove <dir> first <data_dir>/server holds an identity with every role of the config.
enroll at <url>: invalid_argument: the server has the role <role>, and a role cannot go... The config lists fewer roles than the identity. A role never goes from a server.
pki: the peer is not the control plane of this install: ... inside enroll at <url>: ... The control listener has no certificate of the CA that the token names. The token never left the server.
enroll at <url>: unauthenticated: the enrollment token is not valid... The control role refused the token: it is unknown, it expired, it was used, or it was made for another CA (enrollment.md).
enroll at <url>: unavailable: ... No control listener answers at channel.control_url, or its TLS handshake failed, for example before the install has a key-encryption key.

install

Section titled “install”

install installs the release of the hopboxd that runs it. That release is the dir of the binary, with its manifest.json (release-bundle.md). For a first install, run the hopboxd of an unpacked bundle. After that, sudo hopboxd install runs the current release. install must run as root on Linux. The Terraform provider runs it on each new server. guide/install-debian.md runs it by hand.

An install is idempotent: a second run with the same flags changes nothing and does not restart hopboxd. A run from a new release is the last step of an upgrade. server-layout.md lists every path, user, unit, and setting that it makes.

It takes these steps, in order:

  1. It checks the flags. It takes the lock /opt/hopbox/.lock, or the lock that an upgrade passes to it. If another install or upgrade holds the lock, the install stops. It checks the release dir against its manifest.
  2. If the bootstrap config /etc/hopbox/hopboxd.toml exists, it reads the file with the owner and mode checks of hopboxd run (hopboxd-config.md). Then it applies the flags.
  3. With the control role and no Postgres cluster yet, the install makes the control store of this server, so it needs --domain.
  4. With the node role, it checks that data_dir is on XFS with reflinks. The DNS role needs no XFS.
  5. It checks that /usr/local/bin/hopboxd is a symlink or does not exist.
  6. It makes the users: hopbox-pg for the control role, and hopbox-jail with the IDs of the jailer for the node role. It refuses IDs of the jailer that another entry of /etc/subuid, /etc/subgid, /etc/passwd, or /etc/group uses (server-layout.md).
  7. It makes the dirs of the roles: <data_dir>/server for a role that enrolls, and the dirs of the machines for the node role. It refuses a dir that is a symlink or that another user owns, and it sets the mode of each dir (server-layout.md).
  8. With the node role, it runs the preflight check and prints each result to standard error. A failed check of severity fail stops the install.
  9. If /opt/hopbox/releases/<version> does not exist, it copies the release there, and checks that the copy has the manifest of the source.
  10. With the control role, it checks that the Postgres of the release has the major version of the cluster in PG_VERSION (postgres.md). It also makes the schema check of upgrade with the migrations that this hopboxd knows. So a hopboxd install of an older release dir, run by hand, cannot switch into a schema that it does not know.
  11. With the node role, it puts the default image of the release into the image cache. It removes the disk of the image from the release dir. If the cache has a dir of that image without artifact.json, it adds the file of the release. A node that downloads the disk of an image leaves such a dir (firecracker-driver.md).
  12. With the control role, it does three things. If the keyring has no key, it makes the first key-encryption key. On the install of step 3, it writes the hash of --bootstrap-admin-key-hash to a file. A later run ignores the flag and logs a warning. If no cluster exists, it runs initdb.
  13. With the node role, it reserves the SSH ports 10000 to 30000.
  14. If the release, the config, or a unit is about to change, it writes the marker /opt/hopbox/.restart-pending. If the bootstrap config changed, it then writes the file.
  15. It points /opt/hopbox/previous to the release that ran before, and then /opt/hopbox/current to the release. In this order, a crash between the two renames never loses the release of a rollback. It points /usr/local/bin/hopboxd to /opt/hopbox/current/hopboxd.
  16. It writes each unit that changed. If a unit changed, or the marker was there before this run, it runs systemctl daemon-reload. Then it runs systemctl enable hopboxd.service.
  17. If the release, the config, or a unit changed, or the marker was there before this run, it runs systemctl restart hopboxd.service. Otherwise it runs systemctl start hopboxd.service. If hopboxd runs, that start does nothing. Both wait until hopboxd is ready. After a good start, it removes the marker.
  18. It removes the releases other than the current and the previous one.
  19. With the control role, it reads the domain of the install through the admin socket. If --domain names another domain, it sets it. Without --domain, an install without a domain fails.
  20. If the server has a role other than control and no identity yet, it enrolls with the enrollment token, as enroll does.

Steps 1 to 13 make every check that can refuse. They change nothing that a running hopboxd reads: the config, the current release, and the units stay the same until step 14. So a refused install leaves the running hopboxd as it was. If a run stops after step 14 and before the restart, the marker stays. The next run then restarts hopboxd, also without another change. The install never removes data.

upgrade

Section titled “upgrade”

upgrade moves this server to the release of a bundle file. upgrade --rollback moves it back to the previous release. It must run as root on Linux, on a server with an install. If the bundle of a server changes, the Terraform provider runs it.

With --bundle, it takes these steps:

  1. It reads the bootstrap config and /opt/hopbox/current, so it fails on a server without an install.
  2. It takes the lock /opt/hopbox/.lock. It holds the lock until the install of step 6 ends. It passes the lock to that install as the file descriptor 3, which the environment variable HOPBOX_INSTALL_LOCK_FD names. So no other run can prune the new release in between.
  3. It checks the sha256 of the bundle file against --sha256. The manifest proves only that the bundle is whole. The sha256 from a trusted place, such as the .sha256 file of the build, proves that it is the bundle that you built.
  4. It unpacks the bundle to a temp dir /opt/hopbox/releases/.incoming-<random>, and checks the release against its manifest and its owner (release-bundle.md). It renames the temp dir to /opt/hopbox/releases/<version>. If that dir exists with the same manifest, it keeps it. If it exists with another manifest, the upgrade stops.
  5. With the control role, it reads the number of the last schema migration of the control store. It compares the number with schema_version of the new release (release-bundle.md). If the store has a migration that the release does not know, the upgrade stops. It reads through the socket of the running Postgres. If no Postgres answers, it starts the Postgres of the current release for the read, and stops it again. If that Postgres does not start, it uses the Postgres of the new release. After the guard of the install, both have the same major version. Each read has 30 s, and each start has the 60 s of pgsup on top.
  6. It runs /opt/hopbox/releases/<version>/hopboxd install --roles=<roles>, with the roles of the config. The install of the new release does the rest: the Postgres guard, the image cache, the switch of current and previous, the units, and the restart.

With --rollback, it takes the same lock and checks the release of /opt/hopbox/previous and its owner. It makes the schema check of step 5, and runs the hopboxd install --roles=<roles> of that release. The install then points current to the previous release, and previous to the release that ran.

The old hopboxd only unpacks and checks. The new release runs its own install. So each release brings the steps that it needs. The CLI of install is the contract between two releases. Until the install of step 6 switches the release, the running hopboxd keeps running, and nothing that it reads changes.

The microVMs of the machines run in their own units in hopbox-machines.slice, not in hopboxd.service. So they keep running through the restart of an upgrade or a rollback (server-layout.md).

A rollback runs an older hopboxd on the control store of the newer one. If the newer release applied a schema migration, the older hopboxd refuses the database at its start, with store: the database has migrations that this hopboxd does not know (postgres.md). admin

Section titled “admin”

admin calls the admin API of the hopboxd that runs on this server, through its admin socket (admin-api.md). The socket accepts only root and the user that runs hopboxd. On a server, hopboxd runs as root, so run admin with sudo. The audit log records each call, with the actor local_root (control-store.md).

Flag Type Default Description
--config path /etc/hopbox/hopboxd.toml The bootstrap config. admin calls the socket <run_dir>/admin.sock of this config (hopboxd-config.md). If the config does not load, admin prints hopboxd: warning: <error>. Using the admin socket /run/hopbox/admin.sock to standard error and calls that socket, so a bad config never locks you out. A missing default file gets no warning.
--socket path none The admin socket. It overrides --config, and admin then reads no config.

admin finds the admin socket in this order:

  1. The path of --socket.
  2. <run_dir>/admin.sock of the bootstrap config of --config, or of /etc/hopbox/hopboxd.toml.
  3. If the config does not load, /run/hopbox/admin.sock. Then admin prints a warning with the error of the config. If the default file does not exist, it prints no warning. Thus a broken config never locks the operator out of the socket.

Each admin command waits at most 40 s for its call.

The default image of the release

Section titled “The default image of the release”

Each release ships its own default image, because the image holds hopbox-guest of the same commit (release-bundle.md). So at each start, the control role registers the image of control.release_image, by default /opt/hopbox/current/image/artifact.json (hopboxd-config.md). New machines of the name default then take the guest agent of the release. Machines that exist keep their image.

The rules are simple:

  • The start registers the image by its digest. If the install has the digest already, the start changes nothing and writes no audit entry. So a restart of the same release changes nothing. When two control servers start at once, one of them adds the image, and the other one finds it.
  • A new image gets the audit entry image.register with the actor local_root and the detail already false, as admin image register as root does.
  • The start registers only the image of the release, under its own name. It never changes or removes an image of another name.
  • New machines take the image of a name that the install registered last. So an image that an operator registers after the start wins, also an older build. It wins until a release brings an image that the install does not have yet. To keep an image of your own across releases, give it another name, and create machines with that image name.
  • A rollback does not bring its image back. hopboxd upgrade --rollback starts the older release, whose image the install has already. So new machines keep the image of the newer release, with its guest agent. A register of the older image changes nothing either, because the install has its digest. Each guest agent takes the versions of the guest link that its node speaks (guest-link.md).
  • In phase 2, an install can have control servers on two releases, for example during an upgrade. If the install does not have the image of the older release yet, a control server on that release registers it at its next start. That image then becomes the newest, although it is older. The start does not compare the build times, because a reproducible build of the image has a fixed build time. Upgrade the control servers before you make machines.

Only a server with the control role registers the image. The nodes still need the disk of the image: the install of a release puts it into the image cache of a node (firecracker-driver.md).

stop-guest reads the process ID of Firecracker from the env var MAINPID, which systemd sets for ExecStop. Without MAINPID, Firecracker ended already, and stop-guest exits with status 0 at once. Otherwise it sends SendCtrlAltDel through the API socket, and waits for the end of the process. If Firecracker ends within the timeout, it exits with status 0. If Firecracker does not end in time, it exits with status 1. If the call fails, and Firecracker does not end within 2 s, it exits with status 1 too. The unit ignores the status, and systemd then ends Firecracker with SIGTERM. It logs to the journal of the unit, at level info. Without MAINPID, it logs Firecracker ended before the stop, so the guest needs no shutdown. Otherwise it logs asking the guest to shut down, with pid and timeout, and after the end of Firecracker the guest shut down, with duration.

The flags of stop-guest stay the same in each release. A unit keeps the command line of the release that booted the machine, and runs the hopboxd of the current release.

Exit status

Section titled “Exit status”
Status Meaning
0 The command succeeded. For run, the roles stopped after SIGINT or SIGTERM, and every unit stopped well.
1 The command failed. For run, the bootstrap config is not valid, or a unit failed to start, to run, or to stop. For enroll, the preflight check or the enrollment failed. For preflight, a check of severity fail failed. For install and upgrade, a check refused, a step failed, or hopboxd did not start. For stop-guest, the guest did not shut down in time. hopboxd prints hopboxd: error: <message> to standard error.
80 The command line is not valid, for example an unknown command or flag, or a bad flag value.
