Console

The console is the web app of an install. People use it in a browser to sign in, to manage their machines, and to open a shell in a machine. It is a single-page app in React and TypeScript, and hopboxd holds its build. This page gives its pages, its calls, its headers, its build, and its tests. The code is in web/apps/console and internal/console. Use the console shows how to use it.

The first console holds the parts of phase 1:

  • sign-in
  • the list of machines, with the live state of each one
  • the create, stop, start, and delete actions
  • the switch that makes a URL public
  • the web terminal

It also has the pages that the links of the API open, the account page, and the pages of an org. Phase 2 adds the Admin area for instance admins (Admin area).

Where hopboxd serves it

Section titled “Where hopboxd serves it”

The API listener of the control role serves the console at the domain of the install, next to the API (the API server). Each public handler of the control role holds the console, so the console also answers behind the edge. So the console calls the API from its own origin, and the browser needs no CORS rules.

The console takes every path that no API route takes:

Request Who answers
POST /hopbox.v1.<Service>/<Method> and the other API calls the API
GET /auth/github/start, /auth/github/callback, /auth/google/start, /auth/google/callback the sign-in with GitHub and Google (Sign-in with GitHub and Google)
GET /api/ws/exec the WebSocket endpoint of exec (the machine API)
any other GET or HEAD request whose first path segment has no dot the console
any other request, such as GET /hopbox.v1.NoSuchService/Get or GET /index.html the API, with 404 Not Found, so a Connect or gRPC client reads an unknown procedure

The console needs HTTPS at https://<domain>. The session cookie has the __Host- prefix and the Secure flag, and each call with the cookie must carry the Origin header https://<domain> (Sessions, cookies, and sign-in links). Thus the console works only behind a front that ends TLS for the domain of the install, such as the edge. Over plain HTTP, the pages load, but no sign-in works.

Pages

Section titled “Pages”

A page that needs a session sends a browser without one to /signin?return_to=<path>, and the sign-in then returns to the page.

Path Session What it does Calls
/signin?return_to=<path> no Shows the sign-in methods of the install. A browser with a live session goes on to return_to, or /. With again=1, the page stays for a live session too, with the title “Sign in again” (Sign-in). GetInstallInfo, GetAccount, RequestMagicLink
/auth/email#token=<token> no The page of a magic link (Sessions, cookies, and sign-in links). It signs in with the token, then opens the saved return path, or /. A link that adds an email to the account of the session opens /account instead (Sessions, cookies, and sign-in links). VerifyMagicLink
/auth/login-link#token=<token> no The page of a first-admin login link (Sessions, cookies, and sign-in links). It works as /auth/email. VerifyLoginLink
/invite#token=<token> asks for one The page of an invitation to an org (the org API). Without a session, it shows the sign-in methods. With one, it accepts the invitation and opens the org. GetAccount, AcceptInvitation
/device?code=<user code> yes Approves a sign-in of the hopbox CLI (CLI tokens, API keys, admin API keys, and SSH keys). It shows the name, the IP address, and the start of the client. It asks the person to compare the code with the code in the terminal (RFC 8628 section 5.4). It approves exactly that client. Without code, it asks for the code. The approval needs a sign-in within the last 10 minutes. After an older sign-in, the page says so, and its button “Sign in again” opens /signin?again=1&return_to=/device?code=<code>. GetDeviceAuthorization, ApproveDevice
/ yes Opens the last org of this browser, or the personal org. GetAccount, ListOrgs
/account yes The display name, the emails, the sign-in methods, the SSH keys, and the CLI sign-ins of the account. Under the sign-in methods, it links a new method of the install (Sessions, cookies, and sign-in links). The buttons “Link GitHub” and “Link Google” open /auth/<provider>/start?link=1&return_to=/account. A provider that the account holds already gets no button, because an account takes one identity of each provider. The form “Email me a link” sends a link to an email. A link needs a sign-in within the last 10 minutes. After an older sign-in, the form says so, and its button “Sign in again” opens /signin?again=1&return_to=/account. GetAccount, UpdateAccount, ListSignInMethods, RemoveSignInMethod, GetInstallInfo, RequestMagicLink, ListSSHKeys, AddSSHKey, RemoveSSHKey, ListCLISignIns, EndCLISignIn
/orgs yes The orgs of the account, and a form that creates an org. ListOrgs, CreateOrg
/orgs/<org ID> yes The machines of the org with their live states, the usage of the org, and the create, start, stop, and delete actions. WatchMachines, GetOrgUsage, ListMachineSizes, CreateMachine, StartMachine, StopMachine, DeleteMachine
/orgs/<org ID>/machines/<name> yes One machine: its actions, its URL with the public switch and the port, its sharing, and its details. WatchMachines, StartMachine, StopMachine, RebootMachine, DeleteMachine, SetMachineURLVisibility, SetMachineURLPort, ShareMachine, UnshareMachine
/orgs/<org ID>/machines/<name>/terminal yes The web terminal (Web terminal). /api/ws/exec
/orgs/<org ID>/members yes The members and their roles. Owners and admins also see the invitations, and invite people. ListOrgMembers, SetOrgMemberRole, RemoveOrgMember, ListInvitations, CreateInvitation, RevokeInvitation
/orgs/<org ID>/api-keys yes The API keys of the org. A new key shows its secret once. ListAPIKeys, CreateAPIKey, RevokeAPIKey
/orgs/<org ID>/vars yes The env vars and secrets of the org. A secret shows no value. ListVars, SetVar, DeleteVar
/orgs/<org ID>/settings yes The name, the usage and the limits of the org, and the leave and delete actions. GetOrg, UpdateOrg, GetOrgUsage, LeaveOrg, DeleteOrg
/admin/... yes, of an instance admin The Admin area (Admin area). the admin API

Every page of an org also calls GetOrg. Each page shows the actions that the role of the account allows. The service layer still decides each call (the API server), and the page shows its error.

A form, or the question before a delete or another action that cannot be undone, opens in a modal dialog. The dialog keeps the focus inside it. The title of the dialog is its accessible name. The Cancel button, the Escape key, and a click on the dark backdrop close it. A click inside the dialog, or a drag that starts inside it, does not close it.

A path with no page shows “Page not found”. A path with a file extension, or under /assets/, that names no file of the build gets 404 with the text the console has no file <path>.

Admin area

Section titled “Admin area”

The Admin area is the part of the console for instance admins. Use the Admin area shows how to use it. The code is in web/apps/console/src/admin.

Only an instance admin sees the link “Admin” at the top right. The routes under /admin read instance_admin of GetAccount before they load. For any other account, each of them shows “Page not found”. This only hides the pages. The server decides each call: the admin API takes a session only from an instance admin with a sign-in within the last 10 minutes (the admin API).

Path What it does Calls
/admin Opens /admin/servers. none
/admin/servers The servers, with their state, their last heartbeat, their compat class, their labels, and their count of machines. The cordon and uncordon actions. While a server drains, the list reads again every 2 s. ListServers, CordonServer, UncordonServer
/admin/servers/<server ID> One server: its roles, its pool, its status and problems, its heartbeat, its compat class, its CPU, its capacity, its versions, and its certificate. Its cordon, its drain, and a form for its labels. While the server drains, the page reads again every 2 s. GetServer, CordonServer, UncordonServer, SetServerLabels, DrainServer
/admin/pools The pools, with their OVHcloud plan, their hardware, and their counts of servers and sizes. A form that creates a pool, and the delete action. ListPools, CreatePool, DeletePool
/admin/sizes The sizes, with their resources, their pool, and their labels. With “Show retired sizes”, also the retired ones. A form that creates a size, and the retire action. ListSizes, ListPools, CreateSize, RetireSize
/admin/images The machine images, with their digest, their arch, their disk, and their times. It has no action. ListImages
/admin/orgs The orgs, with their members, their usage, their limits, and their suspension, page by page. The suspend, unsuspend, and limits actions, and a form for the default limits. ListOrgs, SuspendOrg, UnsuspendOrg, SetOrgLimits, GetDefaultOrgLimits, SetDefaultOrgLimits
/admin/machines?org=<org ID> The machines of every org, or of one org with org, page by page. Each row has the org, the state, the node, the address, and the size. The stop and delete actions. /admin/admins The instance admins. A form that makes an account an instance admin by its verified email, and the revoke action. ListInstanceAdmins, GrantInstanceAdmin, RevokeInstanceAdmin, GetAccount
/admin/admin-keys The admin API keys. A new key shows its secret once. The revoke action. ListAdminKeys, CreateAdminKey, RevokeAdminKey
/admin/config The domain, the public addresses, the ACME settings, the mail transport, and maintenance mode. A form that changes the domain. A form for the SMTP server, and a form for the app of GitHub and of Google. GetInstallConfig, UpdateInstallConfig, GetSMTPConfig, SetSMTPConfig, ClearSMTPConfig, GetOAuthConfig, SetOAuthClient, ClearOAuthClient
/admin/audit The audit log of the whole install, newest first, page by page. ListAuditEntries with whole_install

Drain of a server

Section titled “Drain of a server”

The server page has the button “Drain” in the danger style. It opens the dialog “Drain ” (Cold move). The dialog says these things:

  • The drain cordons the server and moves each machine to another node, at most 2 at once.
  • A running machine stops, moves, and boots again, so it loses its memory.
  • Each machine keeps its disk, name, URL, SSH port, and address.
  • Once the server holds nothing, the drain decommissions it.
  • “You cannot stop a drain.”
  • If Terraform manages the server, run terraform destroy instead, because the next refresh of Terraform drops a drained server from its state.

A server without the role node has no button “Drain”, because it holds no machine and the install refuses its drain. An admin session cannot drain a server that hosts a control process: the call fails with permission_denied (the admin API).

While the server drains, the page changes:

  • The button reads “Drain again”. It starts the drain again, to try the stranded machines again. Its dialog says that the drain tries each stranded machine again and counts its empty checks from zero.
  • The buttons “Cordon” and “Uncordon” are hidden, because a drain keeps the server cordoned.
  • The section “Drain” shows these facts: Started, Moves, Empty checks (n of 3, and how long ago the last one ran), and Waits, the error of the drain.
  • A notice says that the drain cannot go on by itself when the drain is stuck.
  • A table lists each stranded machine with its reason. A machine whose disk copy a failed move left on this server shows “on another node” under its name.

The admin API has no stream of servers. So the list of servers and the page of a server read again every 2 s while a drain runs.

The calls of the admin API go to the services hopbox.admin.v1.*. Each read of the admin API writes an audit entry. So each load of a page of the Admin area adds entries to the audit log (the admin API).

The Admin area keeps the rules for instance admins:

  • It has no shell, no web terminal, and no file access for a machine. The machine list has no link to the page of a machine.
  • It shows no secret value. No call of the admin API returns the SMTP password, an OAuth client secret, or key material. No call returns the secret of an admin key after its create. The forms of a password and a client secret are write-only: they start empty, and an empty field keeps the value that is set now. After a save, the page empties the field, and the cache of the console drops the request.
  • The secret of a new admin key shows once, as hopboxd admin admin-key create prints it once. When the page closes, the cache of the console drops it.

Each call needs a sign-in within the last 10 minutes. After an older one, a call fails with permission_denied and the detail RecentSignInRequired. The page then shows “This step needs a sign-in within the last 10 min” and the button “Sign in again” (Sign-in).

Look

Section titled “Look”

The console has the look of the public site hopbox.dev. It uses the same colors, fonts, buttons, cards, and icon:

Part Value
Background #0A0E0B, with panels in #111712
Text #ECF2EC, and #A3B1A5 for secondary text
Accent lime #C4F05A, for links, the main button, the focus ring, and the state running
Warning amber #FFB443, for a public URL, a state that changes, and the not verified tag of an email
Error #FF7A6B, for errors and the delete buttons
Text font Bricolage Grotesque
Code font JetBrains Mono, for names, URLs, and the web terminal

The console has a dark theme only, as the site has. It does not follow the light or dark setting of the system.

The look keeps the console accessible:

  • Text has a contrast of at least 4.5:1 on its background (WCAG 2.2 level AA). A disabled control is the only exception.
  • The control that has the keyboard focus shows a lime ring.
  • Each state has a word next to its color, such as running or Public URL: public.
  • A link inside a sentence has an underline, so it differs from the text by more than its color.

The web terminal takes its colors from the same values. If a program picks a text color with a contrast below 4.5:1, xterm.js makes it lighter.

Browsers

Section titled “Browsers”

The console works in these browsers:

Browser Version
Chrome and Edge 111 or later
Firefox 114 or later
Safari 16.4 or later

Vite builds the code for this set, its default build target of Baseline Widely Available browsers.

The terminal page fills the height of the window with the CSS selector :has(). Firefox supports it from version 121. In Firefox 114 to 120, the terminal and its bar are 360 pixels high together, and do not fill the window. Rows of a table with actions also do not light up on hover there, because that rule uses :has() too. The other parts of the console work the same.

On a short window, such as a phone in landscape, the terminal gets smaller, until it and its bar are 360 pixels high together. Then the page scrolls. The head and the tabs of the org keep their height.

Sign-in

Section titled “Sign-in”

The sign-in page asks GetInstallInfo for the sign-in methods:

  • For GitHub and Google, it shows a link to /auth/<provider>/start?return_to=<path>. The browser opens that link, and the API sends it on to the provider (Sign-in with GitHub and Google). The console encodes the path once with encodeURIComponent, and never decodes it (Sign-in with GitHub and Google).

  • For magic links, it shows an email form, which calls RequestMagicLink. After the call, it says that the link went to the email. With mail_to_files in GetInstallInfo, it says instead that the install writes each email to a file on its server. An operator then reads the link with sudo hopboxd admin mail show (Mail).

  • Without a method, it shows the command that makes a first-admin login link: sudo hopboxd admin login-link --email <email>.

A magic link or a login link opens its own page, often in a new tab. So the sign-in page keeps its return path in the local storage of the browser for 15 minutes, the lifetime of a link. The page of the link then opens that path.

Some steps need a recent sign-in, at most 10 minutes old (Sessions, cookies, and sign-in links). In the console, these steps are the approval of a CLI sign-in on /device and the link of a sign-in method on /account. Each call of the Admin area is such a step too. A link of GitHub or Google starts on the browser endpoint, which sends an older session to /signin?again=1&return_to=/account itself (Sign-in with GitHub and Google). A call of such a step with an older session fails with permission_denied and the detail RecentSignInRequired. The page then links to /signin?again=1&return_to=<path of the page>. With again=1, the sign-in page shows the methods to a person who is signed in already. The new sign-in replaces the session of the browser, and the page of the step opens again.

The console checks a return path with the rules of the server. A good path has these properties:

  • It is one path on the install, with at most 512 characters.
  • It starts with one /.
  • It has no backslash, no space, and no control character.
  • It has no . or .. segment.

The console drops any other return path, and opens /.

The pages of the links read the token from the fragment, then remove the fragment from the address bar and the history before the call. A browser never sends a fragment to a server, so the token never reaches a log or a Referer header.

The page of an invitation keeps its token in the session storage of the tab while the person signs in. A sign-in with GitHub or Google in the same tab then comes back to it. A magic link opens in another tab without the token. Go back to the first tab. When the tab gets the focus, it reads the account again and shows the accept button.

A call that fails with unauthenticated on a page that needs a session sends the browser to the sign-in page. “Sign out” calls SignOut, which ends the session and clears the cookie.

Calls

Section titled “Calls”

The console calls the API with the TypeScript SDK @hopbox/sdk of the workspace, in its browser runtime (TypeScript SDK). The session cookie authenticates each call, so the client has no credential. Each call is a Connect POST with the binary format.

The SDK never includes the admin API. So the Admin area has its own generated code of hopbox.admin.v1 in web/apps/console/src/gen (API definitions). It calls the admin API on the same transport of the SDK, with the same retries and idempotency keys.

The pages read and change data with TanStack Query and connect-query on the transport of the SDK. The transport already retries a call that is safe to run again, and puts an idempotency key on each create. A read call gets a retry after unavailable, resource_exhausted, or deadline_exceeded. A change without an idempotency key gets one only after an answer with Hopbox-Not-Run: 1, because fetch does not tell a refused connection from a lost answer (TypeScript SDK). So TanStack Query never retries a call itself. A read stays fresh for 15 seconds. A change reads the data of its service again.

Live machine list

Section titled “Live machine list”

Each page of an org follows the machines of the org with the stream WatchMachines. The stream sends each machine, then a synced message, then each change. The console shows the first list at the synced message. A machine in the state deleted, or a gone_machine_id, leaves the list.

When the stream breaks, the console keeps the old list on show. It opens the stream again after 1, 2, 5, 10, and then 30 seconds. The new first list replaces the old one at its synced message, so a machine that went away in the meantime leaves the list then. The head of the org shows the state of the stream: connecting, live, or reconnecting. An unauthenticated error ends the stream and opens the sign-in page.

Web terminal

Section titled “Web terminal”

The web terminal opens the login shell of the main user of a running machine, as hopbox connect does. It runs exec over the WebSocket endpoint /api/ws/exec with these start fields (the machine API):

Field Value
machine the name of the machine
argv empty, for the login shell
tty true
size the rows and the columns of the terminal
term xterm-256color

The terminal is xterm.js. Each key goes to the shell as stdin, and each change of the size of the page sends a resize. The output of the shell goes to the terminal. When the shell ends, the terminal shows how it ended, such as the shell ended with exit code 2, and offers “Open a new shell”. The button “Open terminal” needs the state running.

The browser sends the session cookie with the WebSocket, and the server checks its Origin header against https://<domain> (Sessions, cookies, and sign-in links). A page of a machine URL thus cannot open a shell with the cookie of a person.

Browser storage

Section titled “Browser storage”

The console keeps no credential in the storage of the browser. It keeps these keys:

Key Storage Value Lifetime
hopbox.lastOrg local the ID of the org that the browser opened last, for / until “Sign out”
hopbox.returnTo local the return path of the last sign-in page, with its time 15 minutes, and one read
hopbox.invite session the token of an invitation that waits for a sign-in until the accept, “Not now”, an accept error that a retry cannot fix, or the end of the tab

A browser without storage loses only these conveniences.

Headers

Section titled “Headers”

Each response of the console has these headers:

Header Value
Content-Security-Policy default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
X-Content-Type-Options nosniff
X-Frame-Options DENY
Referrer-Policy no-referrer
Cross-Origin-Opener-Policy same-origin
Cross-Origin-Resource-Policy same-origin
Permissions-Policy camera=(), microphone=(), geolocation=(), payment=(), usb=()

The policy allows scripts only from the console itself: no inline script, no eval, and no other site. The build has no inline script and no data URL. The console loads nothing from a CDN. No site can show the console in a frame.

The fonts are files of the build, so font-src 'self' covers them. Each file is a variable font in WOFF2, so one file gives every weight that the console uses:

The policy allows inline styles. xterm.js writes style elements and style attributes while it runs, for the size of the cells and the colors of the text. Without inline styles, the terminal shows the text without its colors and its layout. An inline style cannot run code.

The cache headers depend on the file:

File Cache-Control
index.html, and each page of the app no-cache
a file under /assets/, whose name holds the hash of its content public, max-age=31536000, immutable
a file that does not exist no-store

Each file has an ETag from its SHA-256, and a request with a matching If-None-Match gets 304 Not Modified. A file of text, script, JSON, or SVG of at least 1 KiB also has a gzip copy. A request with Accept-Encoding: gzip gets that copy with Content-Encoding: gzip and Vary: Accept-Encoding, unless it asks for a range.

Build

Section titled “Build”

make console builds the console:

  1. It builds the SDK into web/packages/sdk/dist/ with tsc.
  2. It type-checks the console with tsc.
  3. Vite writes the build to internal/console/dist/: index.html, and the hashed files under assets/, the icon and the two fonts among them. The terminal and xterm.js load in a chunk of their own, only on the terminal page. When an instance admin opens a page of the Admin area, the page loads in a chunk of its own.

make build runs make console first, so each hopboxd holds the console of its own commit. tools/bundle refuses a hopboxd without the console, so no release ships without it (Release bundle). internal/console embeds internal/console/dist/ with go:embed. Git ignores the build, apart from the empty file .gitkeep, which go:embed needs. The same lockfile gives the same files, so the build is reproducible.

A hopboxd built without make console, for example with go build, holds no console. Its API listener answers each path of the console with 404. The text is This hopboxd has no console. Build it with make console, then make build. At its start, hopboxd run logs the record this hopboxd has no console. Build it with make console, then make build at level warn.

TestConsole runs a control role with a node that runs machines with the real guest agent. It serves the API with the console of the test binary at https://hop.example.org. An HTTP proxy of the test sits in front, and ends TLS with a certificate that the test makes. Chromium reaches the console through that proxy. The suite:

  1. Checks the headers and the sign-in page without a session, and checks that both fonts load under the policy.
  2. Signs in with a login link, comes back to the page that asked for the sign-in, and finds box1 running. It checks that the scrolling row of tabs does not cut off the focus ring of a tab or the underline of the current tab.
  3. Creates, stops, starts, and deletes a machine, and checks the name suggestion of a taken name.
  4. Makes the URL of box1 public, then private.
  5. Runs echo in the web terminal, then exit. Before that, it checks at 844 by 390 and 1280 by 560 pixels that the tabs of the org keep their height.
  6. Adds and removes an SSH key, creates an API key, and sets an env var.
  7. Opens each dialog, and checks it at a desktop and a phone width. The title starts at the left edge, the text stays inside the dialog, and the buttons sit at the bottom right. The dialogs are “New machine”, “Delete box1”, “Revoke the API key”, “Remove the SSH key”, “Remove the member”, “Leave Team”, and “Delete Team”.
  8. Checks that a click on the backdrop and the Escape key close a dialog, and that a click or a drag inside it does not.
  9. Creates an org, and finds it in the org switcher.
  10. Signs out, and checks that each page then asks for a sign-in.
  11. Drops the cookies of the browser, and opens /device?code=<code> without a session. It signs in with a new login link, comes back to the code, and approves it.
  12. Signs in, makes the session 11 minutes old, and opens /device?code=<code> with a second code. The approval fails and asks for a sign-in again. The suite signs in with a new login link, comes back to the code, and approves it. After the run, the Go test polls both device sign-ins and gets the CLI tokens of the account.
  13. Opens a second browser with the session of user1@example.org, who is not an instance admin. The console shows no “Admin” link, and each page under /admin shows “Page not found”. A call of the admin API from that page gets permission_denied without the detail RecentSignInRequired.
  14. Opens the Admin area. It cordons and uncordons the server of the test, and sets its labels. A label without = shows an error.
  15. Creates a pool and a size in it, retires the size, deletes the pool, and finds the image default.
  16. Sets the limits of the org Team, suspends it with a reason, and unsuspends it. It checks both dialogs at a desktop and a phone width. It finds box1 in the machine list with its address, finds no link or button of a terminal or a shell, and stops box1.
  17. Makes user1@example.org an instance admin, and revokes the role. Creates an admin key, which shows its secret once: after a visit to another page, the page no longer holds the secret. Then it revokes the key.
  18. Sets the SMTP server and the GitHub app with a password and a client secret. The fields empty after the save, and the page says only that each secret is set. The page and the audit log never hold either secret.
  19. Checks that each page of the Admin area fits a phone width of 360 pixels without a horizontal scroll.
  20. Makes the session 11 minutes old, and clicks “Cordon”. The action fails and asks for a sign-in again, and the server stays ready. The suite signs in with a new login link, comes back to /admin/servers, and the cordon works. After the run, the Go test reads the audit log: each action of the Admin area has the actor kind session. The test also finds the new SMTP server of the install.
  21. Turns on the file mail transport, and links the email ann.work@example.org on /account. It opens the link from the mail file, and finds the email link in the sign-in methods. Then it makes the session 11 minutes old, and checks that a second link asks for a sign-in again.
  22. Drains a second server of the test, which holds no machine, from its page. The empty checks of the test come 2 s apart. The badge shows draining or shutting down, the section “Drain” shows, and the button “Uncordon” is gone. Then the badge shows decommissioned, and the page has no drain button. The audit log has server.drain with the actor kind session, and server.decommission with the actor system. The Playwright test is “the drain button drains a server, which then leaves the install”.
  23. Checks that no page error and no policy violation happened.

Steps 12, 14 to 22 each start with a new sign-in through a login link, and step 11 starts without cookies. So they need no session from the steps before them, and their order does not matter. Each sign-in goes through the page of the link and the real sign-in of the API, as for a person.

TestConsole gives Playwright the install in env vars, so you do not set them yourself. HOPBOX_E2E_PROXY is the proxy that serves the console and the API. HOPBOX_E2E_LOGIN_LINK is the first login link of ann@example.org, the account of the suite and an instance admin. A POST to HOPBOX_E2E_LOGIN, a URL on loopback, returns a new login link of that account. HOPBOX_E2E_USER_COOKIE is the session token of user1@example.org, an account with a verified email that is not an instance admin. HOPBOX_E2E_USER_CODE and HOPBOX_E2E_USER_CODE_2 are the codes of the two device sign-ins. A POST to HOPBOX_E2E_AGE_SESSIONS, a URL on loopback, makes every session of ann@example.org 11 minutes old. A POST to HOPBOX_E2E_MAIL, a URL on loopback, turns on the file mail transport. A GET of it returns the link in the newest mail file. HOPBOX_E2E_TEAM_ORG is the ID of the org Team, where bob@example.org is a member of the account of the suite. HOPBOX_E2E_DRAIN_SERVER is the ID of a second server, cordoned and without machines, which the suite drains. The others are HOPBOX_E2E_URL, HOPBOX_E2E_SSH_KEY, and HOPBOX_E2E_MACHINE.

Without HOPBOX_TEST_CONSOLE, TestConsole skips. make test-console sets the variable, and make test does not, so make test needs no browser. The test needs corepack pnpm install, a build of the console, and the Chromium of Playwright: run web/apps/console/node_modules/.bin/playwright install chromium once. If one of them is missing, the test fails.
