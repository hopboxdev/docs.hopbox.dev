The org API

The service hopbox.v1.OrgService of the public API manages the orgs of the caller, their members, their invitations, and reads their usage and limits. The admin API covers the calls of instance admins on orgs: the list of every org, the suspension, and the limits. The API server covers the parts that every call shares: the request gate, the policy check, the idempotency keys, and the error codes. The generated reference is Public API. The code is in internal/service (orgs.go, invitations.go) and internal/api.

Calls What they do
CreateOrg, GetOrg, ListOrgs, UpdateOrg, DeleteOrg Make, read, rename, and delete orgs.
GetOrgUsage Reads what an org uses, and its limits.
ListOrgMembers, SetOrgMemberRole, RemoveOrgMember, LeaveOrg Read and change the members of an org.
CreateInvitation, ListInvitations, RevokeInvitation, AcceptInvitation Invite a person by email, and join with the invitation.

Each call acts as the account of a session or cli_token caller. A member_key acts as its account too, but only in the org of the key, and it never creates, joins, or leaves an org. An org_key has the rights of a member in its own org, without personal resources: it reads the org, its usage, and its members (CLI tokens, API keys, admin API keys, and SSH keys). An instance admin sees the orgs of others only through the admin API. Here, a session of an instance admin has only the rights of its own roles.

The examples on this page use the shell function browser of the sign-in, account, and audit API, with the session cookie of the caller. Work in a team org runs the whole flow on a laptop.

The org of a request

Section titled “The org of a request”

A request that acts in one org has the field org_id, an optional string. Leave it out to act in the personal org of the caller (the API server). ListOrgs, CreateOrg, and AcceptInvitation have no org_id.

The service layer reads the role of the caller in the org before the policy check. A caller that is not a member has no role. So an org that does not exist gets the same permission_denied as an org of others. An org_id that is not a UUID gets invalid_argument.

Roles

Section titled “Roles”

The enum OrgRole names the role of an account in an org (Domain rules). Each role has every right of the roles before it.

Value Role Default
ORG_ROLE_UNSPECIFIED Never in a response. In a request, the field takes its default.
ORG_ROLE_MEMBER member the role of an invitation without a role
ORG_ROLE_ADMIN admin
ORG_ROLE_OWNER owner the role of the account that creates the org

A value that is not in the enum gets invalid_argument with the message invalid argument: the org role <n> is not known.

What each role can do

Section titled “What each role can do”
Call member admin owner
GetOrg, GetOrgUsage, ListOrgMembers, LeaveOrg yes yes yes
ListInvitations, RevokeInvitation no yes yes
CreateInvitation with the role member no yes yes
CreateInvitation with the role admin or owner no no yes
RemoveOrgMember of a member no yes yes
RemoveOrgMember of an admin or an owner no no yes
SetOrgMemberRole, UpdateOrg, DeleteOrg no no yes

Only an owner makes other owners and admins. So an admin invites and removes members only. A caller without the right gets permission_denied, with the message permission denied: a caller of kind session may not do <action>.

Every org keeps an owner

Section titled “Every org keeps an owner”

An org always has at least one owner. If a change takes the last owner from the org, it fails with failed_precondition. These changes can do so: SetOrgMemberRole of the last owner to another role, RemoveOrgMember of the last owner, LeaveOrg by the last owner, and DeleteAccount of the last owner (the sign-in, account, and audit API).

Each such change first locks the row of the org in orgs. Then it reads the role of the caller again, checks the policy again, and counts the owners in a new statement (Control store tables). So two owners that each step down, leave, or remove the other at the same time leave one owner. The second change sees the first one, and fails with failed_precondition or permission_denied. The delete of an account locks every org of the account in the same way. So a promotion of the account to owner during its delete waits for the delete, and then fails with not_found.

Orgs

Section titled “Orgs”

CreateOrg

Section titled “CreateOrg”

Makes an org with the caller as its owner.

Item Value
Procedure /hopbox.v1.OrgService/CreateOrg
Policy action org.create: session and cli_token
Idempotent option yes. A call must have an Idempotency-Key header (the API server). A retry with the same key returns the same org.
Audit entry action org.create, org the new org, target kind org, details name

The request CreateOrgRequest has the field name, a string (Domain rules). The response CreateOrgResponse has the field org, an Org.

An account owns at most 10 orgs besides its personal org. Every new org brings its own usage limits, so this cap keeps one account from many limits. An instance admin changes the cap with SetDefaultOrgLimits (the admin API). The cap counts each org in which the account is an owner. The call takes the row lock of the account, so two creates at the same time cannot pass the cap together.

Error Code
A bad name, for example invalid argument: invalid org name: it must not start or end with a space invalid_argument
The account owns the most orgs: usage limit exceeded: the account owns 10 orgs besides its personal org, the most that the install allows. Delete one, or ask an instance admin to raise the limit resource_exhausted
An instance admin suspended the account after the request gate let the call in (the admin API): permission denied: an instance admin suspended this account. The reason: <reason>. The call changes nothing. permission_denied

DeleteOrg

Section titled “DeleteOrg”

Deletes an org, its memberships, its invitations, and every resource in it. The request must hold the name of the org in confirm.

Item Value
Procedure /hopbox.v1.OrgService/DeleteOrg
Policy action org.delete: a session, cli_token, or member_key with the role owner
Idempotent option no

Field Type Description

Error Code
confirm is not the name: invalid argument: confirm the delete with the name of the org, "Team" invalid_argument
The personal org: failed precondition: a personal org goes only with its account. Delete the account instead failed_precondition

What a member leaves behind

Section titled “What a member leaves behind”

A leave, a removal, and the delete of an account take the account out of the org. They also delete what the account made in the org and did not share. The delete of an org deletes every resource of the org. The service layer does this through the Go interface service.OrgResource, in the transaction of the change:

Method Called by
MemberLeaving(org, account) LeaveOrg, RemoveOrgMember, and DeleteAccount, once for each org other than the personal org. The admin DeleteAccount calls it once for each org that it does not delete.
OrgDeleting(org) DeleteOrg, and DeleteAccount for the personal org. The admin DeleteAccount calls it for the personal org and for each org that the account owns alone (the admin API).
OrgSuspending(org) SuspendOrg of the admin API (the admin API). SuspendAccount of the admin API calls it for each org that it suspends (the admin API).
MemberSuspending(org, account) SuspendAccount of the admin API, once for each org of the account that it does not suspend. These are the orgs other than the personal org, in which another account is an owner too.

Each call holds the row lock of the org while the method runs. A leave, a removal, and an account delete also hold the lock of the account, which they take first. The lock order is the account row, then the org row, then the rows of the resource, such as machines (Control store tables). A change of a resource outside these calls takes the locks in the same order.

The env vars and secrets are built into the service layer, and it runs their methods first. MemberLeaving deletes the private values of the account in the org, with a var.delete entry for each (the env var API). The other values of the org stay. The delete of an org deletes its values through the foreign key. Each other kind of resource in an org adds its implementation to Service.OrgResources. The control role adds the machines (the machine API). A method that fails rolls the whole change back, and the call fails with internal.

The machines do this in each method. Each method locks the machine rows in the order of their IDs, and skips a machine whose target is deleted already.

Method What it does to the machines Audit entry of each machine that changes
MemberLeaving(org, account) Sets the target deleted on each machine that the account made in the org and did not share. A shared machine stays in the org. machine.delete, with the detail reason (member left)
OrgDeleting(org) Sets the target deleted on every machine of the org. machine.delete, with the detail reason (org deleted)
OrgSuspending(org) Sets the target stopped on every machine of the org, except a machine whose target is hibernated. A hibernated machine stays hibernated, because only a delete drops its memory file (Domain rules). machine.stop, with the details old_target and reason (org suspended)
MemberSuspending(org, account) Sets the target stopped on each machine that the account made in the org and did not share. A machine whose target is hibernated stays hibernated. A shared machine keeps running, because the org uses it. machine.stop, with the details old_target and reason (account suspended)

MemberSuspending of the env vars and secrets does nothing, because a value runs nothing. A delete reserves the name and the SSH port of the machine for 7 days, as DeleteMachine does (the machine API). The actor of each entry is the caller of the change, and each change publishes the event machine.updated (the machine API). A delete of an org sets org_id of its machines to null once their target is deleted. The machines then wait for their executor (Control store tables).

Invitations

Section titled “Invitations”

An org owner or an org admin invites a person by email, and the person accepts after the sign-in. An invitation is for one email and gives one role.

Rule Value
Link https://<domain>/invite#token=<token>. The token is 32 random bytes in base64url, as for a sign-in link (Sessions, cookies, and sign-in links). It is in the fragment, so a browser never sends it to a server. The console page /invite reads it and calls AcceptInvitation.
Storage The control store keeps only the SHA-256 of the token (Control store tables). The audit log never holds the token.
Lifetime 7 days
Use once
Open invitations one for each email in an org. A new invitation for the email revokes the open one, so its link stops working.
Rate limits An org makes at most 20 invitations in an hour. An inviting account makes at most 20 in an hour, in all its orgs together. An email gets at most 5 in an hour, from every org together. The control store counts them in org_invitation_sends, a table without foreign keys (Control store tables). So the limits hold across every control server, and the delete of an org or an account resets no limit. Each new invitation takes a transaction lock (LockKeyInvitations, the bundled Postgres), so invitations at the same time cannot pass a limit together.
Email With an SMTP config, the server sends the link to the email (SMTP config). Without one, only the inviter gets the link. With the file mail transport, the server writes the email to a file on the server, and the inviter passes the link on (Mail).
Who accepts A session whose account holds the email of the invitation as a verified email. The email of a login link stays unverified, so it does not count (Sessions, cookies, and sign-in links). A link of the email from a session of the account verifies it (Sessions, cookies, and sign-in links).
Orgs A personal org belongs to one account, so it takes no invitations. A suspended org sends none and takes no new members.
Rights of the inviter An invitation never gives more than its inviter can give now. A leave, a removal, or an account delete of the inviter revokes each open invitation of the inviter in the org. A role change of the inviter revokes each one with a role that the new role cannot give.

The leader deletes an invitation 24 hours after its end: its use, its revoke, or its expiry (hopboxd).

CreateInvitation

Section titled “CreateInvitation”

Invites an email to join an org with a role, and returns the link. With an SMTP config, it also sends the link to the email.

Item Value
Procedure /hopbox.v1.OrgService/CreateInvitation
Policy action org.invitation_create: a session, cli_token, or member_key with the role admin for the role member, or with the role owner for any role
Idempotent option no. The response holds the link, which must never stay in the table of idempotency keys. A retry revokes the invitation of the first try and makes a new one.

AcceptInvitation

Section titled “AcceptInvitation”

Joins the org of an invitation with its role. The account of the caller must hold the email of the invitation as a verified email.

Item Value
Procedure /hopbox.v1.OrgService/AcceptInvitation
Policy action org.invitation_accept: session and cli_token
Idempotent option no
Audit entry action org.invitation_accept, org the org, target kind invitation, details email and role

The request AcceptInvitationRequest has the field token: the value after #token= in the link. The response AcceptInvitationResponse has the field org, the Org with the new role of the caller.

The call locks the row of the org, then the row of the invitation, in the order that CreateInvitation takes them. So two accepts of one link at the same time make one membership. A refused try that is not a used, revoked, or expired link leaves the invitation open, so the right person can still accept it.

Error Code
The token is unknown, used, revoked, or expired: not found: the invitation is not valid: it is unknown, used, revoked, or expired. Ask for a new one not_found
The account has no verified email of the invitation: failed precondition: the invitation is for bob@example.org, and the account has no verified email bob@example.org. Sign in with that email, then open the link again failed_precondition
The account is a member already: failed precondition: the account is a member of the org already, as <role> failed_precondition
A suspended org: failed precondition: org suspended: an instance admin suspended the org, so it takes no new members failed_precondition
An instance admin suspended the account after the request gate let the call in (the admin API): permission denied: an instance admin suspended this account. The reason: <reason>. The call changes nothing. permission_denied

The server logs a refused token as invitation refused at level info, with component=service, and never the token.

Usage limits

Section titled “Usage limits”

Each org has usage limits on machines, vCPUs, RAM, and disk. The install has default limits for every org. An instance admin can change the defaults, and set limits for one org that replace the defaults (the admin API).

Limit Default
Machines 3
vCPUs 6
RAM 24 GiB (25769803776 bytes)
Disk 300 GB (300000000000 bytes)

The defaults fit three machines of the default size (Domain rules). A limit of 0 allows nothing. Domain rules gives the rules of the check.

Usage The machines that count
Machines and disk every machine that is not deleted
vCPUs and RAM the machines whose target state is running or standby

So a stopped machine keeps its disk and its place in the machine count, but frees its vCPUs and its RAM. A machine whose target is deleted counts no more, also while its executor still deletes it. CreateMachine and StartMachine check the limits (the machine API). A start adds only the vCPUs and the RAM of a machine that does not count already, so a start never counts a machine twice. A new limit below the usage stops nothing: the org then creates and starts no more machines until its usage fits.

Suspension

Section titled “Suspension”

An instance admin can suspend an org, for example to handle abuse. The calls are on the admin API (the admin API). The members of the org see the suspension in GetOrg. Its owners and admins see its audit entry in the audit log of the org.

Effect Since
Reads still work. now
The org sends no invitations. CreateInvitation fails with failed_precondition. now
The org takes no new members. AcceptInvitation fails with failed_precondition. now
Owners can still change roles and rename the org. now
Nothing deletes the data of the org, for example the evidence of abuse. DeleteOrg, LeaveOrg, and RemoveOrgMember in the org fail with failed_precondition. So does DeleteAccount of a member of the org, or of the account of a suspended personal org. The admin DeleteAccount goes on, and its audit entry keeps the evidence (the admin API). now
The env vars and secrets of the org do not change. SetVar and DeleteVar fail with failed_precondition (the env var API). now
The members cannot delete a machine of the org. DeleteMachine fails with failed_precondition (Domain rules). now
The machines of the org stop. A hibernated machine stays hibernated (Domain rules). now, through OrgSuspending
The org cannot create, start, or reboot a machine. CreateMachine, StartMachine, and RebootMachine fail with failed_precondition (the machine API). now
The org cannot resume, wake, fork, or restore a machine. with the calls of these actions, in phase 3
The auto-delete of the leader skips the machines of the org. now
Instance admins can still stop and delete any machine of the org (the admin API). now
Exec and file copy are blocked (the machine API). now
The machine URLs are blocked. The edge answers 403, and GET /auth/machine gives no code (the edge role). now
SSH is blocked. The SSH front door refuses every key, and ends the open SSH connections of the org (the SSH front door). now

The end of the suspension starts no machine. The users of the org start them again.

The suspend of an account also suspends orgs (the admin API). It suspends the personal org of the account, and each org in which the account is the only owner, with the reason of the account. An org that is suspended already keeps its suspension and its reason. Each org that the suspend changes then has the effects of the table. UnsuspendAccount ends the suspension of these orgs, but not of an org that SuspendOrg suspended. A SuspendOrg of such an org takes over its suspension, with the reason of the account, so UnsuspendAccount then leaves it suspended. UnsuspendOrg ends the suspension of either kind.

Audit entries

Section titled “Audit entries”

The org calls write these entries in the transaction of the change. Their org is the org of the change, so its owners and admins read them with ListAuditEntries (the sign-in, account, and audit API). The actor is the caller.

Action Call Target Details
org.create CreateOrg the org name
org.update UpdateOrg the org name, old_name
org.delete DeleteOrg, and the admin DeleteAccount for each org that the account owns alone the org name, and reason (account deleted) for the admin DeleteAccount
org.member_set_role SetOrgMemberRole the account role, old_role
org.member_remove RemoveOrgMember, and both DeleteAccount calls for each org of the account that stays the account role, reason (removed or account deleted)
org.leave LeaveOrg the account role
org.invitation_create CreateInvitation the invitation email, role
org.invitation_revoke RevokeInvitation, CreateInvitation for the invitation that it replaces, and a leave, a removal, an account delete, or a role change of the inviter the invitation email, role, and for a revoke by another call reason: replaced, inviter left, or inviter role changed
org.invitation_accept AcceptInvitation the invitation email, role

The admin calls on orgs add org.suspend, org.unsuspend, and org.set_limits to the audit log of the org (the admin API). SuspendAccount and UnsuspendAccount add org.suspend and org.unsuspend too, with the detail account, the ID of the account (the admin API). The machine calls write their own entries in the audit log of the org (the machine API).
