The API server

The control role serves the API of hopbox with Connect. This page covers the listener, the protocols, the request gate, and the callers and the policy check. It also covers the chain of interceptors, idempotency keys, the error codes, reflection, health, and InstallService. The sign-in, account, and audit API covers the sign-in, account, and audit calls. The org API covers the org, member, and invitation calls. The machine API covers the machine calls. The admin API covers the admin API and the admin socket. The internal listener covers the internal listener, which serves the cluster API to the servers of the install over TLS. The chain of a call, the gate, the policy, and the errors of this page apply to it too. The code is in internal/api and internal/service.

Listener

Section titled “Listener”
Item Value
Address control.api_listen of the bootstrap config, by default 127.0.0.1:7080 (the bootstrap config of hopboxd)
Transport TCP without TLS. The address must be a loopback address.
HTTP versions HTTP/1.1, and HTTP/2 with prior knowledge (h2c)
Protocols Connect, gRPC, and gRPC-Web, with the binary protobuf and JSON codecs, and gzip
Services Every service of hopbox.v1: InstallService, AuthService, AccountService, AuditService, OrgService, APIKeyService, SSHKeyService, MachineService, and VarService (the env var API). The services of the admin API, with hopbox.admin.v1.MachineService and hopbox.admin.v1.ImageService (the admin API). gRPC reflection and gRPC health.
Browser endpoints GET /auth/github/start, GET /auth/github/callback, GET /auth/google/start, and GET /auth/google/callback: plain HTTP for the sign-in with GitHub and Google, outside of the chain of a call (Sign-in with GitHub and Google). GET /auth/machine: plain HTTP for the sign-in of a private machine URL (the edge role).
Console every other GET or HEAD request whose first path segment has no dot, outside of the chain of a call (Console). Any other request with an unknown path gets 404.

gRPC needs HTTP/2. Without TLS, a client must start HTTP/2 with prior knowledge, for example curl --http2-prior-knowledge or grpcurl -plaintext. The Connect protocol also works over HTTP/1.1.

The clients of the install do not reach this listener. They reach the edge servers, which forward the requests of the domain of the install to the internal listener of the control role (the edge role). The internal listener serves these requests with the same handler as this listener, with the address of each client as the peer (the internal listener). This listener stays on loopback for the processes and the SSH tunnels of the server. Its peers are loopback addresses, so the rate limits of a client skip them (Sessions, cookies, and sign-in links).

The listener serves the admin API too, for admin API keys and for the Admin area of the console. The edge servers forward it too, so the admin API is public behind the edge. On this listener, the policy refuses every admin call of every other caller (Callers and policy). The Admin area calls a part of the admin API with an admin session: the session of an instance admin with a sign-in within the last 10 minutes (the admin API). Root on the server calls the admin API through the admin socket (the admin API).

HTTP server setting Value
Header read timeout 10 s
Body read timeout of a unary call 30 s from the start of the request, until the whole body arrives. A request without a body, such as a Connect GET, has no such bound. A stream has none, and neither has a connection that a handler takes over, such as a WebSocket. A read that runs out of time fails with the code deadline_exceeded and the message the request body did not arrive in time.
Idle connection timeout 2 min
Largest request message 4 MiB. A larger message gets resource_exhausted before any handler reads it.
HTTP/2 streams of one connection at most 100 at once (api.MaxClientStreams)
HTTP/2 receive window 256 KiB for each stream, and 25 MiB for the connection. The window of the connection holds every stream at once. So a stream whose reads stop, such as an upload to a slow node, never stalls the other calls of the connection.

A path that names no service gets HTTP status 404.

The listener also serves the WebSocket endpoint /api/ws/exec of exec over HTTP/1.1 (the machine API). It also serves the MCP server of hopbox at /mcp, for AI agents with a CLI token or an API key (the MCP server). Each tool of the MCP server calls the API in the process, through the chain of a call below.

The chain of a call

Section titled “The chain of a call”

Every call passes these steps, in this order:

  1. Request ID. The server makes a new UUIDv7 for each HTTP request. It puts the ID in the response header Hopbox-Request-Id, in the logs of the call, and in the audit entries of the call. The server never takes an ID from the client, so an ID always names one request.
  2. Metrics and access log. After the call ends, the server counts it in the metrics (Metrics) and writes one log record (Logs).
  3. Error mapping. The server turns each error into a Connect error with a code (Errors).
  4. Default deadline. A unary call whose client sent no deadline gets a deadline of 30 s. A lifecycle call of a machine gets 61 s instead (api.LifecycleTimeout), so its wait of up to 60 s fits (the machine API). These calls are StartMachine, StopMachine, RebootMachine, RenameMachine, and DeleteMachine of hopbox.v1.MachineService, and StopMachine and DeleteMachine of hopbox.admin.v1.MachineService. A deadline from the client stays as it is, longer or shorter. The client sends a deadline with the header Connect-Timeout-Ms or grpc-timeout. A stream gets no default deadline.
  5. Maintenance mode. In maintenance mode, the server refuses each call that can change the install (Maintenance mode).
  6. Request gate. The gate names the caller of the call (Request gate).
  7. Idempotency. A method with the option (hopbox.v1.idempotent) runs once for each idempotency key (Idempotency keys).
  8. Handler. The handler calls one operation of the service layer. The operation checks the policy first, then its input, then acts.

Reflection and health pass the same steps, except the idempotency step. In place of a service operation, they run the policy check with their own actions (Callers and policy).

Request gate

Section titled “Request gate”

The request gate is the one place where every call proves who calls. It holds a chain of credential resolvers. Each resolver knows one kind of credential. The gate asks each resolver in turn:

  1. A resolver that does not find its kind of credential passes the call to the next resolver.
  2. A resolver that finds its kind of credential, and that credential proves a caller, decides. The call goes on with that caller.
  3. A resolver that finds its kind of credential, but the credential proves no caller, ends the call with unauthenticated and the message the credential is not valid. Examples are an unknown, expired, revoked, or malformed key.
  4. Sometimes a resolver cannot check the credential, for example because the control store does not answer. It then ends the call with unavailable and the message the server failed to check the credential. Retry later. The SDKs retry this call, because its answer carries Hopbox-Not-Run: 1 (Answers of calls that changed nothing).
  5. If no resolver decides and the call has an Authorization header, the gate ends the call with unauthenticated and the message the credential is not valid. A credential that the server cannot check never passes as anonymous.
  6. If no resolver decides and the call has no Authorization header, the caller is anonymous.

The client always gets the fixed messages above. The cause goes only to the log, with the request ID (Logs).

The gate only names the caller. The policy check in the service layer decides what the caller can do.

Listener Resolvers, in order
API listener the session cookie __Host-hopbox_session (Sessions, cookies, and sign-in links), then CLI access tokens, API keys, and admin API keys in the header Authorization: Bearer <credential> (CLI tokens, API keys, admin API keys, and SSH keys)
Admin socket the peer of the socket, which proves the caller local_root (the admin API)
Internal listener the server certificate of the TLS connection, which proves the caller server (the internal listener)

On the internal listener, a step after the gate refuses an anonymous caller on every procedure but /hopbox.cluster.v1.EnrollmentService/Enroll, before the policy check. The call gets unauthenticated with the message this call needs a server certificate. This covers gRPC health and reflection there too. On the other listeners, an anonymous caller reaches every procedure, and the policy decides.

The contract of a resolver

Section titled “The contract of a resolver”

The API listener has a resolver for each credential that hopbox issues: sessions, CLI access tokens, API keys, and admin API keys. Each of the last three reads only the bearer credentials of its own prefix (CLI tokens, API keys, admin API keys, and SSH keys). The resolver of server certificates exists on the internal listener. It reads the certificate of the TLS connection from the context, and ties it to a server of the registry. It refuses an unknown, expired, foreign, or decommissioned certificate with the credential is not valid (the internal listener). A resolver is a Go value with the method Resolve(ctx, credentials) (caller, ok, err) in internal/api. It gets the request headers and the peer, and must keep these rules:

Case It returns
The request does not carry its kind of credential. ok false, no error
The credential proves a caller. the caller, ok true, no error
The credential is of its kind but proves no caller: unknown, expired, revoked, or malformed. an error that wraps api.ErrCredentialRefused. The resolver of the session cookie is the one exception, below.
It cannot check the credential, for example because the control store does not answer. any other error

An error of a resolver goes to the log, so it must never hold a secret, such as the credential itself.

A browser sends a cookie on its own, also long after its session ended. So the resolver of the session cookie treats a cookie that names no live session as no credential. The gate then goes on to the next resolver. The resolver also adds the clear of the cookie to ResponseHeader of the credentials. The response carries the clear, unless the handler sets the cookie itself (Sessions, cookies, and sign-in links). A stale cookie thus never blocks the next sign-in. A live session from a call that fails the check against cross-site requests is refused, as the contract says.

Callers and policy

Section titled “Callers and policy”

Each call has one typed caller. Its kind is also the actor kind of its audit entries (Control store tables).

Kind Caller Proved by
anonymous A caller without a credential. no credential
session A user signed in to the console. The caller also says whether the account is an instance admin. the session cookie (Sessions, cookies, and sign-in links)
cli_token A user through the hopbox CLI. It acts as its account in every org of the account. The caller also says whether the account is an instance admin. a CLI access token (CLI tokens, API keys, admin API keys, and SSH keys)
member_key A member API key, which acts as its account, only in the org of the key. an API key (CLI tokens, API keys, admin API keys, and SSH keys)
org_key An org API key: a service credential of one org, with the rights of a member without personal resources. an API key (CLI tokens, API keys, admin API keys, and SSH keys)
admin_key An admin API key, with install scope. an admin API key (CLI tokens, API keys, admin API keys, and SSH keys)
local_root Root, or the user of hopboxd, on a control server. the peer of the admin socket
server A server of the install, for itself. The caller carries the roles of its certificate, such as node or dns. a server certificate on the internal listener (the internal listener)
control Another control process of the install, for forwarding a data stream. It has no account and no credential ID. It may do only control.forward_stream, besides the actions that every caller may do. the control certificate of its internal listener, which names hopbox://control (the internal listener)
ssh_key An account through the SSH front door. No request of the API carries it. The service layer makes it only to check an SSH connection, for machine.ssh (the SSH front door). It is the actor of the audit entry machine.ssh (the SSH front door). a signature with an SSH key of the account, which the edge server checked

The server.* actions of the control channel and of the edge role have a server as their resource. The policy allows them only to a caller of kind server whose server is that resource. So the certificate of one server never acts for another (the control channel).

Each key-encryption key file lives on one control server, so only root on that server can rotate it, stage it, promote it, list it, or rewrap with it. An admin API key reaches whichever control server answers the call, so it cannot touch a keyring. The first-admin login link is for root on a control server only.

An org_key acts as a member without private machines, and is never an org admin. An instance admin has only the rights of its own roles in the machine.* rules of the public API. A caller that machine.get refuses gets not_found instead of permission_denied, so it learns nothing about the private machines of others (the machine API). For an org, the service layer reads the role of the caller in the org before the check. A caller that is not a member has no role. The check then refuses an org that does not exist in the same way as an org of others. Some changes in an org, such as a role change, lock the org first. They then read the role of the caller again, and run the check again (the org API). A member key has the role of its account, and only in the org of the key. An org key has no role. It has the rights of a member in its own org, without personal resources. So it can read its org with org.get, org.get_usage, and org.member_list. It can also list the shared and all values of the org with var.list. Only people manage keys: no key makes, lists, or deletes an API key or an admin API key. A call without an org_id acts in the org of its API key, or else in the personal org of the caller.

Health and reflection do not call the service layer, so the API runs the policy check for them before their handler.

An admin session is the session of an instance admin whose sign-in is at most 10 minutes old (Sessions, cookies, and sign-in links). The Admin area of the console calls the admin API with it. Every other session is refused on these actions, and so is the cli_token of an instance admin. The admin API lists the calls.

A refused anonymous caller gets unauthenticated with the fixed message this call needs a credential, which names no action. Any other refused caller gets permission_denied, and the message names the caller kind and the action. One case is different. Sometimes the check refuses the session of an instance admin only because its sign-in is too old. The check then returns the error of a recent sign-in instead (Sessions, cookies, and sign-in links). That error has the detail hopbox.v1.RecentSignInRequired, so the console asks the person to sign in again.

Idempotency keys

Section titled “Idempotency keys”

A method with the option (hopbox.v1.idempotent) (API definitions) runs once for each idempotency key. Today these are KeyringService.RotateKEK, ServerService.CreateEnrollmentToken, OrgService.CreateOrg, AdminKeyService.CreateAdminKey, AdminKeyService.RegisterAdminKey, APIKeyService.CreateAPIKey, SSHKeyService.AddSSHKey, and MachineService.CreateMachine. The responses of CreateEnrollmentToken, CreateAdminKey, and CreateAPIKey hold a secret, so the server keeps no copy of them. A replay of these methods fails with already_exists instead of the first response (the admin API).

Header Direction Value
Idempotency-Key request 1 to 255 printable ASCII characters without spaces, for example a UUID. Required on an idempotent method.
Idempotent-Replayed response true on a response that the server replayed from an earlier call. Absent on a first call.

The server handles an idempotent call in these steps:

  1. An anonymous caller gets unauthenticated with the message an idempotent call needs a credential, so that its key belongs to one caller.
  2. A call without the Idempotency-Key header gets invalid_argument.
  3. The server claims the key for the caller in a transaction (Control store tables). The key covers the method and the request body, encoded as deterministic protobuf.
  4. For a new key, the handler runs in the same transaction. Its change, its audit entry, the key, and the response commit together. If the handler fails, nothing commits, and a retry with the same key runs again.
  5. For a known key with the same method and body, the server returns the first response with Idempotent-Replayed: true. The handler does not run.
  6. For a known key with another method or body, the call gets invalid_argument.

Each key belongs to one scope, so two callers never share a key:

Caller Scope of its keys
session, cli_token account:<account ID>. These credentials act as the account, so they share its keys.
member_key member_key:<key ID>. Each script has its own key, so two scripts never replay each other.
org_key org_key:<key ID>
admin_key admin_key:<key ID>
server server:<server ID>. No method of the cluster API has the idempotent option.
local_root local_root, one scope for every local call

The server keeps each key for 24 hours. The leader deletes the expired keys every 10 minutes (hopboxd).

Enum names in JSON

Section titled “Enum names in JSON”

In the JSON codec, an enum value is its full name, such as VAR_SCOPE_PRIVATE. A request with a name that the enum does not know gets invalid_argument, also a name in lowercase, such as private. The handler never runs. The message names the field and lists the values of the enum:

The JSON codec of Connect drops an unknown name, and the field then holds its unspecified value. For some fields, the unspecified value is the default. Examples are the shared scope of SetVar and DeleteVar, the member kind of CreateAPIKey, and the restart policy always of CreateMachine. So without the check, a typo runs the call with a choice that the client did not make. The API listener, the internal listener, and the admin socket all make this check.

The JSON codec still drops an unknown field, so a client with a newer schema keeps working. The unspecified value itself, or an enum number, passes the codec. The service layer takes the unspecified value as the default of the field, or refuses it where the field has no default. It refuses a number that the enum does not know. The binary protobuf codec carries numbers, not names, so it needs no such check.

The check runs in the codec, before the request gate, as for any body that does not decode. So an anonymous call with an unknown name gets invalid_argument, not unauthenticated. The same call with a known name gets unauthenticated. The refusal counts only in hopbox_http_requests_total, as the paragraph “Connect refuses some requests before any interceptor runs” in Errors says.

When a listener stops

Section titled “When a listener stops”

When a listener stops, it lets each running unary call finish. A unary call that still reads its request body gets 2 s more for the read. Then the read fails, so a stalled upload cannot hold the stop. A lifecycle call of a machine that waits for its machine ends its wait at once. It answers with the machine as it is and done false (the machine API). A stream ends at once: the server cancels its context and ends every read of its request body. So a stream that waits for the client, such as a reflection stream, ends too (hopboxd). A shutdown of the HTTP server does not track a connection that a handler took over. So the listener ends each open WebSocket itself, with the close code 1001 and the reason the server shuts down. Connect again. A running tool call of the MCP server ends at once, as a stream does (the MCP server).

Streams and their credential

Section titled “Streams and their credential”

The gate checks the credential of a call once, at its start. A stream can run for hours, so it checks its credential again while it runs. Service.GuardStream of internal/service gives each stream a context. The context ends with the credential:

  • At the expiry of the credential (CLI tokens, API keys, admin API keys, and SSH keys). For a session, that is the end of its lifetime, or 7 days after its last use, whichever comes first (Sessions, cookies, and sign-in links). For a CLI token, it is the end of the newest live access token of its CLI sign-in. So a stream lives on while the CLI refreshes its tokens. For an API key, it is the expiry of the key.
  • At the first check that finds the credential ended. Examples are a sign-out of a session, and the end of a CLI sign-in. The reuse of an old refresh token ends a CLI sign-in too, with its whole family. Others are the revoke of an API key, the leave of the account of a member key from its org, and an expiry. The check runs every 30 s (service.DefaultCredentialRecheck). A check that cannot reach the control store keeps the stream. It logs the check of the credential of a stream failed at level warn with component=service and err, and tries again at the next check.

The stream then ends with unauthenticated and the message the credential of this stream ended. Sign in again: .... WatchMachines, Exec, Upload, Download, StreamMachineLogs, and the WebSocket of exec run under such a guard. A session, a CLI token, a member key, and an org key can hold a stream. Any other kind of caller gets unauthenticated at once.

Maintenance mode

Section titled “Maintenance mode”

Maintenance mode stops every change of the install through the API and the control channels, so that hopboxd admin db export can copy a control store that no longer changes (hopboxd). It is a flag of the install config (Control store tables). Only root on a control server turns it on or off, with SetMaintenance on the admin socket (the admin API). The code is in internal/api/maintenance.go and internal/service/maintenance.go.

In maintenance mode, every listener of the control role refuses each call that can change the control store: the API listener, the admin socket, and the internal listener, also for the requests that the edge servers forward. The maintenance gate sorts each call into one of three kinds:

  • A call of gRPC health or of gRPC reflection (Reflection and health), and SetMaintenance, pass as they are. The policy lets only local_root call SetMaintenance, so the admin socket always takes it. No other write could turn maintenance mode off.
  • A call whose method has the option (hopbox.v1.read_only) (API definitions) runs as a read call. Each write that it makes runs under the maintenance mode of the process, such as its audit entry, or the last use of a machine for its auto-delete timeout. In maintenance mode, the call fails at that write, before the write, with the refusal below. A read call that writes nothing works in maintenance mode.
  • Every other call is refused before the request gate, so it reads no credential and changes nothing.

So these calls work in maintenance mode:

Service Calls
hopbox.v1.InstallService GetInstallInfo
hopbox.v1.AccountService GetAccount, ListSignInMethods, ListCLISignIns
hopbox.v1.AuditService ListAuditEntries
hopbox.v1.APIKeyService ListAPIKeys
hopbox.v1.MachineService GetMachine, ListMachines, ListMachineSizes, WatchMachines
hopbox.v1.OrgService GetOrg, ListOrgs, GetOrgUsage, ListOrgMembers, ListInvitations
hopbox.v1.SSHKeyService ListSSHKeys
hopbox.v1.VarService ListVars
hopbox.admin.v1.InstallConfigService SetMaintenance
gRPC health and reflection every call

Each other call is refused, also these reads: every read of the admin API, such as GetInstallConfig and ListServers, because it writes its audit entry (the admin API), and Download and StreamMachineLogs, because each records a use of its machine. Their node channels are closed in maintenance mode anyway. The audit log thus never loses an access that it would have recorded.

Each refusal changes nothing. It has the code unavailable, the message the install is in maintenance mode, so it takes only reads. Retry later, and the headers Hopbox-Not-Run: 1 and Retry-After: 30:

The plain HTTP routes that can change the install answer HTTP 503 with the same headers and message: the sign-in with GitHub and Google at /auth/<provider>/start and /auth/<provider>/callback (Sign-in with GitHub and Google), the sign-in of private machine URLs at /auth/machine (the edge role), and the WebSocket endpoint /api/ws/exec. The console, health, and the MCP endpoint keep serving. Each tool of the MCP server calls the API, so it gets the refusal of its call.

The last use of a session, an API key, an admin API key, or a CLI token is a write of the request gate too, but a lost time of a last use is harmless. So in maintenance mode, the request gate skips that write, and the call goes on (CLI tokens, API keys, admin API keys, and SSH keys).

A read call can run while maintenance mode turns on. Each of its writes either ends before SetMaintenance returns, or is refused before it changes anything. So no write of a read call comes after the turn to on either. A stream such as Download that runs at the turn ends at its next record of the use of its machine.

When maintenance mode turns on, the control process ends each call without the option (hopbox.v1.read_only) that still runs: the unary calls, the streams such as Exec, and the control channels of the servers (the control channel). A call that maintenance mode ended gets unavailable with the message the install went into maintenance mode, which ended this call. Retry later, and no Hopbox-Not-Run header, because it can have changed something before its end. The leader also pauses its jobs (hopboxd). A turn to on with SetMaintenance succeeds only after each of these ended in every live control process of the install while maintenance mode stayed on, so no change of the API or of a server comes after it. The other control processes report this in their rows of control_processes (the admin API). The call gives up with unavailable after at most 30 s, the deadline of the call, and maintenance mode stays on. If maintenance mode turns off during the wait, for example by a second root on the socket, the turn to on fails with unavailable: unavailable: maintenance mode turned off while it waited for the calls, control channels, and leader jobs to end, because the work runs again. hopboxd admin db export also reads the flag in the snapshot of its dump, and refuses a store out of maintenance mode.

The request gate checks a server certificate on the internal listener, also for health and reflection. The first use of a certificate, which retires the other certificates of its server, and the alarm of a retired certificate write to the store. In maintenance mode, the gate refuses such a call with the refusal above, before the write (Enrollment and the install PKI).

When maintenance mode turns off, the listeners take every call again, the servers dial their control channels again, and the leader runs its jobs again. Each control process reads the flag at its start, and again at each change event install.maintenance_changed (Control store tables). So a control process that starts on a store in maintenance mode, such as a copy of hopboxd admin db export, starts in maintenance mode too.

Reflection and health

Section titled “Reflection and health”

gRPC server reflection is on, so grpcurl can list and call the services. The server serves the reflection services grpc.reflection.v1.ServerReflection and grpc.reflection.v1alpha.ServerReflection. They list the services of their listener.

The health service is grpc.health.v1.Health, with the methods Check and Watch. A check can name the whole server, with an empty service name, or one service of the listener. It returns SERVING while the control store answers a ping within 2 s, and NOT_SERVING otherwise. A check of an unknown service gets not_found. Watch sends the status at once. Then it checks again every 5 s, and sends the status each time that it changes. Each listener serves at most 64 open Watch calls. One more gets resource_exhausted.

Field Type Description
domain string The domain of the install, for example example.com. It is empty until an instance admin sets it with UpdateInstallConfig (the admin API).
sign_in_methods repeated SignInMethod The sign-in methods that anyone can use on the install (the sign-in, account, and audit API). SIGN_IN_METHOD_EMAIL_LINK is in the list while the install has an SMTP config (SMTP config) or the file mail transport (Mail). SIGN_IN_METHOD_GITHUB and SIGN_IN_METHOD_GOOGLE are in it while the install has a domain and the client of the provider (Sign-in with GitHub and Google). The first-admin login link is never in it, because only root can make one.
ssh_host_key string The public host key of the SSH front door, in the authorized_keys format, for example ssh-ed25519 AAAA.... The edge servers show it on every SSH port (the SSH front door). It is empty until a control process made the keys of the front door, which needs a key-encryption key.
version string The version of hopboxd on the server that answered, for example v0.1.0 (the version command).
mail_to_files bool true on a dev or test install with the file mail transport (Mail). Then no magic link or invitation reaches its recipient by email. The console uses it to tell the person to ask the operator for the link.

In the JSON codec, a field with its default value is left out, so an empty domain does not appear.

Logs

Section titled “Logs”

The API writes these records with component=api. The access log record covers every call, also refused ones.

Message Level Fields
api call info procedure, protocol, peer, caller, code, duration, and request_id. protocol is connect, grpc, grpcweb, or websocket for the WebSocket endpoint of exec. peer is the address of the client, empty on the admin socket. code is ok or the error code. caller is the caller kind, or unresolved after the gate refused the credential. A call of a tool of the MCP server also has mcp_request_id, the request ID of its MCP request (the MCP server).
api call failed error procedure, err, request_id. For an internal error.
api call failed warn procedure, err, request_id. For a Connect error from a library, which keeps its code.
api call stopped info procedure, err, request_id. For deadline_exceeded and canceled.
api credential refused info err, request_id. A resolver refused a credential.
api credential check failed error err, request_id. A resolver failed to check a credential.
machine URL sign-in failed error err, request_id. GET /auth/machine failed with 500 (the edge role).
websocket upgrade failed info path, err, request_id. The upgrade of a request to the WebSocket endpoint /api/ws/exec failed (the machine API).

The HTTP server writes its own errors, such as a protocol error of a client, at level warn with component=http.
