# Try hopbox

> How to try hopbox on the preview install: sign in, create a machine, open a shell, and open its URL. Also the words of these docs.

This guide makes your first machine on the preview install of hopbox. Its address is <https://dev.hopbox.dev>. You sign in, create a machine, open a shell in it, and open its URL. You need only a browser, and a GitHub account or an email address. The steps take about five minutes.

The preview install is for tests. Its data can go at any time before version 1.0, so keep no work there that you cannot lose.

## Sign in

1. Open <https://dev.hopbox.dev> in a browser.
2. Click “Sign in with GitHub”, and approve the request on GitHub. Or type your email in “Email”, and click “Email me a sign-in link”. Open the link in the email. It works once, for 15 minutes.

The first sign-in creates your account and its personal org, “Personal”. An org holds machines, and a personal org has only you as its member. The console then opens the page “Machines” of that org. Next to the name of the org, the word `live` tells you that the list follows the install as it changes.

The line under the title shows the usage and the limits of the org. By default, an org can hold 3 machines, 6 vCPUs, 24 GiB of RAM, and 300 GB of disk. The operator of the install can change the limits of an org.

## Create a machine

1. Click “New machine”.
2. Leave the name empty for a free name, or type a name of your own.
3. Keep the size `default`: 2 vCPUs, 8 GiB of RAM, and a 100 GB disk.
4. Click “Create”.

A machine name is unique on the install, because it is also the first part of the machine URL. If another account holds the name that you typed, the dialog says so and offers a free name, such as “Use box2”. Click it, then click “Create”. This guide calls the machine `box1`. Use the name of your own machine in its place.

The state of the machine goes from `pending` to `starting` to `running`, without a reload of the page. If the node did not run the image before, the create takes about 25 seconds, because the node unpacks the image first.

## Open a shell

1. Click the name of the machine. The page of the machine shows its actions, its URL, its sharing, and its details.
2. Click “Open terminal”. The web terminal opens the login shell of the user `user` in the machine.
3. Type `uname -a`, and press Enter. The machine prints its Linux kernel.

The machine runs Ubuntu. `user` has `sudo` without a password. The files that you make stay on the disk of the machine, also after a stop and a start.

## Open the URL of the machine

Each machine gets an HTTPS URL, such as `https://box1.dev.hopbox.dev`. The URL reaches port 8000 in the machine. The default image has nginx on that port, but nginx is off at first. Turn it on in the terminal:

```sh
sudo systemctl enable --now nginx
```

Go back to the page of the machine, and click the URL in the section “URL”. The page of nginx opens.

The URL is private at first. Only a signed-in account that can use the machine opens it. Your browser has your session, so the URL opens for you. To let anyone open it without an account, turn on the switch “Public URL”. Turn the switch off to make the URL private again.

To serve another port, type it in the field “Port” of the section “URL”, and click “Set port”.

## Connect over SSH

The SSH front door of the install takes `ssh`, `scp`, `rsync`, and port forwards. It finds your account by your SSH key.

1. Click your name at the top right to open the page “Account”.
2. In the section “SSH keys”, paste your public key, such as the text of `~/.ssh/id_ed25519.pub`, into “Public key”.
3. Click “Add SSH key”.
4. On the page of the machine, read the “SSH port” in the section “Details”, such as `10001`.

Then connect from a terminal on your computer. Use your own port:

```sh
ssh -p 10001 user@dev.hopbox.dev
```

At the first connection, ssh asks whether you trust the host key of the install, and shows its fingerprint. The API of the install gives the same key in the field `sshHostKey` of `GetInstallInfo`. Print its fingerprint in a second terminal. The command needs `jq`:

```sh
curl -s -X POST -H 'Content-Type: application/json' -d '{}' \
  https://dev.hopbox.dev/hopbox.v1.InstallService/GetInstallInfo | jq -r .sshHostKey | ssh-keygen -lf -
```

If the `SHA256:` fingerprint matches the fingerprint that ssh shows, type `yes`. The hopbox CLI writes the host key and an alias such as `box1.hop` for you ([Install the hopbox CLI](/guide/install-cli/)). After `hopbox login` and `hopbox list`, `ssh box1.hop` works without the port. [Reach a machine over SSH](/guide/ssh/) shows `scp`, `rsync`, and port forwards.

## Stop, start, and delete the machine

On the page of the machine:

1. Click “Stop”. The machine shuts down, and its disk stays. A stopped machine holds no vCPUs and no RAM of the org.
2. Click “Start”. The machine boots with the same disk.
3. Click “Delete”, then “Delete” in the dialog. The machine and its disk go. Its name and its SSH port stay reserved for your org for 7 days.

“Sign out” at the top right ends the session in this browser.

## What the preview does not offer yet

* The hopbox CLI has no public download yet. [Install the hopbox CLI](/guide/install-cli/) gives the steps for the day it does. Until then, use the console.

## Words in these docs

* Install: one running copy of hopbox, with its own domain, such as `dev.hopbox.dev`.
* Org: a group of accounts that owns machines and other resources.
* Machine: a persistent Linux computer that hopbox runs as a microVM on a node.
* Node: a server of the install that runs machines.
* Size: the number of vCPUs, the RAM, and the disk of a machine.
* Image: the base disk that a new machine starts from.
* CLI token: the credential of the hopbox CLI. The CLI gets it after you approve its sign-in in the console.
* API key: a credential for scripts, which works in one org.
* Machine URL: the HTTPS URL of a machine, such as `box1.dev.hopbox.dev`.
* SSH front door: the SSH endpoint of the install, which passes your SSH connection to a machine.

# Install the hopbox CLI

> How to download the hopbox CLI, check it, put it on the PATH, and sign it in to an install.

The hopbox CLI makes and uses machines from a terminal. This guide downloads the CLI, checks the download, puts it on your `PATH`, and signs it in to an install. [Use the hopbox CLI](/guide/cli/) then shows each kind of command.

The download link of the CLI is not public yet, so `<cli-download-url>` below stands for it. Until the link is public, use the console of your install ([Try hopbox](/guide/quickstart/)).

## What you need

* A Mac with Apple Silicon, or a Linux computer on x86_64 or arm64. On Windows, use the Linux build in WSL.
* An account on an install, and a browser where you are signed in to its console. The preview install is at <https://dev.hopbox.dev>. This guide uses the install `https://example.com`.

## Download the CLI

Each release has one file of the CLI for each platform, and the file `SHA256SUMS` with the sha256 of each file:

| Platform               | File                                    |
| ---------------------- | --------------------------------------- |
| macOS on Apple Silicon | `hopbox-cli-v0.1.0-darwin-arm64.tar.gz` |
| Linux on x86_64        | `hopbox-cli-v0.1.0-linux-amd64.tar.gz`  |
| Linux on arm64         | `hopbox-cli-v0.1.0-linux-arm64.tar.gz`  |

Download the file of your platform and the sums. On a Mac:

```sh
curl -fLO <cli-download-url>/hopbox-cli-v0.1.0-darwin-arm64.tar.gz
curl -fLO <cli-download-url>/SHA256SUMS
```

## Check the download

Compare the sha256 of the file with its line in `SHA256SUMS`:

```sh
grep hopbox-cli-v0.1.0-darwin-arm64.tar.gz SHA256SUMS | shasum -a 256 -c
```

```text
hopbox-cli-v0.1.0-darwin-arm64.tar.gz: OK
```

On Linux, use `sha256sum -c` in place of `shasum -a 256 -c`. If the command prints `FAILED`, delete the file and download it again. Do not run a file that fails the check.

## Put the CLI on your PATH

The file holds one program, `hopbox`. Unpack it, and copy it to a dir of your `PATH`:

```sh
tar -xzf hopbox-cli-v0.1.0-darwin-arm64.tar.gz
sudo install -m 0755 hopbox /usr/local/bin/hopbox
hopbox version
```

```text
hopbox v0.1.0 (commit 1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b, built 2026-10-16T09:00:00Z, go1.27.1 darwin/arm64)
```

Without `sudo`, copy the program to a dir of your own, such as `~/.local/bin`, and add that dir to your `PATH`.

## Sign in to an install

Give the CLI the URL of the install. A bare domain gets `https://`:

```sh
hopbox login --url https://example.com
```

The CLI prints a code and a link, then waits:

```text
To sign in, open this page in a browser and approve the code KWJQ-LBZV:


  https://example.com/device?code=KWJQ-LBZV


Waiting for the approval. Press Ctrl-C to stop.
```

1. Open the link in the browser where you are signed in to the console.
2. Check that the code on the page matches the code in your terminal.
3. Check the client: it is `hopbox CLI on` and the name of your computer. Approve only a sign-in that you started yourself.
4. Click “Approve”.

The approval needs a sign-in to the console within the last 10 minutes. After an older sign-in, the page says so after your click on “Approve”, and shows “Sign in again”. Click it, and sign in. The console then shows the same code. Click “Approve” again.

The CLI sees the approval within a few seconds:

```text
Signed in to https://example.com as user1@example.org. The profile default is active.
Added the SSH key ~/.ssh/hopbox_ed25519 (SHA256:rkEGrocWsFODhePtstCZFcyj1D0BUmGYu1rexwam/mo) to your account.
```

The code works for 10 minutes. After that time, run `hopbox login` again.

The login also prepares `~/.ssh` for the SSH front door. If your account had no SSH key, the CLI made the key `~/.ssh/hopbox_ed25519` and added it to your account. It also wrote the host key of the install to `~/.ssh/known_hosts`. `--no-ssh-config` leaves `~/.ssh` alone ([hopbox CLI](/reference/cli/#ssh-files)).

Check who you are:

```sh
hopbox whoami
```

```text
profile  default
url      https://example.com
account  01a14a7c-813f-7a14-b6bc-44a4e57ac6ff
name     user1
emails   user1@example.org
org      Personal (01a14a7c-813f-7a1c-946b-db123b23c342)
role     owner
```

# Use the hopbox CLI

> How to sign the hopbox CLI in, work in an org, make API keys and SSH keys, script it with JSON, keep the sign-in alive, use a second install, and sign out.

The hopbox CLI signs in to an install with your browser. Then it manages your machines, orgs, API keys, and SSH keys. This guide runs each kind of command once against the install `https://example.com`. [Use machines from the CLI](/guide/cli-machines/) covers the machines. [hopbox CLI](/reference/cli/) lists every command, flag, file, and exit status.

## What you need

* The hopbox CLI, installed and signed in to an install, as in [Install the hopbox CLI](/guide/install-cli/).
* `python3`, for one of the examples.

## Sign in

`hopbox login` signs in with a device flow. The CLI prints a code and a link. You open the link in a browser where you are signed in to the console, check the code, and click “Approve” ([Install the hopbox CLI](/guide/install-cli/#sign-in-to-an-install)):

```sh
hopbox login --url https://example.com
```

The approval needs a sign-in to the console within the last 10 minutes. After an older sign-in, the page asks you to sign in again, then shows the code again.

The CLI keeps its tokens in `~/.config/hopbox/credentials.toml`, mode 0600, and the URL of the install in `~/.config/hopbox/config.toml` ([hopbox CLI](/reference/cli/#files)). Ask who you are:

```sh
hopbox whoami
```

```text
profile  default
url      https://example.com
account  01a14a7c-813f-7a14-b6bc-44a4e57ac6ff
name     user1
emails   user1@example.org
org      Personal (01a14a7c-813f-7a1c-946b-db123b23c342)
role     owner
```

## Work in an org

Each command acts in one org. Until you pick one, that is your personal org. Make an org for a team, and make it the active org of the profile:

```sh
hopbox org create org1 --use
hopbox org list
```

```text
id         01a14a7c-be1e-74cc-9748-ff40254c5d55
name       org1
role       owner
personal   no
active     yes
suspended  no
created    2026-10-17T15:30:51Z
   ID                                    NAME      ROLE   PERSONAL  SUSPENDED
   01a14a7c-813f-7a1c-946b-db123b23c342  Personal  owner  yes       no
*  01a14a7c-be1e-74cc-9748-ff40254c5d55  org1      owner  no        no
```

The star marks the active org. Commands now act in `org1`. One command can act in another org with `--org`, by name or UUID, such as `hopbox --org Personal org usage`. See what the org uses, and invite a colleague:

```sh
hopbox org usage
hopbox org invite user2@example.org --role admin
```

```text
RESOURCE  USED   LIMIT
machines  0      3
vcpus     0      6
memory    0 GiB  24 GiB
disk      0 GB   300 GB
https://example.com/invite#token=<token>
The link invites user2@example.org as admin until 2026-10-24T15:30:51Z. It is a secret until then. The install sent no email, so pass the link on yourself.
```

With an SMTP config, the install also emails the link. The colleague signs in, and joins with `hopbox org join '<link>'`, or opens the link in a browser. Their account must hold the email of the invitation as a verified email. Then `hopbox org member list` shows them, and `hopbox org member set-role user2@example.org member` changes their role. [Work in a team org](/guide/orgs/) covers the roles.

## Make an API key for a script

A script uses an API key, not your CLI sign-in. A member key acts as you in the active org:

```sh
KEY=$(hopbox api-key create ci --expires 30d)
hopbox api-key list
```

```text
The member key 01a14a7c-beb0-7c35-a4c4-5c81288a9055 (ci) works until 2026-11-16T15:30:51Z. This is its only copy.
ID                                    NAME  KIND    EXPIRES               LAST USED
01a14a7c-beb0-7c35-a4c4-5c81288a9055  ci    member  2026-11-16T15:30:51Z  never
```

The secret went to `$KEY`, and the note went to stderr. The install keeps only a hash of the key, so this is its only copy. Give the key to the CLI of the script in `HOPBOX_API_KEY`, and the URL of its install in `HOPBOX_URL`. The CLI never sends a key to the URL of a profile, because a profile can name another install:

```sh
HOPBOX_API_KEY=$KEY HOPBOX_URL=https://example.com hopbox whoami
HOPBOX_API_KEY=$KEY HOPBOX_URL=https://example.com hopbox api-key create child; echo "status $?"
```

```text
profile  default
url      https://example.com
account  01a14a7c-813f-7a14-b6bc-44a4e57ac6ff
name     user1
emails   user1@example.org
org      org1 (01a14a7c-be1e-74cc-9748-ff40254c5d55)
role     owner
hopbox: permission_denied: permission denied: a caller of kind member_key may not do api_key.create
status 3
```

The key works in its own org, `org1`. No key can make another key, and the status 3 tells a script that the install refused the call. After the last run of the script, revoke the key with `hopbox api-key revoke <id>`.

An org admin or an org owner also makes org keys, with `--kind org`. An org key is a credential of the org, not of a person. So if its creator leaves the org, the key stays. [CLI tokens, API keys, admin API keys, and SSH keys](/reference/credentials/#api-keys) gives the rights of each kind.

## Add an SSH key

The SSH front door finds your account by your SSH key ([Reach a machine over SSH](/guide/ssh/)). The login added `~/.ssh/hopbox_ed25519`. To use another key too, add its public key, never the private key:

```sh
hopbox ssh-key add ~/.ssh/id_ed25519.pub
```

```text
id           01a14a7c-e079-7778-9819-39ade2a33482
name         user1@laptop
type         ssh-ed25519 256
fingerprint  SHA256:DRdf39Nvm+zAXRzjpCOtwde9E/UUaXIbgz0+g1NA+10
```

The comment of the key became its name. RSA keys need at least 3072 bits, so Ed25519 is the simple choice. A key works for one account only, so the same key on another account fails with `already_exists`. `hopbox ssh-key add ~/.ssh/id_ed25519` fails with `this is a private key. Give the public key, the .pub file`, and status 80.

## Use the output in a script

Each command prints JSON with `--json`. An error then goes to stderr as JSON too:

```sh
hopbox org list --json | python3 -c 'import json,sys; print([o["name"] for o in json.load(sys.stdin)])'
hopbox --profile nope whoami --json; echo "status $?"
```

```text
['Personal', 'org1']
{"error":{"code":"signed_out","message":"not signed in: the profile nope has no install. Run hopbox login --url <URL>"}}
status 2
```

Status 2 always means that the profile has no live sign-in. [hopbox CLI](/reference/cli/#exit-status) lists each status.

## Keep the sign-in alive

The access token lives 1 hour, and the refresh token lives 30 days. The CLI trades them for new ones by itself. With `--debug`, each refresh writes the log line `refreshed the CLI tokens` to stderr.

A refresh token works once. A used one that comes back ends the whole sign-in, because the install takes it for a stolen copy. So the CLI refreshes under a lock of its config dir. Many commands at once, in many terminals, make one refresh, and the others read the new tokens. [CLI tokens, API keys, admin API keys, and SSH keys](/reference/credentials/#cli-tokens) gives the rules.

## Sign in to a second install

A profile holds one install. To use a second install, such as the install `hop.example.com` of your company, sign in with another profile:

```sh
hopbox --profile work login --url hop.example.com
```

A login makes its profile active. List the profiles, and switch back:

```sh
hopbox profile list
hopbox profile use default
```

```text
   PROFILE  URL                      SIGNED IN  ORG
   default  https://example.com      yes        01a14a7c-be1e-74cc-9748-ff40254c5d55
*  work     https://hop.example.com  yes        -
The active profile is now default.
```

`HOPBOX_PROFILE=work` picks a profile for one shell, and `--profile work` for one command.

## Sign out

```sh
hopbox logout
hopbox whoami; echo "status $?"
```

```text
Signed out the profile default.
hopbox: not signed in: the profile default has no CLI sign-in. Run hopbox login
status 2
```

`logout` ended the CLI sign-in on the install too, so a copy of its tokens does not work anymore. The profile keeps its URL and its active org, so `hopbox login` alone signs in again.

If you lose a laptop, end its sign-in from another device. Open the page “Account” of the console. The section “CLI sign-ins” lists each sign-in with the name of its client and its last use. Click “End” on the row of the lost laptop.

# Use machines from the CLI

> How to make and use a machine with the hopbox CLI: commands, files, the log, a shell, and the SSH alias.

This guide makes a machine with the hopbox CLI, works in it, and deletes it. It runs a command, copies files, reads the log, opens a shell, and reaches the machine by its SSH alias. [hopbox CLI](/reference/cli/#machines-in-commands) lists every command, flag, and exit status.

Each machine is a Firecracker microVM on a node of the install. It gets an address on the network of its node ([Check the network of a machine](/guide/node-network/)). `exec`, `cp`, `logs`, and `connect` reach the machine through the API. The SSH alias and the URL of a machine reach it through the edge servers of the install.

## What you need

* An account on an install with machines, such as the preview install of [Try hopbox](/guide/quickstart/). This guide uses the install `https://example.com`.
* The hopbox CLI, signed in to that install, as in [Install the hopbox CLI](/guide/install-cli/).

## What the login did

`hopbox login` prepared `~/.ssh` for the SSH front door. If your account had no SSH key, the login made one and added it:

```text
Signed in to https://example.com as user1@example.org. The profile default is active.
Added the SSH key ~/.ssh/hopbox_ed25519 (SHA256:rkEGrocWsFODhePtstCZFcyj1D0BUmGYu1rexwam/mo) to your account.
```

An account that has a key keeps its keys as they are. Then add your own key with `hopbox ssh-key add ~/.ssh/id_ed25519.pub`.

## Make a machine

```sh
hopbox new box1
```

The CLI makes the machine, and waits until it runs. Then it prints the machine:

```text
id             01a15e16-fe58-74f1-a778-d1350c527612
name           box1
org            01a14a7c-813f-7a1c-946b-db123b23c342
state          running
size           default (2 vCPU, 8 GiB RAM, 100 GB disk)
image          default (sha256:0f3c...)
shared         no
url            https://box1.example.com (private, port 8000)
ssh            ssh box1.hop (port 10001)
restart        always
start command  -
auto-delete    off
last used      2026-10-21T10:52:07Z
created        2026-10-21T10:52:07Z
```

The first machine of an image on a node takes about 25 s, because the node unpacks the image first. To get the new machine at once, give `--wait 0`. If the machine does not run within 5 minutes, the command fails with status 6. The machine stays in both cases.

A name that another machine holds fails with status 5. The install then names a free name:

```text
hopbox: already_exists: already exists: the machine name "box1" is taken. A free name is "box2"
```

List the machines of the org:

```sh
hopbox list
```

```text
NAME  STATE    SIZE     SHARED  URL                       SSH
box1  running  default  no      https://box1.example.com  box1.hop
```

## Look at the SSH alias

The CLI added the machine to a managed block at the top of `~/.ssh/config`. Your own lines stay below it, as they were:

```sh
sed -n '/# BEGIN hopbox/,/# END hopbox/p' ~/.ssh/config
```

```text
# BEGIN hopbox
# The hopbox CLI writes this block at each create, rename, and delete of a machine. Edits inside it are lost.
Host box1.hop
  # hopbox machine=01a15e16-fe58-74f1-a778-d1350c527612 org=01a14a7c-813f-7a1c-946b-db123b23c342
  HostName example.com
  Port 10001
  User user
  IdentityFile ~/.ssh/hopbox_ed25519
  IdentitiesOnly yes
  HostKeyAlias hopbox-example.com
Host *
# END hopbox
```

With this entry, `ssh box1.hop`, `scp`, `rsync`, and VS Code Remote-SSH reach the machine through the SSH front door ([Reach a machine over SSH](/guide/ssh/)). The login also puts the host key of the install into `~/.ssh/known_hosts`, so the first connection asks no question. An install without a key-encryption key has no host key, and `known_hosts` then gets no line.

A rename moves the entry, and a delete removes it. `hopbox list` also adds the machines that the console made, and removes the machines that are gone. Give `--no-ssh-config` to a command that must leave `~/.ssh` alone, such as a command of a CI job.

## Run commands

```sh
hopbox exec box1 uname -sr
hopbox exec box1 -e GREETING=hello -- sh -c 'echo $GREETING from $(hostname)'
```

```text
Linux 6.1.167
hello from box1
```

Each word after the machine belongs to the command, flags too. The exit code of the command is the exit status of the CLI:

```sh
hopbox exec box1 sh -c 'echo out; echo err >&2; exit 3'; echo "status $?"
```

```text
out
err
status 3
```

For a script, `--json` keeps stdout and stderr apart in one object:

```sh
hopbox exec --json box1 sh -c 'echo out; echo err >&2; exit 3'
```

```json
{"exit_code":3,"signal":"","error":"","timed_out":false,"stdout":"out\n","stderr":"err\n","stdout_truncated":false,"stderr_truncated":false}
```

The input of the CLI goes to the command:

```sh
printf 'b\na\n' | hopbox exec box1 sort
```

```text
a
b
```

A Ctrl-C goes to the command as SIGINT. A second Ctrl-C ends the exec, and the machine then ends the command. `--timeout 30s` ends a command after 30 seconds, with the exit code 124.

## Copy files

Copy a file into the machine, and read it back:

```sh
echo 'hello' > notes.txt
hopbox cp notes.txt box1:
hopbox cp box1:notes.txt -
```

```text
hello
```

A target that ends with `/`, or an empty one, takes the name of the source. Copy a directory with `-r`. Its contents go into the target directory:

```sh
mkdir -p site && echo '<h1>hi</h1>' > site/index.html
hopbox cp -r site box1:site
hopbox cp -r box1:site ./site-copy
ls site-copy
```

```text
index.html
```

A copy to the laptop has at most 4 MiB. A larger one fails with status 1, and leaves no file behind.

## Serve the URL

Run a web server as the start command, on the port of the URL:

```sh
hopbox machine update box1 --start-command 'python3 -m http.server 3000'
hopbox url port box1 3000
hopbox machine reboot box1
```

```text
https://box1.example.com (private, port 3000)
Rebooted the machine box1 in 4.812s.
```

The start command writes its output to the log of the machine. Read it, and keep it open with `-f` until Ctrl-C:

```sh
hopbox logs -f box1
```

```text
Serving HTTP on 0.0.0.0 port 3000 (http://0.0.0.0:3000/) ...
```

The URL is private: only signed-in accounts with access to the machine open it. The edge servers of the install serve it ([Run the edge role and open machine URLs](/guide/machine-urls/#open-the-url-of-a-machine)). Make it public:

```sh
hopbox url public box1
```

```text
https://box1.example.com (public, port 3000)
```

## Open a shell

```sh
hopbox connect box1
```

`connect` opens the login shell of `user` through the API on port 443. It needs no SSH key. The terminal is in raw mode until the shell ends, so Ctrl-C and Ctrl-Z go to the shell. A resize of the window reaches the shell too. Type `exit` to leave. The CLI then exits with the status of the shell.

## Set env vars

A personal org has no shared machines, so its values are `private` or `all`:

```sh
hopbox env set GREETING=hello --scope private
printf 's3cret' | hopbox env set API_TOKEN --secret --scope all
hopbox env list
```

```text
Set the env var GREETING in the scope private.
Set the secret API_TOKEN in the scope all.
NAME       SCOPE    SECRET  VALUE     UPDATED
API_TOKEN  all      yes     (secret)  2026-10-21T11:02:40Z
GREETING   private  no      hello     2026-10-21T11:02:39Z
```

The value of a secret comes from stdin, so it stays out of the shell history. The machine gets the values at its next boot and in each new login shell.

## Stop and start the machine

A stop shuts the guest down. The disk of the machine stays, with your files:

```sh
hopbox machine stop box1
hopbox list
hopbox machine start box1
hopbox cp box1:notes.txt -
```

```text
Stopped the machine box1 in 512ms.
NAME  STATE    SIZE     SHARED  URL                       SSH
box1  stopped  default  no      https://box1.example.com  box1.hop
Started the machine box1 in 1.204s.
hello
```

A stopped machine holds no vCPUs and no RAM of the org. So the start first checks the limits of the org and the room on the node. Each command waits for the machine for up to 60 s. If the machine does not get there in that time, the command fails with status 6, and the machine keeps its target ([hopbox CLI](/reference/cli/#machine-start)).

## Delete the machine

```sh
hopbox machine delete box1
```

```text
Delete the machine box1 and its disk? Its name stays reserved for 7 days. [y/N] y
Deleted the machine box1 in 2.104s.
```

A script has no terminal for the question, so it adds `--yes`. The CLI removed the entry of `box1` from `~/.ssh/config`. It was the last machine, so the block and its markers are gone, and the file holds only your own lines again.

# Work in the prompt of the CLI

> How to work in the prompt of the hopbox CLI: Tab completion of commands and live machine names, quotes, a shell, Ctrl-C, the history, and profiles.

This guide opens the prompt of the hopbox CLI and works in it. The prompt runs one command after another, and the Tab key completes commands, flags, and machine names. [hopbox CLI](/reference/cli/#the-prompt) lists every key, rule, and exit status of the prompt.

## What you need

* The CLI, signed in to an install, as in [Use the hopbox CLI](/guide/cli/).
* A terminal. The prompt does not open in a script, in a pipe, or with `--json`.
* For the machine names, an install with a node, as in [Use machines from the CLI](/guide/cli-machines/). Without a node, the prompt still runs every command, and Tab completes the commands and the flags.

## Open the prompt

Run `hopbox` without a command:

```sh
hopbox
```

The prompt shows:

```text
hopbox>
```

Type a command without the word `hopbox`, and press Enter:

```text
hopbox> list
NAME  STATE    SIZE     SHARED  URL                       SSH
box1  running  default  no      https://box1.example.com  box1.hop
hopbox>
```

Each line runs as the same command does in a shell. The output, the errors, and the effects are the same. A line that starts with `hopbox` also works, so you can paste a command from a shell or from these docs.

## Complete with Tab

Type the start of a command, and press Tab:

```text
hopbox> mach<Tab>
hopbox> machine
```

If many words fit, Tab shows them all:

```text
hopbox> machine s<Tab>
show     start    stop     share    sizes
```

Press Tab again to move through the list, and Enter to take a word.

After a command that names a machine, Tab completes the names of the machines of the org:

```text
hopbox> connect b<Tab>
hopbox> connect box1
```

The names are live. In a second terminal, make a machine:

```sh
hopbox new box2
```

Back in the prompt, `connect box2` completes at once, with no new start of the prompt. For `cp`, Tab adds a `:` after the name, as in `box1:`, so you can type the path in the machine next.

A word that starts with `-` completes the flags. For a flag with a fixed set of values, the values complete too:

```text
hopbox> new box3 --restart <Tab>
always   never
```

## Use quotes as in a shell

The prompt splits a line into words as a shell does. Quotes keep a space in a word:

```text
hopbox> exec box1 -- sh -c 'echo "hello from $(hostname)"'
hello from box1
```

The prompt does no expansion other than `~` for your home dir. In the line above, the shell in the machine expands `$(hostname)`, not the prompt.

## Open a shell, then come back

`connect` opens a shell in the machine, as in a shell on your laptop:

```text
hopbox> connect box1
user@box1:~$ exit
hopbox>
```

The shell gets every key until it ends. Then the prompt gets the keys again.

## Stop a command

A Ctrl-C stops the command that runs, and the prompt stays open:

```text
hopbox> logs -f box1
hello
^Chopbox: canceled: context canceled
hopbox>
```

At the prompt itself, Ctrl-C drops the line that you typed, and nothing runs.

## Find an earlier line

Up and Down move through the lines that you ran. Ctrl-R searches them: press Ctrl-R, type a part of the line, and press Enter to run the line that it found. The prompt keeps the last 1000 lines in `~/.config/hopbox/history`, so they are there the next time too.

The history leaves out a line that can hold a secret, such as `env set TOKEN=value` and `org join`. To keep any other line out, start it with a space. To set a secret, leave the value out, and type it at the question, where it does not show on the screen:

```text
hopbox> env set TOKEN --secret --scope private
Value of TOKEN:
Set the secret TOKEN in the scope private.
```

## Use another profile

Global flags before no command apply to each line of the prompt. The prompt names a profile other than `default`:

```sh
hopbox --profile dev
```

```text
hopbox (dev)> whoami
```

`hopbox profile use` and `hopbox org use` in the prompt change the profile and the org of the next lines, as in a shell. The machine names then come from the new org.

## Close the prompt

Type `exit` or `quit`, or press Ctrl-D on an empty line. The CLI exits with status 0, and the terminal is as it was before.

# Get the wildcard certificate of an install

> How to get the wildcard certificate of an install, first from the test CA Pebble on a Mac, then from Let's Encrypt on a server.

This guide gets the certificate of an install for its domain and for every machine name, such as `example.com` and `*.example.com`. First it runs the whole flow on a Mac against Pebble, a test CA of Let’s Encrypt. Then it gets a real certificate from Let’s Encrypt on a server.

[The certificate of the install](/reference/acme/) covers the ACME config, the job, and the backoff in full.

The release files of hopbox are not public yet. The hopbox team gives them on request.

## How the certificate gets issued

ACME is the protocol that a CA uses to issue certificates automatically. The CA issues a wildcard certificate only after a DNS-01 challenge: the CA gives a value, and the install puts it in a TXT record at `_acme-challenge.<domain>`. The DNS role of the install serves that record ([Serve the domain of an install with the DNS role](/guide/dns-role/)).

The leader of the control role runs the ACME job. The job adds the TXT records to the zone, waits until each name server serves them, and then asks the CA to check them. It stores the certificate and its key, sealed, in the control store. After two thirds of the lifetime of the certificate, it renews it.

The job asks for no certificate until an instance admin agrees to the terms of the CA.

## What you need

* For the steps on a server: a server installed from the release bundle, as in [Install hopbox on a Debian 13 server by hand](/guide/install-debian/) or [Install hopbox on an OVHcloud server with Terraform](/guide/install-on-ovhcloud/).
* For the steps on a Mac: a checkout of the source of hopbox, built with `make build`. The source is not public yet, so these steps are for the people who work on hopbox.
* For the steps on a Mac: the bundled Postgres. `make pg` builds it on the first run and prints its dir.
* Go, to install Pebble, and `dig`.

## Run the flow on a Mac with Pebble

### Start Pebble

Install Pebble, and start it from its module dir, where its test config and its test certificates are. `-dnsserver` sends each DNS query of Pebble to the DNS role on port 15353. `PEBBLE_VA_NOSLEEP=1` stops the random wait of Pebble before each check:

```sh
go install github.com/letsencrypt/pebble/v2/cmd/pebble@v2.10.1
PEBBLE_DIR="$(go env GOMODCACHE)/github.com/letsencrypt/pebble/v2@v2.10.1"
cd "$PEBBLE_DIR" && PEBBLE_VA_NOSLEEP=1 "$(go env GOPATH)/bin/pebble" -config test/config/pebble-config.json -dnsserver 127.0.0.1:15353
```

Pebble serves its ACME directory at `https://localhost:14000/dir`. Leave it running, and use a second terminal for the next steps.

### Write the bootstrap config

The server runs the control role and the DNS role. The DNS role listens on a high port, so `acme.name_servers` tells the job where to check the zone. Pebble serves HTTPS with a certificate of its own test CA, so `acme.ca_file` makes the job trust that CA ([the bootstrap config of hopboxd](/reference/hopboxd-config/#keys)):

```sh
PEBBLE_DIR="$(go env GOMODCACHE)/github.com/letsencrypt/pebble/v2@v2.10.1"
mkdir -p /tmp/hba && chmod 700 /tmp/hba
cat > /tmp/hba/hopboxd.toml <<EOF
roles = ["control", "dns"]
data_dir = "$HOME/hopbox-acme-dev"
run_dir = "/tmp/hba"


[dns]
listen = ["127.0.0.1:15353"]


[acme]
name_servers = ["127.0.0.1:15353"]
ca_file = "$PEBBLE_DIR/test/certs/pebble.minica.pem"


[postgres]
install = "$(make pg)"
EOF
```

Run the `cat` command in the checkout of hopbox, so `make pg` finds the recipe of Postgres.

### Start hopboxd

```sh
./bin/darwin_arm64/hopboxd run --config /tmp/hba/hopboxd.toml
```

The install has no domain yet, so the job waits:

```json
{"level":"INFO","msg":"the install gets no certificate yet","component":"acme","reason":"the install has no domain"}
```

Leave it running, and use a third terminal. Set two variables, so the commands stay short:

```sh
H=./bin/darwin_arm64/hopboxd
C=/tmp/hba/hopboxd.toml
```

### Enroll the DNS role

The DNS role gets its zone over the control channel, so the server enrolls with the control role of the same `hopboxd`:

```sh
$H admin --config $C kek rotate
TOKEN="$($H admin --config $C enrollment-token create --roles dns)"
HOPBOX_ENROLLMENT_TOKEN="$TOKEN" $H enroll --config $C
```

### Set the domain and the ACME config

The public address is the address of `ns1` and `ns2` in the zone. The ACME directory is the one of Pebble. `--acme-agree-terms` agrees to the terms of the CA, so the job starts:

```text
$ $H admin --config $C config set --domain example.com --public-address 127.0.0.1 \
    --acme-directory-url https://localhost:14000/dir --acme-email ops@example.org --acme-agree-terms
domain  example.com
public_addresses  127.0.0.1
acme_directory_url  https://localhost:14000/dir
acme_email  ops@example.org
acme_terms_agreed  true
mail_transport  smtp
version  2
update_time  2026-10-20T22:58:38Z
```

Within some seconds, the log of `hopboxd run` shows the attempt. The job sets the CAA record, makes the account, solves the challenge of the domain and of the wildcard, and stores the certificate:

```json
{"level":"INFO","msg":"getting the certificate of the install","component":"acme","domain":"example.com","directory_url":"https://localhost:14000/dir","reason":"the install has no certificate"}
{"level":"INFO","msg":"changed the CAA issuers of the zone","component":"service","caa_issuers":["pebble.letsencrypt.org"],"old_caa_issuers":["letsencrypt.org"],"serial":1792537119}
{"level":"INFO","msg":"stored the ACME account","component":"service","directory_url":"https://localhost:14000/dir","account_url":"https://localhost:14000/my-account/55ce84861e84b3ee"}
{"level":"INFO","msg":"trying to solve challenge","component":"acme","identifier":"example.com","challenge_type":"dns-01"}
{"level":"INFO","msg":"trying to solve challenge","component":"acme","identifier":"*.example.com","challenge_type":"dns-01"}
{"level":"INFO","msg":"got the certificate of the install","component":"acme","domain":"example.com","serial":"4553a65221ea631b","issuer":"CN=Pebble Intermediate CA 512ad8","not_after":"2027-01-18T22:58:38Z","renew_at":"2026-12-19T22:58:38.333333333Z"}
{"level":"INFO","msg":"the next attempt for the certificate is planned","component":"acme","reason":"the certificate is due for renewal","at":"2026-12-19T23:58:38.333333333+01:00"}
```

### Read the certificate

```text
$ $H admin --config $C certificate get
domain  example.com
names  example.com,*.example.com
serial  4553a65221ea631b
issuer  CN=Pebble Intermediate CA 512ad8
not_before  2026-10-20T22:58:39Z
not_after  2027-01-18T22:58:38Z
renew_time  2026-12-19T22:58:38Z
directory_url  https://localhost:14000/dir
update_time  2026-10-20T22:58:44Z
failures  0
last_attempt_time  2026-10-20T22:58:38Z
last_error  -
next_attempt_time  -
ca_wait  false
terms_url  data:text/plain,Do%20what%20thou%20wilt
renewals_stopped  -
```

`terms_url` names the terms that your agreement covers. Pebble has no real terms, so it names a short text.

The job renews the certificate at `renew_time`, after two thirds of its lifetime.

### Check the zone

The CAA record now names the CAA identity of Pebble, and the challenges left the zone:

```text
$ dig @127.0.0.1 -p 15353 example.com CAA +short
0 issue "pebble.letsencrypt.org"
$ dig @127.0.0.1 -p 15353 _acme-challenge.example.com TXT +short
```

### Stop

Press Ctrl-C in the terminal of `hopboxd`, then in the terminal of Pebble. To start from nothing, remove `~/hopbox-acme-dev` and `/tmp/hba`.

## Get the certificate from Let’s Encrypt on a server

In this example, the install serves `example.com`. Before the job can get a certificate, the domain must be delegated to the DNS role of the install ([Serve the domain of an install with the DNS role](/guide/dns-role/#delegate-the-domain-of-the-install)). Let’s Encrypt asks the name servers of the delegation, and those are the servers with the DNS role.

1. Check the delegation from your laptop. The answer must come from the DNS role of the install:

   ```sh
   dig +trace example.com SOA
   ```

2. Test against the staging CA of Let’s Encrypt first. Its rate limits are higher, and its certificates are not trusted, so a mistake costs nothing. Do this only while the install has no trusted certificate. A change of the directory replaces the certificate at once. After a move from the production CA to the staging CA, every browser refuses the HTTPS of the install. Set the contact email of the operator, and agree to the terms of Let’s Encrypt at <https://letsencrypt.org/repository/>:

   ```sh
   sudo hopboxd admin config set --acme-directory-url https://acme-staging-v02.api.letsencrypt.org/directory \
     --acme-email ops@example.org --acme-agree-terms
   ```

3. Read the certificate. Within a minute, it names the staging CA of Let’s Encrypt as the issuer. The log shows each step of the job:

   ```sh
   sudo hopboxd admin certificate get
   journalctl -u hopboxd | grep '"component":"acme"'
   ```

4. Move to the production CA. A new directory clears the agreement, so give `--acme-agree-terms` again. The job gets a new certificate at once, because the certificate is from another directory:

   ```sh
   sudo hopboxd admin config set --acme-directory-url https://acme-v02.api.letsencrypt.org/directory --acme-agree-terms
   ```

The CAA record of the zone then names `letsencrypt.org`:

```sh
dig @1.1.1.1 example.com CAA +short
```

If an attempt fails, `sudo hopboxd admin certificate get` shows the error in `last_error`, and the time of the next attempt in `next_attempt_time`. The log record `getting the certificate of the install failed. The certificate before it stays` has the same facts. The job waits 1 minute after the first failure, and doubles the wait after each failure, up to 6 hours ([the certificate of the install](/reference/acme/#renewal-and-backoff)). A common cause is a name server that the control role cannot reach on port 53. A change of the domain, the public addresses, or an ACME setting ends the wait, unless the CA asked for it with a rate limit.

## Serve the certificate

A server with the edge role serves the certificate. The control role pushes each new certificate to it over the control channel, so a renewal needs no restart ([the control channel](/reference/control-channel/#edge-pushes)). Once the edge role has it, check the certificate that the edge serves:

```sh
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -enddate
```

The metric `hopbox_edge_certificate_not_after_seconds` gives the same end ([Metrics](/reference/metrics/#metrics-of-the-edge-role)). [Run the edge role and open machine URLs](/guide/machine-urls/) opens a machine URL with it.

# Use the console

> How to use the console of an install in a browser: sign in, create a machine, open a shell, approve the hopbox CLI, and the other pages.

The console is the web app of an install. You sign in, create and stop machines, make a URL public, and open a shell in a machine, all in a browser ([Console](/reference/console/)). `hopboxd` serves it at the domain of the install, next to the API. This guide uses the install `https://example.com`. For the preview install at <https://dev.hopbox.dev>, [Try hopbox](/guide/quickstart/) gives the same first steps.

## What you need

* A browser.
* An account on an install, or a sign-in method of the install that makes one, such as GitHub.

## Sign in

Open `https://example.com/` in the browser. Without a session, the console sends you to `/signin`. The page shows the sign-in methods of the install:

* GitHub and Google: the buttons “Sign in with GitHub” and “Sign in with Google”. The operator sets them up as in [Sign in with GitHub and Google](/guide/github-google-sign-in/).
* Magic links: a field “Email” and the button “Email me a sign-in link”. The link works once, for 15 minutes.
* No method yet: a new install shows the command that makes a first-admin login link. The operator runs it on a control server, as in [First sign-in on a new install](/guide/first-sign-in/).

The first sign-in creates your account and its personal org. The console then opens the machines of that org. The head of the org shows `live`: the list follows the install as it changes.

## Create a machine and open a shell

1. On the page of the org, click “New machine”. Leave the name empty for a free name, such as `box1`, or type one. Click “Create”.
2. The machine shows `pending`, then `starting`, then `running`, without a reload of the page.
3. Click the name of the machine. Its page has the actions, the URL, and the sharing.
4. Turn on the switch “Public URL”. Anyone can now open the URL without an account. Turn it off to make the URL private again. Only the creator of a machine can change the switch.
5. Click “Open terminal”. The terminal opens the login shell of the machine. Type `uname -a`, then `exit`.
6. Back on the list, click “Stop”, then “Start”, then “Delete”. The delete asks first.

A machine name is also the first part of its URL, so each name is unique on the install. If another account holds the name, the dialog offers a free name, such as “Use box2”.

## Approve the hopbox CLI

The hopbox CLI signs in with a device flow ([Install the hopbox CLI](/guide/install-cli/)). Run it on your laptop:

```sh
hopbox login --url https://example.com
```

The CLI prints a link such as `https://example.com/device?code=WDJB-MJHT`. Open it in the browser where you signed in. The page shows the name and the IP address of the client that asks. Check that the code matches the code in your terminal. Approve only a sign-in that you started yourself. Click “Approve”, and the CLI gets its tokens.

The approval needs a sign-in within the last 10 minutes ([Sessions, cookies, and sign-in links](/reference/sessions/#recent-sign-in)). If you signed in earlier, the page says so and shows “Sign in again”. Click it, and sign in. The console then opens the page of the code again. Click “Approve” again.

## More pages

| Page     | Where                                 | What you do there                                                                                            |
| -------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Account  | the name at the top right             | Change the display name. See the emails and the sign-in methods. Add and remove SSH keys. End a CLI sign-in. |
| Orgs     | “All orgs” in the org list at the top | See your orgs, and create one.                                                                               |

| Settings | the tab of an org                     | Rename, leave, or delete the org, and see its limits.                                                        |

# Serve the domain of an install with the DNS role

> How to run the DNS role, set the domain and the public addresses, and query the zone. Also how to delegate the domain of an install.

This guide runs the DNS role next to the control role, first on a Mac and then on a server. The DNS role answers DNS queries for the domain of the install, such as `example.com`. The domain then points at the public addresses of the install, and each machine name, such as `box1.example.com`, points at them too. At the end, the guide delegates the domain from its parent zone, so every resolver on the internet finds the DNS role.

[The DNS role](/reference/dns/) covers the zone, the answers, and the push in full.

The release files of hopbox are not public yet. The hopbox team gives them on request.

## How the zone reaches the DNS role

The DNS role holds no zone of its own. The control role builds the zone from the install config: the domain, the public addresses, and the TXT records of ACME. Then it pushes the zone over the control channel to each server with the DNS role ([the control channel](/reference/control-channel/)). So a server with the DNS role enrolls with the control role, as a node does.

Each change of the domain or the addresses raises the serial of the zone. Within a second, the DNS role answers with the new zone.

## What you need

* For the steps on a server: a server installed from the release bundle, as in [Install hopbox on a Debian 13 server by hand](/guide/install-debian/) or [Install hopbox on an OVHcloud server with Terraform](/guide/install-on-ovhcloud/).
* For the steps on a Mac: a checkout of the source of hopbox, built with `make build`. The source is not public yet, so these steps are for the people who work on hopbox.
* For the steps on a Mac: the bundled Postgres. `make pg` builds it on the first run and prints its dir.
* `dig`. macOS has it.

## Run the DNS role on a Mac

Port 53 needs root, so the DNS role on a Mac listens on a high port. Do not use port 5353, because macOS uses it for multicast DNS.

### Write the bootstrap config

A unix socket path has at most 103 bytes on macOS, so put the sockets in a short dir under `/tmp`:

```sh
mkdir -p /tmp/hbd && chmod 700 /tmp/hbd
cat > /tmp/hbd/hopboxd.toml <<EOF
roles = ["control", "dns"]
data_dir = "$HOME/hopbox-dns-dev"
run_dir = "/tmp/hbd"


[dns]
listen = ["127.0.0.1:15353"]


[postgres]
install = "$(make pg)"
EOF
```

The server enrolls at the default `channel.control_urls`, `["https://127.0.0.1:7443"]`, which is the internal listener of the same `hopboxd` ([the bootstrap config of hopboxd](/reference/hopboxd-config/#keys)). The `[channel]` keys apply to each server that enrolls, also to a server with the DNS role alone.

### Start hopboxd

```sh
./bin/darwin_arm64/hopboxd run --config /tmp/hbd/hopboxd.toml
```

The units of the control role start first. Then the unit `dns` opens its sockets, and the unit `channel` waits for the enrollment of the server:

```json
{"level":"INFO","msg":"dns listening","component":"dns","network":"udp","addr":"127.0.0.1:15353"}
{"level":"INFO","msg":"dns listening","component":"dns","network":"tcp","addr":"127.0.0.1:15353"}
{"level":"INFO","msg":"waiting for the enrollment of this server","component":"node","dir":"/Users/user1/hopbox-dns-dev/server"}
```

Leave it running, and use a second terminal for the next steps. Set two variables, so the commands stay short:

```sh
H=./bin/darwin_arm64/hopboxd
C=/tmp/hbd/hopboxd.toml
```

The DNS role has no zone yet, so it answers `SERVFAIL`. A resolver then asks another name server:

```text
$ dig @127.0.0.1 -p 15353 example.com A +norec | grep status
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 39721
```

### Enroll the server with the DNS role

The install needs a key-encryption key before it has a CA. A token for the DNS role names the role `dns`:

```text
$ $H admin --config $C kek rotate
file:1
$ TOKEN="$($H admin --config $C enrollment-token create --roles dns)"
$ HOPBOX_ENROLLMENT_TOKEN="$TOKEN" $H enroll --config $C
hopboxd: enrolled as the server 01a14a5e-b88d-7c9f-81cc-5f5b8e5b1e48. hopboxd run connects it to the control plane.
01a14a5e-b88d-7c9f-81cc-5f5b8e5b1e48
```

A server without the node role runs no machine. So `enroll` runs no preflight check, and the enrollment works on a Mac. Within 2 seconds, the channel connects, and the first heartbeat brings the zones:

```text
$ $H admin --config $C server list
ID                                    POOL     STATE  STATUS  ROLES  HOSTNAME  VERSION  LAST HEARTBEAT
01a14a5e-b88d-7c9f-81cc-5f5b8e5b1e48  default  ready  ok      dns    macbook   v0.1.0   2026-10-17T14:58:05Z
```

The install has no domain yet, so the set of zones is empty. The DNS role now refuses every name:

```text
$ dig @127.0.0.1 -p 15353 example.com A +norec | grep status
;; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 57040
```

### Set the domain and the public addresses

The public addresses are the addresses at which the edge servers take traffic. On a laptop, use any address. The examples use the documentation ranges `203.0.113.0/24` and `2001:db8::/32`:

```text
$ $H admin --config $C config set --domain example.com --public-address 203.0.113.10 --public-address 2001:db8::10
domain  example.com
public_addresses  203.0.113.10,2001:db8::10
acme_directory_url  https://acme-v02.api.letsencrypt.org/directory
acme_email  -
acme_terms_agreed  false
mail_transport  smtp
version  2
update_time  2026-10-17T14:58:13Z
```

The log of `hopboxd run` shows the new zone:

```json
{"level":"INFO","msg":"serving dns zones","component":"dns","serial":1792249094,"zones":["example.com."],"records":12}
```

### Query the zone

A machine name gets the address through the wildcard. The flag `aa` says that the answer is authoritative:

```text
$ dig @127.0.0.1 -p 15353 box1.example.com A +norec
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 9368
;; flags: qr aa; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
...
;; ANSWER SECTION:
box1.example.com.  60  IN  A  203.0.113.10
```

The NS query names `ns1` and `ns2`, with their addresses:

```text
$ dig @127.0.0.1 -p 15353 example.com NS +norec +noall +answer +additional
example.com.    60  IN  NS  ns1.example.com.
example.com.    60  IN  NS  ns2.example.com.
ns1.example.com.  60  IN  A  203.0.113.10
ns1.example.com.  60  IN  AAAA  2001:db8::10
ns2.example.com.  60  IN  A  203.0.113.10
ns2.example.com.  60  IN  AAAA  2001:db8::10
```

The CAA record lets only Let’s Encrypt, the default ACME CA, issue certificates for the domain. It follows the ACME CA of the install ([the DNS role](/reference/dns/#caa-records)):

```text
$ dig @127.0.0.1 -p 15353 example.com CAA +short
0 issue "letsencrypt.org"
```

A name below `ns1` does not exist, and a name outside the zone gets no answer:

```text
$ dig @127.0.0.1 -p 15353 x.ns1.example.com A +norec | grep -E 'status|SOA'
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 23694
example.com.    60  IN  SOA  ns1.example.com. hostmaster.example.com. 1792249094 3600 600 604800 60
$ dig @127.0.0.1 -p 15353 example.org A +norec | grep status
;; ->>HEADER<<- opcode: QUERY, status: REFUSED, id: 47432
```

TCP works too:

```text
$ dig @127.0.0.1 -p 15353 example.com SOA +tcp +short
ns1.example.com. hostmaster.example.com. 1792249094 3600 600 604800 60
```

### Change the addresses

Set two new IPv4 addresses. The list replaces the old one, so this install now has no IPv6 address:

```sh
$H admin --config $C config set --public-address 203.0.113.11,203.0.113.12
```

Within a second, the domain has both addresses, and `ns2` takes the second one:

```text
$ dig @127.0.0.1 -p 15353 example.com A +short
203.0.113.11
203.0.113.12
$ dig @127.0.0.1 -p 15353 ns2.example.com A +short
203.0.113.12
```

The metrics count the queries, and show the serial that the DNS role serves ([the DNS role](/reference/dns/#metrics)):

```sh
curl -s http://127.0.0.1:9464/metrics | grep '^hopbox_dns'
```

### Stop hopboxd

Press Ctrl-C in the first terminal. `hopboxd` stops the unit `channel` first, then the unit `dns`, then the units of the control role. To start from nothing, remove `~/hopbox-dns-dev` and `/tmp/hbd`.

## Delegate the domain of the install

In this example, the install serves `example.com` from one server, with the public addresses `203.0.113.10` and `2001:db8::10`. A delegated zone needs two name servers. The install has one server, so both name servers point at it.

### Give the server the DNS role

A server with every role lists all four in its bootstrap config:

```toml
roles = ["control", "node", "dns", "edge"]
```

`hopboxd install --roles control,node,dns,edge` writes this list ([hopboxd](/reference/hopboxd/#install)). The roles of a server are in its certificate, so a server that enrolled without `dns` must enroll again to get it ([Enrollment and the install PKI](/reference/enrollment/)). The token for this server names the three roles that enroll:

```sh
TOKEN="$(sudo hopboxd admin enrollment-token create --roles node,dns,edge)"
```

The tested OS runs `systemd-resolved` on `127.0.0.53:53`, so the DNS role cannot listen on port 53 of every address. The Terraform provider writes `dns.listen` with port 53 of each public address before the install ([hopbox Terraform provider](/reference/terraform-provider/#create)). Open UDP and TCP port 53 in each firewall in front of the server.

### Set the public addresses

The provider sets the public addresses of the install at the create of the server. To set them by hand:

```sh
sudo hopboxd admin config set --public-address 203.0.113.10 --public-address 2001:db8::10
```

### Check the server before the delegation

From your laptop, ask the server directly. The answer must have the flag `aa` and the address of the server:

```sh
dig @203.0.113.10 example.com SOA +norec
dig @203.0.113.10 box1.example.com A +norec
```

### Make the records in the parent zone

The parent zone holds the delegation: the NS records and the glue records. For a domain such as `example.com`, the records are in the zone `com`, and the registrar of the domain makes them. Give the registrar the two name servers and their addresses. For a subdomain such as `hop.example.net`, add the records in the zone `example.net`. For `example.com`, the records are:

| Name               | Type   | Target             |
| ------------------ | ------ | ------------------ |
| `example.com.`     | `NS`   | `ns1.example.com.` |
| `example.com.`     | `NS`   | `ns2.example.com.` |
| `ns1.example.com.` | `A`    | `203.0.113.10`     |
| `ns2.example.com.` | `A`    | `203.0.113.10`     |
| `ns1.example.com.` | `AAAA` | `2001:db8::10`     |
| `ns2.example.com.` | `AAAA` | `2001:db8::10`     |

The `A` and `AAAA` records are the glue records. They must hold the same addresses as `ns1` and `ns2` in the zone that the DNS role serves. Without IPv6 on the server, leave out the two `AAAA` records. For a subdomain, the parent zone must have no other record at the subdomain or below it, because the delegation hands those names to the DNS role.

### Check the delegation

The parent zone can take some minutes to publish the change. Then follow the delegation from the root:

```sh
dig +trace box1.example.com A
```

The last step names `ns1.example.com` or `ns2.example.com`, and gives `203.0.113.10`. A public resolver gives the same answer:

```sh
dig @1.1.1.1 box1.example.com A +short
```

The TTL of each record is 60 seconds. So a later change of the public addresses reaches every resolver within a minute.

# Enroll the node role on one server

> How to enroll the node role of a server with the control role of the same server, and check its heartbeats.

This guide gives one server both the control role and the node role. The node role enrolls with the control role of the same `hopboxd`. Then it keeps its control channel to the control role, over mutual TLS on loopback. At the end, `hopboxd admin server list` shows the server as `ready`, with the facts of its heartbeats.

[Enrollment and the install PKI](/reference/enrollment/) covers the enrollment in full, and [the control channel](/reference/control-channel/) covers the channel.

## What you need

* A Linux server with KVM. hopbox tests Debian 13 with the kernel `6.18.57-hopbox1` ([Host kernel](/reference/host-kernel/)).
* A data dir on a file system with reflinks, such as XFS made with `reflink=1`. The default data dir is `/var/lib/hopbox`.
* `hopboxd` and the bundled Postgres on the server.
* Root on the server. Every command below runs with `sudo`.

A Mac cannot run the node role, because it has no KVM. The preflight check of `hopboxd enroll` refuses it:

```text
$ ./bin/darwin_arm64/hopboxd enroll --config /tmp/hb/hopboxd.toml --token "$TOKEN"
preflight kvm  fail  hopbox runs machines only on Linux with KVM, and this host runs darwin
preflight cgroup2  fail  hopbox runs machines only on Linux with KVM, and this host runs darwin
preflight tun  fail  hopbox runs machines only on Linux with KVM, and this host runs darwin
preflight nftables  fail  hopbox runs machines only on Linux with KVM, and this host runs darwin
preflight reflink  fail  hopbox runs machines only on Linux with KVM, and this host runs darwin
preflight kernel  warn  this host runs darwin with the kernel 27.0.0, and hopbox tests only Debian 13 with the kernel 6.18.57-hopbox1. hopbox runs, with a higher risk
hopboxd: error: the preflight check failed, so this server cannot run machines:
  kvm: hopbox runs machines only on Linux with KVM, and this host runs darwin
  cgroup2: hopbox runs machines only on Linux with KVM, and this host runs darwin
  tun: hopbox runs machines only on Linux with KVM, and this host runs darwin
  nftables: hopbox runs machines only on Linux with KVM, and this host runs darwin
  reflink: hopbox runs machines only on Linux with KVM, and this host runs darwin
```

That refusal is correct. Use a Linux server for this guide.

## Check the server

Run the preflight check first. It tests KVM, cgroup v2, tun, nftables, and reflinks on the data dir ([the preflight check](/reference/preflight/)):

```text
$ sudo hopboxd preflight
preflight kvm  ok
preflight cgroup2  ok
preflight tun  ok
preflight nftables  ok
preflight reflink  ok
preflight kernel  ok
```

A line with `fail` names a problem that you must fix before the enrollment. A line with `warn` only warns.

## Write the bootstrap config

Give the server the control role and the node role. Every other key keeps its default ([the bootstrap config of hopboxd](/reference/hopboxd-config/#keys)):

```sh
sudo mkdir -p /etc/hopbox
sudo tee /etc/hopbox/hopboxd.toml >/dev/null <<'EOF'
roles = ["control", "node"]


[channel]
labels = { zone = "gra" }
EOF
```

With the defaults, the internal listener of the control role listens on `127.0.0.1:7443`, and the node dials `https://127.0.0.1:7443`. The labels are optional. Each heartbeat reports them.

## Start hopboxd

```sh
sudo hopboxd run
```

`hopboxd` starts the units of the control role, then the `channel` unit, which keeps the control channel of the server. The server has no identity yet, so the unit waits, and logs this record once. Its records have `component=node`:

```json
{"time":"2026-10-16T09:00:01.000000000Z","level":"INFO","msg":"waiting for the enrollment of this server","component":"node","dir":"/var/lib/hopbox/server"}
```

On a fresh install, the internal listener also warns `the internal listener has no certificate yet`, because the install CA needs a key-encryption key. Leave `hopboxd` running, and use a second terminal for the next steps.

## Make the first key-encryption key

`hopboxd install` makes the first key-encryption key, so a server that it set up can skip this step ([Install hopbox on a Debian 13 server by hand](/guide/install-debian/)). So can any install with a key-encryption key already.

```text
$ sudo hopboxd admin kek rotate
file:1
```

The internal listener now makes the install CA at its next handshake, without a restart.

## Make an enrollment token

```sh
TOKEN="$(sudo hopboxd admin enrollment-token create)"
```

The token works once, for 1 hour, in the pool `default`. It is a secret, so keep it in a variable and out of your shell history.

All servers of a pool have identical hardware. The first server of a pool records its CPU model, CPU threads, RAM, and disks, and the enrollment of a server with other hardware fails ([Enrollment and the install PKI](/reference/enrollment/#hardware-of-a-pool)). If the new server is another model, make the token for another pool ([Add pools and sizes](/guide/pools-and-sizes/)).

## Enroll the server

```text
$ sudo HOPBOX_ENROLLMENT_TOKEN="$TOKEN" hopboxd enroll
preflight kvm  ok
preflight cgroup2  ok
preflight tun  ok
preflight nftables  ok
preflight reflink  ok
preflight kernel  ok
hopboxd: enrolled as the server 01a14403-6bd1-7522-9ab0-b3ab4517e0e4. hopboxd run connects it to the control plane.
01a14403-6bd1-7522-9ab0-b3ab4517e0e4
```

`enroll` made a key for the server. Before it sent the token, it checked the CA of the control role against the hash in the token. The identity of the server is now in `/var/lib/hopbox/server`.

Within 2 seconds, the waiting `channel` unit finds the identity and opens its channel. The log of `hopboxd run` shows:

```json
{"time":"2026-10-16T09:02:11.000000000Z","level":"INFO","msg":"control channel connected","component":"node","server":"01a14403-6bd1-7522-9ab0-b3ab4517e0e4","control":"https://127.0.0.1:7443","state":"SERVER_STATE_READY"}
```

## See the server

```text
$ sudo hopboxd admin server list

01a14403-6bd1-7522-9ab0-b3ab4517e0e4  default  ready  ok      node   server1   v0.1.0   2026-10-16T09:02:16Z
```

## Cordon and uncordon

A cordoned server keeps its machines and takes no new one:

```text
$ sudo hopboxd admin server cordon 01a14403-6bd1-7522-9ab0-b3ab4517e0e4 --json
{"id":"01a14403-6bd1-7522-9ab0-b3ab4517e0e4","pool":"default","hostname":"server1","roles":["node"],"state":"cordoned","cordoned":true,...}
$ sudo hopboxd admin server uncordon 01a14403-6bd1-7522-9ab0-b3ab4517e0e4
```

The output of `--json` here is cut short. The next heartbeat answer tells the node its new state. The audit log records both calls, with the actor `local_root`.

## Stop and start hopboxd

Press Ctrl-C in the first terminal. `hopboxd` stops the `channel` unit first, which closes the channel. Then it stops the units of the control role.

In an install with other control servers, the leader marks a server unresponsive after 20 seconds without a heartbeat. The state is then `unresponsive`, and the audit log has the entry `server.mark_unresponsive` with the actor `system`. On one server, the leader stops with the node, so no one marks the server while `hopboxd` is down.

Start `hopboxd` again with `sudo hopboxd run`. The node reads its identity, opens its channel, and sends a heartbeat at once. The first heartbeat makes an unresponsive server `ready` again. A server that you cordoned becomes `cordoned` again. There is no need to enroll again: the identity stays in `/var/lib/hopbox/server`, and the node renews its certificate over the channel every 20 days.

## Start again from nothing

To enroll the server again, stop `hopboxd`, remove `/var/lib/hopbox/server`, and repeat the steps from [Make an enrollment token](#make-an-enrollment-token). The server gets a new ID. The old ID stays in the registry as an unresponsive server.

# Set env vars and secrets

> How to set env vars and secrets with the hopbox CLI in each scope, list them, share a machine with them, and rewrap the secrets after a rotation of the key-encryption key.

An env var or a secret goes into the machines of an org at boot and into every login shell. You can read an env var back. A secret is sealed, and nobody can read it back. This guide sets values with each scope, lists them, shows which machines get which value, and shares a machine. [The env var API](/reference/vars-api/) has every call and rule.

This guide uses the hopbox CLI. The tab “Env vars” of an org in the console does the same work in a browser ([Use the console](/guide/console/#more-pages)).

## What you need

* The hopbox CLI, signed in to an install, as in [Install the hopbox CLI](/guide/install-cli/). This guide uses the install `https://example.com`.
* For secrets: a key-encryption key on the install. The operator makes the first one with `hopboxd admin kek rotate` ([Run the control role on a laptop](/guide/run-hopboxd/#act-through-the-admin-socket)). Without it, a secret fails with `failed_precondition`.

## Pick a scope

Each value has a scope. The scope says which machines get the value:

| Scope                 | Reaches                              | Who sets it               |
| --------------------- | ------------------------------------ | ------------------------- |
| `shared`, the default | the shared machines of the org       | org admins and org owners |
| `private`             | your own private machines in the org | any member                |
| `all`                 | every machine of the org             | org admins and org owners |

If a private value and an all value have the same name, your private machines get the private value.

## Set values in your personal org

A command without `--org` acts in the active org of the profile, at first your personal org. A personal org has no shared machines, so a value with the default scope reaches no machine. hopbox refuses it:

```sh
hopbox env set REGION=eu-west; echo "status $?"
```

```text
hopbox: invalid_argument: invalid argument: a personal org has no shared machines, so a shared value reaches no machine. Use the scope all or private
status 1
```

Set an env var for every machine of the org:

```sh
hopbox env set REGION=eu-west --scope all
```

```text
Set the env var REGION in the scope all.
```

Set a secret for your own private machines. Without `=VALUE`, the CLI asks for the value and does not show it, so the value stays out of the shell history:

```sh
hopbox env set GITHUB_TOKEN --secret --scope private
```

```text
Value of GITHUB_TOKEN:
Set the secret GITHUB_TOKEN in the scope private.
```

A script gives the value on stdin instead, such as `hopbox env set GITHUB_TOKEN --secret --scope private < token.txt`. No later command returns the value of a secret.

A private value can have the name of an all value. Your private machines then get the private value:

```sh
hopbox env set REGION=eu-central --scope private
```

Some names, such as `EDITOR` and `NODE_OPTIONS`, make a program run code. Only a private value can take them, for your own machines:

```sh
hopbox env set EDITOR=vim --scope all; echo "status $?"
hopbox env set EDITOR=nvim --scope private
```

```text
hopbox: reserved env var name: EDITOR. A program can load or run code from it, so only a private value can take it
status 80
Set the env var EDITOR in the scope private.
```

The CLI checks the name before it sends the value. A set with the same name and scope replaces the value.

## List the values

```sh
hopbox env list
```

```text
NAME          SCOPE    SECRET  VALUE       UPDATED
EDITOR        private  no      nvim        2026-10-17T10:25:49Z
GITHUB_TOKEN  private  yes     (secret)    2026-10-17T10:25:49Z
REGION        all      no      eu-west     2026-10-17T10:25:49Z
REGION        private  no      eu-central  2026-10-17T10:25:49Z
```

The list holds the values of the org and your own private values, sorted by name. Nobody else sees your private values, also not an owner of the org.

## See what each machine gets

hopbox builds the env of each machine from these values. With the values above, your private machines in this org get:

```text
EDITOR=nvim
GITHUB_TOKEN=<your token>
REGION=eu-central
```

The guest agent writes these values to `/etc/hopbox/env`, which every login shell reads. Exec and the start command get them too. Make a machine, and read a value in a login shell:

```sh
hopbox new box1
hopbox exec box1 bash -lc 'echo "$REGION"'
```

```text
eu-central
```

[The env var API](/reference/vars-api/#env-of-a-machine) gives the rules for every kind of machine. Delete the machine with `hopbox machine delete box1 --yes`. Its name stays reserved for your personal org for 7 days, so the next section uses `box2`.

## Share values with a team

Make an org for a team, `org1`, as in [Use the hopbox CLI](/guide/cli/#work-in-an-org), and make it the active org:

```sh
hopbox org create org1 --use
```

As the owner, set a secret for the shared machines, and an env var for every machine:

```sh
printf 'postgres://db.internal/app' | hopbox env set DATABASE_URL --secret
hopbox env set REGION=eu-west --scope all
```

A name of the org has one scope. So a shared value cannot take the name of an all value:

```sh
hopbox env set REGION=us-east; echo "status $?"
```

```text
hopbox: already_exists: already exists: the org has a value REGION with the scope all. Set it with that scope, or delete it first
status 5
```

A member of the team sets only private values. A shared value or an all value from a member fails with `permission_denied`.

An org key reads the names of the org values, as a member does, and sets nothing:

```sh
ORG_KEY=$(hopbox api-key create reader --kind org --expires 30d)
HOPBOX_API_KEY=$ORG_KEY HOPBOX_URL=https://example.com hopbox env set X=1; echo "status $?"
```

```text
The org key 01a14965-7890-7d12-9c3a-1f2e3d4c5b6a (reader) works until 2026-11-16T10:25:49Z. This is its only copy.
hopbox: permission_denied: permission denied: a caller of kind org_key may not do var.set
status 3
```

Revoke the key after the test with `hopbox api-key revoke <id>`.

## Share a machine with the team

A machine is private to its creator until the creator shares it. A share changes which values reach the machine. Your private values leave it, and the shared values of the org reach it. Create a machine in `org1`, and share it:

```sh
hopbox new box2
hopbox machine share box2
```

Before the share, `box2` gets `REGION=eu-west`. After the share, it gets `DATABASE_URL` and `REGION=eu-west`. hopbox pushes the new env to the running machine, so a new login shell reads it:

```sh
hopbox exec box2 bash -lc 'echo "$DATABASE_URL"'
```

```text
postgres://db.internal/app
```

Before the share, hopbox resolves the env that the machine gets as a shared machine. If that env does not resolve, the share fails, and the machine stays private. Two causes are a secret of the org that does not open, and a keyring without a key-encryption key. For example, on an install that lost its key-encryption key, the share fails with:

```text
hopbox: failed_precondition: failed precondition: the env of the machine as a shared machine does not resolve, so the machine stays private: the keyring has no key-encryption key to seal or open the value. Run hopboxd admin kek rotate to make the first one
```

The machine keeps its old env, with your private values, and only you can use it. Ask the operator of the install to put the key file back from a backup, then share again. If the key is lost, the operator makes a new one. Then set each secret of the org again, and share again. [The machine API](/reference/machine-api/#sharemachine) lists each cause.

## Names that hopbox refuses

No value of any scope takes a name that the shell or the loader runs code from, or a name that hopbox sets itself:

```sh
hopbox env set LD_PRELOAD=/tmp/x.so --scope private
```

```text
hopbox: reserved env var name: LD_PRELOAD. No name can start with LD_
```

A value of the scope `all` reaches the private machines of every member. So a shared or an all value also cannot take a name that makes a language runtime, a tool, or glibc load or run code:

```sh
hopbox env set NODE_OPTIONS='--require /tmp/x.js' --scope all
```

```text
hopbox: reserved env var name: NODE_OPTIONS. A program can load or run code from it, so only a private value can take it
```

This list reduces the risk that an org admin runs code in your private machines. It does not remove it, because any env var can change what a program does. [The env var API](/reference/vars-api/#names-and-values) lists every reserved name.

## Trust the admins of your org

The members of an org trust its org admins and org owners. The org admins and org owners set the all values, and an all value reaches your private machines too. So the scope `private` does not protect a machine from the all values of its org. An all value can change what a program in the machine does, even with a name that no list reserves. An org admin cannot open a shell in your private machine, but can change what runs there with an all value.

To see the all values that reach your private machines, list the values of the org:

```sh
hopbox env list
```

```text
NAME          SCOPE   SECRET  VALUE     UPDATED
DATABASE_URL  shared  yes     (secret)  2026-10-17T10:25:49Z
REGION        all     no      eu-west   2026-10-17T10:25:49Z
```

Each value with the scope `all` reaches your private machines in this org, unless you have a private value with the same name. Here, `REGION` is such a value. To replace an all value in your private machines, set a private value with the same name.

You are the only member of your personal org. So in your personal org, only you set the all values.

## Find the changes in the audit log

Each set and each delete writes an audit entry, without the value. The org admins read the audit log, so the entry of a private value also leaves out its name. An owner or an admin of the org reads the entries with a member key of the org:

```sh
KEY=$(hopbox api-key create audit --expires 30d)
curl -s -X POST -H 'Content-Type: application/json' -H "Authorization: Bearer $KEY" \
  -d '{"pageSize":50}' https://example.com/hopbox.v1.AuditService/ListAuditEntries |
  jq -c '.entries[] | select(.action == "var.set") | .details'
```

```text
{"kind":"env_var","name":"REGION","replaced":"false","scope":"all"}
{"kind":"secret","name":"DATABASE_URL","replaced":"false","scope":"shared"}
```

The newest entries come first.

## Delete a value

Name the value and its scope:

```sh
hopbox env unset REGION --scope all
```

A second unset fails with status 4, because the value is gone.

When a member leaves the org, hopbox deletes the private values of the member in that org.

## Move the secrets to a new key

This section is for the operator of the install. A rotation of the key-encryption key leaves each secret on its old key. The rewrap moves them, with the other sealed values of the install, such as the SMTP password. Run both commands as root on a control server:

```sh
sudo hopboxd admin kek rotate
sudo hopboxd admin kek rewrap
```

```text
file:2
rewrapped 2 to file:2
file:1  0
file:2  2  current
```

Your numbers depend on the earlier rotations and on the other sealed values of the install. Each line names a key and the number of values that it seals. A key that seals no value can go, after a backup ([Sealing](/reference/sealing/#rewrap)).

If the install has more than one control server, `kek rotate` refuses, because it makes the new key current only on its own server. Then stage the key, copy the staged file to each control server, and promote it before the rewrap, as [Run the control role on a laptop](/guide/run-hopboxd/#add-a-second-control-server) shows.

# Run commands and copy files in a machine

> How to run commands in a machine, copy files, and read its log through the API with grpcurl, and open a shell over the WebSocket.

This guide runs a command in a machine through the API, copies a file in and out, and reads the log of the start command. It uses the access calls of the API: `Exec`, `Upload`, `Download`, and `StreamMachineLogs` ([the machine API](/reference/machine-api/#access-calls)). Use these calls from your own tools. The hopbox CLI does the same work with `exec`, `cp`, `logs`, and `connect` ([Use machines from the CLI](/guide/cli-machines/)). The console uses the WebSocket of exec, and this guide shows it too.

Each access call needs a machine that runs, except the log. For a machine that does not run, the calls answer `failed_precondition`, with a message such as `the machine box1 is pending, not running. Start it first`.

## What you need

* A machine `box1` that runs, as in [Use machines from the CLI](/guide/cli-machines/#make-a-machine). This guide uses the install `example.com`.
* An API key of your org in `KEY`, in the form `hbx_<key>`. Make one with `KEY=$(hopbox api-key create tools --expires 30d)`, as in [Use the hopbox CLI](/guide/cli/#make-an-api-key-for-a-script). An exec streams in both directions, so it needs gRPC or HTTP/2. A tool such as grpcurl speaks gRPC, so it sends the key.
* grpcurl, from <https://github.com/fullstorydev/grpcurl>. The API serves gRPC reflection, so grpcurl needs no proto files.

The edge servers of the install serve the API over TLS on port 443:

```sh
API=example.com:443
hb() { grpcurl -H "Authorization: Bearer $KEY" "$@"; }
```

## Run a command

`Exec` takes the start chunk first, then the input. In JSON, a bytes field such as `stdin` or `stdout` is base64. This command prints a line on each output, and exits with the code 3:

```sh
hb -d @ $API hopbox.v1.MachineService/Exec <<'EOF'
{"chunk":{"start":{"name":"box1","argv":["sh","-c","echo out; echo err >&2; exit 3"]}}}
{"chunk":{"stdinEof":true}}
EOF
```

```text
{"chunk":{"stdout":"b3V0Cg=="}}
{"chunk":{"stderr":"ZXJyCg=="}}
{"chunk":{"exit":{"code":3}}}
```

`b3V0Cg==` is `out` and a newline. Add `"timeout":"10s"` to the start chunk to end a command after 10 seconds. Such a command ends with the code 124 and `"timedOut":true`.

A member of the org cannot run a command in your machine until you share it. An org admin can never run one in your private machine ([the machine API](/reference/machine-api/#who-can-call-them)).

## Copy a file into the machine

`Upload` takes the start message first, then the data. grpcurl ends the data at the end of its input:

```sh
hb -d @ $API hopbox.v1.MachineService/Upload <<EOF
{"start":{"name":"box1","path":"notes.txt","mode":384}}
{"data":"$(printf 'hello from the laptop\n' | base64)"}
EOF
```

```text
{"bytes":"22"}
```

The mode 384 is 0600. A relative path starts at the home directory of the user `user`. To copy a directory, send a tar stream of its contents, with `"archive":true`.

## Copy the file back

```sh
hb -d '{"name":"box1","path":"notes.txt"}' $API hopbox.v1.MachineService/Download
```

```text
{"info":{"mode":384,"size":"22"}}
{"data":"aGVsbG8gZnJvbSB0aGUgbGFwdG9wCg=="}
```

A download to a laptop has at most 4 MiB. A larger file fails with `failed_precondition`. Pack the file in the machine and copy it in parts, or copy it over SSH.

## Read the log

The log holds the output of the start command of the machine. The node keeps it for 7 days or 100 MiB. This call sends the last 20 lines, then each new line, until you press Ctrl-C:

```sh
hb -d '{"name":"box1","tail":20,"follow":true}' $API hopbox.v1.MachineService/StreamMachineLogs
```

```text
{"entry":{"time":"2026-10-18T09:12:03.418Z","stream":"MACHINE_LOG_STREAM_STDOUT","data":"c2VydmluZyBvbiA6ODAwMA=="}}
{"synced":true}
```

The log stays readable while the machine is stopped.

## Open a shell from the console

The console opens a WebSocket to `/api/ws/exec` with the session cookie. Each binary message holds one `ExecChunk` encoded as protobuf. The generated messages of the TypeScript SDK, in `@hopbox/sdk/v1`, make and read it ([Call the API from TypeScript](/guide/typescript-sdk/)). A start chunk without `argv` and with `tty` opens the login shell, as `hopbox connect` does:

```ts
import { create, toBinary, fromBinary } from "@bufbuild/protobuf";
import { ExecChunkSchema } from "@hopbox/sdk/v1";


const ws = new WebSocket("wss://example.com/api/ws/exec");
ws.binaryType = "arraybuffer";
ws.onopen = () => {
  const start = create(ExecChunkSchema, {
    chunk: { case: "start", value: { machine: { case: "name", value: "box1" }, tty: true, size: { rows: 24, cols: 80 } } },
  });
  ws.send(toBinary(ExecChunkSchema, start));
};
ws.onmessage = (ev) => {
  const chunk = fromBinary(ExecChunkSchema, new Uint8Array(ev.data));
  if (chunk.chunk.case === "stdout") console.log(new TextDecoder().decode(chunk.chunk.value));
};
ws.onclose = (ev) => console.log("closed", ev.code, ev.reason);
```

The TypeScript SDK wraps this socket in `exec`, with the same session for a browser and for Node.js ([Call the API from TypeScript](/guide/typescript-sdk/#use-the-sdk-in-the-console)). The page must have the origin of the install, so this works only from the console. A page of another site gets HTTP status 403. At the end of the shell, the socket closes with the code 1000. An error closes it with 4000 plus the Connect code, such as 4007 for `permission_denied` ([the machine API](/reference/machine-api/#the-websocket-endpoint)).

# Run the control store on an external Postgres

> How to run the control store on an external Postgres, such as managed PostgreSQL: the database, the CA and password files, the config, and the checks. Also how to move a one-server install there with hopboxd admin db export and maintenance mode.

This guide puts the control store of an install on an external Postgres, such as managed PostgreSQL of OVHcloud. An install needs it before it can run more than one control server, because the bundled Postgres listens only on its unix socket. [The bundled Postgres](/reference/postgres/#external-postgres) lists every rule.

The guide first sets up a new control server on an empty database. Then it moves an install with one server from its bundled Postgres to the external Postgres with `hopboxd admin db export`.

## What you need

* A Postgres 18 service with TLS, such as managed PostgreSQL with the plan Production. Managed PostgreSQL offers the versions 15 to 18. Pick 18, because hopbox needs the major version of its bundled Postgres or a newer one.
* The host name of the service, its port, and the CA certificate of its TLS certificate. OVHcloud shows them in the control panel of the service.
* A database for hopbox, and a user that owns it. The default user of managed PostgreSQL, `avnadmin`, is no superuser, and hopbox needs none.
* A Debian 13 server with root access, and a release bundle, as in [Install hopbox on a Debian 13 server by hand](/guide/install-debian/#what-you-need).
* An allowed address range of the service that holds the address of the control server. Managed PostgreSQL refuses every other client.

hopbox holds one session per connection: it keeps the leader lock and a `LISTEN` on their own connections. So connect directly to the service, or through a pooler in session mode, never in transaction mode.

## 1. Make the database

Make the database `hopbox` in the service. On managed PostgreSQL, use the control panel or the API of OVHcloud. On another Postgres, run as a user that can make databases:

```sql
CREATE DATABASE hopbox OWNER avnadmin;
```

## 2. Write the CA and the password on the control server

Save the CA certificate of the service and the password of the user as root. The password file must be readable by root alone, or `hopboxd` refuses it. `read -rs` keeps the password out of the screen and the shell history, and the `umask` gives the file the mode `0400`:

```sh
sudo install -d -m 0755 /etc/hopbox
sudo install -m 0644 ca.pem /etc/hopbox/postgres-ca.pem
read -rs PGPW
printf '%s\n' "$PGPW" | sudo sh -c 'umask 0377; cat > /etc/hopbox/postgres-password'
unset PGPW
```

## 3. Name the Postgres in the bootstrap config

Write `[postgres]` into `/etc/hopbox/hopboxd.toml` before the install. The install keeps every key that its flags do not set ([hopboxd](/reference/hopboxd/#install)):

```sh
sudo tee /etc/hopbox/hopboxd.toml >/dev/null <<'EOF'
[postgres]
url = "postgres://avnadmin@db.example.org:20184/hopbox?sslmode=verify-full"
ca_file = "/etc/hopbox/postgres-ca.pem"
password_file = "/etc/hopbox/postgres-password"
EOF
sudo chmod 0644 /etc/hopbox/hopboxd.toml
```

Use the host, the port, and the user of your service. The URL must have `sslmode=verify-full` and no password ([the bootstrap config of hopboxd](/reference/hopboxd-config/#keys)).

## 4. Install

Run the install of the bundle, as in [Install hopbox on a Debian 13 server by hand](/guide/install-debian/#4-install):

```sh
sudo ./hopbox-v0.2.0/hopboxd install --roles control,node --domain example.com
```

The install connects to the database first. The database has no schema yet, so this install is the first one of the install, and it needs `--domain`. It makes no Postgres cluster and no user `hopbox-pg`. A wrong CA, a wrong password, or an address outside the allowed range stops the install before it changes anything.

## 5. Check the connection

The first start of `hopboxd` runs the migrations on the database. Check its log:

```sh
sudo journalctl -u hopboxd -o cat | grep 'using the external postgres'
```

```json
{"time":"2026-10-25T10:00:00Z","level":"INFO","msg":"using the external postgres","url":"postgres://avnadmin@db.example.org:20184/hopbox","ca_file":"/etc/hopbox/postgres-ca.pem"}
```

Check that each connection of `hopboxd` uses TLS. The bundled `psql` speaks TLS too:

```sh
PGPASSWORD="$(sudo cat /etc/hopbox/postgres-password)" /opt/hopbox/current/postgres/bin/psql \
  "postgres://avnadmin@db.example.org:20184/hopbox?sslmode=verify-full&sslrootcert=/etc/hopbox/postgres-ca.pem" \
  -c "SELECT a.application_name, s.ssl FROM pg_stat_activity a JOIN pg_stat_ssl s USING (pid) WHERE a.application_name LIKE 'hopboxd%'"
```

Each row shows `t` in the column `ssl`: the pool `hopboxd`, the leader election `hopboxd-leader`, and the event subscriber `hopboxd-events`.

## If the Postgres fails over

`hopboxd` reads the schema of the control store every 10 s. If 12 reads in a row fail, it stops, and systemd starts it again. A read that takes more than 5 s counts as failed, so a store that does not answer for about 2 minutes stops `hopboxd`. A managed PostgreSQL that promotes a replica after 60 s comes back in time, and `hopboxd` only logs `reading the schema of the control store failed` with the number of failed reads. The limit of 12 reads is safe only because of a second guard. A control process that cannot renew its row in the store for 15 s fences itself. It then refuses every call, with `unavailable` and `Retry-After: 30`, and runs no control channel and no leader job, until it reaches the store again. So it never writes while the other control processes no longer count it. A client that retries, or that goes through another control server, loses nothing. See [the bundled Postgres](/reference/postgres/#two-releases-on-one-store).

## See the control processes

Each control process of the install records itself in the control store. The list shows the ones on this store, with their release and when they last renewed their row:

```sh
sudo hopboxd admin control list
```

```text
ID                                    LIVE  HOSTNAME  INTERNAL URL              RELEASE  SCHEMA  KEKS     MAINTENANCE  LAST RENEWAL
01a14404-ce7b-72d9-b18e-5006c3e462db  true  control1  https://172.31.0.11:7443  v0.2.0   45      default  off          2026-10-26T09:00:05Z
```

A process that runs an older release can hold back a migration of a newer one. The migration runner waits up to 40 s for a live process that does not run with the migration, and then it fails with the process, its host, and its release. Upgrade or stop the control role of that server first. [hopboxd](/reference/hopboxd/#admin-control-list) describes the command.

When you turn maintenance mode on with several control servers on one store, `hopboxd admin maintenance on` returns after every live control process reported that its calls, control channels, and leader jobs ended. A turn to on waits until each other live process reports that it read maintenance mode at the version that the turn wrote, and that it is drained.

A control process of a release before migration `0045` writes no row, so none of these checks sees it: the migration guard, the maintenance wait, the KEK promote, the decommission check, and the rolling upgrade order. Upgrade every control server before you rely on them.

## If the start fails

`hopboxd` exits with status 1, and systemd restarts it. The error names the cause:

| Error                                                            | What to do                                                                                                               |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `x509: certificate signed by unknown authority`                  | `postgres.ca_file` holds another CA. Download the CA of the service again.                                               |
| `x509: certificate is valid for <names>, not <host>`             | The host of `postgres.url` is not the name of the service. Use the host name from the control panel, not its IP address. |
| `password authentication failed`                                 | The password file holds another password. A newline at its end is fine.                                                  |
| `permission denied for schema public`                            | The user does not own the database. Make it the owner.                                                                   |
| `postgres.password_file: ... which lets group or others read it` | Run `sudo chmod 0400 /etc/hopbox/postgres-password`.                                                                     |

[The bundled Postgres](/reference/postgres/#external-postgres) and [the bootstrap config of hopboxd](/reference/hopboxd-config/#errors) list every error.

## Move a one-server install to the external Postgres

An install that started on one server keeps its control store in the bundled Postgres. `hopboxd admin db export` copies that store into an empty external Postgres ([hopboxd](/reference/hopboxd/#admin-db-export)). The install is in maintenance mode from the start of the copy until a control server runs on the copy ([the API server](/reference/api/#maintenance-mode)). In that window, the API takes only the reads that write nothing, `hopboxd admin` takes only `maintenance on` and `off`, and the machine URLs and the SSH front door answer no client. An open SSH session to a machine ends in the window, because its edge server cannot check its access again. The machines keep running.

### 1. Prepare the database and the files

Make an empty database, as in [step 1](#1-make-the-database). Write the CA and the password on the server with the bundled Postgres, as in [step 2](#2-write-the-ca-and-the-password-on-the-control-server). The export uses these files, and so does the control server that runs on the copy.

### 2. Copy the store

Run the export on the server with the bundled Postgres. It prints the config lines for the copy on standard output, so keep them in a file:

```sh
sudo hopboxd admin db export \
  --to 'postgres://avnadmin@db.example.org:20184/hopbox?sslmode=verify-full' \
  --ca-file /etc/hopbox/postgres-ca.pem --password-file /etc/hopbox/postgres-password | sudo tee /root/postgres.toml
```

The export checks the target before it changes anything: the TLS certificate, the major version of Postgres, the right to create tables, and an empty database. Then it turns maintenance mode on, dumps the store, restores it, and checks the row count of each table. It prints lines such as these on standard error:

```text
hopboxd: copied the control store to postgres://avnadmin@db.example.org:20184/hopbox (Postgres 18.1): migration 44, 61 tables, 2317 rows, in 4s.
hopboxd: the install stays in maintenance mode. Stop hopboxd on this server now, so that two control planes never run: sudo systemctl stop hopboxd. Then give the new control server these lines in its bootstrap config and the key files of /var/lib/hopbox/kek, start it, and run hopboxd admin maintenance off there.
```

### 3. Stop hopboxd on the source

Stop `hopboxd` at once, so the bundled store never serves again:

```sh
sudo systemctl stop hopboxd
```

The bundled cluster stays in `/var/lib/hopbox/pg`. The copy is in maintenance mode too, because the flag lives in the store.

Do not roll the source back to a release older than schema version 44 while it is in maintenance mode. Such a release does not know the flag, so it serves writes from the bundled store again.

### 4. Start the control role on the copy

The control role needs the key-encryption keys, because the store holds secrets that they seal ([Sealing](/reference/sealing/#key-files)). On the same server, the keys are in place. Add the printed keys to the table `[postgres]` of `/etc/hopbox/hopboxd.toml`, next to its other keys, and start `hopboxd`:

```sh
sudo cat /root/postgres.toml
sudo vi /etc/hopbox/hopboxd.toml
sudo systemctl start hopboxd
```

On another control server, copy the key files of `/var/lib/hopbox/kek` with their mode `0400`, the CA file, and the password file first ([Run the control role on a laptop](/guide/run-hopboxd/#add-a-second-control-server)). The start of the control role fails when the key files do not open the install CA. Then put the printed keys and `control` in `roles` into its bootstrap config, and start it.

`hopboxd` starts in maintenance mode, and logs `the install is in maintenance mode: the API takes only reads, and the control role serves no control channel. Turn it off with hopboxd admin maintenance off`.

### 5. Turn maintenance mode off

On the control server that runs on the copy:

```sh
sudo hopboxd admin maintenance off
```

The servers dial their control channels again within 30 s. Their heartbeats bring new grants of the machine leases, and the machine URLs and the SSH front door answer again. Check that each server is `ready`:

```sh
sudo hopboxd admin server list
```

### If the export fails

A refusal before the copy changes nothing, and the error ends with `The export changed nothing`. Fix the cause, such as the CA file, and run the export again.

A failure after the start of maintenance mode leaves the install in maintenance mode on its bundled Postgres. The restore runs in one transaction, so a failed restore leaves the target empty. To go back to the bundled Postgres, run on the source:

```sh
sudo hopboxd admin maintenance off
```

A failed check of the copy leaves the tables of the copy in the target. Drop the database of the target and make it again before the next export, because the export takes only an empty database.

# Run machines with Firecracker

> How to follow a machine on its node: its systemd unit, its disk, a restart of hopboxd with the machine running, and the causes of a failed boot.

This guide follows one machine on a server with the node role. It makes the machine, finds its systemd unit and its files, restarts `hopboxd` with the machine running, and deletes the machine. [The Firecracker driver](/reference/firecracker-driver/) describes each step of the driver.

The node also connects each machine to its node network. [Check the network of a machine](/guide/node-network/) follows the network of a machine.

## What you need

* A Linux server with the control role and the node role, installed as in [Install hopbox on a Debian 13 server by hand](/guide/install-debian/). The server needs KVM, systemd, and `/var/lib/hopbox` on XFS with reflinks. `sudo hopboxd admin server list` must show the server `ready`.
* The default image of the release, registered as in [Create and manage machines](/guide/machines/#register-the-default-image). The install put it in the image cache.
* The hopbox CLI, signed in to the install, as in [Use the hopbox CLI](/guide/cli/).

## Make a machine

```sh
hopbox new box1
```

The CLI waits until the machine runs. The first machine of an image takes longer, because the node unpacks the image first. On the [tested server](/reference/preflight/#the-tested-server), it takes about 25 s. The log of `hopboxd` shows each step:

```sh
sudo journalctl -u hopboxd -o cat | grep -E 'unpacked|booted|state changed'
```

```text
{"level":"INFO","msg":"unpacked the disk of an image","component":"firecracker","digest":"sha256:e591c258...","duration":22400000000}
{"level":"INFO","msg":"booted a microVM","component":"firecracker","machine":"01a1610f-...","unit":"hopbox-machine-01a1610f-....service","jail_id":1879048192,"tap":"hbt3f2c9a0b1d4e","duration":76000000}
{"level":"INFO","msg":"machine state changed","component":"executor","machine":"01a1610f-...","from":"starting","to":"running","boot_generation":0}
```

Run a command in the machine:

```sh
hopbox exec box1 uname -r
```

```text
6.1.188-hopbox1
```

## Find the unit of the machine

Each machine runs in a systemd unit of its own, in the slice `hopbox-machines.slice`:

```sh
systemctl list-units 'hopbox-machine-*'
```

```text
UNIT                                                         LOAD   ACTIVE SUB     DESCRIPTION
hopbox-machine-01a1610f-26b5-71c8-abbd-93be11b94c53.service loaded active running hopbox machine 01a1610f-26b5-71c8-abbd-93be11b94c53
```

The main process of the unit is Firecracker. It runs as the jail user of the machine, in the jail of the machine. The journal of the unit holds the serial console of the guest and the log of Firecracker:

```sh
sudo journalctl -u hopbox-machine-01a1610f-26b5-71c8-abbd-93be11b94c53.service
```

## Look at the disk

The disk of the machine is a reflink copy of the image, as large as the disk size of the machine. Only the blocks that the machine writes take space of their own:

```sh
sudo du -h --apparent-size /var/lib/hopbox/machines/01a1610f-26b5-71c8-abbd-93be11b94c53/disk.raw
sudo du -h /var/lib/hopbox/machines/01a1610f-26b5-71c8-abbd-93be11b94c53/disk.raw
```

The first command prints the size of the disk, 94G for 100 GB. The second prints the space of the file system that the file uses, at most the size of the image. The blocks that the disk shares with the image count in it too.

## Restart hopboxd

A restart or an upgrade of `hopboxd` stops only the processes of `hopboxd.service`. The unit of the machine is not one of them:

```sh
systemctl show -P MainPID hopbox-machine-01a1610f-26b5-71c8-abbd-93be11b94c53.service
sudo systemctl restart hopboxd
systemctl show -P MainPID hopbox-machine-01a1610f-26b5-71c8-abbd-93be11b94c53.service
hopbox exec box1 uptime
```

Both commands print the same PID, and `uptime` shows that the machine did not boot again. The new `hopboxd` logs `attached to a microVM` for the machine. Then it gives the machine a new link key, and the guest agent connects again.

## Reboot the server

A reboot or a shutdown of the server shuts each guest down cleanly. You do not need to stop the machines first. The unit of each machine runs `hopboxd stop-guest` at its stop, which asks the guest to shut down. Look at the stop command of the unit:

```sh
systemctl show -P ExecStop hopbox-machine-01a1610f-26b5-71c8-abbd-93be11b94c53.service
```

The output names `/opt/hopbox/current/hopboxd stop-guest`, with the API socket of the machine. At a shutdown, systemd stops `hopboxd` first and then the machines. Each guest writes its data to the disk, and unmounts its file systems. If a guest does not end within 30 s, systemd kills its Firecracker.

After the boot of the server, `hopboxd` boots each machine with the target `running` again. A machine that ran before the reboot thus runs again, with its disk:

```sh
sudo systemctl reboot
```

After the reboot, `hopbox exec box1 uptime` shows a new boot of the machine. A microVM that an older release booted can have no `ExecStop`. Stop and start such a machine once, so that its unit gets one.

Do not stop a machine with `systemctl stop` on the server. `hopboxd` did not ask for that stop, so the restart policy applies ([the Firecracker driver](/reference/firecracker-driver/#a-stop-through-systemd)). Use `hopbox machine stop` instead.

## Stop, start, and delete

```sh
hopbox machine stop box1
hopbox machine start box1
hopbox machine delete box1
```

A stop asks the guest to shut down, and kills the microVM after 30 s. A start boots the machine from its disk, so the files of the machine stay. A delete stops the microVM, and removes its unit, its disk, its jail, and its tap device.

## When a boot fails

A machine whose boot fails gets the state `failed` ([the node executor](/reference/executor/#actions)). The log of `hopboxd` holds the error of the boot, in the record `a machine action failed` of the executor:

```sh
sudo journalctl -u hopboxd -o cat | grep 'a machine action failed'
```

These are the common causes:

| Error                                                                          | What to do                                                                                   |
| ------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| `the node has no guest kernel with the sha256 <sha256>, which the image needs` | Install the release that shipped the image. Its install adds its kernel to the kernel cache. |
| `the image cache has no image <digest>, and the image has no URL`              | Install the release of the image, or register the image with `--url`.                        |
| `the file system of <dir> has no reflinks`                                     | Put `/var/lib/hopbox` on XFS made with `mkfs.xfs -m reflink=1`.                              |
| `the jailer or Firecracker ended at its start`                                 | Read the journal of the unit. The error names it.                                            |

After a failed boot, no microVM of the machine runs. The restart policy `always` boots the machine again after a backoff.

## Run the KVM tests

`make test-kvm` runs the same steps on a test host, with names of its own for the units and the tap devices.

# First sign-in on a new install

> How the first instance admin signs in to a new install with a login link, reads the audit log, and turns on magic links.

A new install has no SMTP config and no OAuth app, and hopbox has no passwords. So the first instance admin signs in through a one-time login link that root prints on a control server. This guide signs in that way on a laptop. Then it reads the account and the audit log, and sets up magic links for everyone else.

This guide calls the API with curl, in the same way as the console does, so it shows each call. [Use the console](/guide/console/) signs in with the same link in a browser.

## What you need

* `hopboxd` with the control role on a laptop, as in [Run the control role on a laptop](/guide/run-hopboxd/). This guide uses its bootstrap config `/tmp/hb/hopboxd.toml` and the API on `127.0.0.1:7080`.
* curl.
* For magic links: an SMTP server. A local mail catcher such as [Mailpit](https://mailpit.axllent.org) works, on `127.0.0.1:1025`. Without one, use the file mail transport, as in [Magic links without an SMTP server](#magic-links-without-an-smtp-server).

Start `hopboxd`, and leave it running:

```sh
./bin/darwin_arm64/hopboxd run --config /tmp/hb/hopboxd.toml
```

In a second terminal, define a short name for the admin command:

```sh
admin() { ./bin/darwin_arm64/hopboxd admin --config /tmp/hb/hopboxd.toml "$@"; }
```

On a server, the same commands run as root: `sudo hopboxd admin ...`.

## Set the domain

A link points at the domain of the install, so the install needs one first:

```sh
admin config set --domain example.com
```

```text
domain  example.com
public_addresses  -
acme_directory_url  https://acme-v02.api.letsencrypt.org/directory
acme_email  -
acme_terms_agreed  false
mail_transport  smtp
version  2
update_time  2026-10-16T09:09:15Z
```

Without a domain, `login-link` fails with `failed_precondition`.

## Print the login link

```sh
admin login-link --email root@example.org
```

```text
https://example.com/auth/login-link#token=tOzJ8YQyibHutrU34tIWLHnGd5XlzYs4WoIBXgSDh5I
The link signs in root@example.org once, until 2026-10-16T09:24:15Z.
```

The link works once, for 15 minutes. Treat it as a password until then. The audit log records that root made it, but never the token ([Sessions, cookies, and sign-in links](/reference/sessions/#first-admin-login-links)).

On an install with an edge, you open this link in a browser ([Use the console](/guide/console/#sign-in)). The console page reads the token after `#token=` and calls `VerifyLoginLink`. Here, you make that call yourself.

## Sign in with the link

Put the token in a shell variable, and call `VerifyLoginLink`:

```sh
TOKEN=tOzJ8YQyibHutrU34tIWLHnGd5XlzYs4WoIBXgSDh5I
curl -s -D /tmp/hb/headers -X POST -H 'Content-Type: application/json' \
  -H 'Connect-Protocol-Version: 1' -H 'Origin: https://example.com' \
  -d "{\"token\":\"$TOKEN\"}" \
  http://127.0.0.1:7080/hopbox.v1.AuthService/VerifyLoginLink
```

```json
{"account":{"id":"01a143f9-1cee-7ec0-9238-7976abaacfd6", "emails":[{"email":"root@example.org"}], "instanceAdmin":true, "personalOrgId":"01a143f9-1cee-7ec1-a648-71fea47ae54f", "version":"1", "createTime":"2026-10-16T09:09:21.774252Z"}, "newAccount":true, "sessionExpireTime":"2026-11-15T09:09:21.774252Z"}
```

The link created your account, made it an instance admin, and gave it a personal org. Your email stays unverified. So a later magic link or GitHub sign-in with the same email reaches another account ([Sessions, cookies, and sign-in links](/reference/sessions/#what-a-sign-in-does)).

The two headers `Origin` and `Connect-Protocol-Version` are what the console sends. Without them, the call fails with `permission_denied`, so no page of another site can sign a browser in. Try the link a second time, and it fails with `unauthenticated`: it works once.

The response sets the session cookie. The cookie has the `Secure` flag, so curl does not send it back over plain HTTP. Copy it from the saved headers:

```sh
COOKIE=$(sed -n 's/^Set-Cookie: \(__Host-hopbox_session=[^;]*\).*/\1/p' /tmp/hb/headers)
browser() {
  curl -s -X POST -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
    -H 'Origin: https://example.com' -H "Cookie: $COOKIE" "$@"
}
```

The session lasts 30 days. After 7 days without a call, it ends before that ([Sessions, cookies, and sign-in links](/reference/sessions/#lifetimes)).

## Read your account

```sh
browser -d '{}' http://127.0.0.1:7080/hopbox.v1.AccountService/GetAccount
```

```json
{"account":{"id":"01a143f9-1cee-7ec0-9238-7976abaacfd6", "emails":[{"email":"root@example.org"}], "instanceAdmin":true, "personalOrgId":"01a143f9-1cee-7ec1-a648-71fea47ae54f", "version":"1", "createTime":"2026-10-16T09:09:21.774252Z"}}
```

The same call from another origin fails. A page that a machine serves, such as `https://box1.example.com`, is another origin too:

```sh
curl -s -X POST -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
  -H 'Origin: https://evil.example' -H "Cookie: $COOKIE" -d '{}' \
  http://127.0.0.1:7080/hopbox.v1.AccountService/GetAccount
```

```json
{"code":"unauthenticated","message":"the credential is not valid"}
```

## Read the audit log of the install

An instance admin reads the audit log of the whole install:

```sh
browser -d '{"wholeInstall":true}' http://127.0.0.1:7080/hopbox.v1.AuditService/ListAuditEntries
```

The newest entries come first: `instance_admin.grant`, `auth.sign_in`, and `account.create` by your session, then `login_link.create` and `install_config.update` by `local_root` ([the sign-in, account, and audit API](/reference/auth-api/#listauditentries)).

## Turn on magic links

Magic links let everyone else sign up and sign in by email. They need an SMTP config ([SMTP config](/reference/smtp/)). A password needs a key-encryption key to seal it, so make the first one now:

```sh
admin kek rotate
```

```text
file:1
```

For a local mail catcher without TLS and without a login:

```sh
admin config smtp set --host 127.0.0.1 --port 1025 --tls none --from 'hopbox <no-reply@example.org>'
```

For a real SMTP server, pass the password on standard input, so it never shows in the process list:

```sh
printf '%s\n' "$SMTP_PASSWORD" | admin config smtp set \
  --host smtp.example.org --username hopbox@example.org --password-stdin \
  --from 'hopbox <no-reply@example.org>'
```

The install now lists the email link as a sign-in method:

```sh
curl -s --http2-prior-knowledge \
  'http://127.0.0.1:7080/hopbox.v1.InstallService/GetInstallInfo?encoding=json&message=%7B%7D'
```

```json
{"domain":"example.com", "signInMethods":["SIGN_IN_METHOD_EMAIL_LINK"], "version":"v0.0.0-20261016090852-6a5e58e824e1"}
```

Ask for a link:

```sh
curl -s -X POST -H 'Content-Type: application/json' -d '{"email":"ann@example.org"}' \
  http://127.0.0.1:7080/hopbox.v1.AuthService/RequestMagicLink
```

```json
{}
```

The email holds a link of the form `https://example.com/auth/email#token=<token>`. Sign in with its token as above, with `VerifyMagicLink` in place of `VerifyLoginLink`. The first sign-in creates the account of Ann and her personal org. An email gets at most 5 links an hour ([Sessions, cookies, and sign-in links](/reference/sessions/#rate-limits)). If the SMTP server fails, the call gets `unavailable`, and the log of `hopboxd` has the record `the magic link email failed` with the cause.

## Magic links without an SMTP server

A dev or test install often has no SMTP server. The file mail transport then writes each mail to a file on the server, and sends nothing ([Mail](/reference/mail/)). A production install uses SMTP, because with files no person gets a mail.

Turn on the file transport. It needs no SMTP config:

```sh
admin config set --mail-transport file
```

The output has the line `mail_transport file`. `hopboxd` logs `mail goes to files, not to recipients` at level warn, and again with each mail.

Ask for a link, as above:

```sh
curl -s -X POST -H 'Content-Type: application/json' -d '{"email":"ann@example.org"}' \
  http://127.0.0.1:7080/hopbox.v1.AuthService/RequestMagicLink
```

List the mail files of the server, newest first:

```sh
admin mail list
```

```text
20261016T091530.120044000Z-5cb912a8d0bb45d7.eml  2026-10-16T09:15:30Z  <ann@example.org>  Sign in to example.com
```

Print the newest file. The text has the link whole, on one line:

```sh
admin mail show
```

```text
name  20261016T091530.120044000Z-5cb912a8d0bb45d7.eml
create_time  2026-10-16T09:15:30Z
to  <ann@example.org>
subject  Sign in to example.com


Open this link to sign in to example.com:


https://example.com/auth/email#token=Zm9vYmFyYmF6cXV4cXV1eGNvcmdlZ3JhdWx0Z2FycGx5


The link works once, for 15 minutes. If you did not ask for it, you can ignore this email.
```

Sign in with its token as above, with `VerifyMagicLink` in place of `VerifyLoginLink`. On a server, run `sudo hopboxd admin mail show` on the control server that took the request. Only root on that server reads the files, which live in `<data_dir>/mail` with mode `0700`.

When the install gets an SMTP server, set its config, then switch back:

```sh
admin config set --mail-transport smtp
```

## Keep a second instance admin

An install keeps at least one instance admin, so `admin instance-admin revoke` refuses the last one. Make a second admin first, for example the account of Ann, by her verified email:

```sh
admin instance-admin grant --email ann@example.org
admin instance-admin list
```

```text
01a143f9-1cee-7ec0-9238-7976abaacfd6  root@example.org (unverified)  2026-10-16T09:09:21Z
01a14411-5a20-7d3e-9f0e-0c6c2b3e4a51  ann@example.org  2026-10-16T09:20:02Z
```

Root on a control server can always print a new login link, or grant the role again. So a lost session never locks the operator out.

## Sign out

```sh
browser -d '{}' http://127.0.0.1:7080/hopbox.v1.AuthService/SignOut
```

The response clears the cookie, and the session ends. The next call with the old cookie runs as an anonymous caller, and a call that needs a credential gets `unauthenticated`.

# Sign in with GitHub and Google

> How an operator registers the GitHub OAuth app and the Google OAuth client of an install, gives hopbox their clients, and signs in with GitHub.

People can sign up and sign in to an install with GitHub or Google. hopbox cannot register the OAuth apps for you. Each app has redirect URIs on the domain of one install, and its client secret belongs to you. So you register one app at each provider, and give hopbox the client ID and the secret. This guide does that for GitHub and Google. Then it signs in with GitHub on a laptop install and reads the new account.

The first sign-in with GitHub makes an account and a personal org. This is task 1 of the end of phase 1. [Sign-in with GitHub and Google](/reference/oauth/) has every rule of the flow.

## What you need

* `hopboxd` with the control role, with a domain and a key-encryption key, as in [First sign-in on a new install](/guide/first-sign-in/). This guide uses the laptop install of that guide, with the domain `example.com` and the API on `127.0.0.1:7080`.
* An account at GitHub, and for Google, a Google Cloud project.
* A web browser and curl.

Define the short name for the admin command, as in [First sign-in on a new install](/guide/first-sign-in/):

```sh
admin() { ./bin/darwin_arm64/hopboxd admin --config /tmp/hb/hopboxd.toml "$@"; }
```

## Print the redirect URIs

Each provider sends the browser back to one redirect URI on the domain of the install. Print the URIs to register:

```sh
admin config oauth
```

```text
github  off  -  https://example.com/auth/github/callback
google  off  -  https://example.com/auth/google/callback
```

Register the exact URI, and keep the exact matching of the provider. Only with exact matching does the provider refuse a sign-in with another URI.

## Register the GitHub OAuth app

1. On GitHub, open Settings, then Developer settings, then OAuth Apps, and click New OAuth App. For an app that an organization owns, open the settings of the organization instead.

2. Fill in the form:

   | Field                      | Value                                      |
   | -------------------------- | ------------------------------------------ |
   | Application name           | `hopbox`                                   |
   | Homepage URL               | `https://example.com`                      |
   | Authorization callback URL | `https://example.com/auth/github/callback` |
   | Enable Device Flow         | off                                        |

3. Click Register application. Copy the Client ID.

4. Click Generate a new client secret, and copy the secret. GitHub shows it only once.

5. In the settings of the app, turn off wildcard matching for the callback URL. With wildcard matching, GitHub also takes a redirect URI on a subdomain or in a subdirectory of the callback URL. A machine URL such as `https://box1.example.com` is a subdomain of the install, and it serves the content of a user. So without this step, a link can send the code of a sign-in to a machine. hopbox still sends the exact redirect URI in the token request, and the code needs the state cookie and the PKCE verifier. But the code must not leave the install at all.

Use an OAuth app, not a GitHub App. hopbox asks only for the scope `user:email`, to read the emails and whether GitHub verified them.

## Register the Google OAuth client

1. In the Google Cloud console, select the project, and open Google Auth Platform.
2. On the page Branding, fill in the app name, the user support email, and the developer contact email. Add the domain of the install as an authorized domain, for example `example.com`.
3. On the page Audience, choose the user type External. While the app has the publishing status Testing, only test users can sign in. Add each Google account that must sign in as a test user.
4. On the page Data Access, add the scopes `openid`, `email`, and `profile`. These scopes are not sensitive, so the app needs no verification by Google for them.
5. On the page Clients, click Create client. Choose the application type Web application.
6. Under Authorized redirect URIs, add `https://example.com/auth/google/callback`. Google matches this URI exactly.
7. Click Create. Copy the client ID and the client secret at once. Google shows a new client secret only at its creation. If you lose it, add a new secret to the client.

## Give hopbox the clients

Pass each secret on standard input, so it never shows in the process list or in the shell history:

```sh
read -rs GITHUB_CLIENT_SECRET
printf '%s\n' "$GITHUB_CLIENT_SECRET" | admin config oauth set github \
  --client-id Ov23liExampleClient --client-secret-stdin
```

```text
github  on  Ov23liExampleClient  https://example.com/auth/github/callback
```

```sh
read -rs GOOGLE_CLIENT_SECRET
printf '%s\n' "$GOOGLE_CLIENT_SECRET" | admin config oauth set google \
  --client-id 123-abc.apps.googleusercontent.com --client-secret-stdin
```

```text
google  on  123-abc.apps.googleusercontent.com  https://example.com/auth/google/callback
```

hopbox seals each secret with the current key-encryption key ([Sealing](/reference/sealing/)). Without a key, the command fails and asks you to run `admin kek rotate`. On a server, run the same commands as root: `sudo hopboxd admin config oauth set ...`.

The install now offers both providers:

```sh
curl -s -X POST -H 'Content-Type: application/json' -d '{}' \
  http://127.0.0.1:7080/hopbox.v1.InstallService/GetInstallInfo
```

```json
{"domain":"example.com", "signInMethods":["SIGN_IN_METHOD_GITHUB", "SIGN_IN_METHOD_GOOGLE"], "version":"v0.1.0"}
```

## Sign in with GitHub

On an install with an edge and a console, a person clicks Sign in with GitHub, and the browser does every step on its own. The laptop install of this guide runs no edge role, so its API answers only on `127.0.0.1` over plain HTTP. Here you do the two steps of hopbox with curl, and only the step at GitHub in the browser.

Start the sign-in. Save the headers, which hold the URL of GitHub and the state cookie:

```sh
curl -s -o /dev/null -D /tmp/hb/start 'http://127.0.0.1:7080/auth/github/start?return_to=/'
sed -n 's/^Location: //p' /tmp/hb/start
```

```text
https://github.com/login/oauth/authorize?client_id=Ov23liExampleClient&code_challenge=...&code_challenge_method=S256&redirect_uri=https%3A%2F%2Fexample.com%2Fauth%2Fgithub%2Fcallback&response_type=code&scope=user%3Aemail&state=...
```

The domain `example.com` of this guide is a public host that is not your install. Before you open the URL, map the domain to your laptop in `/etc/hosts`:

```sh
echo '127.0.0.1 example.com' | sudo tee -a /etc/hosts
```

Without this line, the browser sends the code and the state of the sign-in to the public host `example.com`. A browser with its own DNS-over-HTTPS resolver, or with `example.com` in its cache, can skip the line. So before the sign-in, open `https://example.com/` in the browser, and make sure that it shows a refused connection, not the public page of `example.com`. If it shows the public page, turn off the secure DNS setting of the browser for this test, restart the browser, and open the page again.

Open that URL in the browser, and click Authorize. GitHub then sends the browser to `https://example.com/auth/github/callback?code=...&state=...`. The name now points at `127.0.0.1`, and the install does not listen on port 443, so the browser shows an error page for a refused connection. Copy the whole URL from the address bar into a shell variable:

```sh
CALLBACK='https://example.com/auth/github/callback?code=...&state=...'
```

The code works once, for a few minutes. Send it to hopbox with the state cookie of the start, as the browser does:

```sh
STATE=$(sed -n 's/^Set-Cookie: \(__Host-hopbox_oauth_github=[^;]*\).*/\1/p' /tmp/hb/start)
curl -s -D /tmp/hb/callback -H "Cookie: $STATE" "http://127.0.0.1:7080${CALLBACK#https://example.com}"
grep -E '^(HTTP/|Location:)' /tmp/hb/callback
```

```text
HTTP/1.1 303 See Other
Location: /
```

The callback compared the state of the URL with the state of the cookie. Then it traded the code at GitHub, read your primary email, and made your account with a personal org. Your email is verified, because GitHub verified it. Without the cookie, the callback fails with `400`, so a link from another site cannot end a sign-in in your browser ([Sign-in with GitHub and Google](/reference/oauth/#callback)).

Copy the session cookie, and read your account:

```sh
COOKIE=$(sed -n 's/^Set-Cookie: \(__Host-hopbox_session=[^;]*\).*/\1/p' /tmp/hb/callback)
curl -s -X POST -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
  -H 'Origin: https://example.com' -H "Cookie: $COOKIE" -d '{}' \
  http://127.0.0.1:7080/hopbox.v1.AccountService/ListSignInMethods
```

```json
{"methods":[{"id":"01a14f02-6b1e-7d4c-9a51-2b1c5e8f0a7d", "method":"SIGN_IN_METHOD_GITHUB", "email":"ann@example.org", "lastUseTime":"2026-10-21T09:12:04.118Z", "createTime":"2026-10-21T09:12:04.118Z"}]}
```

Your login-link account from [First sign-in on a new install](/guide/first-sign-in/) has an unverified email, so the GitHub sign-in made a new account. To make it an instance admin too, grant the role by its verified email:

```sh
admin instance-admin grant --email ann@example.org
```

A sign-in with Google works in the same way, with `/auth/google/start` and the cookie `__Host-hopbox_oauth_google`. If an account holds the same verified email, Google links to that account. So you get one account with two sign-in methods ([Sessions, cookies, and sign-in links](/reference/sessions/#what-a-sign-in-does)).

After the sign-ins, remove the line `127.0.0.1 example.com` from `/etc/hosts`. This command works on macOS and Linux, and keeps a copy of the old file in `/etc/hosts.bak`:

```sh
sudo sed -i.bak '/^127\.0\.0\.1 example\.com$/d' /etc/hosts
```

## Try a server before it has an edge

A server without the edge role answers only on `127.0.0.1:7080` ([the edge role](/reference/edge/)). Until the server runs the edge role, forward the port, and run the same steps on your laptop against the forward:

```sh
ssh -N -L 7080:127.0.0.1:7080 debian@203.0.113.10
```

Through the tunnel, the commands and the `Origin` header use the domain of the server install.

When the edge role serves the install over HTTPS, open `https://example.com/auth/github/start` in the browser, and the browser does every step. The edge then passes the address of each client, so the rate limits of a client apply ([Sign-in with GitHub and Google](/reference/oauth/#rate-limits)).

## When a sign-in fails

The failed step answers with a plain text page that says why, and a request ID for the server log ([Sign-in with GitHub and Google](/reference/oauth/#errors)).

| Message                                                                                  | What to do                                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `the sign-in is not valid: it did not start in this browser, it was used, or it expired` | Start the sign-in again. A flow lasts 10 minutes, and works once.                                                                                                                                                                                                   |
| `the provider has not verified an email of this account`                                 | At GitHub, verify an email and make it the primary email. At Google, use an account with a verified email.                                                                                                                                                          |
| `the provider did not approve the sign-in: GitHub refused the sign-in code`              | Compare the client secret and the redirect URI with the app at GitHub. The log record `oauth sign-in refused by the provider` has the answer of GitHub.                                                                                                             |
| `failed precondition: this install has no GitHub client`                                 | Run `admin config oauth set github`.                                                                                                                                                                                                                                |
| `the sign-in conflicts with a sign-in method of the account`                             | The account holds another GitHub user. If the person lost it, sign in with a magic link and remove the old method. Without another method, run `admin account sign-in-method remove` ([Sign-in with GitHub and Google](/reference/oauth/#recover-a-lost-identity)). |

To turn a provider off, clear its client. The accounts keep their sign-in methods, which work again after a new set:

```sh
admin config oauth clear google
```

# Install hopbox on a Debian 13 server by hand

> How to install hopbox on a Debian 13 server by hand, the path that the Terraform provider automates, and how to upgrade it and roll it back.

This guide installs hopbox on one Debian 13 server with the control role and the node role, then upgrades it and rolls it back. [Serve the domain of an install with the DNS role](/guide/dns-role/) adds the DNS role.

The hopbox Terraform provider does these steps for each server of an install ([Install hopbox on an OVHcloud server with Terraform](/guide/install-on-ovhcloud/)). Use this guide to try a release bundle on a test server, or to see what the provider does. An install of the hosted service gets its servers only from the provider.

The release files of hopbox are not public yet. The hopbox team gives them on request.

## What you need

* A Debian 13 server for `amd64`, with KVM and root access. The preflight check tells you what is missing ([the preflight check](/reference/preflight/)).
* The package of the tested host kernel `6.18.57-hopbox1`, `linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb`, and its `.sha256` file, from the release files. Step 1 installs it. With another kernel, the install goes on with a warning.
* A free disk or partition for `/var/lib/hopbox`. The disks of machines need XFS with reflinks there.
* The release bundle `hopbox-v0.1.0-linux-amd64.tar.gz` and its `.sha256` file, from the release files. The people who work on hopbox can build them with `make bundle` instead.
* A domain for the install, such as `example.com`.

## 1. Install the host kernel

The host kernel `6.18.57-hopbox1` is the kernel that hopbox tests ([Host kernel](/reference/host-kernel/)). The Debian kernels stay installed as fallbacks. Copy the package and its checksum file to the server, then check the package there:

```sh
scp linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb* root@server:/root/
ssh root@server
cd /root
sha256sum -c linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb.sha256
dpkg -i linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb
ls /boot/vmlinuz-6.18.57-hopbox1 /boot/initrd.img-6.18.57-hopbox1
```

`sha256sum` prints `linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb: OK`. If it prints `FAILED`, do not install the package. The pin below makes it the default of GRUB, also after a later upgrade of the Debian kernel.

GRUB names each menu entry after the UUID of the root file system, so the pin uses the ID of the entry. Read the UUID first:

```sh
uuid="$(findmnt -no UUID /)"
echo "$uuid"
```

If `echo` prints nothing, stop: the pin needs the UUID. Else write the pin, and make sure that `grub.cfg` has the entry:

```sh
mkdir -p /etc/default/grub.d
printf 'GRUB_DEFAULT="gnulinux-advanced-%s>gnulinux-6.18.57-hopbox1-advanced-%s"\n' "$uuid" "$uuid" \
  > /etc/default/grub.d/20_hopbox_kernel.cfg
update-grub
grep -F "'gnulinux-6.18.57-hopbox1-advanced-$uuid'" /boot/grub/grub.cfg
```

The `grep` prints the line of the entry. If it prints nothing, `grub.cfg` has no entry for the kernel. Then remove `/etc/default/grub.d/20_hopbox_kernel.cfg`, run `update-grub` again, and keep the Debian kernel.

Reboot, and check the kernel after the reboot:

```sh
reboot
```

```sh
uname -r
```

```text
6.18.57-hopbox1
```

On the tested server, SSH answered 187 to 319 seconds after the reboot.

## 2. Make the XFS file system

Install the XFS tools, and make the file system with reflinks on the free partition. This example uses `/dev/md3`. Use the name of your partition.

```sh
sudo apt-get install -y xfsprogs
sudo mkfs.xfs -m reflink=1 /dev/md3
sudo mkdir -p /var/lib/hopbox
echo '/dev/md3 /var/lib/hopbox xfs defaults 0 2' | sudo tee -a /etc/fstab
sudo mount /var/lib/hopbox
```

`mkfs.xfs` erases the partition. Check the name of the partition before you run it.

## 3. Copy and check the bundle

Copy the bundle and its checksum file to the server, then check it there:

```sh
scp hopbox-v0.1.0-linux-amd64.tar.gz* root@server:/root/
ssh root@server
cd /root
sha256sum -c hopbox-v0.1.0-linux-amd64.tar.gz.sha256
```

`sha256sum` prints `hopbox-v0.1.0-linux-amd64.tar.gz: OK`.

## 4. Install

Unpack the bundle, and run its `hopboxd install` as root:

```sh
tar -xzf hopbox-v0.1.0-linux-amd64.tar.gz
sudo ./hopbox-v0.1.0/hopboxd install --roles control,node --domain example.com
```

The install copies the release to `/opt/hopbox/releases/v0.1.0`, makes the users, the dirs, the config, the first key-encryption key, and the Postgres cluster. It reserves the SSH ports, writes the systemd units, runs the preflight check, and starts `hopboxd` ([hopboxd](/reference/hopboxd/#install)). It prints the preflight check, log records, and these last lines:

```text
hopboxd: installed v0.1.0, and hopboxd runs. Changed: users, release files, keys, postgres, ports, config, release, units.
v0.1.0
```

The Terraform provider also passes `--bootstrap-admin-key-hash` with the hash of the first admin API key. At its first start, the control role registers that hash as the admin API key `bootstrap` and removes the file ([Server layout](/reference/server-layout/#the-bootstrap-admin-api-key)). A server that you install by hand does not need it: root makes admin keys with `hopboxd admin admin-key create` ([hopboxd](/reference/hopboxd/#admin-admin-key-create)).

Check that `hopboxd` runs, and that the install has its domain:

```sh
systemctl status hopboxd
sudo hopboxd admin config get
```

`systemctl status` shows `active (running)`. `admin config get` prints `domain example.com`. The log of `hopboxd` is in the journal: `journalctl -u hopboxd`.

You can run the install again at any time. With the same flags, it changes nothing and does not restart `hopboxd`:

```text
$ sudo hopboxd install --roles control,node
hopboxd: installed v0.1.0, and hopboxd runs. Nothing changed.
v0.1.0
```

## 5. Enroll the node role

The node role of the server enrolls with the control role of the same server ([Enroll the node role on one server](/guide/enroll-node/)). Make an enrollment token, and give it to the install:

```sh
TOKEN="$(sudo hopboxd admin enrollment-token create)"
sudo HOPBOX_ENROLLMENT_TOKEN="$TOKEN" hopboxd install --roles control,node
sudo hopboxd admin server list
```

The install prints `hopboxd: enrolled as the server <id>.` Within a few seconds, `admin server list` shows the server as `ready`.

## 6. Sign in

Make a login link for the first instance admin, and open it ([First sign-in on a new install](/guide/first-sign-in/)):

```sh
sudo hopboxd admin login-link --email you@example.org
```

## Upgrade

Copy the new bundle and its checksum file to the server. Then run:

```sh
sudo hopboxd upgrade --bundle hopbox-v0.2.0-linux-amd64.tar.gz \
  --sha256 "$(cut -d' ' -f1 hopbox-v0.2.0-linux-amd64.tar.gz.sha256)"
```

The upgrade unpacks the bundle to `/opt/hopbox/releases/v0.2.0` and runs the install of the new release ([hopboxd](/reference/hopboxd/#upgrade)). That install restarts `hopboxd`. The running machines stay up, because they run in `hopbox-machines.slice`, outside `hopboxd.service`. The data stays: the config, the keys, the cluster, and the identity of the server.

If the new release has another major version of Postgres, the upgrade stops before the switch, and the old release keeps running. The error starts with `postgres data dir /var/lib/hopbox/pg/data holds a Postgres 18 cluster`. The same holds for a release that does not run with the newest schema migration of the control store ([the bundled Postgres](/reference/postgres/#two-releases-on-one-store)).

An install with more than one server upgrades one server at a time: first the control servers, then the edge and DNS servers, then the nodes. The hopbox Terraform provider keeps this order ([hopbox Terraform provider](/reference/terraform-provider/#rolling-upgrade)). The release before can run beside the new one, so the servers that wait keep working.

## Roll back

The server keeps the previous release. To go back to it, run:

```sh
sudo hopboxd upgrade --rollback
```

A rollback cannot undo a schema migration of the newer release. Each migration names the oldest release that runs with it. If the newer release applied a migration that does not allow the previous release, the rollback stops before the switch, and the newer release keeps running. The error starts with `the control store has the schema migration`. Upgrade to a release that knows the migrations instead ([hopboxd](/reference/hopboxd/#upgrade)).

v0.1.0 runs only on a store whose migrations it knows. So a rollback from v0.2.0 to v0.1.0 stops with that error. A rollback from a later release, such as v0.3.0, to v0.2.0 works when the migrations of v0.3.0 allow v0.2.0. Then `readlink /opt/hopbox/current` prints `releases/v0.2.0`, and `readlink /opt/hopbox/previous` prints `releases/v0.3.0`. A second rollback goes forward again.

## If the install stops

The install makes every check before it changes the config, the current release, or the units. So after a refusal, fix the cause and run the same command again.

| Message                                                                              | Fix                                                                                                                                           |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `/var/lib/hopbox is on ext4, but the disks of machines need XFS with reflinks there` | Do step 2.                                                                                                                                    |
| `the preflight check failed, so this server cannot run machines`                     | Fix each failed check that the lines above it list, such as KVM in the firmware ([the preflight check](/reference/preflight/)).               |
| `--domain is required on the first install of the control role on a server`          | Add `--domain`.                                                                                                                               |
| `/usr/local/bin has mode 0775, which lets group or others change it`                 | A Debian host that was upgraded from an old release can have the mode 2775 with the group `staff` there. Run `sudo chmod 755 /usr/local/bin`. |
| `/opt/hopbox/releases belongs to uid 1000, ...`                                      | Run `sudo chown root:root` on the dir that the message names.                                                                                 |
| `hopboxd v0.2.0 did not start`                                                       | Read `journalctl -u hopboxd`, then run `sudo hopboxd upgrade --rollback`.                                                                     |

[Server layout](/reference/server-layout/) lists every path, user, and unit of the install.

# Install hopbox on an OVHcloud server with Terraform

> How to install hopbox on an OVHcloud server with Terraform, and how to upgrade, import, and destroy it.

This guide makes a new install of hopbox on one OVHcloud dedicated server with the hopbox Terraform provider. The server gets every role. The provider adopts a server that your account rents, or orders a new one ([Order a new server](#order-a-new-server)) and pays for it. Then the guide upgrades the server, changes its labels, imports it into a new state, and destroys it.

hopbox supports only the servers that this provider sets up. [hopbox Terraform provider](/reference/terraform-provider/) lists every attribute and each step that the provider takes. [Install hopbox on a Debian 13 server by hand](/guide/install-debian/) shows the same install by hand.

The release files of hopbox are not public yet. The hopbox team gives them on request.

The apply erases the server. Back up anything on it first.

## What you need

* An OVHcloud dedicated server with KVM, rented in your account. The [tested server](/reference/preflight/#the-tested-server) has an Intel Xeon E5-1650 v4 CPU. You need its service name, such as `ns1234567.ip-198-51-100.eu`. The OVHcloud manager shows it. To order a new server instead, you need a payment method in the account and the budget for a monthly rental. See [Order a new server](#order-a-new-server).
* An OVHcloud API application and a consumer key with the rights of [step 1](#1-make-the-ovhcloud-api-keys).
* A Mac with Apple Silicon or a Linux host on x86_64, with Terraform 1.5 or later. This example uses the Mac.
* The release files of v0.1.0, from the hopbox team ([2. Check the release files](#2-check-the-release-files)).
* A domain for the install, such as `example.com`.
* An SSH key pair for the operators, without a passphrase. This example uses `~/.ssh/id_ed25519`.

## 1. Make the OVHcloud API keys

Make an application and a consumer key on the page `https://eu.api.ovh.com/createToken/`. Give the consumer key these rights, and no other:

| Method | Path                            |
| ------ | ------------------------------- |
| `GET`  | `/dedicated/server/*`           |
| `POST` | `/dedicated/server/*/reinstall` |

To order new servers, also give it these rights ([hopbox Terraform provider](/reference/terraform-provider/#ovhcloud-api-rights)):

| Method   | Path            |
| -------- | --------------- |
| `GET`    | `/me`           |
| `GET`    | `/order/cart`   |
| `POST`   | `/order/cart`   |
| `GET`    | `/order/cart/*` |
| `POST`   | `/order/cart/*` |
| `DELETE` | `/order/cart/*` |
| `GET`    | `/me/order/*`   |

A key with `POST /order/cart/*` can pay for orders with the payment method of the account. Give it only to the people who are allowed to spend that money.

Keep the values in your shell, not in a file:

```sh
export OVH_ENDPOINT=ovh-eu
export OVH_APPLICATION_KEY=...
export OVH_APPLICATION_SECRET=...
export OVH_CONSUMER_KEY=...
```

## 2. Check the release files

Put these release files in one folder, such as `~/hopbox-release`:

| File                                                                     | What it holds                                                                                                 |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `terraform-provider-hopbox_0.1.0_darwin_arm64.zip`                       | The provider for a Mac with Apple Silicon. Linux hosts use `terraform-provider-hopbox_0.1.0_linux_amd64.zip`. |
| `hopbox-v0.1.0-linux-amd64.tar.gz` and its `.sha256` file                | The release bundle of the servers ([Release bundle](/reference/release-bundle/)).                             |
| `linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb` and its `.sha256` file | The tested host kernel, a Debian package ([Host kernel](/reference/host-kernel/)).                            |
| `SHA256SUMS`                                                             | The sha256 of each other file.                                                                                |

Check each file against its line in `SHA256SUMS`. On Linux, use `sha256sum -c` in place of `shasum -a 256 -c`:

```sh
cd ~/hopbox-release
grep -e terraform-provider-hopbox_0.1.0_darwin_arm64.zip -e hopbox-v0.1.0-linux-amd64.tar.gz -e linux-image-6.18.57 SHA256SUMS |
  shasum -a 256 -c
```

The command prints `OK` for each of the four files. `SHA256SUMS` has no line for the `.sha256` file of the host kernel package. If it prints `FAILED`, get that file again.

The people who work on hopbox can build the same files from a checkout instead.

## 3. Write the Terraform files

The provider is in no registry. Put its zip in the local mirror of Terraform, in the dir of its source address:

```sh
dir=~/.terraform.d/plugins/registry.terraform.io/hopboxdev/hopbox
mkdir -p "$dir"
cp ~/hopbox-release/terraform-provider-hopbox_0.1.0_darwin_arm64.zip "$dir/"
```

Terraform reads the dir `~/.terraform.d/plugins` as a local mirror only without a `provider_installation` block in its CLI config. If your CLI config has such a block, add a `filesystem_mirror` block for that dir to it.

Make a folder for the install:

```sh
mkdir -p ~/hopbox-install && cd ~/hopbox-install
```

Write `main.tf`. Put the paths of step 2 in it, and the sha256 values of the two `.sha256` files:

```hcl
terraform {
  required_providers {
    hopbox = { source = "hopboxdev/hopbox", version = "0.1.0" }
  }
}


provider "hopbox" {
  ssh_private_key = file(pathexpand("~/.ssh/id_ed25519"))
}


resource "hopbox_server" "first" {
  ovh_service_name = "ns1234567.ip-198-51-100.eu"
  bootstrap        = true
  domain           = "example.com"
  labels           = { zone = "gra" }


  bundle = {
    source = pathexpand("~/hopbox-release/hopbox-v0.1.0-linux-amd64.tar.gz")
    sha256 = "<the sha256 of the bundle>"
  }
  host_kernel = {
    source = pathexpand("~/hopbox-release/linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb")
    sha256 = "<the sha256 of the package>"
  }
}


output "ipv4" {
  value = hopbox_server.first.ipv4
}


output "admin_api_key" {
  value     = hopbox_server.first.admin_api_key
  sensitive = true
}
```

The state holds the first admin API key of the install, and the pinned host key of the server. Keep the state in a place that only the instance admins can read. A `terraform.tfstate` file on a laptop is fine to try the provider. For a real install, use a backend with encryption and access control.

## 4. Apply

```sh
terraform init
terraform apply
```

The apply takes 30 to 90 minutes. Most of it is the reinstall at OVHcloud, and the reboot into the host kernel. To follow the steps, set `TF_LOG_PROVIDER=INFO`. The log shows lines such as `reinstalling the server`, `pinned the host key of the server`, `installing the host kernel`, and `installing hopboxd`.

At the end, Terraform prints the output `ipv4`. A warning such as `The preflight check of the server warns: ...` means that the server runs, with a risk that the warning names.

## 5. Check the server

The first login of the provider trusted the host key that the server showed, and pinned it in the state. Compare it with the key on the console of the server in the OVHcloud manager ([hopbox Terraform provider](/reference/terraform-provider/#host-key-trust)):

```sh
terraform state show hopbox_server.first | grep ssh_host_key
```

Log in with the key of the operators. The OVHcloud template of Debian 13 has the user `debian`, with `sudo`:

```sh
ssh -i ~/.ssh/id_ed25519 debian@"$(terraform output -raw ipv4)" sudo hopboxd admin server list
```

The output shows one server, `ready`, with the version of the bundle:

```text
ID                                    POOL     STATE  STATUS  ROLES          HOSTNAME   VERSION  LAST HEARTBEAT
01a14404-ce7b-72d9-b18e-5006c3e462db  default  ready  ok      node,dns,edge  ns1234567  v0.1.0   2026-10-16T09:00:05Z
```

The ROLES column lists the roles that enrolled. The control role of the first server runs in the same `hopboxd` from its bootstrap config, without a server record.

`uname -r` on the server prints `6.18.57-hopbox1`.

The server also has the DNS role, which answers DNS for the domain of the install. The provider set the public addresses of the install to the addresses of the server, so the domain points at the server. The DNS role listens on port 53 of these addresses, because `systemd-resolved` of the OS holds port 53 on `127.0.0.53` ([hopbox Terraform provider](/reference/terraform-provider/#create)). Read them:

```sh
ssh -i ~/.ssh/id_ed25519 debian@"$(terraform output -raw ipv4)" sudo hopboxd admin config get
```

The line `public_addresses` holds the IPv4 address of the server. If OVHcloud reports a `/128` block that a network interface of the server holds, the line holds that IPv6 address too. Then delegate the domain from its parent zone, as [Serve the domain of an install with the DNS role](/guide/dns-role/#delegate-the-domain-of-the-install) shows. Use the same addresses for the glue records.

The server also has the edge role. It serves the API, the console, and the machine URLs on ports 443 and 80 ([the edge role](/reference/edge/)). It starts HTTPS once the ACME job got the certificate of the domain ([Get the wildcard certificate of an install](/guide/acme-certificate/)). Open TCP ports 80 and 443 in each firewall in front of the server.

## 6. Keep the admin API key

```sh
terraform output -raw admin_api_key
```

The key starts with `hbxadm_`. It is the first admin API key of the install, with the name `bootstrap`. It expires after 90 days. Before it expires, make a new key on the server and use it in the provider block of your other configurations:

```sh
ssh -i ~/.ssh/id_ed25519 debian@"$(terraform output -raw ipv4)" sudo hopboxd admin admin-key create --name terraform --lifetime 365d
```

## 7. Sign in

Make a login link for the first instance admin, and open it ([First sign-in on a new install](/guide/first-sign-in/)):

```sh
ssh -i ~/.ssh/id_ed25519 debian@"$(terraform output -raw ipv4)" sudo hopboxd admin login-link --email you@example.org
```

## Upgrade

Get the bundle of the new release and its `.sha256` file. Change `bundle` in `main.tf` to its path and sha256, and apply:

```sh
terraform apply
```

The plan shows an update in place of `bundle` and `version`. The provider uploads the bundle and runs `hopboxd upgrade` on the server. The running machines stay up ([hopboxd](/reference/hopboxd/#upgrade)). If the new release cannot run on the data, the upgrade stops before the switch, and the old release keeps running.

The provider then waits until the server is `ready` on the new version. An install with more servers upgrades them one at a time, the first server before the nodes ([hopbox Terraform provider](/reference/terraform-provider/#rolling-upgrade)).

## Change the labels

Change `labels` in `main.tf`, for example to `{ zone = "gra", disk = "nvme" }`, and apply. The provider calls `SetServerLabels`. `sudo hopboxd admin server get <id>` on the server then shows `labels disk=nvme,zone=gra` and `labels_set_by_admin true`.

## Add pools and sizes

After the first server runs, you can add pools and sizes in the same Terraform files. A pool groups the servers of one model, and a size can keep its machines in one pool. Both need the admin API, so set `install_url` and `admin_api_key` in the provider block first, with the key of step 6:

```hcl
provider "hopbox" {
  ssh_private_key = file("~/.ssh/id_ed25519")
  install_url     = "https://example.com"
}


resource "hopbox_pool" "big" {
  name     = "big"
  ovh_plan = "24adv01"
}


resource "hopbox_size" "large" {
  name       = "large"
  vcpus      = 8
  memory_gib = 32
  disk_gb    = 200
  pool       = hopbox_pool.big.name
}
```

Keep the key out of the files: export it as `HOPBOX_ADMIN_API_KEY` before the apply. The first server stays in the pool `default`. A server that joins `big` sets `pool = hopbox_pool.big.name`. [Add pools and sizes](/guide/pools-and-sizes/) explains the rules, and [hopbox Terraform provider](/reference/terraform-provider/#resource-hopbox_pool) lists every attribute.

## Import a server into a new state

A server that the provider set up can move to a new state, for example after the loss of the state file:

```sh
terraform import hopbox_server.first ns1234567.ip-198-51-100.eu
```

The import logs in with the key of the operators. It reads the server ID, the version, and the domain from the server. The new state has no `admin_api_key`. Make a new admin API key as in step 6. The new state also forgets a cordon that a failed kernel reboot left. Check the server with `sudo hopboxd admin server get <id>`. If it shows `cordoned true` and nobody cordoned it on purpose, run `sudo hopboxd admin server uncordon <id>`. The first plan after the import shows an update of `bundle`. If the bundle of `main.tf` is the release that the server runs, the apply changes nothing on the server.

## Order a new server

The provider can order the server in place of a server that your account rents. The apply pays for it with the preferred payment method of the account. It rents the server by the month, without a commitment.

Find the plan code of a server model, and the options of its families, in the public catalog of OVHcloud. This call needs no key:

```sh
curl -s 'https://eu.api.ovh.com/1.0/order/catalog/public/baremetalServers?ovhSubsidiary=FR' -o catalog.json
jq -r '.plans[] | [.planCode, .invoiceName] | @tsv' catalog.json
jq '.plans[] | select(.planCode == "<plan code>") | {configurations, families: [.addonFamilies[] | {name, mandatory, addons}]}' catalog.json
```

The `configurations` show the datacenters of the plan, in `dedicated_datacenter`. Pick one option of each family with `"mandatory": true`, such as the memory, the storage, and the bandwidth. For the storage, pick a `softraid-` option: the provider refuses a `hardraid-` option, because hopbox tests only software RAID. All the servers of a pool have the same model, so use the same plan and options for each server of a pool.

In `main.tf` of step 3, replace `ovh_service_name` with the order:

```hcl
resource "hopbox_server" "first" {
  ovh_plan       = "<plan code>"
  ovh_datacenter = "gra"
  ovh_options    = ["<memory option>", "<storage option>", "<bandwidth option>"]
  ovh_order_key  = "hop-example-first"
  ovh_max_price  = 120
  bootstrap      = true
  domain         = "example.com"
  labels         = { zone = "gra" }


  bundle = {
    source = pathexpand("~/hopbox-release/hopbox-v0.1.0-linux-amd64.tar.gz")
    sha256 = "<the sha256 of the bundle>"
  }
  host_kernel = {
    source = pathexpand("~/hopbox-release/linux-image-6.18.57-hopbox1_6.18.57-1_amd64.deb")
    sha256 = "<the sha256 of the package>"
  }


  lifecycle {
    prevent_destroy = true
  }
}
```

`ovh_max_price` is the highest price with tax that the checkout pays, in the currency of your account. The checkout pays the first invoice: the first month and any setup fee, not only the monthly rent. If the cart costs more, the apply stops before the checkout and orders nothing. The error then shows the price of the cart. `ovh_order_key` names the order in your OVHcloud account. Give each server its own key. The provider marks the cart of the order with it. So a later apply finds an order that an apply lost, and does not pay twice.

Plan first, and read the warning:

```sh
terraform plan
```

The plan says `Apply orders and pays for a new OVHcloud server`, with the plan, the datacenter, and the options. Only a create orders. Then apply:

```sh
terraform apply
```

The apply output shows the price of the checkout in the warning `The apply ordered the OVHcloud server of the order <id>`. The log of the provider shows `ordering a server` with the price, `ordered a server` with the order ID, and `waiting for the order` with its status. OVHcloud delivers some models in minutes, and others in days. The apply waits up to 2 hours. Then it reinstalls the server and goes on as in step 4. `terraform state show hopbox_server.first` shows the service name of the new server in `ovh_service_name`, and the order in `ovh_order_id`.

If OVHcloud did not deliver the server in 2 hours, the apply stops with `the order <id> is not delivered after 2h0m0s`, and Terraform marks the resource as tainted. Do not remove the resource. Untaint it and apply again later:

```sh
terraform untaint hopbox_server.first
terraform apply
```

The apply waits for the same order, and orders nothing new. Do the same after a failure of a later step, such as the install.

After the create, the plan refuses each change that orders a new server: another `ovh_plan`, `ovh_datacenter`, `ovh_options`, or `ovh_order_key`, and a change of `pool` or `bootstrap`. To change the model of a server, add a new resource and remove the old one.

`terraform taint`, `terraform apply -replace`, and `create_before_destroy` also replace the server, and the replacement orders a new one. The provider cannot see these replacements. The block `lifecycle { prevent_destroy = true }` makes Terraform refuse them. Keep it on each ordered server, and remove it only before a destroy on purpose.

## Destroy

```sh
terraform destroy
```

The destroy decommissions the server in the install, and stops `hopboxd` on it. It refuses a server that holds machines. Delete the machines first. The OVHcloud server stays rented, with its disks as they are. With `ovh_service_name`, another apply of `main.tf` erases the server again and makes a new install.

The destroy never cancels an order and never ends a rental, also for a server that the provider ordered. For an ordered server, remove `prevent_destroy` from `main.tf` before the destroy. After the destroy, another apply of `main.tf` with the order attributes orders and pays for a new server. To make a new install on the same server, replace the order attributes with `ovh_service_name` of that server first. To stop paying for the server, end its rental in the OVHcloud manager, and remove the resource from `main.tf`.

## If the apply stops

| Message                                                                                                   | Fix                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `the provider has no OVHcloud credentials`                                                                | Export the variables of step 1 in the shell that runs Terraform.                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| `ovh: ... HTTP 403 ... This call has not been granted`                                                    | The consumer key lacks a right of step 1. Make a new consumer key.                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `ovh: GET /dedicated/server/<name>: HTTP 404`                                                             | The service name is wrong, or the server is in another account.                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `the disk group <n> sits behind the hardware RAID controller`                                             | Pick a server model without hardware RAID.                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| `log in to the reinstalled server ...: context deadline exceeded`                                         | The server did not answer SSH for 30 minutes after the reinstall. Check the server in the OVHcloud manager, then run `terraform apply` again. Terraform reinstalls the server.                                                                                                                                                                                                                                                                                                                                 |
| `remote: the host key of the server is not the pinned one`                                                | Someone reinstalled the server outside Terraform, or a machine sits between you and the server. Check the key first. A reinstall of the first server erased its install. To accept it, run `terraform state rm hopbox_server.first` and apply, which makes a new install. For an ordered server, first replace the order attributes in `main.tf` with `ovh_service_name` of the same server. Otherwise the apply orders a new server.                                                                          |
| `/boot/grub/grub.cfg has no entry for <release>. The provider removed the pin, and the old default stays` | GRUB made no menu entry for the kernel, and the server still boots its old kernel. After a failed create of a server that your account rents, Terraform marks the server as tainted. The next apply starts again with a new reinstall. With `lifecycle { prevent_destroy = true }`, Terraform refuses that apply with `Instance cannot be destroyed`. Then run `terraform state rm hopbox_server.first`, and apply again. `terraform untaint` does not help, because the state then holds a server without `hopboxd`, and the next apply installs nothing. A failed create of an ordered server works another way: see [Order a new server](#order-a-new-server).

# Run the edge role and open machine URLs

> How to run the edge role on a Mac and call the API through it. Also how a private URL, its port, and a public URL work.

The edge role takes the HTTPS traffic of an install. It serves the API and the console on the domain of the install, such as `example.com`. It also serves the URL of each machine, such as `box1.example.com`. This guide runs the edge role on a Mac with the test CA Pebble, and calls the API through it. Then it shows how a machine URL works: the private URL with its sign-in, the URL port, and the public URL. [The edge role](/reference/edge/) covers the edge role in full.

## How a request reaches its target

The edge role gets the wildcard certificate of the install from the control role, over the control channel. It refuses a TLS handshake without a server name (SNI), or for a name outside the domain. Then it routes each request by its host:

* The domain goes to the internal listener of the control role, over the mutual TLS of the server. The edge role names the address of the client in the header `Hopbox-Client-Addr`. The control role trusts this header only from a server with the edge role. So the rate limits of sign-in count each client.
* `<name>.<domain>` goes to the URL port of the machine `<name>`, port 8000 by default.
* Plain HTTP goes to HTTPS with a `301` answer.

## What you need

* The setup of [Get the wildcard certificate of an install](/guide/acme-certificate/) on a Mac: a build of hopbox, the bundled Postgres, Pebble, and `dig`.
* `curl`.

## Run the edge role on a Mac

### Start Pebble

Start Pebble as in [Get the wildcard certificate of an install](/guide/acme-certificate/#start-pebble), and leave it running:

```sh
PEBBLE_DIR="$(go env GOMODCACHE)/github.com/letsencrypt/pebble/v2@v2.10.1"
cd "$PEBBLE_DIR" && PEBBLE_VA_NOSLEEP=1 "$(go env GOPATH)/bin/pebble" -config test/config/pebble-config.json -dnsserver 127.0.0.1:15353
```

### Write the bootstrap config

The server runs the control role, the DNS role, and the edge role. Ports 443 and 80 need root, so the edge role listens on high ports of loopback ([the bootstrap config of hopboxd](/reference/hopboxd-config/#keys)). A Mac has no nftables, so the SSH front door listens only on its own port, and reaches no machine ([the SSH front door](/reference/ssh-front-door/)). Run the `cat` command in the checkout of hopbox, so `make pg` finds the recipe of Postgres:

```sh
PEBBLE_DIR="$(go env GOMODCACHE)/github.com/letsencrypt/pebble/v2@v2.10.1"
mkdir -p ~/hbe/run && chmod 700 ~/hbe ~/hbe/run
cat > ~/hbe/hopboxd.toml <<EOF
roles = ["control", "dns", "edge"]
data_dir = "$HOME/hbe/data"
run_dir = "$HOME/hbe/run"


[dns]
listen = ["127.0.0.1:15353"]


[edge]
https_listen = "127.0.0.1:8443"
http_listen = "127.0.0.1:8080"
ssh_listen = "127.0.0.1:2222"
ssh_redirect = false


[acme]
name_servers = ["127.0.0.1:15353"]
ca_file = "$PEBBLE_DIR/test/certs/pebble.minica.pem"


[postgres]
install = "$(make pg)"
EOF
```

### Start hopboxd

```sh
./bin/darwin_arm64/hopboxd run --config ~/hbe/hopboxd.toml
```

The edge role opens its listeners, and waits for its certificate:

```json
{"level":"INFO","msg":"edge listening","component":"edge","https":"127.0.0.1:8443","http":"127.0.0.1:8080"}
```

Leave it running, and use a third terminal. Set two variables, so the commands stay short:

```sh
H=./bin/darwin_arm64/hopboxd
C=~/hbe/hopboxd.toml
```

### Enroll the DNS role and the edge role

Both roles get their data over the control channel of the server. So the server enrolls with the control role of the same `hopboxd`:

```sh
$H admin --config $C kek rotate
TOKEN="$($H admin --config $C enrollment-token create --roles dns,edge)"
HOPBOX_ENROLLMENT_TOKEN="$TOKEN" $H enroll --config $C
```

### Set the domain and get the certificate

```sh
$H admin --config $C config set --domain example.com --public-address 127.0.0.1 \
  --acme-directory-url https://localhost:14000/dir --acme-email ops@example.org --acme-agree-terms
```

The edge role gets the domain with its first routes. Within some seconds, the ACME job gets the certificate, and the edge role serves it:

```json
{"level":"INFO","msg":"serving the machine URLs of a domain","component":"edge","domain":"example.com","machines":0}
{"level":"INFO","msg":"got the certificate of the install","component":"acme","domain":"example.com","serial":"2a61b67498df3f2a","issuer":"CN=Pebble Intermediate CA 12b00b","not_after":"2027-01-19T11:18:51Z"}
{"level":"INFO","msg":"serving a certificate","component":"edge","domain":"example.com","not_after":"2027-01-19T11:18:51Z","serial":"2a61b67498df3f2a"}
```

### Call the API through the edge

Pebble makes a new root CA at each start. Save it, so curl trusts the certificate. The flag `--resolve` sends each name to the edge role on loopback, with the right server name:

```sh
curl -sk https://localhost:15000/roots/0 > ~/hbe/pebble-root.pem
R=(--resolve example.com:8443:127.0.0.1 --resolve box1.example.com:8443:127.0.0.1 --cacert ~/hbe/pebble-root.pem)
```

Call `InstallService.GetInstallInfo` on the domain. The answer comes from the control role, over HTTP/2, with HSTS:

```text
$ curl -s "${R[@]}" -D - -H 'Content-Type: application/json' -d '{}' \
    https://example.com:8443/hopbox.v1.InstallService/GetInstallInfo
HTTP/2 200
strict-transport-security: max-age=31536000; includeSubDomains
...
{"domain":"example.com", "version":"v0.1.0"}
```

The edge role refuses the requests that it does not serve:

```text
$ curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' \
    --resolve box1.example.com:8080:127.0.0.1 'http://box1.example.com:8080/a?b=1'
301 https://box1.example.com/a?b=1
$ curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' "${R[@]}" https://box1.example.com:8443/
303 https://example.com/auth/machine?machine=box1&path=%2F
$ curl -s "${R[@]}" -H 'Content-Type: application/json' -d '{}' \
    https://example.com:8443/hopbox.cluster.v1.EdgeService/AuthorizeMachineRequest
No such page.
$ curl -s --cacert ~/hbe/pebble-root.pem https://127.0.0.1:8443/; echo "exit $?"
exit 35
```

The first redirect goes to port 443, because the edge role of an install listens there. No machine has the name `box1`. The edge role still answers as for a private URL, so a client cannot tell which names have a machine. The last request has no server name, so the handshake fails.

### Sign in through the edge

Sign in with a first-admin login link, as the console does ([First sign-in on a new install](/guide/first-sign-in/)). The session cookie comes back through the edge:

```text
$ LINK=$($H admin --config $C login-link --email ann@example.org | grep -o 'https://[^ ]*')
$ curl -s "${R[@]}" -D - -o /dev/null -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
    -H 'Origin: https://example.com' -d "{\"token\":\"${LINK#*#token=}\"}" \
    https://example.com:8443/hopbox.v1.AuthService/VerifyLoginLink | grep -i set-cookie
set-cookie: __Host-hopbox_session=<token>; Path=/; Expires=Fri, 20 Nov 2026 11:19:47 GMT; Max-Age=2591999; HttpOnly; Secure; SameSite=Lax
```

The access log of the control role names the address of curl as the peer of each call, such as `"peer":"127.0.0.1:57382"`. The port changes with each run of curl, because it is the port of the client, not the port of the edge role.

### Stop

Press Ctrl-C in the terminal of `hopboxd`, then in the terminal of Pebble. To start from nothing, remove `~/hbe`.

## Open the URL of a machine

A Mac has no KVM, so it runs no machine. These steps need an install with a node. The node gives each machine its address, and the edge role reaches the machine there ([the node network](/reference/node-network/)).

The steps call the API with an API key ([Use the hopbox CLI](/guide/cli/#make-an-api-key-for-a-script)). Keep the key in `HOPBOX_API_KEY`, and define a function:

```sh
api() {
  curl -s -X POST -H 'Content-Type: application/json' -H "Authorization: Bearer $HOPBOX_API_KEY" \
    "https://example.com/hopbox.v1.MachineService/$1" -d "$2"
  echo
}
```

### A private URL

The URL of a new machine is private. Open `https://box1.example.com/` in a browser:

1. Without a sign-in for the machine, the edge role sends the browser to `https://example.com/auth/machine`.
2. The browser has a console session of an account that uses the machine. So the control role sends it back to the machine host with a one-time code.
3. The edge role trades the code for the cookie `__Host-hopbox_machine`, and opens the page that the browser asked for.

Without a console session, step 2 shows `sign in to the console of this install first, then open the machine URL again`. Sign in, then open the machine URL again. The creator of a private machine opens its URL. Once the creator shares the machine, every member of its org does too. An org admin cannot open the private URL of a private machine of another member.

A sign-out ends the machine URLs of the browser too. So does an unshare, for each member that is not the creator.

### The URL port

The URL reaches port 8000 in the machine by default. The creator picks another port:

```sh
api SetMachineURLPort '{"name":"box1","port":3000}'
```

The edge role gets the new port with the next routes, within a second or two.

### A public URL

The creator makes the URL public, so it needs no sign-in:

```sh
api SetMachineURLVisibility '{"name":"box1","visibility":"URL_VISIBILITY_PUBLIC"}'
curl -s https://box1.example.com/
```

To make it private again, set `URL_VISIBILITY_PRIVATE`.

### What the code of the machine sees

The request reaches the machine over plain HTTP, with these headers:

* `Host: box1.example.com`.
* `X-Forwarded-For`: the IP address of the client.
* `X-Forwarded-Proto: https`.

The edge role takes each cookie of hopbox out of the request, so the machine never gets a credential of the install. It also drops a `Set-Cookie` of the machine for another host than its own, such as `Domain=example.com`. Such a cookie can reach the console and the other machines of the install.

### When the URL does not open

| Page                                                                    | Cause                                                                                                  |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `404` `no machine has the name "box1"` on the domain, after the sign-in | No machine holds the name, or the account does not see the machine.                                    |
| `403`                                                                   | The account has no access to the machine, or an instance admin suspended its org.                      |
| `503` `The machine box1 is stopped.`                                    | The machine does not run. Start it.                                                                    |
| `503` `... has no network address on its node`                          | The machine has no address.                                                                            |
| `502` `The machine did not answer on its URL port.`                     | No server listens on the URL port in the machine. Check the port, and start the server in the machine. |

[The edge role](/reference/edge/#machine-urls) lists every answer.

# Create and manage machines

> How to register the default image, then create, list, watch, stop, and delete a machine through the API, and how the operator sees and stops the machines of every org.

This guide registers the default image, then creates, lists, watches, stops, and deletes a machine through the API. At the end, the operator sees and stops the machines of every org with `hopboxd admin`. [The machine API](/reference/machine-api/) has every call and rule, and [Placement](/reference/placement/) covers how a create picks a node.

The executor of a machine on its node boots and stops its microVM with Firecracker ([the node executor](/reference/executor/), [the Firecracker driver](/reference/firecracker-driver/)). Each machine gets an address on the network of its node, where its URL and its SSH port reach it ([Check the network of a machine](/guide/node-network/)). [Run commands and copy files in a machine](/guide/exec-and-files/) runs commands in a machine over its guest link.

This guide calls the API with curl, in the same way as the console does, so it shows each call. The console does the same work in a browser ([Use the console](/guide/console/#create-a-machine-and-open-a-shell)). The hopbox CLI does the same with `hopbox new`, `hopbox list`, and `hopbox machine` ([Use machines from the CLI](/guide/cli-machines/)).

The release files of hopbox are not public yet. The hopbox team gives them on request.

## What you need

* A Linux server with the control role and the node role, enrolled as in [Enroll the node role on one server](/guide/enroll-node/). `sudo hopboxd admin server list` must show the server `ready`, with the status `ok`. A create needs a ready node with room for the size `default`: 2 vCPUs and 8 GiB of RAM ([Placement](/reference/placement/#hard-filters)). Without one, it fails with `unavailable`.
* A domain and a session cookie of a signed-in account, as in [First sign-in on a new install](/guide/first-sign-in/). Keep the cookie in `COOKIE`, in the form `__Host-hopbox_session=<token>`.
* The default image. A server installed from the release bundle registers the default image of its release at each start, so it needs no more step ([Install hopbox on a Debian 13 server by hand](/guide/install-debian/)). Another build of the image needs its `artifact.json` on the server, and its compressed disk at a URL that the nodes reach. The people who work on hopbox build one with `make image` into `bin/image/`.

A Mac cannot be the node, because it has no KVM. On a Mac with only the control role, every create fails with `no capacity: ... The install has no node yet`.

Define a function that calls the API with the headers of the console. The API listens on `control.api_listen`, by default `127.0.0.1:7080`:

```sh
API=http://127.0.0.1:7080
browser() {
  curl -s -X POST -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
    -H 'Origin: https://example.com' -H "Cookie: $COOKIE" "$@"
  echo
}
```

## Register the default image

A create takes the newest image of a name, `default` by default. A control server that runs a release registers the default image of that release at each start, unless the install has a default image from a newer release ([hopboxd](/reference/hopboxd/#the-default-image-of-the-release)). A control role without a release, such as `hopboxd` on a laptop, has no image, so a create fails:

```json
{"code":"failed_precondition","message":"failed precondition: the install has no image \"default\". An instance admin registers one with hopboxd admin image register"}
```

Register the image from its `artifact.json`. The install keeps only the metadata. `--url` tells the nodes where to download the compressed disk:

```text
$ sudo hopboxd admin image register artifact.json --url https://dl.example.org/images/default/disk.raw.zst
id  01a1460a-7c21-7d4e-8f90-1a2b3c4d5e6f
name  default
digest  sha256:422d31d7a4fd5e6958162b22e3d772f71b5a1465cbd6255d253ae8c087873dc8
registered  true
```

The digest is the sha256 of the bytes of `artifact.json`, so it names this one build. A second register of the same file changes nothing, and prints `registered false`. A new build of the image has a new digest. Once you register it, new machines take it, and the machines that exist keep their image.

```text
$ sudo hopboxd admin image list
01a1460a-7c21-7d4e-8f90-1a2b3c4d5e6f  default  sha256:422d31d7a4fd5e6958162b22e3d772f71b5a1465cbd6255d253ae8c087873dc8  2026-10-16T16:01:40Z
```

## See the sizes

```sh
browser -d '{}' $API/hopbox.v1.MachineService/ListMachineSizes
```

```json
{"sizes":[{"name":"default","vcpus":2,"memoryBytes":"8589934592","diskBytes":"100000000000"}]}
```

A fresh install has one size. A create without a size takes `default`.

## Create a machine

A create takes an idempotency key, so a retry with the same key returns the same machine and makes no second one. Keep the key in a variable:

```sh
KEY=$(uuidgen)
browser -H "Idempotency-Key: $KEY" -d '{"name":"box1"}' $API/hopbox.v1.MachineService/CreateMachine
```

```json
{"machine":{"id":"01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10","orgId":"01a14565-8448-7753-9c1f-5ec0a86b8d92","name":"box1","state":"MACHINE_STATE_PENDING","targetState":"MACHINE_STATE_RUNNING","size":{"name":"default","vcpus":2,"memoryBytes":"8589934592","diskBytes":"100000000000"},"imageName":"default","imageDigest":"sha256:422d31d7a4fd5e6958162b22e3d772f71b5a1465cbd6255d253ae8c087873dc8","creatorAccountId":"01a14565-8448-774f-9317-ea6348e9a930","restartPolicy":"RESTART_POLICY_ALWAYS","url":"https://box1.example.com","urlPort":8000,"urlVisibility":"URL_VISIBILITY_PRIVATE","sshPort":21467,"lastActivityTime":"2026-10-16T16:02:11.402518Z","stateChangeTime":"2026-10-16T16:02:11.402518Z","version":"1","createTime":"2026-10-16T16:02:11.402518Z","updateTime":"2026-10-16T16:02:11.402518Z"}}
```

The request leaves out `orgId`, so the machine is in the personal org of the account. The create picked the node, granted it the lease of the machine, and claimed the name `box1` and a random SSH port. It did not wait: the machine is `pending`, with the target `running`. The node boots it at once. At the first boot of an image, the node also unpacks the image, so the machine runs about 25 s later on the [tested server](/reference/preflight/#the-tested-server).

Send the same request with the same key again. The response is the same, with the header `Idempotent-Replayed: true`.

Machine names are unique in the whole install. A new create with the name `box1` fails, and suggests a free name:

```sh
browser -H "Idempotency-Key: $(uuidgen)" -d '{"name":"box1"}' $API/hopbox.v1.MachineService/CreateMachine
```

```json
{"code":"already_exists","message":"already exists: the machine name \"box1\" is taken. A free name is \"box2\""}
```

A create without a name gets the first free name of `box1`, `box2`, and so on. Each org has usage limits, by default 3 machines, 6 vCPUs, 24 GiB of RAM, and 300 GB of disk ([the org API](/reference/org-api/#usage-limits)). A fourth machine of the size `default` fails with `resource_exhausted`.

If no node has room, the create fails with `unavailable` and names the reason of each node:

```json
{"code":"unavailable","message":"no capacity: no node has room for a machine of size default (2 vCPUs, 8 GiB of RAM): 1 node is cordoned, unresponsive, or decommissioned"}
```

The failed create leaves nothing behind. Uncordon the node, or enroll another one, then retry.

## List and read the machines

```sh
browser -d '{}' $API/hopbox.v1.MachineService/ListMachines
browser -d '{"name":"box1"}' $API/hopbox.v1.MachineService/GetMachine
```

`ListMachines` returns the machines of the org that you see, by name. A machine is private to its creator until the creator shares it with `ShareMachine`. Other members of the org do not see a private machine, and get `not_found` for it. An org admin or owner sees it, and can stop or delete it, but cannot start it or change it ([the machine API](/reference/machine-api/#who-can-do-what)).

## Watch the machines

`WatchMachines` is a server stream. It sends each machine, then `{"synced":true}`, then each change as it happens. A call with the session cookie must use the Connect protocol, so use curl with the streaming form of Connect. Each message of the stream has a 5-byte prefix: one byte of flags and a 4-byte length. The request below sends the message `{}` with its prefix. The small Python program prints each message of the response on one line:

```sh
printf '\000\000\000\000\002{}' | curl -sN -X POST \
    -H 'Content-Type: application/connect+json' -H 'Connect-Protocol-Version: 1' \
    -H 'Origin: https://example.com' -H "Cookie: $COOKIE" \
    --data-binary @- $API/hopbox.v1.MachineService/WatchMachines |
  python3 -c '
import struct, sys
r = sys.stdin.buffer
while (h := r.read(5)):
    print(r.read(struct.unpack(">I", h[1:])[0]).decode(), flush=True)
'
```

```text
{"machine":{"id":"01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10",...,"name":"box1","state":"MACHINE_STATE_RUNNING","targetState":"MACHINE_STATE_RUNNING",...}}
{"synced":true}
```

The output here is cut short. Leave the watch running, and stop the machine in a second terminal. The watch prints the machine again, with its new target, and then with its new state:

```text
{"machine":{"id":"01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10",...,"name":"box1","state":"MACHINE_STATE_RUNNING","targetState":"MACHINE_STATE_STOPPED",...}}
{"machine":{"id":"01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10",...,"name":"box1","state":"MACHINE_STATE_STOPPED","targetState":"MACHINE_STATE_STOPPED",...}}
```

Press Ctrl-C to end the watch. The stream has no deadline. A watch of an org that you leave ends with `permission_denied` within 30 s.

## Stop the machine

A stop sets the target `stopped`, then waits for the machine, for up to 60 s:

```sh
browser -d '{"name":"box1"}' $API/hopbox.v1.MachineService/StopMachine
```

```json
{"machine":{"id":"01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10",...,"state":"MACHINE_STATE_STOPPED","targetState":"MACHINE_STATE_STOPPED",...},"duration":"0.512s","done":true}
```

The node asks the guest to shut down, and the call returns as soon as the machine is stopped. If the wait ends first, `done` is `false`, and the JSON codec leaves it out. The call still succeeded then: the target is `stopped`, and the machine goes on toward it. A machine with the restart policy `never` can also stop by itself, for example with `sudo reboot` inside it. Its target then turns `stopped`, so it stays stopped until a start.

To wait less, send a shorter deadline. The wait ends 1 s before it:

```sh
browser -H 'Connect-Timeout-Ms: 5000' -d '{"name":"box1"}' $API/hopbox.v1.MachineService/StartMachine
```

The start sets the target `running` again, and the node boots the machine from its disk. The call returns once the machine runs, or after about 4 s with `done` false. A stopped machine holds no vCPUs and no RAM. So the start first checks the limits of the org and the room on the node of the machine.

## Manage the machines as the operator

An instance admin sees the machines of every org, with metadata only. Root on a control server calls the admin API with `hopboxd admin`:

```text
$ sudo hopboxd admin machine list
01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10  box1  org=01a14565-8448-7753-9c1f-5ec0a86b8d92  running  target=running  server=01a14403-6bd1-7522-9ab0-b3ab4517e0e4
```

`--org-id` lists the machines of one org. To handle abuse, stop or delete any machine, also in a suspended org:

```text
$ sudo hopboxd admin machine stop --name box1
id  01a1460c-1f6e-7b8a-9c42-3d5e7f8a9b10
name  box1
state  stopped
target_state  stopped
duration  512ms
done  true
```

Each `admin` command waits at most 40 s for its call, so its wait ends after about 39 s at the latest. The audit log of the org records the entry `machine.admin_stop` of `local_root`, so the owners of the org see it.

A suspension of the org stops each of its machines too ([the org API](/reference/org-api/#suspension)). The members of a suspended org cannot create, start, reboot, or delete a machine until the suspension ends.

## Delete the machine

```sh
browser -H 'Connect-Timeout-Ms: 5000' -d '{"name":"box1"}' $API/hopbox.v1.MachineService/DeleteMachine
```

The machine gets the target `deleted` and a `deleteRequestTime`. The node stops its microVM, and removes its disk and its jail. It stops counting in the usage of the org at once. Its name and its SSH port stay reserved for your org for 7 days, so another org cannot take `box1` in that time. Your org can: a new create with the name `box1` succeeds. A second delete of the same machine fails with `failed_precondition`.

## Read the audit log

Each change writes an audit entry in the org of the machine: `machine.create`, `machine.stop`, `machine.start`, `machine.admin_stop`, and `machine.delete` here ([the machine API](/reference/machine-api/#audit-entries)). The owner of the personal org reads them:

```sh
browser -d '{"orgId":"01a14565-8448-7753-9c1f-5ec0a86b8d92","pageSize":5}' $API/hopbox.v1.AuditService/ListAuditEntries
```

To run commands in the machine and copy files, see [Run commands and copy files in a machine](/guide/exec-and-files/).

# Connect an AI agent to hopbox with MCP

> How to connect Claude Code to the MCP server of an install with an API key, and let it make and use a machine.

This guide connects Claude Code to the MCP server of hopbox. Then the agent makes a machine, runs a command in it, and writes and reads a file. It also makes the URL of the machine public, stops and starts the machine, and deletes it. MCP is the Model Context Protocol, which AI agents use to call tools. [The MCP server](/reference/mcp/) lists every tool, the credentials, and the limits. Any other client of the Streamable HTTP transport of MCP works the same way.

## What you need

* An account on an install with machines, such as the preview install of [Try hopbox](/guide/quickstart/). The MCP server of an install is at `https://<domain>/mcp`. This guide uses `https://example.com/mcp`.
* The hopbox CLI, signed in to the install, as in [Install the hopbox CLI](/guide/install-cli/). Without the CLI, make the API key on the tab “API keys” of the org in the console ([Use the console](/guide/console/#more-pages)).
* Claude Code, from <https://docs.claude.com/en/docs/claude-code>.
* `curl` and `jq` for the first check.

## Make an API key for the agent

The agent acts with the rights of its credential, and no more. Give it a member key of its own, in the org where it works. A CLI access token works too, but it lives only 1 hour, and the MCP server does not refresh it:

```sh
export HOPBOX_MCP_KEY=$(hopbox api-key create claude-code --expires 30d)
```

```text
The member key 01a15f0f-6c5c-7d2b-8b8f-df1b2d6de212 (claude-code) works until 2026-11-20T15:30:51Z. This is its only copy.
```

The key can do what you can do in the org of the key, with machines, env vars, and SSH keys. It cannot make API keys, invite people, or delete your account. The server serves no tool for these actions ([the MCP server](/reference/mcp/#left-out-methods)).

## Check the endpoint

Ask the server for its tools. Each request is one `POST` with one JSON-RPC message:

```sh
curl -s https://example.com/mcp \
  -H "Authorization: Bearer $HOPBOX_MCP_KEY" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | jq -r '.result.tools[].name'
```

```text
exec
hopbox_v1_APIKeyService_ListAPIKeys
hopbox_v1_APIKeyService_RevokeAPIKey
hopbox_v1_AccountService_GetAccount
...
machine_logs
read_file
write_file
```

Without the key, the server answers `401 Unauthorized` with `the MCP server needs the header Authorization: Bearer with a CLI token or an API key`.

## Add the server to Claude Code

Add the server for the current project. Claude Code reads the key from the env var `HOPBOX_MCP_KEY` at its start, so the key stays out of the file:

```sh
claude mcp add --transport http --scope project hopbox https://example.com/mcp \
  --header 'Authorization: Bearer ${HOPBOX_MCP_KEY}'
```

The command writes `.mcp.json` in the project:

```json
{
  "mcpServers": {
    "hopbox": {
      "type": "http",
      "url": "https://example.com/mcp",
      "headers": {
        "Authorization": "Bearer ${HOPBOX_MCP_KEY}"
      }
    }
  }
}
```

Start Claude Code with the key in its env, and type `/mcp`. The list shows `hopbox` as connected, with 44 tools.

## Let the agent do a task

Ask Claude Code:

```text
Make a hopbox machine named box1. Wait until it runs. Then run "uname -a" in it,
write "hello" to notes.txt, and read the file back. Make the URL of box1 public.
Stop box1, start it again, and read notes.txt once more. Then delete the machine.
```

The agent calls these tools in order. Claude Code asks you before each call that you did not allow:

1. `hopbox_v1_MachineService_CreateMachine` with `{"name": "box1"}`.
2. `hopbox_v1_MachineService_GetMachine` with `{"machine": {"which": "name", "name": "box1"}}`, until `state` is `MACHINE_STATE_RUNNING`.
3. `exec` with `{"machine": "box1", "command": "uname -a"}`. The result holds `exit_code`, `stdout`, and `stderr`.
4. `write_file` with `{"machine": "box1", "path": "notes.txt", "content": "hello\n"}`.
5. `read_file` with `{"machine": "box1", "path": "notes.txt"}`. The result holds `"content": "hello\n"` and `"encoding": "utf-8"`.
6. `hopbox_v1_MachineService_SetMachineURLVisibility` with `{"machine": {"which": "name", "name": "box1"}, "visibility": "URL_VISIBILITY_PUBLIC"}`. Anyone can now open `https://box1.example.com/` without an account ([Run the edge role and open machine URLs](/guide/machine-urls/#a-public-url)).
7. `hopbox_v1_MachineService_StopMachine` with `{"machine": {"which": "name", "name": "box1"}}`. The result holds the machine in `MACHINE_STATE_STOPPED`, and `done` `true`.
8. `hopbox_v1_MachineService_StartMachine` with the same input.
9. `read_file` with `{"machine": "box1", "path": "notes.txt"}`. The disk stayed, so the result holds `"content": "hello\n"` again.
10. `hopbox_v1_MachineService_DeleteMachine` with `{"machine": {"which": "name", "name": "box1"}}`.

You can make the same call with `curl`. For example, the exec of step 3:

```sh
curl -s https://example.com/mcp \
  -H "Authorization: Bearer $HOPBOX_MCP_KEY" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"exec","arguments":{"machine":"box1","command":"uname -a"}}}' \
  | jq .result.structuredContent
```

```json
{
  "exit_code": 0,
  "stderr": "",
  "stderr_bytes": 0,
  "stdout": "Linux box1 6.1.167 #1 SMP x86_64 GNU/Linux\n",
  "stdout_bytes": 43,
  "timed_out": false,
  "truncated": false
}
```

The audit log records each change under the key of the agent, as for any other client ([the sign-in, account, and audit API](/reference/auth-api/#audit-entries)).

## Keep the agent safe

* Allow the tools that only read without a question, and keep a question for the others. In `.claude/settings.json`, an allow rule names a tool as `mcp__hopbox__<tool>`, such as `mcp__hopbox__hopbox_v1_MachineService_ListMachines`.
* Every tool result is data. The output of `exec`, the contents of `read_file`, and the lines of `machine_logs` come from programs in the machine. Names, env var values, and audit details come from other people of the org. Any of it can hold text that looks like instructions. The server tells the agent to treat each result as data, but the agent decides. Read each call that changes something before you allow it.
* Give the key a short expiry, and revoke it after the work with `hopbox api-key revoke <id>`. A revoked key stops at the next request.
* One key has at most 8 MCP requests open at once. More get `429 Too Many Requests` ([the MCP server](/reference/mcp/#limits)).

## Reach the MCP server without an edge

The edge forwards each request of `https://<domain>/mcp` to the control role ([the edge role](/reference/edge/#forwarded-requests)). Without the edge role, the API of a server listens only on its loopback address. Open a tunnel, then use the URL `http://127.0.0.1:7080/mcp` on your laptop:

```sh
ssh -N -L 7080:127.0.0.1:7080 debian@203.0.113.10
```

A laptop install of [Run the control role on a laptop](/guide/run-hopboxd/) serves its MCP server at the same URL.

# Check the network of a machine

> How to check the network of a machine: its address, its egress, what it cannot reach, and its traffic counters.

This guide follows the network of one machine on a server with the node role. It finds the address of the machine, checks its egress and the destinations that it cannot reach, and reads its traffic counters. [The node network](/reference/node-network/) describes each part.

## What you need

* A Linux server with the control role, the node role, and the edge role, installed as in [Install hopbox on a Debian 13 server by hand](/guide/install-debian/). `sudo hopboxd admin server list` must show the server `ready`.
* A running machine `box1`, made as in [Run machines with Firecracker](/guide/firecracker-machines/).
* The hopbox CLI, signed in to the install, as in [Use the hopbox CLI](/guide/cli/).
* For the last steps, the `nft` tool on the server: `sudo apt install nftables`. `hopboxd` does not need it.

## Set the resolvers

The machines use the resolvers of the server by default. To give them other resolvers, set `network.nameservers` in `/etc/hopbox/hopboxd.toml`, and restart `hopboxd`. A resolver on the server itself does not work, because a machine reaches no service of its node:

```toml
[network]
nameservers = ["213.186.33.99", "9.9.9.9"]
```

```sh
sudo systemctl restart hopboxd
```

The running machines keep their network during the restart. A machine gets the new resolvers at its next boot.

## Find the address of the machine

Each machine has an IPv4 address of the subnet of its node, as a `/32`:

```sh
hopbox exec box1 ip -4 addr show eth0
hopbox exec box1 ip route
```

```text
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1420 qdisc pfifo_fast state UP group default qlen 1000
    inet 10.240.0.1/32 scope global eth0
default via 169.254.0.1 dev eth0 onlink
169.254.169.254 dev eth0 scope link
```

The guest agent wrote the resolvers of the node to `/etc/resolv.conf` of the machine:

```sh
hopbox exec box1 cat /etc/resolv.conf
```

The node routes the address to the tap device of the machine. The tap device has the alias `hopbox machine <id>`:

```sh
ip -d link show | grep -B1 'alias hopbox machine'
ip route show 10.240.0.1
```

```text
10.240.0.1 dev hbt3f2c9a0b1d4e proto static scope link
```

## Check the egress

A machine reaches the internet. The node gives its packets the address of the server:

```sh
hopbox exec box1 curl -sS https://ifconfig.me
```

The command prints the public address of the server, not the address of the machine.

## Check what the machine cannot reach

A machine reaches no service of its node, no private range, and no other machine. Each of these commands fails after the timeout of 3 seconds:

```sh
hopbox exec box1 curl -m 3 http://169.254.0.1:9464/metrics
hopbox exec box1 curl -m 3 http://192.168.1.1/
hopbox exec box1 curl -m 3 http://10.240.0.2:8000/
```

```text
curl: (28) Connection timed out after 3002 milliseconds
```

The edge role on the node still reaches the machine. A machine URL and an SSH session work as in [Run the edge role and open machine URLs](/guide/machine-urls/) and [Reach a machine over SSH](/guide/ssh/).

## Read the table and the counters

The node keeps its rules in the nftables table `inet hopbox_node`:

```sh
sudo nft list table inet hopbox_node
```

The sets `machines` and `inbound` hold the tap device of each machine, each with its counter:

```text
  set machines {
    type ifname . ipv4_addr
    counter
    elements = { "hbt3f2c9a0b1d4e" . 10.240.0.1 counter packets 1520 bytes 194311 }
  }


  set inbound {
    type ifname
    counter
    elements = { "hbt3f2c9a0b1d4e" counter packets 61 bytes 8840 }
  }
```

Do not flush the nftables ruleset of the server, and do not restart `nftables.service`: the machines lose their isolation for a moment. Within milliseconds, `hopboxd` installs the table again, ends each connection that a machine opened to the server in the gap, and logs `the nftables table inet hopbox_node lost a part outside hopboxd`. `hopbox_node_network_repairs_total` counts these repairs.

The metrics listener serves the same counters for each machine:

```sh
curl -s http://127.0.0.1:9464/metrics | grep '^hopbox_machine_'
```

```text
hopbox_machine_egress_bytes_total{machine="01a1610f-26b5-71c8-abbd-93be11b94c53"} 194311
hopbox_machine_egress_packets_total{machine="01a1610f-26b5-71c8-abbd-93be11b94c53"} 1520
hopbox_machine_inbound_bytes_total{machine="01a1610f-26b5-71c8-abbd-93be11b94c53"} 8840
hopbox_machine_inbound_packets_total{machine="01a1610f-26b5-71c8-abbd-93be11b94c53"} 61
```

The inbound counter grows only with the connections that the node opened, such as a request through the machine URL. The answers to the egress of the machine do not count. Each heartbeat tells the control role which machines got inbound traffic, so these machines count as used for their auto-delete timeout.

## Docker on the server

A server with Docker drops each forwarded packet that Docker does not know, so the egress of the machines times out. Accept the tap devices in the chain `DOCKER-USER`:

```sh
sudo iptables -I DOCKER-USER -i hbt+ -j ACCEPT
sudo iptables -I DOCKER-USER -o hbt+ -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
```

The first rule lets out the packets of the machines. The second one lets in the replies to them. The table `inet hopbox_node` still drops what a machine must not reach. Docker makes the chain again at each start, without these rules, so add them to the boot of the server.

If Docker came after the first start of `hopboxd`, the table has the forward guard, which drops the forwarded traffic of the containers. Remove the guard, and restart `hopboxd`:

```sh
sudo rm /var/lib/hopbox/network/forward-guard
sudo systemctl restart hopboxd
```

## When something fails

| What you see                                                                               | Cause and fix                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hopboxd` stops at its start with `the host names no resolver that a machine can reach`    | The resolv.conf of the server names only a loopback resolver. Set `network.nameservers`.                                                                                                                               |
| The log of `hopboxd` has `the machine boots without network`                               | The machine has no address, for example on a node without the node network. Its tap device stays down.                                                                                                                 |
| The egress of a machine times out, but the edge reaches the machine                        | A host with Docker drops forwarded packets in the chain `FORWARD` of iptables. Accept the tap devices in the chain `DOCKER-USER`, as in [Docker on the server](#docker-on-the-server), or run the node without Docker. |
| The log of `hopboxd` has `the nftables table inet hopbox_node lost a part outside hopboxd` | Something flushed the ruleset, such as a restart of `nftables.service`. `hopboxd` installed the table again. Find what flushed it, and stop it.                                                                        |
| `no capacity: the subnet ... has no free machine address`                                  | The node holds 4094 machines and held addresses. Delete a machine, and wait 5 minutes for the hold of its address.                                                                                                     |

# Work in a team org

> How to share an org with a team, and how the operator sets the limits of an org and suspends it.

Every account has a personal org. A team needs an org that several accounts share, with roles. This guide creates an org, invites a second person by email, and gives roles. Then, as the operator, it lists the orgs, sets the limits of the org, and suspends it. [The org API](/reference/org-api/) has every call and rule.

This guide calls the API with curl, in the same way as the console does, so it shows each call. The console pages of an org do the same work in a browser ([Use the console](/guide/console/#more-pages)).

## What you need

* `hopboxd` with the control role on a laptop, as in [Run the control role on a laptop](/guide/run-hopboxd/), with the API on `127.0.0.1:7443`.
* A domain and an SMTP config, as in [First sign-in on a new install](/guide/first-sign-in/#turn-on-magic-links). An invitation is for one verified email, so each person signs in with a magic link. A local mail catcher such as [Mailpit](https://mailpit.axllent.org) works.
* Two accounts, user1 and user2, each signed in with a magic link of [First sign-in on a new install](/guide/first-sign-in/#turn-on-magic-links). Keep the session cookie of each one in a file: `/tmp/hb/user1` and `/tmp/hb/user2`, each with one line of the form `__Host-hopbox_session=<token>`.

Define a function that calls the API as one of them, with the headers of the console:

```sh
API=http://127.0.0.1:7443
as() {
  who=$1; shift
  curl -s -X POST -H 'Content-Type: application/json' -H 'Connect-Protocol-Version: 1' \
    -H 'Origin: https://example.com' -H "Cookie: $(cat /tmp/hb/$who)" "$@"
  echo
}
admin() { ./bin/darwin_arm64/hopboxd admin --config /tmp/hb/hopboxd.toml "$@"; }
```

## Create an org

`CreateOrg` makes an org with you as its owner. A create call takes an idempotency key, so a retry with the same key returns the same org:

```sh
as user1 -H "Idempotency-Key: $(uuidgen)" -d '{"name":"org1"}' $API/hopbox.v1.OrgService/CreateOrg
```

```json
{"org":{"id":"01a14565-a2df-75a1-9401-ed28dfa37fc4","name":"org1","role":"ORG_ROLE_OWNER","version":"1","createTime":"2026-10-16T15:47:31.166821Z"}}
```

Keep the ID:

```sh
ORG=01a14565-a2df-75a1-9401-ed28dfa37fc4
```

`ListOrgs` now shows the personal org of user1 first, then org1:

```sh
as user1 -d '{}' $API/hopbox.v1.OrgService/ListOrgs
```

A call that leaves out `orgId` acts in the personal org of the caller. A personal org belongs to one account, so it takes no invitations.

## Invite a person

An owner invites with any role. An admin invites members only. An admin or an owner can change what runs in the private machines of every member ([Read the members and the roles](#read-the-members-and-the-roles)). So give these roles only to a person whom every member trusts. Invite user2 as an admin:

```sh
as user1 -d "{\"orgId\":\"$ORG\",\"email\":\"user2@example.org\",\"role\":\"ORG_ROLE_ADMIN\"}" \
  $API/hopbox.v1.OrgService/CreateInvitation
```

```json
{"invitation":{"id":"01a14565-a316-74dd-968e-fac72d706827","orgId":"01a14565-a2df-75a1-9401-ed28dfa37fc4","email":"user2@example.org","role":"ORG_ROLE_ADMIN","inviterAccountId":"01a14565-8448-774f-9317-ea6348e9a930","createTime":"2026-10-16T15:47:31.221754Z","expireTime":"2026-10-23T15:47:31.221754Z"},"url":"https://example.com/invite#token=vH_2434xeosR22NllAU0tHE8LoqC08ZYHX1JhHZK4UA","emailSent":true}
```

The response holds the link, and `emailSent` says that the server mailed it to user2 too. Without an SMTP config, `emailSent` is `false`, and you send the link to user2 yourself. The same goes for the file mail transport of a dev install ([Mail](/reference/mail/)). The link works once, for 7 days. Treat it as a password until then. A new invitation for the same email replaces this one, so its link stops working.

## Accept the invitation

On an install with a console, user2 opens the link in a browser. The console page `/invite` reads the token after `#token=` and calls `AcceptInvitation`. Here, make that call yourself. The invitation is for `user2@example.org`, so user1 cannot use it:

```sh
TOKEN=vH_2434xeosR22NllAU0tHE8LoqC08ZYHX1JhHZK4UA
as user1 -d "{\"token\":\"$TOKEN\"}" $API/hopbox.v1.OrgService/AcceptInvitation
```

```json
{"code":"failed_precondition","message":"failed precondition: the invitation is for user2@example.org, and the account has no verified email user2@example.org. Sign in with that email, then open the link again"}
```

The refused try leaves the invitation open. Then user2 accepts it:

```sh
as user2 -d "{\"token\":\"$TOKEN\"}" $API/hopbox.v1.OrgService/AcceptInvitation
```

```json
{"org":{"id":"01a14565-a2df-75a1-9401-ed28dfa37fc4","name":"org1","role":"ORG_ROLE_ADMIN","version":"1","createTime":"2026-10-16T15:47:31.166821Z"}}
```

A second accept of the same link fails with `not_found`: the link works once.

## Read the members and the roles

Each member reads the members of the org:

```sh
as user2 -d "{\"orgId\":\"$ORG\"}" $API/hopbox.v1.OrgService/ListOrgMembers
```

The members of an org trust its admins and owners. An admin or an owner sets the env vars and secrets with the scope `all`, and these reach the private machines of every member ([Set env vars and secrets](/guide/env-vars/#trust-the-admins-of-your-org)). An admin cannot open a shell in the private machine of another member, but can change what runs there with such a value.

Only an owner makes other owners and admins. So user2, an admin, cannot change a role:

```sh
as user2 -d "{\"orgId\":\"$ORG\",\"accountId\":\"<the ID of user1>\",\"role\":\"ORG_ROLE_MEMBER\"}" \
  $API/hopbox.v1.OrgService/SetOrgMemberRole
```

```json
{"code":"permission_denied","message":"permission denied: a caller of kind session may not do org.member_set_role"}
```

Every org keeps at least one owner. So user1, the only owner, cannot leave yet:

```sh
as user1 -d "{\"orgId\":\"$ORG\"}" $API/hopbox.v1.OrgService/LeaveOrg
```

```json
{"code":"failed_precondition","message":"failed precondition: the account is the only owner of the org, and every org keeps at least one owner. Make another member an owner first, or delete the org"}
```

To leave, user1 first makes user2 an owner with `SetOrgMemberRole` and the role `ORG_ROLE_OWNER`. An account that leaves an org loses what it made in the org and did not share.

## Read the usage and the limits

```sh
as user2 -d "{\"orgId\":\"$ORG\"}" $API/hopbox.v1.OrgService/GetOrgUsage
```

```json
{"usage":{},"limits":{"machines":3,"vcpus":6,"memoryBytes":"25769803776","diskBytes":"300000000000"}}
```

The org has no machines yet, so it uses nothing. The limits are the defaults of the install: 3 machines, 6 vCPUs, 24 GiB of RAM, and 300 GB of disk.

## Manage the orgs as the operator

An instance admin sees the metadata of every org, but not its members or its resources. Root on a control server calls the admin API with `hopboxd admin`:

```sh
admin org list
```

```text
01a14565-8448-7753-9c1f-5ec0a86b8d92  Personal  personal  members=1  active  machines=0/3
01a14565-85d5-7087-a903-d66b5cabce88  Personal  personal  members=1  active  machines=0/3
01a14565-a2df-75a1-9401-ed28dfa37fc4  org1  org  members=2  active  machines=0/3
```

Give org1 more room. A limit that you leave out takes the default of the install:

```sh
admin org set-limits --org-id $ORG --machines 10 --memory-gib 64
```

```text
id  01a14565-a2df-75a1-9401-ed28dfa37fc4
name  org1
members  2
state  active
machines  0/10
vcpus  0/6
memory_bytes  0/68719476736
disk_bytes  0/300000000000
version  2
```

Change the defaults of every other org with `admin org default-limits set`, for example `--machines 5`. Each new org brings its own limits, so an account owns at most 10 orgs besides its personal org. Change that cap with `admin org default-limits set --max-orgs-per-account N`.

To handle abuse, suspend the org:

```sh
admin org suspend --org-id $ORG --reason 'spam reports'
```

The members see the suspension and its reason:

```sh
as user1 -d "{\"orgId\":\"$ORG\"}" $API/hopbox.v1.OrgService/GetOrg
```

```json
{"org":{"id":"01a14565-a2df-75a1-9401-ed28dfa37fc4","name":"org1","role":"ORG_ROLE_OWNER","suspended":true,"suspendTime":"2026-10-16T15:47:41.931248Z","suspendReason":"spam reports","version":"3","createTime":"2026-10-16T15:47:31.166821Z"}}
```

A suspended org sends no invitations and takes no new members. Reads still work. A suspension also stops the machines of the org, and blocks the create, the start, and the delete of a machine ([the org API](/reference/org-api/#suspension)). The owners find the entry `org.suspend` of `local_root` in the audit log of the org:

```sh
as user1 -d "{\"orgId\":\"$ORG\",\"pageSize\":1}" $API/hopbox.v1.AuditService/ListAuditEntries
```

End the suspension:

```sh
admin org unsuspend --org-id $ORG
```

## Delete the org

Only an owner deletes an org, and the request must hold its name in `confirm`. A suspended org keeps its data as evidence, so the delete waits for the end of the suspension:

```sh
as user1 -d "{\"orgId\":\"$ORG\",\"confirm\":\"org1\"}" $API/hopbox.v1.OrgService/DeleteOrg
```

```json
{}
```

The delete removes the memberships, the invitations, and every resource of the org. A personal org goes only with its account ([the sign-in, account, and audit API](/reference/auth-api/#deleteaccount)).

# Add pools and sizes

> How to add a pool for a second server model and a size whose machines land in it, why enrollment refuses a server with other hardware, and how to retire a size and delete a pool.

This guide adds a pool for a second server model, and a size whose machines land only in that pool. A pool is a named group of servers with identical hardware. A size sets the vCPUs, the RAM, and the disk of a machine. An operator size can also name a pool and labels. A user picks a size for a new machine, and never a pool.

[The admin API](/reference/admin-api/#poolservice) covers the calls, [hopboxd](/reference/hopboxd/#admin-pool-create) the commands, and [hopbox Terraform provider](/reference/terraform-provider/#resource-hopbox_pool) the Terraform resources.

## Why pools and sizes

Every install has the pool `default` and the size `default`: 2 vCPUs, 8 GiB of RAM, and a sparse disk of 100 GB. That is enough for an install of one server model. Two rules make a second model need its own pool:

* All servers of a pool have identical hardware. The first server that enrolls into a pool records its CPU model, its CPU threads, its RAM, and its disks. The enrollment of a server with other hardware fails.
* Placement filters use pools and labels. A size that names a pool keeps its machines on the nodes of that pool. A size that names labels keeps them on the nodes with each label.

So a bigger server model goes into its own pool, and a bigger size can keep its machines there.

## What you need

* An install with its first server, as [Install hopbox on an OVHcloud server with Terraform](/guide/install-on-ovhcloud/) sets up.
* Root on a control server, for the commands. Every command below runs with `sudo`.
* For Terraform: the provider with `install_url` and an admin API key ([Install hopbox on an OVHcloud server with Terraform](/guide/install-on-ovhcloud/#6-keep-the-admin-api-key)).

## 1. Add the pool

```sh
sudo hopboxd admin pool create big --ovh-plan 24adv01
```

`--ovh-plan` records the OVHcloud plan code of the servers of the pool. Leave it out for a pool of adopted servers. The pool has no hardware until its first server enrolls:

```text
$ sudo hopboxd admin pool list
NAME     OVH PLAN  SERVERS  SIZES  HARDWARE
big      24adv01   0        0      -
default  -         1        0      -
```

## 2. Enroll a server into the pool

Make a token for the pool, and enroll the new server with it ([Enroll the node role on one server](/guide/enroll-node/)):

```sh
TOKEN="$(sudo hopboxd admin enrollment-token create --pool big)"
```

The first server of `big` records its hardware. `hopboxd admin pool get big` then shows it, and the log of the control role has the record `recorded the hardware of a pool`. A later server of another model fails, and its token stays unused:

```text
hopboxd: error: enroll at https://10.0.0.1:7443: failed_precondition: failed precondition: the hardware of this server differs from the pool big: it has 16 CPU threads, not 12. All servers of a pool have identical hardware, so enroll it into a pool of its server model
```

RAM and each disk can differ by 2%, because two servers of one model can show a few MiB more or less. The CPU model, the thread count, and the count of disks must be the same.

To put another model in a pool, decommission every server of the pool first. A pool without a live server takes the hardware of its next server. The pool keeps its `ovh_plan`, which then names the old model, and no call changes the plan of a pool. So for another model, prefer a new pool. To keep the name, delete the empty pool and create it again with the new plan, before the first server of the new model enrolls:

```sh
sudo hopboxd admin pool delete big
sudo hopboxd admin pool create big --ovh-plan 24adv02
```

The delete needs a pool without live sizes, so retire the sizes of the pool first. With Terraform, a change of `ovh_plan` of the `hopbox_pool` does the same delete and create.

## 3. Add a size for the pool

```sh
sudo hopboxd admin size create large --vcpus 8 --memory-gib 32 --disk-gb 200 --pool big --label disk=nvme
```

A machine of the size `large` lands only on a node of `big` that has the label `disk=nvme`. Set the labels of a server with `hopboxd admin server set-labels`, or with `labels` of its `hopbox_server`. A user sees the new size, without its pool and labels:

```text
$ hopbox machine sizes
NAME     VCPUS  MEMORY  DISK
default  2      8 GiB   100 GB
large    8      32 GiB  200 GB
```

A machine of the size `large` that finds no node of `big` with room, or no node with the label, fails with `unavailable`. The message names the reason ([Placement](/reference/placement/#when-no-node-has-room)):

```text
no capacity: no node has room for a machine of size large (8 vCPUs, 32 GiB of RAM): 1 node is in another pool, 1 node lacks a label
```

## 4. Change or retire a size

A size never changes, because each machine copies the numbers of its size. To change a size, add a size with a new name, and retire the old one:

```sh
sudo hopboxd admin size create large2 --vcpus 16 --memory-gib 64 --disk-gb 400 --pool big
sudo hopboxd admin size retire large
```

A retired size takes no new machine. Its machines keep running and keep their size. Its name stays taken, because those machines name it. `hopboxd admin size list --all` shows the retired sizes too. The size `default` cannot retire, because a create without a size takes it.

## 5. Delete a pool

```sh
sudo hopboxd admin pool delete big
```

The delete frees the name. The install refuses it while the pool holds a server that is not decommissioned, or while a size names it that is not retired. Decommission the servers and retire the sizes first. The pool `default` cannot go.

## The same with Terraform

The provider manages pools and sizes with `hopbox_pool` and `hopbox_size`. Both call the admin API, so the provider block needs `install_url`, and `HOPBOX_ADMIN_API_KEY` in the environment:

```hcl
resource "hopbox_pool" "big" {
  name     = "big"
  ovh_plan = "24adv01"
}


resource "hopbox_size" "large" {
  name       = "large"
  vcpus      = 8
  memory_gib = 32
  disk_gb    = 200
  pool       = hopbox_pool.big.name
  labels     = { disk = "nvme" }
}
```

A `hopbox_server` joins the pool with `pool = hopbox_pool.big.name`. The first server of an install stays in the pool `default`, because no other pool exists before it. A destroy of `hopbox_size` retires the size, and a destroy of `hopbox_pool` deletes the pool. A plan that changes a size and keeps its name fails with `A size never changes`. Give the changed size a new name, and Terraform retires the old one.

# Run the control role on a laptop

> How to run the control role on a laptop, call the API and the admin socket, read the audit log, make an admin API key, open the console behind Caddy, and sign the CLI in with curl.

This guide runs `hopboxd` with the control role on a Mac, without root. It reads the install info over the API. Then it sets the domain of the install and rotates the key-encryption key through the admin socket, and finds both actions in the audit log. It also makes an admin API key, opens the console on the laptop, and signs the CLI in without a browser. On a server, the same steps run as root with the default paths.

The release files of hopbox are not public yet. The hopbox team gives them on request. They hold no `hopboxd` for macOS, so this guide builds `hopboxd` from a checkout of the source of hopbox. The source is not public yet either, so this guide is for the people who work on hopbox. To run an install on a server, use [Install hopbox on a Debian 13 server by hand](/guide/install-debian/) or [Install hopbox on an OVHcloud server with Terraform](/guide/install-on-ovhcloud/).

## What `hopboxd run` does

`hopboxd run` reads one small file, the bootstrap config. The file lists the roles of the server and a few paths ([the bootstrap config of hopboxd](/reference/hopboxd-config/)). Everything else about the install lives in the control store and changes through the admin API.

The control role is a chain of units. Each unit needs the units before it, so `hopboxd` starts them in this order and stops them in the reverse order:

1. `postgres`: the bundled Postgres.
2. `store`: the connection pool and the schema migrations.
3. `leader election`: one control process becomes the leader and runs the leader jobs.
4. `api`: the API listener, for every client.
5. `internal listener`: the cluster API over TLS, for the servers of the install ([the internal listener](/reference/internal-listener/)).
6. `admin socket`: the admin API for root on this server.

Every call on every listener passes one request gate, which names the caller. Then one policy check in the service layer decides what that caller can do ([the API server](/reference/api/)). On the admin socket, the kernel proves the user of the caller. On a laptop, `hopboxd` runs as you, so the socket accepts you without `sudo`.

## What you need

* A checkout of the source of hopbox, built with `make build`.
* The bundled Postgres: `make pg` builds it on the first run and prints its dir.
* curl 7.47 or later, for `--http2-prior-knowledge`.

## Write the bootstrap config

A unix socket path has at most 103 bytes on macOS, so put the sockets in a short dir under `/tmp`. Group and others must not be able to write in the dir.

```sh
mkdir -p /tmp/hb && chmod 700 /tmp/hb
cat > /tmp/hb/hopboxd.toml <<EOF
roles = ["control"]
data_dir = "$HOME/hopbox-dev"
run_dir = "/tmp/hb"


[postgres]
install = "$(make pg)"
EOF
```

The API listener keeps its default address, `127.0.0.1:7080`, and the internal listener keeps `127.0.0.1:7443`.

## Start hopboxd

```sh
./bin/darwin_arm64/hopboxd run --config /tmp/hb/hopboxd.toml
```

The first start creates the Postgres cluster in `~/hopbox-dev/pg`, which takes a few seconds. `hopboxd` writes one JSON log record per line. The record `hopboxd is ready` means that every unit runs. Leave it running, and use a second terminal for the next steps.

The install has no key-encryption key yet, so it has no CA, and the internal listener has no certificate. `hopboxd` logs `the internal listener has no certificate yet` at level warn. The rotation in [Act through the admin socket](#act-through-the-admin-socket) makes the first key. The next TLS handshake of the internal listener then makes the CA.

## Read the install info

`GetInstallInfo` needs no credential:

```sh
curl -s --http2-prior-knowledge \
  'http://127.0.0.1:7080/hopbox.v1.InstallService/GetInstallInfo?encoding=json&message=%7B%7D'
```

```json
{"version":"v0.0.0-20261016030431-02092f6e6161"}
```

The domain is empty, so the JSON leaves it out. Your version names your commit.

An admin call on the API listener needs an admin API key, and this install has none yet. So the gate leaves the call anonymous, and the policy refuses it:

```sh
curl -s -X POST -H 'Content-Type: application/json' -d '{}' \
  http://127.0.0.1:7080/hopbox.admin.v1.InstallConfigService/GetInstallConfig
```

```json
{"code":"unauthenticated","message":"this call needs a credential"}
```

[Make an admin API key](#make-an-admin-api-key) makes one, so that the same call works.

## Act through the admin socket

Set the domain of the install, then rotate the key-encryption key:

```sh
./bin/darwin_arm64/hopboxd admin --config /tmp/hb/hopboxd.toml config set --domain example.com
./bin/darwin_arm64/hopboxd admin --config /tmp/hb/hopboxd.toml kek rotate
```

```text
domain  example.com
public_addresses  -
acme_directory_url  https://acme-v02.api.letsencrypt.org/directory
acme_email  -
acme_terms_agreed  false
mail_transport  smtp
version  2
update_time  2026-10-16T09:00:00Z
file:1
```

`admin` finds the socket in the `run_dir` of the config, here `/tmp/hb/admin.sock`. The rotation wrote the key file `~/hopbox-dev/kek/1.key`. Read the install info again, and it now has the domain:

```sh
curl -s --http2-prior-knowledge \
  'http://127.0.0.1:7080/hopbox.v1.InstallService/GetInstallInfo?encoding=json&message=%7B%7D'
```

```json
{"domain":"example.com","version":"v0.0.0-20261016030431-02092f6e6161"}
```

## Find the actions in the audit log

Every admin call writes an audit entry. Read the entries with the `psql` of the bundled Postgres, over its socket:

```sh
"$(make pg)/bin/psql" -h /tmp/hb/pg -U hopbox hopbox \
  -c "SELECT actor_kind, action, target_id, details FROM audit_log ORDER BY id"
```

```text
 actor_kind |        action         | target_id |      details
------------+-----------------------+-----------+------------------------------------------------------------------------
 local_root | install_config.update |           | {"domain": "example.com", "peer_pid": "49450", "peer_uid": "501", "old_domain": "", ...}
 local_root | keyring.rotate.start  | file:1    | {"peer_pid": "49449", "peer_uid": "501", "idempotency": "5046b3c8...2fccc2d"}
 local_root | keyring.rotate        | file:1    | {"peer_pid": "49449", "peer_uid": "501", "idempotency": "5046b3c8...2fccc2d"}
(3 rows)
```

The output here is cut short. The entry `install_config.update` holds each setting before and after the change, such as `old_domain` and `domain`. A rotation writes two entries: `keyring.rotate.start` before it writes the key file, and `keyring.rotate` after it ([the admin API](/reference/admin-api/#rotatekek)). `idempotency` is the SHA-256 of the idempotency key of the call. `peer_uid` and `peer_pid` name the user and the process that called through the socket.

## Read the metrics

`hopboxd` counts every API call in its Prometheus metrics on `127.0.0.1:9464` ([Metrics](/reference/metrics/)):

```sh
curl -s http://127.0.0.1:9464/metrics | grep '^hopbox_api_calls_total'
```

```text
hopbox_api_calls_total{code="ok",listener="admin_socket",procedure="/hopbox.admin.v1.InstallConfigService/UpdateInstallConfig"} 1
hopbox_api_calls_total{code="ok",listener="admin_socket",procedure="/hopbox.admin.v1.KeyringService/RotateKEK"} 1
hopbox_api_calls_total{code="ok",listener="api",procedure="/hopbox.v1.InstallService/GetInstallInfo"} 2
hopbox_api_calls_total{code="unauthenticated",listener="api",procedure="/hopbox.admin.v1.InstallConfigService/GetInstallConfig"} 1
```

## Make an admin API key

The admin API on the API listener takes an admin API key ([CLI tokens, API keys, admin API keys, and SSH keys](/reference/credentials/#admin-api-keys)). Only root on a control server makes one, through the admin socket. On the laptop, that is you:

```sh
admin() { ./bin/darwin_arm64/hopboxd admin --config /tmp/hb/hopboxd.toml "$@"; }
ADMIN_KEY="$(admin admin-key create --name terraform)"
curl -s -X POST -H 'Content-Type: application/json' -H "Authorization: Bearer $ADMIN_KEY" -d '{}' \
  http://127.0.0.1:7080/hopbox.admin.v1.InstallConfigService/GetInstallConfig
```

```text
The admin key 01a145b6-3fc1-7ba1-a54d-d1dceac38930 (terraform) works until 2027-01-14T17:15:34Z. This is its only copy.
{"config":{"domain":"example.com","version":"2","updateTime":"2026-10-16T17:14:47.254670Z"}}
```

The key operates the install, but the keyring stays with root on the server:

```sh
curl -s -X POST -H 'Content-Type: application/json' -H "Authorization: Bearer $ADMIN_KEY" -d '{}' \
  http://127.0.0.1:7080/hopbox.admin.v1.KeyringService/ListKEKs
```

```json
{"code":"permission_denied","message":"permission denied: a caller of kind admin_key may not do keyring.list"}
```

The hopbox Terraform provider never sends its key to the server. It makes the key itself, and the server registers only its SHA-256. Do the same by hand:

```sh
KEY="hbxadm_$(head -c 32 /dev/urandom | base64 | tr '+/' '-_' | tr -d '=')"
admin admin-key register --name bootstrap --sha256 "$(printf '%s' "$KEY" | shasum -a 256 | cut -d' ' -f1)"
admin admin-key list
```

```text
01a145b6-400d-7c41-979e-14666fc2fe21  bootstrap  2027-01-14T17:15:34Z  never
01a145b6-3fc1-7ba1-a54d-d1dceac38930  terraform  2027-01-14T17:15:34Z  2026-10-16T17:15:34Z
01a145b6-400d-7c41-979e-14666fc2fe21  bootstrap  2027-01-14T17:15:34Z  never
```

The first line is the output of `register`, and the next two are the list. `$KEY` now calls the admin API. Run `register` again with the same hash, and it prints the same key: a repeated install makes no second key. Delete a key with `admin admin-key revoke --id <id>`. The audit log has `admin_key.create`, `admin_key.register`, and `admin_key.list` with the actor `local_root`.

## Open the console on the laptop

`make build` builds the console into `hopboxd`, after `corepack pnpm install`. The console needs HTTPS. Its session cookie has the `Secure` flag, and each call with the cookie must come from the origin `https://<domain>` ([Sessions, cookies, and sign-in links](/reference/sessions/#calls-with-the-cookie)). On an install, the edge ends TLS. On the laptop, [Caddy](https://caddyserver.com) 2.8 or later does that job.

With `hopboxd` running, ask the API listener for a page of the console:

```sh
curl -sI http://127.0.0.1:7080/orgs | grep -i -e '^HTTP' -e '^content-security-policy'
```

```text
HTTP/1.1 200 OK
Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'
```

If you get `404` and the text `This hopboxd has no console`, the binary came from `go build`. Run `make build` again.

A browser treats each name under `localhost` as the laptop itself. So `hop.localhost` works as the domain of the install without a DNS record:

```sh
admin config set --domain hop.localhost
```

```text
domain  hop.localhost
public_addresses  -
...
```

Save this file as `/tmp/hb/Caddyfile`:

```text
hop.localhost {
  tls internal
  reverse_proxy 127.0.0.1:7080
}
```

`tls internal` makes Caddy sign a certificate for `hop.localhost` with its own local CA. Make the browser trust that CA once, then start Caddy in a third terminal:

```sh
caddy trust
caddy run --config /tmp/hb/Caddyfile
```

`caddy trust` asks for your password, because it adds the CA to the trust store of macOS. Caddy listens on port 443 and sends each request on to the API listener. It keeps the `Host` and `Origin` headers, so the checks of the session cookie pass.

Open `https://hop.localhost/` in the browser. The console sends you to `/signin`. The install has no SMTP server and no OAuth app yet, so the page shows the command for a login link. Make the link, and open it in the browser:

```sh
admin login-link --email root@example.org
```

```text
https://hop.localhost/auth/login-link#token=tOzJ8YQyibHutrU34tIWLHnGd5XlzYs4WoIBXgSDh5I
The link signs in root@example.org once, until 2026-10-21T14:57:56Z.
```

The page reads the token after `#token=`, removes it from the address bar, and signs you in. Then the steps of [Use the console](/guide/console/#create-a-machine-and-open-a-shell) work, but a machine needs a node. The laptop runs only the control role, so a create fails with an error about capacity. Enroll a node first ([Enroll the node role on one server](/guide/enroll-node/)). The CLI signs in to the same console with `./bin/darwin_arm64/hopbox login --url https://hop.localhost`.

Stop Caddy with Ctrl-C. To remove the CA of Caddy from the trust store, run `caddy untrust`. To go back to the domain of the other guides, run `admin config set --domain example.com`.

## Sign in the CLI with curl

A person approves a sign-in of the hopbox CLI on the console page `/device` ([Install the hopbox CLI](/guide/install-cli/#sign-in-to-an-install)). To test the device flow without a browser, approve it with curl, as that page does. This section needs the domain `example.com`, a signed-in instance admin, and the shell function `browser` of [First sign-in on a new install](/guide/first-sign-in/#sign-in-with-the-link). [CLI tokens, API keys, admin API keys, and SSH keys](/reference/credentials/#the-device-flow) gives each step of the flow.

Build the CLI, and give it a short name. On Linux, use `bin/linux_amd64` or `bin/linux_arm64`:

```sh
make build
hopbox() { ./bin/darwin_arm64/hopbox "$@"; }
API=http://127.0.0.1:7080
```

Start the sign-in in the background, so the same shell can approve it:

```sh
hopbox login --url $API > /tmp/hb/login.out 2> /tmp/hb/login.err &
sleep 1; cat /tmp/hb/login.err
```

```text
To sign in, open this page in a browser and approve the code KWJQ-LBZV:


  https://example.com/device?code=KWJQ-LBZV


Waiting for the approval. Press Ctrl-C to stop.
```

The URL uses plain `http`, which the CLI accepts only for a loopback address. Now be the person at the console. Look up the code, check that the client is your own CLI, and approve it with the start time that the lookup showed:

```sh
CODE=$(sed -n 's/.*approve the code \([A-Z-]*\):/\1/p' /tmp/hb/login.err)
browser -d "{\"userCode\":\"$CODE\"}" $API/hopbox.v1.AuthService/GetDeviceAuthorization | tee /tmp/hb/shown.json
CREATED=$(python3 -c 'import json; print(json.load(open("/tmp/hb/shown.json"))["createTime"])')
browser -d "{\"userCode\":\"$CODE\",\"createTime\":\"$CREATED\"}" $API/hopbox.v1.AuthService/ApproveDevice
```

```json
{"clientName":"hopbox CLI on user1-laptop", "clientIp":"127.0.0.1", "createTime":"2026-10-17T15:30:36.792730Z", "expireTime":"2026-10-17T15:40:36.792730Z"}
{"clientName":"hopbox CLI on user1-laptop", "clientIp":"127.0.0.1", "createTime":"2026-10-17T15:30:36.792730Z"}
```

The approval needs a sign-in within the last 10 minutes ([Sessions, cookies, and sign-in links](/reference/sessions/#recent-sign-in)). If your sign-in is older, the call fails with `permission_denied`:

```json
{"code":"permission_denied","message":"permission denied: this action needs a sign-in within the last 10 minutes. Sign in again, then retry","details":[{"type":"hopbox.v1.RecentSignInRequired","value":"CgMI2AQ","debug":{"maxAge":"600s"}}]}
```

The code keeps waiting. Print a new login link, and put the part of the link after `#token=` in `TOKEN`. Then sign in with your old cookie, as a browser does. The new sign-in ends the old session and starts a new one. Take the new cookie, and approve again:

```sh
admin login-link --email root@example.org
TOKEN='<the part of the link after #token=>'
curl -s -D /tmp/hb/headers -X POST -H 'Content-Type: application/json' \
  -H 'Connect-Protocol-Version: 1' -H 'Origin: https://example.com' -H "Cookie: $COOKIE" \
  -d "{\"token\":\"$TOKEN\"}" $API/hopbox.v1.AuthService/VerifyLoginLink
COOKIE=$(sed -n 's/^Set-Cookie: \(__Host-hopbox_session=[^;]*\).*/\1/p' /tmp/hb/headers)
browser -d "{\"userCode\":\"$CODE\",\"createTime\":\"$CREATED\"}" $API/hopbox.v1.AuthService/ApproveDevice
```

The CLI polls every 5 seconds, so it sees the approval within a few seconds:

```sh
wait; cat /tmp/hb/login.out
```

```text
Signed in to http://127.0.0.1:7080 as root@example.org (unverified). The profile default is active.
Added the SSH key ~/.ssh/hopbox_ed25519 (SHA256:rkEGrocWsFODhePtstCZFcyj1D0BUmGYu1rexwam/mo) to your account.
```

To see a refresh of the CLI tokens at once, mark the access token as ended in the file. On Linux, use `sed -i` without `''`:

```sh
sed -i '' 's/^\(    access_token_expire_time = \).*/\12026-01-01T00:00:00Z/' ~/.config/hopbox/credentials.toml
hopbox --debug whoami 2>&1 | head -1
```

```text
time=2026-10-17T17:31:00.445+02:00 level=DEBUG msg="refreshed the CLI tokens" cli_sign_in=01a14a7c-abae-7e4d-bde7-34c1e1d6870d
```

## Call the access calls on the laptop

The API listener of the laptop listens on `127.0.0.1:7080` without TLS. So the grpcurl calls of [Run commands and copy files in a machine](/guide/exec-and-files/) need `-plaintext` there, and an API key of your org in `KEY`:

```sh
API=127.0.0.1:7080
hb() { grpcurl -plaintext -H "Authorization: Bearer $KEY" "$@"; }
```

Each access call but the log needs a running machine, so the laptop also needs a node ([Enroll the node role on one server](/guide/enroll-node/)). Without one, a new machine stays `pending`, and the calls answer `failed_precondition`.

## Add a second control server

Two control servers share one control store ([Run the control store on an external Postgres](/guide/external-postgres/)), and they need the same key-encryption keys. Copy the key dir of the first server to the second one before the second one starts for the first time. Do not run `hopboxd install` on it first with the control role and no keys, because that makes a first key that the other server does not have. The start of the control role checks that its key files open the install CA, and fails when they do not.

On the first server, `cp1`, copy the dir as root. The dir has the mode `0700`, and each key file has the mode `0400` and belongs to root:

```sh
sudo rsync -a /var/lib/hopbox/kek/ root@cp2:/var/lib/hopbox/kek/
ssh root@cp2 ls -l /var/lib/hopbox/kek
```

```text
total 4
-r-------- 1 root root 32 Oct 16 09:00 1.key
```

Start `hopboxd` on `cp2`. If the keys are wrong, it stops with `control: the key files in /var/lib/hopbox/kek do not open the install CA of the control store: ... Copy the key files of a running control server there`.

Later, add a key to both servers with a stage and a promote. A plain `kek rotate` fails while the other server is live:

```sh
sudo hopboxd admin kek stage
sudo scp -p /var/lib/hopbox/kek/2.staged root@cp2:/var/lib/hopbox/kek/2.staged
sudo hopboxd admin kek promote file:2
sudo hopboxd admin kek rewrap
```

```text
file:2  /var/lib/hopbox/kek/2.staged
file:2
rewrapped 3 to file:2
file:1  0
file:2  3  current
```

[Sealing](/reference/sealing/#several-control-servers) gives the steps and the errors. hopbox does not copy key files between servers yet, so you copy them over SSH.

## Stop hopboxd

Press Ctrl-C in the first terminal. `hopboxd` stops the units in the reverse order: the admin socket, the internal listener, the API, the leader election, the store, Postgres, and the metrics listener last. It removes `/tmp/hb/admin.sock` and exits with status 0. The next start keeps the cluster, the domain, and the key.

To start again from nothing, stop `hopboxd`, then remove the dirs `~/hopbox-dev` and `/tmp/hb`.

# Reach a machine over SSH

> How to reach a machine through the SSH front door with ssh, scp, sftp, rsync, and port forwards. Also what each failure means.

The SSH front door lets `ssh`, `scp`, `sftp`, `rsync`, port forwards, and VS Code Remote-SSH reach a machine. Each machine has its own SSH port on the edge servers. Your SSH key proves your account. The user name is the Linux user in the machine, `user` by default. [The SSH front door](/reference/ssh-front-door/) covers the front door in full.

## How a connection reaches the machine

1. Your SSH client connects to the domain of the install, at the SSH port of the machine, such as `example.com` port 10022.
2. nftables on the edge server sends the connection to the SSH front door. The port names the machine.
3. The front door shows the one host key of the install. The hopbox CLI wrote it to `~/.ssh/known_hosts` at your login, so ssh asks no question.
4. Your client signs in with your SSH key. The control role checks that your account uses the machine, as for `hopbox exec`.
5. The front door opens its own SSH connection to the OpenSSH server in the machine, and passes your channels through it.

An org admin cannot open a private machine of another member, as with `hopbox exec`. A shared machine opens for every member of its org.

## What you need

* An account on an install with machines, such as the preview install of [Try hopbox](/guide/quickstart/). This guide uses the install `https://example.com`.
* The hopbox CLI, installed as in [Install the hopbox CLI](/guide/install-cli/). Without the CLI, add your SSH key on the page “Account” of the console, and give the SSH port of the machine to ssh ([Try hopbox](/guide/quickstart/#connect-over-ssh)).
* OpenSSH on your laptop. macOS and most Linux systems have it.

## Sign in and make a machine

```sh
hopbox login --url https://example.com
hopbox new box1
```

If your account had no SSH key, the login made `~/.ssh/hopbox_ed25519` and added it to your account. It also wrote the host key of the install to `~/.ssh/known_hosts`. `hopbox new` added the entry `box1.hop` to the managed block of `~/.ssh/config` ([Use machines from the CLI](/guide/cli-machines/)):

```text
Host box1.hop
  HostName example.com
  Port 10022
  User user
  IdentityFile ~/.ssh/hopbox_ed25519
  IdentitiesOnly yes
  HostKeyAlias hopbox-example.com
```

## Open a shell, and copy files

```sh
ssh box1.hop
ssh box1.hop 'uname -sr; id -un'
scp ./notes.txt box1.hop:/tmp/
sftp box1.hop
rsync -a ./site/ box1.hop:site/
```

The second command prints the kernel of the machine and `user`. The exit status of a remote command is the exit status of `ssh`. For root, use `ssh root@box1.hop`. The main user also has `sudo` without a password.

## Forward ports

```sh
ssh -N -L 8000:127.0.0.1:8000 box1.hop
ssh -N -R 9000:127.0.0.1:3000 box1.hop
ssh -A box1.hop
```

The first command makes port 8000 of the machine reach `http://127.0.0.1:8000` on your laptop. The second one makes port 9000 in the machine reach port 3000 on your laptop. The third one forwards your SSH agent, so `git` in the machine can use your keys. X11 forwarding stays off.

In VS Code, install the Remote-SSH extension, and connect to the host `box1.hop`. VS Code reads the managed block, and uses a local port forward.

## Use another key

```sh
hopbox ssh-key add ~/.ssh/id_ed25519.pub
ssh -i ~/.ssh/id_ed25519 -p 10022 -o HostKeyAlias=hopbox-example.com user@example.com
```

The managed block sets `IdentitiesOnly yes`, so `ssh box1.hop` offers only `~/.ssh/hopbox_ed25519`. Give another key with `-i`, as above. A key works for one account only. A removal with `hopbox ssh-key rm` ends the open SSH connections of the key within seconds.

## See who connected

Each SSH sign-in writes the audit entry `machine.ssh` in the org of the machine. The entry names the account, the key fingerprint, the machine, the Linux user, and the IP address of the client. A refused sign-in writes no entry. The org owners and the org admins read the entries. An org member reads none.

`hopbox new box1` made `box1` in your active org. If you are an owner or an admin of that org, make a member key in it, and read the newest entries:

```sh
KEY=$(hopbox api-key create audit --expires=30d)
curl -s -X POST -H 'Content-Type: application/json' -H "Authorization: Bearer $KEY" \
  -d '{"pageSize":50}' https://example.com/hopbox.v1.AuditService/ListAuditEntries |
  jq -c '.entries[] | select(.action == "machine.ssh") | [.createTime, .details.name, .details.linux_user, .details.client_ip, .details.fingerprint]'
```

```text
["2026-10-25T15:19:59.295802Z","box1","user","192.0.2.10","SHA256:FXuRc2JyZfKx3tXHxoblBpr+f1jfrmFaGfkF4S5o0Ho"]
```

`hopbox ssh-key list` shows the fingerprints of your own keys. The checks of an open connection write no entry, so one connection gives one line. [The SSH front door](/reference/ssh-front-door/#audit) lists every field.

## When the connection fails

| What ssh prints                                                                                                                                             | What to do                                                                                                                                                                   |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Permission denied (publickey)`                                                                                                                             | Your key opens no machine at this port for this user. Check `hopbox ssh-key list`, the user name, and that you use the machine. The front door never says which part failed. |
| `channel 0: open failed: connect failed: hopbox: the machine box1 cannot take SSH connections now: it is stopped. Start it with: hopbox machine start box1` | Start the machine, then retry.                                                                                                                                               |
| `... it has no network address on its node. Use hopbox connect instead`                                                                                     | The machine has no address. Run `hopbox connect box1` for a shell.                                                                                                           |
| `... its guest agent has not reported the SSH host keys of the machine yet. Retry in a few seconds`                                                         | The machine just booted. Retry.                                                                                                                                              |
| `Connection closed` right after a connection                                                                                                                | The client held 64 connections, or the edge server has no keys of the front door yet.                                                                                        |
| `WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!`                                                                                                          | The line `hopbox-<domain>` of `~/.ssh/known_hosts` holds another key. Run `hopbox login` again, which writes the key of `GetInstallInfo`.                                    |

## Check the front door on an edge server

This section is for the operator of an install. On an edge server, the redirect and the listener show like this:

```sh
sudo nft list table inet hopbox_edge
curl -s http://127.0.0.1:9464/metrics | grep '^hopbox_edge_ssh_'
```

`hopbox_edge_ssh_connections_total{result="forwarded"}` counts the connections that reached their machine. The other results and the logs are in [the SSH front door](/reference/ssh-front-door/#metrics).

# Call the API from TypeScript

> How to call the API of an install from Node.js and from the console with the TypeScript SDK, which a reader builds from a checkout.

The TypeScript SDK `@hopbox/sdk` is not on npm yet. You build it from the source of hopbox, which is not public yet. So today, only people with access to the source can follow this guide.

This guide calls the API of an install from a Node.js script with the TypeScript SDK. The script reads the install and the account, lists the machines, and runs a command in a machine. Then the guide copies a file in and out, and shows how the console opens a shell in a browser. [TypeScript SDK](/reference/ts-sdk/) has every function, option, and error.

The SDK wraps the generated client of each service with the same rules as the Go client of the hopbox CLI. It retries a call that failed with `unavailable`, `resource_exhausted`, or `deadline_exceeded` twice, after a short random wait, if a second run of the call does no harm. It puts an idempotency key on each create, so a retry never makes a second machine. Each error is a class of its own, such as `NotFoundError`, with the request ID of the server.

## What you need

* A checkout of the source of hopbox, with `corepack pnpm install` done.
* Node.js 24 or later.
* An account on an install, and an API key of your org in `HOPBOX_API_KEY`, in the form `hbx_<key>`. Make the key with `hopbox api-key create`, as in [Use the hopbox CLI](/guide/cli/#make-an-api-key-for-a-script). This guide uses the install `https://example.com`, with a running machine `box1`.

Build the SDK in the checkout:

```sh
corepack pnpm --filter @hopbox/sdk build
```

The build writes `web/packages/sdk/dist/`. Make a folder for the script outside the checkout, and install the SDK from the checkout into it. Replace `~/src/hopbox` with the path of your checkout:

```sh
mkdir ~/hopbox-script && cd ~/hopbox-script
npm init -y
npm install ~/src/hopbox/web/packages/sdk
```

npm links the folder. So after a new build of the SDK, the script gets the new code without a second install.

## Write the script

Save this script as `machines.mjs`:

```js
import { bearerToken, byName, createClient, HopboxError } from "@hopbox/sdk";
import { MachineState } from "@hopbox/sdk/v1";


const hb = createClient({
  url: process.env.HOPBOX_URL,
  credentials: bearerToken(process.env.HOPBOX_API_KEY ?? ""),
});


try {
  const info = await hb.install.getInstallInfo({});
  console.log(`install ${info.domain}`);


  const { account } = await hb.account.getAccount({});
  console.log(`signed in as ${account?.emails[0]?.email}`);


  const { machines } = await hb.machines.listMachines({});
  console.log(`${machines.length} machines`);
  for (const m of machines) {
    console.log(`${m.name}\t${MachineState[m.state]}`);
  }


  const out = await hb.exec({ machine: byName("box1"), argv: ["uname", "-sr"] }).output();
  process.stdout.write(out.stdout);
  console.log(`exit code ${out.exit.code}`);
} catch (err) {
  if (!(err instanceof HopboxError)) {
    throw err;
  }
  console.log(err.message);
  console.log(`request ID ${err.requestId}`);
  process.exitCode = 1;
} finally {
  hb.close();
}
```

`createClient` takes the URL of the install. A bare domain gets `https://`. Plain `http://` works only on a loopback address, so the API key never crosses a network in the clear. In Node.js, the client speaks HTTP/2, which the exec stream needs. `hb.close()` ends the connection, so the script exits at once.

`@hopbox/sdk/v1` holds the generated messages and enums of the API, such as `MachineState`.

## Run the script

```sh
HOPBOX_URL=https://example.com node machines.mjs
```

```text
install example.com
signed in as user1@example.org
1 machines
box1  RUNNING
Linux 6.1.188-hopbox1
exit code 0
```

Without a machine `box1`, the exec fails, and the script prints the typed error:

```text
not_found: not found: no machine has the name "box1"
request ID 01a15e1c-f6ef-7a62-895e-c4e77f85f3f7
```

The request ID names the call in the log of `hopboxd`. When you report a problem, give it to the operator of the install. On the control server, the operator finds the call with grep:

```sh
sudo journalctl -u hopboxd -o cat | grep 01a15e1c-f6ef-7a62-895e-c4e77f85f3f7
```

```json
{"time":"2026-10-21T12:58:38.960182+02:00","level":"INFO","msg":"api call","component":"api","procedure":"/hopbox.v1.MachineService/Exec","protocol":"connect","peer":"192.0.2.10:65499","caller":"member_key","code":"not_found","duration":518709,"request_id":"01a15e1c-f6ef-7a62-895e-c4e77f85f3f7"}
```

A machine that does not run gives a `FailedPreconditionError` with the message `the machine box1 is pending, not running. Start it first`. To tell the errors apart, use `instanceof`:

```js
import { FailedPreconditionError, NotFoundError } from "@hopbox/sdk";


if (err instanceof NotFoundError) {
  // Create the machine.
} else if (err instanceof FailedPreconditionError) {
  await hb.machines.startMachine({ machine: byName("box1") });
}
```

## See the retries

Pass a logger to see each retry. `console` works:

```js
const hb = createClient({ url: process.env.HOPBOX_URL, credentials: bearerToken(key), logger: console });
```

Run the script against a port of your laptop where nothing listens, such as `HOPBOX_URL=http://127.0.0.1:1`. Each call that cannot reach the install fails with `unavailable`, so the client tries it 3 times. Before each retry, it logs `retrying a call` with the procedure, the code, and the wait. Then the script prints the error:

```text
retrying a call {
  procedure: '/hopbox.v1.InstallService/GetInstallInfo',
  code: 'unavailable',
  retry: 1,
  waitMs: 19
}
retrying a call {
  procedure: '/hopbox.v1.InstallService/GetInstallInfo',
  code: 'unavailable',
  retry: 2,
  waitMs: 541
}
unavailable: connect ECONNREFUSED 127.0.0.1:1
request ID
```

The request ID is empty, because the call never reached an install. The waits are random, up to 500 ms and then up to 1 s.

The client retries only a call that is safe to run again ([TypeScript SDK](/reference/ts-sdk/#retries)). `GetInstallInfo` only reads, so it gets its retries after any of the three codes. A call that changes state and has no idempotency key, such as `createInvitation`, is different. A lost answer does not tell the client whether the install ran the call, and a second run sends a second invitation. So the client retries such a call only when its try surely did not reach the install. In Node.js, a refused connection is such a case. To see it, save this script as `invite.mjs`, and run it with the same `HOPBOX_URL`. The org ID does not matter, because the call never reaches an install:

```js
import { bearerToken, createClient } from "@hopbox/sdk";


const hb = createClient({ url: process.env.HOPBOX_URL, credentials: bearerToken(process.env.HOPBOX_API_KEY ?? ""), logger: console });
await hb.orgs.createInvitation({ orgId: "0199d1c4-0000-7000-8000-000000000001", email: "user1@example.org" });
```

`node invite.mjs` logs two retries, as above, and then fails with `unavailable`. An install refuses the call with the member key of this guide: with `failed_precondition` in a personal org, and with `permission_denied` in another org, where only an org admin or an org owner invites ([the org API](/reference/org-api/#invitations)).

A browser cannot tell a refused connection from a lost answer, because `fetch` rejects both with a `TypeError`. So in a browser, the same call fails after one try. The install marks each refusal that changed nothing with the header `Hopbox-Not-Run: 1`, such as a rate limit, and each client retries such an answer.

## Run a command with input, or a shell

`exec` returns a session. Give the input with `stdin`, and the session sends the end of the input after it:

```js
const out = await hb.exec({ machine: byName("box1"), argv: ["sort"] }, { stdin: "b\na\n" }).output();
console.log(new TextDecoder().decode(out.stdout));
```

For a shell, ask for a terminal, and read the output as it comes:

```js
const shell = hb.exec({ machine: byName("box1"), tty: true, size: { rows: 24, cols: 80 } });
process.stdin.setRawMode(true);
process.stdin.on("data", (b) => shell.write(b).catch(() => {}));
process.stdout.on("resize", () => shell.resize(process.stdout.rows, process.stdout.columns).catch(() => {}));
for await (const ev of shell) {
  if (ev.kind === "stdout") {
    process.stdout.write(ev.data);
  } else if (ev.kind === "exit") {
    process.exitCode = ev.exit.code;
  }
}
process.stdin.setRawMode(false);
process.stdin.pause();
```

A start without `argv` runs the login shell of the user `user`, as `hopbox connect` does. A write or a resize after the end of the shell rejects, so the handlers drop that error. The `for await` loop reports how the shell ended.

## Copy files

`upload` takes bytes, a string, a `Blob`, or a stream. A file stream of Node.js works:

```js
import { createReadStream } from "node:fs";
import { writeFile } from "node:fs/promises";


const { bytes } = await hb.upload({ machine: byName("box1"), path: "notes.txt", mode: 0o600 }, createReadStream("notes.txt"));
console.log(`the machine got ${bytes} bytes`);


const d = await hb.download({ machine: byName("box1"), path: "notes.txt" });
await writeFile("notes-copy.txt", await d.bytes());
```

A download to a laptop holds at most 4 MiB ([the machine API](/reference/machine-api/#limits)).

## Use the SDK in the console

In a browser, the same import gives a client that uses `fetch` and the session cookie. Leave out `credentials`:

```ts
import { byName, createClient } from "@hopbox/sdk";


const hb = createClient({ url: window.location.origin });
const { machines } = await hb.machines.listMachines({});


const shell = hb.exec({ machine: byName("box1"), tty: true, size: { rows: 24, cols: 80 } });
for await (const ev of shell) {
  if (ev.kind === "stdout") {
    terminal.write(ev.data);
  }
}
```

Here `terminal` is the terminal widget of the page, such as xterm.js. In a browser, `exec` uses the WebSocket `/api/ws/exec`, because a browser has no stream in both directions over HTTP. The page must come from the origin of the install, as the console does. A page of another site gets HTTP status 403 ([Sessions, cookies, and sign-in links](/reference/sessions/#calls-with-the-cookie)). A browser cannot stream an upload, so `upload` fails there with an `UnimplementedError`.
