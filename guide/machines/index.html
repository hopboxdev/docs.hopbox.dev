Create and manage machines

This guide registers the default image, then creates, lists, watches, stops, and deletes a machine through the API. At the end, the operator sees and stops the machines of every org with hopboxd admin. reference/machine-api.md has every call and rule, and reference/placement.md covers how a create picks a node.

The executor of a machine on its node boots and stops its microVM with Firecracker (reference/executor.md, reference/firecracker-driver.md). Each machine gets an address on the network of its node, where its URL and its SSH port reach it (node-network.md). exec-and-files.md runs commands in a machine over its guest link.

This guide calls the API with curl, in the same way as the console does, so it shows each call. The console does the same work in a browser (console.md). The hopbox CLI does the same with hopbox new, hopbox list, and hopbox machine (cli-machines.md).

What you need

Section titled “What you need”
  • A Linux server with the control role and the node role, enrolled as in enroll-node.md. sudo hopboxd admin server list must show the server ready, with the status ok. A create needs a ready node with room for the size default: 2 vCPUs and 8 GiB of RAM (reference/placement.md). Without one, it fails with unavailable.
  • A domain and a session cookie of a signed-in account, as in first-sign-in.md. Keep the cookie in COOKIE, in the form __Host-hopbox_session=<token>.
  • The default image, built with make image into bin/image/. Copy bin/image/artifact.json to the server.

A Mac cannot be the node, because it has no KVM. On a Mac with only the control role, every create fails with no capacity: ... The install has no node yet.

Register the default image

Section titled “Register the default image”

A create takes the newest image of a name, default by default. A control server that runs a release registers the default image of that release at each start (reference/hopboxd.md). A control role without a release, such as hopboxd on a laptop, has no image, so a create fails:

Register the image from its artifact.json. The install keeps only the metadata. --url tells the nodes where to download the compressed disk:

The digest is the sha256 of the bytes of artifact.json, so it names this one build. A second register of the same file changes nothing, and prints registered false. A new build of the image has a new digest. Once you register it, new machines take it, and the machines that exist keep their image.

See the sizes

Section titled “See the sizes”

A fresh install has one size. A create without a size takes default.

Create a machine

Section titled “Create a machine”

A create takes an idempotency key, so a retry with the same key returns the same machine and makes no second one. Keep the key in a variable:

The request leaves out orgId, so the machine is in the personal org of the account. The create picked the node, granted it the lease of the machine, and claimed the name box1 and a random SSH port. It did not wait: the machine is pending, with the target running. The node boots it at once. At the first boot of an image, the node also unpacks the image, so the machine runs about 25 s later on the tested server.

Send the same request with the same key again. The response is the same, with the header Idempotent-Replayed: true.

Machine names are unique in the whole install. A new create with the name box1 fails, and suggests a free name:

A create without a name gets the first free name of box1, box2, and so on. Each org has usage limits, by default 3 machines, 6 vCPUs, 24 GiB of RAM, and 300 GB of disk (reference/org-api.md). A fourth machine of the size default fails with resource_exhausted.

If no node has room, the create fails with unavailable and names the reason of each node:

The failed create leaves nothing behind. Uncordon the node, or enroll another one, then retry.

List and read the machines

Section titled “List and read the machines”

ListMachines returns the machines of the org that you see, by name. A machine is private to its creator until the creator shares it with ShareMachine. Other members of the org do not see a private machine, and get not_found for it. An org admin or owner sees it, and can stop or delete it, but cannot start it or change it (reference/machine-api.md).

Stop the machine

Section titled “Stop the machine”

A stop sets the target stopped, then waits for the machine, for up to 60 s:

The node asks the guest to shut down, and the call returns as soon as the machine is stopped. If the wait ends first, done is false, and the JSON codec leaves it out. The call still succeeded then: the target is stopped, and the machine goes on toward it. A machine with the restart policy never can also stop by itself, for example with sudo reboot inside it. Its target then turns stopped, so it stays stopped until a start.

To wait less, send a shorter deadline. The wait ends 1 s before it:

The start sets the target running again, and the node boots the machine from its disk. The call returns once the machine runs, or after about 4 s with done false. A stopped machine holds no vCPUs and no RAM. So the start first checks the limits of the org and the room on the node of the machine.

Manage the machines as the operator

Section titled “Manage the machines as the operator”

An instance admin sees the machines of every org, with metadata only. Root on a control server calls the admin API with hopboxd admin:

--org-id lists the machines of one org. To handle abuse, stop or delete any machine, also in a suspended org:

Each admin command waits at most 40 s for its call, so its wait ends after about 39 s at the latest. The audit log of the org records the entry machine.admin_stop of local_root, so the owners of the org see it.

A suspension of the org stops each of its machines too (reference/org-api.md). The members of a suspended org cannot create, start, reboot, or delete a machine until the suspension ends.

Delete the machine

Section titled “Delete the machine”

The machine gets the target deleted and a deleteRequestTime. The node stops its microVM, and removes its disk and its jail. It stops counting in the usage of the org at once. Its name and its SSH port stay reserved for your org for 7 days, so another org cannot take box1 in that time. Your org can: a new create with the name box1 succeeds. A second delete of the same machine fails with failed_precondition.
