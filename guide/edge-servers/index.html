Run edge servers apart from the nodes

The network redesign of 2026-10-27 changes this page. hopbox leaves the vRack and the OVHcloud API, and the servers talk over their public addresses (Q90). This page still describes the current code. Milestones N26 to N32 change the code and this page. Before you set up a fleet on the vRack, read Q90.

An edge server takes the public traffic of an install: the URL of each machine, SSH, the API, and the console. It also takes the egress of the machines to the internet (the egress of the machines). A small install runs every role on one server. A bigger install runs the edge role and the DNS role on two servers of their own, edge1 and edge2. The install then has two name servers. When one edge server stops, the other one takes the traffic. This guide adds two edge servers to an install whose servers talk over their peer addresses. Then it reaches a machine through each edge server.

An edge server without the node role reaches each machine over the mesh, the WireGuard device hbm0 between the servers (the mesh). The edge role covers the way to the machines in full.

The release files of hopbox are not public yet. The hopbox team gives them on request.

How a client reaches a machine

Section titled “How a client reaches a machine”
  1. The client asks DNS for box1.example.com. Each edge server answers with the DNS role. The zone names the floating IPv4 address of each edge server, and its floating IPv6 address. ns1 is edge1, and ns2 is edge2.
  2. The client connects to one of the addresses. It uses HTTPS for a machine URL or the API, and SSH for the SSH port of the machine.
  3. The edge server finds the node of the machine in its routes. It connects to the address of the machine over hbm0, from its mesh address.
  4. The node lets the connection reach the machine, because the mesh address belongs to an edge server.

A floating address is a public IPv4 address that the provider of the servers can route to one server and then to another. Examples are an Additional IP of OVHcloud, and a floating IP of another provider. The operator routes it to the edge server at the provider. A replacement of the edge server takes the same address, so the zone never changes. The floating IPv6 address of an edge server is an IPv6 address that the operator routes to the edge server at the provider. The edge server holds it on its uplink as a /128. hopboxd does not put it there (the edge role). The IPv6 egress of the machines leaves from another address: the IPv6 address of the uplink.

What you need

Section titled “What you need”
  • An install with a control server that listens on its peer address, and nodes in the mesh (the mesh).
  • Two servers for edge1 and edge2.
  • One floating IPv4 address for each edge server. This guide uses 203.0.113.101 for edge1 and 203.0.113.102 for edge2. The operator routes each address to its edge server at the provider. The edge server holds it on its uplink as a /32, and the peer address stays the source of its default route. So the connections of the edge server to the other servers leave from its peer address. The Terraform provider sets this up with the attribute floating_addresses (hopbox Terraform provider). Without the provider, set it up by hand.
  • One floating IPv6 address for each edge server, held on its uplink as a /128. This guide uses 2001:db8::11 for edge1 and 2001:db8::12 for edge2. The Terraform provider sets this up with the attribute public_ipv6.
  • An IPv6 default route and a global IPv6 address on the uplink of each edge server, for the IPv6 egress of the machines. This guide uses 2001:db8:1::21 for edge1 and 2001:db8:2::22 for edge2.
  • The internal URL of the control server on its peer address, such as https://203.0.113.11:7443 (the internal listener).
  • The peer address of each server: its public IPv4 address on its uplink, at which the other servers reach it (Enrollment and the install PKI). This guide uses 203.0.113.21 for edge1, 203.0.113.22 for edge2, and 203.0.113.31 for the node node1.
  • dig, curl, and ssh on your laptop.

Check the egress of the machines

Section titled “Check the egress of the machines”

Each node sends the egress of its machines through an egress tunnel to one edge server. The hash of the machine address picks the edge server (the egress of the machines). On edge1, check its tunnel, and the routes of the replies back into it:

The tunnel has each node as a peer, with its subnet and the IPv6 /64 of that subnet. The rule fwmark 0x68620100 lookup 26819 sends the replies back into the tunnel. The chain egress_nat gives the IPv6 egress of the machines the address of the uplink, 2001:db8:1::21 (NAT66).

In a machine, ask a server on the internet for the address that it sees:

The commands print the floating IPv4 address and the IPv6 address of the uplink of one edge server, such as 203.0.113.101 and 2001:db8:1::21. The IPv6 egress never leaves from the floating IPv6 address. Both families of one machine leave through the same edge server. An edge server without edge.public_ipv4 gives the IPv4 egress the address of its uplink, and logs a warning at its start. An edge server without a global IPv6 address on its uplink refuses the IPv6 egress, and logs a warning.

When an edge server stops

Section titled “When an edge server stops”

The other edge server goes on: it answers DNS, the machine URLs, SSH, and the API. A resolver that gets no answer from one name server asks the other one. The control role marks the stopped edge server unresponsive after 20 s. At their next heartbeat, the nodes then send all the egress of their machines to the other edge server. The address of the stopped edge server gives no answer to a client. It answers again when the edge server is back, or when its replacement takes the address.

A DNS server keeps the last zones of the control plane on its disk (the DNS role). So an edge server that restarts while no control server runs answers with those zones. Its log shows serving the dns zones on the disk until the control plane sends its zones.

Replace an edge server

Section titled “Replace an edge server”

The new server takes the same addresses as the old one:

  1. Write the bootstrap configuration of the new server with the same edge.public_ipv6 and edge.public_ipv4. Put the floating IPv4 address on its uplink as a /32, and the floating IPv6 address as a /128. The Terraform provider does this step with floating_addresses and public_ipv6.
  2. Install and enroll the new server as above, with a token for its own peer address. The servers of the install then take SSH from the new server as a jump host.
  3. Route the floating IPv4 address and the floating IPv6 address to the new server at the provider. The Terraform provider never moves an address.

The public addresses of the install stay the same, so the zone and the glue records need no change. The IPv6 egress of the machines leaves from the uplink address of the new server, so its IPv6 source changes (the egress of the machines).

Take the edge role from a server

Section titled “Take the edge role from a server”

A server can give its roles edge and DNS to the edge servers and keep its other roles (the admin API). An example is a first server that keeps the roles control and node. This section takes them from the server server1, while the edge servers keep them.

  1. Make sure that another edge server is ready with the roles edge and DNS, and holds a floating address. The removal checks it.

  3. Wait until each name server serves the new zone, as in Check each name server. The parent zone keeps its glue records only for the name servers that stay.

  4. Start the removal. Run on a control server:

  5. If server1 is a control server whose internal listener listens on loopback, move the listener to the peer address of server1. The control role refuses a token with a peer address on a call from loopback, and in step 6 server1 calls its own listener. Run on server1, with every role that it has now (the internal listener):

  6. End the removal on server1. Make a token for the server and the roles that stay, and run the install with every role that stays:

  7. After the restart of hopboxd, remove the floating addresses of server1 from its uplink. The uplink is the interface of the IPv4 default route, which ip route show default names after dev. This example uses eth0, the floating IPv4 address 203.0.113.100, and the floating IPv6 address 2001:db8::10. Run on server1:

    Then remove the addresses from the network configuration of the host too, so that a reboot does not put them back.

hopboxd restarts without the roles edge and DNS, and the services of server1 stop for some seconds. Its host firewall closes ports 80, 443, 53, and the SSH ports of the machines. From then on, port 22 takes only the jump hosts. So reach server1 through an edge server that stays (Reach the servers through the edge servers). For a server that Terraform manages, drop the roles edge and dns from its configuration, and apply instead. Drop its floating addresses there too. The provider runs steps 4 to 7 (hopbox Terraform provider).
