Use the Admin area

The Admin area is the part of the console for instance admins. An instance admin is an account that operates the whole install. In the Admin area, you see the state of the install, its capacity, the machines that use the most, the servers, the pools, the sizes, the images, the accounts, and the orgs. You cordon and drain nodes. You also manage the instance admins, the admin API keys, and the config of the install, and you read the audit log of the install. Console lists each page and its calls.

This guide uses the install https://example.com, an org org1, a machine box1, and an account user1@example.org.

What you need

Section titled “What you need”
  • An account that is an instance admin. The first instance admin signs in with a login link (First sign-in on a new install). An instance admin makes another account one on the page “Instance admins”.
  • A sign-in within the last 10 minutes. The next section gives the reason.

Open the Admin area

Section titled “Open the Admin area”
  1. Sign in at https://example.com/ (Use the console).
  2. Click “Admin” at the top right. Only an instance admin sees this link.
  3. The Admin area opens on the page “Overview”. The tabs lead to the other pages.

A person who is not an instance admin sees no “Admin” link. The address https://example.com/admin shows “Page not found” to such a person. The admin API also refuses each call of such a session with permission_denied (the admin API).

Sign in again after 10 minutes

Section titled “Sign in again after 10 minutes”

The Admin area acts on the whole install, and a session lives for up to 30 days in a browser. So each call of the Admin area needs a sign-in within the last 10 minutes, the reads too. The server checks this on each call, not the console (Sessions, cookies, and sign-in links).

After 10 minutes, a page or an action of the Admin area shows “This step needs a sign-in within the last 10 min”. It also shows the button “Sign in again”:

  1. Click “Sign in again”. The sign-in page opens with the title “Sign in again”.
  2. Sign in with a method of your account.
  3. The console opens the page of the Admin area again. Do the action again.

The new sign-in replaces the session of this browser. The sessions of your account in other browsers stay.

Overview, Capacity, and Machines

Section titled “Overview, Capacity, and Machines”

The pages “Overview”, “Capacity”, and “Machines” are the main view of the state of the install. They need no Prometheus. hopboxd keeps a history of samples: once a minute, each control process writes the values of its metrics to the control store, and keeps them for 24 hours (Metrics). The pages read the same metrics as the dashboards of the monitoring bundle, so the numbers match Grafana. Each page reads the history again every minute while it is open in the front tab of the browser. These reads write no entry in the audit log, so the reads every minute do not flood it. After 10 minutes, a page keeps its last numbers and shows “Sign in again to refresh” (Sign in again after 10 minutes).

The page “Overview” has these parts:

  • Six tiles: the servers, the running machines, the allocated vCPUs, the pending accounts, your open notices, and the public URLs with the count of their orgs. While an alert of the monitoring bundle fires, the tile of the notices counts the alerts that fire under its number, and turns red for a critical alert (Alerts).
  • “Needs your attention”: the alerts of the monitoring bundle that fire, the machines that used 90% or more of their vCPUs over the last 30 minutes, the pending accounts, the servers that are not ready or that are degraded, and your open notices. Each alert shows its name, its summary, and since when it fires, with the link “See alert” to the page “Notices”. The list shows the 20 newest alerts, and one line counts the rest. A machine shows here only once it has 30 minutes of samples. A restart of hopboxd does not end its samples. Each line has a link to the page that acts on it, such as “Open machine” for the machines of the org of a busy machine.
  • “Last 24 h”: the sign-ups, the new orgs and API keys, the changes of machine URLs and the URLs made public, the refusals of the rate limits and of the org limits, the failed API calls, and the failed actions of the executors.
  • “Health”: one line for the control plane, the nodes, the edge, and the network. DNS and SSH get their checks with milestone O6. Each line is ok, warning, critical, or unknown, and names each problem. The checks use the thresholds of the alerts of the monitoring bundle (the admin API).

The page “Capacity” shows each node, with its pool, its roles, and its state: the vCPUs, the RAM, and the disk that the machines reserve, against the capacity of the node. Under each one, a chart shows the use over the last 24 hours or the last hour. hopbox places at most 2 vCPUs for each CPU thread, and never overcommits RAM.

The page “Machines” starts with the running machines that use the most CPU, RAM, disk, or egress. Pick the order in “Sort by”. Each row names the org and the email of its first owner, so you know whom to contact. The name of a machine opens the list of the machines of its org, where you stop or delete it (Handle an abuse report). The list of every machine follows.

The page “Accounts” starts with “Activity, last 24 h”: the sign-ups, the new orgs and API keys, the changes of machine URLs, and the refusals of the rate limits, hour by hour. A chart turns to the warning color in an hour that reaches the threshold of its alert, such as 5 sign-ups in an hour. Below the charts are the public URLs, the URLs made public in the 24 hours, the suspended orgs, and the refusals of each rate limit.

A server with the node role and without the control role sends no sample, so its machines do not show on these pages yet. The Prometheus of the monitoring bundle does not see them either.

When the install config has the URL of Grafana, the pages link to its dashboards. Set the URL on a control server. With the Grafana host, the URL is the host:

After that hour, the link asks you to sign in again. The sign-in ends in the Admin area, so open the link again.

Cordon a server

Section titled “Cordon a server”

A cordoned server takes no new machine. Its machines keep running. Cordon a server before work on it.

  1. Open the page “Servers”. Each row shows the state of a server, its last heartbeat, its labels, and its count of machines. It also shows the compat class: the group of servers that can restore the memory state of each other.
  2. Click “Cordon” in the row of the server. The state changes to cordoned.
  3. After the work, click “Uncordon”. The state changes to ready.

To set the labels of a server, click its name. Type the labels as key=value pairs, such as disk=nvme, zone=a, and click “Set labels”. A size can ask for labels, and placement then puts its machines only on servers with them (Add pools and sizes).

The Admin area does not add or remove a server. The hopbox Terraform provider does that (Install hopbox on your servers with Terraform). To take a server out of the install with its machines, drain it first (Drain a node). The server page has a button “Drain” for it.

Drain a server

Section titled “Drain a server”

A drain moves every machine of a server to other nodes, and then decommissions the server (Drain a node). A running machine stops, moves, and boots again, so it loses its memory. Each machine keeps its disk, name, URL, SSH port, and address.

  1. Click the name of the server node1. The page of the server opens.
  2. Click “Drain”. The dialog “Drain node1” explains the drain. It says that “Cancel drain” ends the drain and keeps the server. It also says to destroy a server that Terraform manages with Terraform, because the next refresh of Terraform drops a drained server from its state.
  3. Click “Drain”. The state changes to draining. The buttons “Cordon” and “Uncordon” disappear, because a drain keeps the server cordoned.
  4. Watch the section “Drain”. It shows when the drain started, the moves that run, and the empty checks, such as 1 of 3. The page reads again every 2 s.
  5. When the server holds nothing, the state changes to shutting down, and after 3 empty checks, to decommissioned.

Only a server with the role node has the button. The Admin area cannot drain a server that hosts a control process, because the drain ends in a decommission. Drain such a server as root on a control server, or with terraform destroy.

A machine that the drain cannot move shows in a table with its reason. The notice “The drain cannot go on by itself” appears when each machine left on the server is stranded. A machine without room moves once a node has room, because the drain tries it again each minute. For the other reasons, fix the reason, then click “Drain again” to try the machines again.

To keep the server, click “Cancel drain” during the drain. No new move starts, a move whose machine still stops ends, and a move whose disk copies already goes on to its end. The server turns cordoned or ready, as it was before the drain (Drain a node).

Handle an abuse report

Section titled “Handle an abuse report”

An abuse report names the machine box1 in the org org1. You stop the machine, and you suspend the org until its owners answer:

  1. Open the page “Machines”. Under “Every machine”, each row shows the org, the state, the node, and the address of a machine, such as 10.240.0.2. A machine that uses much CPU or egress shows at the top, under “Top machines”.
  2. Click “Stop” in the row of box1. The state changes to stopped.
  3. Open the page “Orgs”. The row of org1 shows its tags. The tag “port 25 open” says that the machines of the org can send email to other mail servers. Click “Suspend” in the row of org1.
  4. Type a reason, such as abuse report 1, and click “Suspend”. The members of org1 see the reason. The org stops its machines, and creates and starts no machine until the end of the suspension.
  5. When the report is settled, click “Unsuspend”.

The account user1@example.org made box1. If that account caused the abuse, suspend the account too:

  1. Open the page “Accounts”. Each row shows an account, its emails, its ID, its state, and its tier. Choose “Active” in the state filter to see only the active accounts.
  2. Click “Suspend” in the row of user1@example.org. The dialog “Suspend user1@example.org” says what a suspend does.
  3. Type a reason, such as abuse report 1, and click “Suspend”. The state changes to suspended, and the row shows the reason.

The suspend deletes nothing (the admin API). The account cannot sign in, and its sign-in page shows the reason. Its sessions and its CLI sign-ins end. Its API keys and its SSH keys stop working. The suspend also suspends the personal org of the account, and each org that the account owns alone. Their machines stop. In the other orgs of the account, its private machines stop, and its shared machines keep running.

For a smaller step than a suspend, click “Make limited” in the row of the account (Move an account to another tier). The account keeps its access, but it creates no new org, and its personal org gets the small limits of the tier. The move keeps what the account has, so stop or delete its machines yourself.

If the report is about spam from org1, click “Limits” in the row of org1, and choose “blocked” for “Outbound TCP port 25”. Each machine of the org takes the change at its next start or reboot, so stop and start the machines that run.

Then read what the account did:

  1. Open the page “Audit log”. It shows the entries of the whole install, newest first.
  2. Find the entries about the account. The column “Target” shows account and the full ID of the account, for example in the entry admin_account.suspend. The column “Actor” shows account and the first 8 characters of the ID of the account that acted.
  3. Read the actions of the account, such as machine.create and org.create. Keep a note of what you find with the report.

Then decide. Keep the account suspended as evidence, or delete it. To give the account back its access, click “Unsuspend” in its row. The orgs that its suspend suspended become active again, but an org that you suspended on the page “Orgs” stays suspended. The machines stay stopped until their users start them.

The Admin area does not delete an account. The account of the report can be a bot of the sign-up mode open. To delete it, run the delete as root on a control server:

  1. Run sudo hopboxd admin account delete --account-id=ID --reason='abuse report 1', with the ID from the page “Accounts”.
  2. If it fails, delete each machine that the error names, with the sudo hopboxd admin machine delete command that the error gives for it. These machines are in the personal org of the account, or in an org that the account owns alone. The private machines of the account in its other orgs count too. Then run the delete of the account again.
  3. The account is suspended, so the delete ends the evidence of the suspension. The command asks for the account ID a second time. Type the ID again, and press Enter.

The command also deletes each org that the account owns alone. A suspended org does not stop it. The command prints the ID of each deleted org. The audit entry admin_account.delete keeps the reason, the IDs of the deleted orgs, and the detail suspended. The command deletes no audit entry of the account (hopboxd).

A bot often signs up again with a new email. In the sign-up mode approval, its new account waits for you. Reject it with a block, so its email and its GitHub or Google identity cannot sign up again (Approve or reject new accounts):

If the bot uses many addresses of one email domain, block the whole domain:

The Admin area has no shell and no file access for a machine. It never shows a secret or an env var of an org. An instance admin sees the metadata of an org, not its contents. The audit log of org1 shows each of these actions to the owners of the org.

The row of each org shows its usage against its limits, also its stored state and its saves in 24 hours. To change the limits of one org, click “Limits” in its row. A field that you leave empty takes the default of the install. For the personal org of a limited account, that is the default of the tier limited. The row of such an org has the tag “limited”. The dialog shows the limits that apply now. Four fields bound the saved state of the org:

  • “Stored state in GiB”: the memory files of hibernated machines, and later checkpoints and snapshots. A hibernate never checks it.
  • “Snapshots” and “Backups in GiB”: no snapshot or backup exists yet.
  • “Saves in 24 hours, in GiB”: the daily budget of saves. A hibernate above it fails, and the machine runs on.

The dialog also has two choices:

  • “Public URLs”: “yes” lets the creator of a machine make its URL public, to anyone. “no” refuses a new public URL, and keeps each URL that is public already. The row then has the tag “no public URLs”.
  • “Outbound TCP port 25”: “open” lets the machines of the org send email to other mail servers. The default is “blocked”. Open it only for an org that you trust. A machine takes a change of port 25 at its next start or reboot. The row of an org with port 25 open has the tag “port 25 open”.

The section “Default limits” sets those defaults, in two groups. “Team orgs and personal orgs of full accounts” holds the defaults of each org, apart from the personal org of a limited account. Its field “Orgs of one full account, besides its personal org” is the most orgs that a full account owns. A limited account owns no org. “Personal org of a limited account” holds the defaults of the tier limited: machines, vCPUs, RAM, disk, the four limits of saved state, and public URLs. No default opens port 25. The org API gives the defaults of a fresh install.

Approve or reject new accounts

Section titled “Approve or reject new accounts”

The sign-up mode of the install decides how a new person gets an account (Sessions, cookies, and sign-in links). The default is approval. In this mode, the first sign-in of a new person makes a pending account. A pending account can sign in, write a note to the instance admins, and delete itself, and nothing else. It waits for you.

Each new pending account gives each instance admin a notice in the console. The emails come as a digest: at most one email every 15 minutes, with the new pending accounts (the admin API). The digest links to the page “Accounts” of the Admin area, where you approve or reject each account.

In the Admin area:

  1. Open “Notices”, and click “See the pending accounts” under “New accounts”. Or open “Accounts”, and choose the filter “Pending”.
  2. Read the row of each account: its emails, its sign-in methods, its note, its client address, and the time of its sign-up. For a GitHub sign-up, the row also shows the GitHub login. A GitHub user made less than 24 hours before the sign-up gets the tag “new GitHub user”, which is a hint of a bot.
  3. Click “Approve” for an account that you trust, or “Approve as limited” to give it the tier limited. A limited account creates no org. Its personal org gets the limits of the tier, and no public URL. In that org, a new machine without a size gets the size tiny. If the install sends mail, the person gets an email.
  4. Click “Reject” for an account that you do not want. In the dialog, check “Also block this email or identity” to keep its email and its GitHub or Google identity from a new sign-up. Then click “Reject”.

The section “Block list of sign-ups” of the same page lists the block list. It blocks a whole email domain with “Block the domain”, and removes an entry with “Remove”. The page “Config” sets the sign-up mode in its section “Sign-ups”.

You can also decide as root on a control server:

  1. List the pending accounts with their sign-ups:

    For each account, sign_up shows the method, the client address, and the time. It also shows the note of the person. For a GitHub sign-up, it shows the GitHub login and github_create_time. A GitHub user made the same day is a hint of a bot.

  2. Approve an account that you trust. If the install sends mail, the person gets an email:

    Add --tier=limited to approve the account with the tier limited.

  3. Reject an account that you do not want. The reject deletes the account and its personal org. Add --block to keep its email and its GitHub or Google identity from a new sign-up:

A pending account that nobody approves expires after 30 days, and the leader deletes it. Each client address makes at most 3 new accounts a day without an invitation, and the install holds at most 50 pending accounts (Sessions, cookies, and sign-in links).

sudo hopboxd admin account blocks lists the block list, and sudo hopboxd admin account unblock --id=ID removes an entry (hopboxd). A block stops only new accounts. An account that exists still signs in. A block of an email also stops the same address with any +tag, such as user4+1@example.org for user4@example.org. A block of a domain also stops its subdomains.

To let each new person in at once, with an active account of the tier limited, set the mode open:

Each change of the mode gives each other instance admin a notice and an email, with the command that sets the old mode back. Set --sign-up-mode=approval to go back.

Invite a new person

Section titled “Invite a new person”

An instance invitation lets one new person in with an active account of the tier full, in every sign-up mode (the admin API). The person skips the pending step. An open invitation of an org also lets a new person in, with an active account of the tier limited (Sessions, cookies, and sign-in links).

To close sign-up to everyone without an invitation, set the mode invite_only. The accounts that exist keep working:

A new person without an invitation then gets the error this install takes new accounts only by invitation. Ask an admin of <domain> for one. The audit log records each refusal as account.sign_up_refused, with the email and the client address.

In the Admin area:

  1. Open “Accounts”, and find the section “Invitations”.
  2. Type the email of the person in “Email”, and click “Invite”.
  3. If the install sends mail, the person gets the link by email. Else, copy the link from “Invitation link”, and send it to the person yourself.

The person opens the link, and signs in with any method that proves the email: an email link, GitHub, or Google. The link works once, for 7 days. Click “Revoke” on the row of an invitation to end it.

You can also invite as root on a control server:

admin invite create prints the link (hopboxd). The block list still applies: an invitation lets no blocked email or identity in.

Move an account to another tier

Section titled “Move an account to another tier”

The tier of an account sets the default limits of its personal org, and whether the account creates orgs (the org API). To change the tier of an active or a suspended account:

  1. Open the page “Accounts”. The row of each account shows its tier.
  2. Click “Make full” in the row of a limited account, or “Make limited” in the row of a full account. The tier changes at once, without a dialog.

The move keeps what the account has: its machines, its orgs, and its public URLs. The limits of the new tier refuse only what comes after. For example, a full account with 2 orgs and 2 machines in its personal org moves to limited. It keeps the orgs and the machines, but it creates no new org. Its personal org creates and starts no more machines until its usage fits the limit of 1 machine. To give one org other limits, click “Limits” in its row on the page “Orgs”.

A pending account has no such button. It gets its tier from “Approve” or “Approve as limited”. The admin API gives the call.

Make an admin API key

Section titled “Make an admin API key”

An admin API key lets a script or the hopbox Terraform provider call the admin API (CLI tokens, API keys, admin API keys, and SSH keys).

  1. Open the page “Admin keys”.
  2. Type a name, such as terraform, pick a lifetime, and click “Create admin key”.
  3. Copy the key at once. It starts with hbxadm_. The install keeps only its hash, so the console shows the key only once.

Click “Revoke” in the row of a key to end it. Every call with the key then fails at once.

Change the SMTP server

Section titled “Change the SMTP server”
  1. Open the page “Config”, section “Email”.
  2. Type the host, the username, the password, and the sender, and click “Save the SMTP server”.

The page never shows the password, and the API never returns it. The page says only whether a password is set. Leave the field “Password” empty to keep the password that is set now. The section “Sign-in with GitHub and Google” works the same for the client secret of each app (Sign in with GitHub and Google).

Set the bucket of the backups

Section titled “Set the bucket of the backups”
  1. Open the page “Config”, section “Object storage”.
  2. Type the endpoint, the region, the bucket, the access key ID, and the secret key, and click “Save the object storage”.

The page first checks the bucket: the control server writes, reads, and deletes one small object. A failed check changes nothing, and the page shows its cause, such as the signature does not match, so the secret key is wrong. Leave the field “Secret key” empty to keep the secret key that is set now. The page empties that field after each save, also after a failed one, so type the key again for the next try. For a server with a private CA, paste its PEM certificates in the field “CA certificates”. Click “Check the bucket” to check it again later. Give an install a bucket for backups sets up the bucket at the provider.

Change the domain

Section titled “Change the domain”
  1. Open the page “Config”, section “Domain”.
  2. Type the new domain, such as hop.example.org, and click “Change the domain”. Point the DNS records of the new domain to the install first.
  3. Click “Change” in the dialog. The API, the console, and every machine URL move to the new domain.
  4. Open the console at the new domain, such as https://hop.example.org/, and sign in there.

The console at the old domain stops working at once. The session cookie and the Origin check belong to one domain (Sessions, cookies, and sign-in links).

Read the security notices

Section titled “Read the security notices”

Some actions last after the session that did them:

  • a new admin API key, a new instance admin, or the revoke of an instance admin
  • a new sign-in method of an instance admin
  • the suspend, the unsuspend, or the delete of an instance admin account
  • a change of the SMTP server, of the mail transport, or of the domain
  • a change or the removal of the object storage
  • a change of the ACME settings, of the sign-up mode, or of the GitHub or Google app

If another caller does one of them, you get a notice in the console and an email (the admin API). The email goes to each email of your account, also when the SMTP server just changed. The email of a new domain names the old domain and the new one, and has no link, because the console at the old domain no longer answers. Some mail clients make the new domain clickable. Check the change first, then type the new domain in your browser yourself and open the page “Notices”. If you do one of them yourself, you get a copy of the email, and no notice in the console.

While you have an open notice, each page of the console shows a banner with the count, such as “2 security notices for the instance admins”. To read and close the notices, do these steps:

  1. Click “See the notices” in the banner, or open the page “Notices” of the Admin area.
  2. Read each notice. It says what changed, who did it, when, and the ID of its audit entry.
  3. If nobody that you trust made the change, do what the notice says. For example, revoke the new key on the page “Admin keys”, or revoke the role on the page “Instance admins”.
  4. Click “Dismiss” on a notice. With two or more notices, the page also has the button “Dismiss all”. A dismissed notice leaves your list. The audit log keeps the action.

A dismiss changes only your own list. Each other instance admin has a list of their own.

Alerts

Section titled “Alerts”

When Alertmanager of the monitoring bundle calls the alert webhook of hopboxd, each alert that fires gives each instance admin a notice (Monitor an install with Prometheus and Grafana). Each call of Alertmanager carries a group of alerts, and gives you one email that lists its new alerts, the first 20 by name. The page “Notices” lists these notices under “Alerts”, the first heading. A critical alert has a red frame. Each notice shows these facts:

  • the name of the alert and its severity, such as HopboxDiskFull and critical
  • the summary and the description of the alert
  • the labels that name a machine or a server: machine, name, org, server, and instance
  • since when the alert fires, the last time that Alertmanager sent it, and the ID of its audit entry
  • the link “What the alert means and what to do”, to the entry of the alert in the guide

Alertmanager sends a firing alert again every 4 hours, or every 24 hours for an info alert. A repeat updates the notice and sends no email. When the alert ends, its notice closes by itself on the page of each instance admin. The alert then moves to the section “Resolved alerts” of the page “Notices”, with the time it fired and the time it ended. That section lists the alerts that ended in the last 30 days, also when you have no open notice. A dismiss closes the notice on your page only, and a repeat does not open it again. The audit log keeps the start and the end of each alert, as the actions alert.fire and alert.resolve (the admin API). An alert that fires again later gives a new notice, and the email of its call.

The alert Watchdog never makes a notice. It always fires, for the outside check of the install.

Abuse signals

Section titled “Abuse signals”

hopboxd watches each account for the signals of abuse that the alerts of the monitoring bundle watch for the whole install: a machine at full CPU for hours, high egress, a scan of outbound connections, bursts of orgs, API keys, or machines, a churn of machine URLs, and a public URL of a new account (Abuse detection). It also watches each org for saved state at 90% of its limit, and for saves at 90% of the budget of 24 hours. It needs no Prometheus. Each signal gives each instance admin one notice under the heading “Abuse signals” of the page “Notices”. The notice names the account, and the machines or the org when the signal has them.

The detection runs every minute. A repeat of the signal updates the notice. When the signal ends, the notice closes by itself, and the signal moves to the section “Resolved alerts” for 30 days. While a signal is active, the page “Overview” also lists it under “Needs your attention”. Without a token of the alert webhook, each run with new signals also sends you one email. With a token, Prometheus emails you its alerts. The detection then emails you only the signals that no alert of Prometheus watches: a public URL of a new account, and the two signals of saved state.

hopbox stops nothing by itself. Legitimate work, such as a build or an AI agent, can use a whole CPU for hours. To act on a notice, do these steps:

  1. Read the notice. It names the signal, its value, the threshold, and the account, such as org_burst for 6 orgs in one hour.
  2. Open the page “Audit log”, and read the entries of the account (Handle an abuse report).
  3. For a machine signal, open the page “Machines”, and find the machines that the notice names. For a signal of saved state, open the page “Orgs”, and read the stored state and the saves in 24 hours in the row of the org. Raise its limits, or suspend the org if a loop of hibernates is abuse.
  4. If it is abuse, follow Handle an abuse report: stop the machine, suspend the org, or suspend the account. Otherwise, dismiss the notice.

To change a threshold, open the section “Abuse detection” of the page “Config”, or run sudo hopboxd admin config set with an --abuse- flag (hopboxd). For example, a team that builds all day can raise the CPU time before a notice:

What stays with root on a control server

Section titled “What stays with root on a control server”

Some work never goes through the Admin area. Run sudo hopboxd admin on a control server for it (hopboxd):

Work Command
Maintenance mode hopboxd admin maintenance on and off
The key-encryption keys hopboxd admin kek rotate, stage, promote, list, and rewrap
The mail files of the file transport hopboxd admin mail list and show
A first-admin login link hopboxd admin login-link
An enrollment token for a new server hopboxd admin enrollment-token create, or the Terraform provider
The register of an admin key from its hash, or of an image hopboxd admin admin-key register and hopboxd admin image register
The recovery of a lost sign-in method hopboxd admin account sign-in-method remove
The delete of another account hopboxd admin account delete
The token of the alert webhook hopboxd admin config alert-token set and clear
