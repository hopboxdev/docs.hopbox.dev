Work in a team org

Every account has a personal org. A team needs an org that several accounts share, with roles. This guide creates an org, invites a second person by email, and gives roles. Then, as the operator, it lists the orgs, sets the limits of the org, and suspends it. The org API has every call and rule.

This guide calls the API with curl, in the same way as the console does, so it shows each call. The console pages of an org do the same work in a browser (Use the console).

What you need

Section titled “What you need”
  • hopboxd with the control role on a laptop, as in Run the control role on a laptop, with the API on 127.0.0.1:7443.
  • A domain and an SMTP config, as in First sign-in on a new install. An invitation is for one verified email, so each person signs in with a magic link. A local mail catcher such as Mailpit works.
  • Two accounts, user1 and user2, each signed in with a magic link of First sign-in on a new install. Keep the session cookie of each one in a file: /tmp/hb/user1 and /tmp/hb/user2, each with one line of the form __Host-hopbox_session=<token>.

Invite a person

Section titled “Invite a person”

An owner invites with any role. An admin invites members only. An admin or an owner can change what runs in the private machines of every member (Read the members and the roles). So give these roles only to a person whom every member trusts. Invite user2 as an admin:

The response holds the link, and emailSent says that the server mailed it to user2 too. Without an SMTP config, emailSent is false, and you send the link to user2 yourself. The same goes for the file mail transport of a dev install (Mail). The link works once, for 7 days. Treat it as a password until then. A new invitation for the same email replaces this one, so its link stops working.

Read the members and the roles

Section titled “Read the members and the roles”

Each member reads the members of the org:

The members of an org trust its admins and owners. An admin or an owner sets the env vars and secrets with the scope all, and these reach the private machines of every member (Set env vars and secrets). An admin cannot open a shell in the private machine of another member, but can change what runs there with such a value.

Only an owner makes other owners and admins. So user2, an admin, cannot change a role:

Every org keeps at least one owner. So user1, the only owner, cannot leave yet:

To leave, user1 first makes user2 an owner with SetOrgMemberRole and the role ORG_ROLE_OWNER. An account that leaves an org loses what it made in the org and did not share.

Read the usage and the limits

Section titled “Read the usage and the limits”

The org has no machines yet, so it uses nothing. The limits are the defaults of the install: 3 machines, 6 vCPUs, 24 GiB of RAM, and 300 GB of disk.

Manage the orgs as the operator

Section titled “Manage the orgs as the operator”

An instance admin sees the metadata of every org, but not its members or its resources. Root on a control server calls the admin API with hopboxd admin:

Give org1 more room. A limit that you leave out takes the default of the install:

Change the defaults of every other org with admin org default-limits set, for example --machines 5. Each new org brings its own limits, so an account owns at most 10 orgs besides its personal org. Change that cap with admin org default-limits set --max-orgs-per-account N.

Delete the org

Section titled “Delete the org”

Only an owner deletes an org, and the request must hold its name in confirm. A suspended org keeps its data as evidence, so the delete waits for the end of the suspension:

The delete removes the memberships, the invitations, and every resource of the org. A personal org goes only with its account (the sign-in, account, and audit API).
