Install hopbox on your servers with Terraform

This guide makes a new install of hopbox on one server with the hopbox Terraform provider. The server gets every role. Then the guide upgrades the server and changes its labels. It grows the install into a fleet, imports a server into a new state, and destroys a server.

The provider installs hopbox over SSH on hosts that run Debian 13. A host can come from any provider of servers, or be a computer that you own. You order each host and install Debian 13 on it. The provider takes it from there. It calls no API of a provider of servers (Q90).

hopbox supports only the servers that this provider sets up. hopbox Terraform provider lists every attribute and each step that the provider takes. Install hopbox on a Debian 13 server by hand shows the same install by hand.

The release files of hopbox are not public yet. The hopbox team gives them on request.

Use a host that holds nothing else of value. The apply installs another kernel on the host, and reboots it.

What you need

Section titled “What you need”
  • One host for the first server, with these items. 1. Set up the hosts shows each one.
    • A CPU for amd64 with KVM. The tested server has an Intel Xeon E5-1650 v4 CPU.
    • Debian 13.
    • A public IPv4 address on its own uplink, with no NAT in front of it. This is the peer address of the server (Enrollment and the install PKI). This guide uses 203.0.113.10.
    • A free partition or disk for /var/lib/hopbox.
    • A console at its provider, such as a KVM or serial console.
  • A Mac with Apple Silicon or a Linux host on x86_64, with Terraform 1.5 or later. This example uses the Mac.
  • The release files of v0.2.0, the first release with this provider, from the hopbox team (2. Get the release files). Until the hopbox team tags v0.2.0, build the files from a checkout.
  • A domain for the install, such as example.com.
  • An SSH key pair for the operators, without a passphrase. This example uses ~/.ssh/id_ed25519.

1. Set up the hosts

Section titled “1. Set up the hosts”

Do these steps on each host before the apply that creates its server (hopbox Terraform provider). The SSH port of a new host faces the internet before hopboxd and its host firewall run. So the host must take SSH keys alone from the start.

  1. Order the host at its provider with Debian 13 for amd64. Pick a server model with KVM. Keep a partition or a disk free for /var/lib/hopbox.

  2. Put the public key of the operators in the authorized_keys of root. Most providers take an SSH key at the install of the OS. Instead of root, you can use a user with sudo without a password, such as debian. Then set ssh_user = "debian" in the resource of the server.

  3. Open the console of the host at its provider. Log in there, and print the SSH host key of the host and its fingerprint:

    Copy the first line, such as ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI... root@host1, for ssh_host_key. A comment after the key changes nothing.

  4. Log in to the host over SSH as root, or log in as the sudo user and run sudo -i. At the first login, ssh shows the fingerprint of the host key. Type yes only if it is the fingerprint that step 3 printed.

  5. Make sure that the host holds its peer address on its uplink:

    The line of the uplink names the public address, such as 203.0.113.10/24. If the host holds only a private address, such as 10.0.0.5, a NAT sits in front of it. Such a host cannot join an install. For a node, also make sure that the host names a resolver that machines reach:

    One line names an address outside 127.0.0.0/8, such as 192.0.2.53. A resolver on loopback alone, such as a local unbound, reaches no machine.

  6. Make sure that the host has KVM. ls -l /dev/kvm shows the device.

  7. Turn off the password logins of sshd:

    The last command prints passwordauthentication no and kbdinteractiveauthentication no. If you log in as another user, such as debian, run it again with that user in user=. The provider makes the same check before the create, so a Match block that turns passwords on for one of these logins fails it. sshd takes the first value of a key, and reads the files of /etc/ssh/sshd_config.d in the order of their names. So 10-hopbox.conf comes before a file of the provider, such as 50-cloud-init.conf. If the command prints yes, look for another file that sets the key first.

  8. Make /var/lib/hopbox an XFS file system with reflinks, on its free partition or disk, as Install hopbox on a Debian 13 server by hand shows. mkfs.xfs erases the partition, so make sure that you name the free one.

  9. Make sure that the file system is ready:

    The commands print xfs and reflink=1.

Take the host key from the console alone. Do not take it from ssh-keyscan, or from the first SSH login over the internet without the check of step 4. A machine between you and the host can show its own key there. The provider pins the key of ssh_host_key before its first login, and refuses any other key (hopbox Terraform provider).

An edge server of a fleet also needs its floating addresses. Route each one to the host at its provider before the apply (Grow the install into a fleet). The first server of this guide has none until the fleet.

4. Apply

Section titled “4. Apply”

Most of the apply is the upload of the bundle, and the reboot into the host kernel. To follow the steps, set TF_LOG_PROVIDER=INFO. The log shows lines such as logged in to the server with its pinned host key, installing the host kernel, and installing hopboxd.

Before it changes the host, the provider makes sure that the host is ready. It refuses another host key, sshd with password logins, and a host that holds an install. It also refuses another OS, a host without its peer address, and /var/lib/hopbox without XFS. Each error names the fix (If the apply stops). A warning such as The preflight check of the server warns: ... means that the server runs, with a risk that the warning names.

Upgrade

Section titled “Upgrade”

Get the bundle of the new release and its .sha256 file. Change local.bundle in main.tf to its path and sha256, and apply:

The plan shows an update in place of bundle and version. The provider uploads the bundle and runs hopboxd upgrade on the server. The running machines stay up (hopboxd). If the new release cannot run on the data, the upgrade stops before the switch, and the old release keeps running.

The provider then waits until the server is ready on the new version. An install with more servers upgrades them one at a time, the control servers before the nodes (hopbox Terraform provider).

An install from an earlier release of the provider, which ordered and reinstalled its servers at OVHcloud, keeps its servers. Before the first plan with this release, remove the ovh_ attributes of each server. Give it address, ssh_host_key, and ssh_user, with the values of its state. The first refresh moves the state, with no change on the server (hopbox Terraform provider). The guide for ks shows these steps for ks.

Change the labels

Section titled “Change the labels”

Change labels in main.tf, for example to { zone = "zone1", disk = "nvme" }, and apply. The provider calls SetServerLabels. hopboxd admin server get <id> on the server then shows labels disk=nvme,zone=zone1 and labels_set_by_admin true.

Grow the install into a fleet

Section titled “Grow the install into a fleet”

A fleet runs the roles on several servers: edge servers that take the public traffic, control servers that share one external Postgres, and nodes that run machines. The servers talk over their peer addresses on the public internet. The host firewall of each server takes the traffic of the install only from the peer addresses of the other servers (the host firewall). This section builds a fleet of five servers in two pools:

Resource Roles Pool Peer address Floating address
first control, node, dns, edge default 203.0.113.10 198.51.100.5
edge2 edge, dns default 203.0.113.11 198.51.100.6
cp2 control, node default 203.0.113.13 none
node1 node default 203.0.113.21 none
node2 node big 203.0.113.22 none

What a fleet needs

Section titled “What a fleet needs”
  • A host for each new server, set up as in 1. Set up the hosts. The hosts can come from other providers. All the servers of a pool have the same hardware (Enrollment and the install PKI).
  • One floating IPv4 address for each edge server. A floating address is a public IPv4 address that the provider of the servers can route to one server and then to another. Examples are an Additional IP of OVHcloud, and a floating IP of another provider. This example uses 198.51.100.5 and 198.51.100.6.
  • For the second control server, an external Postgres that the control servers reach (Run the control store on an external Postgres).

You route each floating address at the provider of the servers. The Terraform provider never moves an address. It puts each address of floating_addresses on the uplink of the server as a /32. It also makes the peer address the source of the default route (hopbox Terraform provider). So the connections of an edge server to the other servers leave from its peer address, which their host firewalls take.

This guide uses IPv4 alone, so the zone has no AAAA record. An edge server can also take one floating IPv6 address for the AAAA records, with public_ipv6 (hopbox Terraform provider).

4. Add a second control server

Section titled “4. Add a second control server”

A second control server shares the control store with the first one, so the install must run on the external Postgres first. Move the store as Run the control store on an external Postgres shows. Set up the host of cp2 as in 1. Set up the hosts. Then add the server:

6. Replace an edge server

Section titled “6. Replace an edge server”

To move edge2 to a new host at 203.0.113.14, set up that host as in 1. Set up the hosts. Do not route the floating address to it yet. Change the address and the host key of edge2 in main.tf:

Apply. A new address replaces the server. With create_before_destroy, Terraform creates the new server first, and the new server holds 198.51.100.6 on its uplink. Then Terraform destroys the old server: the provider decommissions it, stops hopboxd, and removes the address from its uplink.

When the apply prints hopbox_server.edge2: Creation complete, route 198.51.100.6 to the new host at the provider. The address gives no answer from the destroy of the old server until the provider routes it to the new one. In that time, clients reach the install at 198.51.100.5, because the zone names both addresses since step 5. The public addresses of the install, and the records of the zone, stay the same.

The old host stays with its provider. If you do not use it again, end its rental there.

7. Let the first server leave the install

Section titled “7. Let the first server leave the install”

Once the zone names the edge servers, the first server can leave the install. The install keeps running on the other servers. Before you start, make sure that these conditions are true:

  • A second control server is live, on the external Postgres, as in step 4.

  • The first server holds no machine. Move each of its machines to another node with hopboxd admin machine move (hopboxd), or delete it.

  • Each other server knows cp2. The channel.control_urls of a server made before cp2 names only the first server. The control role sends the URLs of the live control servers on the control channel, and each server keeps them in /var/lib/hopbox/server/control-urls (the control channel). Import a server into a new state

Section titled “Import a server into a new state”

A server that the provider set up can move to a new state, for example after the loss of the state file. Write its resource in main.tf first, with its address and the ssh_host_key from the console of its provider. Then import it by its peer address:

The import logs in at the address with the key of the operators, as root, then as debian. A server without the role edge gets the login through the jump host of the provider block. The import reads the server ID, the version, and the domain from the server. The install must know a server with that peer address, so an import never takes a server of another install (hopbox Terraform provider).

The import has no pinned host key yet, so it keeps the key that the server shows. The next plan compares that key with ssh_host_key. If they differ, the plan fails with The SSH host key of a server cannot change, before any change of the server. Then compare both keys with the console of the provider.

The new state has no admin_api_key. Make a new admin API key as in step 6. The new state also forgets a cordon that a failed kernel reboot left. Run hopboxd admin server get <id> on a control server. If it shows cordoned true and nobody cordoned the server on purpose, run hopboxd admin server uncordon <id>. The first plan after the import shows an update of bundle. If the bundle of main.tf is the release that the server runs, the apply changes nothing on the server.

Destroy

Section titled “Destroy”

For the first server, remove the block lifecycle { prevent_destroy = true } from main.tf first. Then run the destroy:

The destroy drains the server, so its machines move to other nodes. On an install with one server, the drain has no other node, so delete the machines first. Then the destroy decommissions the server in the install, stops hopboxd, and removes the secrets of the install from the host. It removes the table of the host firewall, so the public address of the server takes SSH again. It also removes the network setup of an edge server, with its floating addresses (hopbox Terraform provider).

If the table stays on a server without the role edge, the destroy fails with the commands to run, and keeps the resource. The jump host still reaches the server. Fix the cause, and run terraform destroy again.

The host stays with its provider, with its disks as they are. A destroy never ends a rental. End it at the provider. To use the host again, apply main.tf again: the destroy removed the identity of the server, so the host takes a new create.

After a failed create, Terraform marks the server as tainted. The next apply destroys it, which undoes the steps that ran, and creates it again on the same host (hopbox Terraform provider). With lifecycle { prevent_destroy = true }, Terraform refuses that apply with Instance cannot be destroyed. Then remove the block for that apply, and put it back after. terraform untaint does not help, because the state then holds a server without hopboxd, and the next apply installs nothing.

The destroy of a first server that never enrolled keeps its control store in /var/lib/hopbox/pg, and its keys in /var/lib/hopbox/kek, with a warning. The new create then refuses the host. Remove both dirs on the host first.
