Run the control role on a laptop

This guide runs hopboxd with the control role on a Mac, without root. It reads the install info over the API. Then it sets the domain of the install and rotates the key-encryption key through the admin socket, and finds both actions in the audit log. On a server, the same steps run as root with the default paths.

What hopboxd run does

Section titled “What hopboxd run does”

hopboxd run reads one small file, the bootstrap config. The file lists the roles of the server and a few paths (reference/hopboxd-config.md). Everything else about the install lives in the control store and changes through the admin API.

The control role is a chain of units. Each unit needs the units before it, so hopboxd starts them in this order and stops them in the reverse order:

  1. postgres: the bundled Postgres.
  2. store: the connection pool and the schema migrations.
  3. leader election: one control process becomes the leader and runs the leader jobs.
  4. api: the API listener, for every client.
  5. internal listener: the cluster API over TLS, for the servers of the install (reference/internal-listener.md).
  6. admin socket: the admin API for root on this server.

Every call on every listener passes one request gate, which names the caller. Then one policy check in the service layer decides what that caller can do (reference/api.md). On the admin socket, the kernel proves the user of the caller. On a laptop, hopboxd runs as you, so the socket accepts you without sudo.

What you need

Section titled “What you need”
  • A checkout of hopbox, built with make build.
  • The bundled Postgres: make pg builds it on the first run and prints its dir.
  • curl 7.47 or later, for --http2-prior-knowledge.

Write the bootstrap config

Section titled “Write the bootstrap config”

A unix socket path has at most 103 bytes on macOS, so put the sockets in a short dir under /tmp. Group and others must not be able to write in the dir.

The API listener keeps its default address, 127.0.0.1:7080, and the internal listener keeps 127.0.0.1:7443.

Start hopboxd

Section titled “Start hopboxd”

The first start creates the Postgres cluster in ~/hopbox-dev/pg, which takes a few seconds. hopboxd writes one JSON log record per line. The record hopboxd is ready means that every unit runs. Leave it running, and use a second terminal for the next steps.

The install has no key-encryption key yet, so it has no CA, and the internal listener has no certificate. hopboxd logs the internal listener has no certificate yet at level warn. The rotation in Act through the admin socket makes the first key. The next TLS handshake of the internal listener then makes the CA.

Section titled “Find the actions in the audit log”

Every admin call writes an audit entry. Read the entries with the psql of the bundled Postgres, over its socket:

The output here is cut short. The entry install_config.update holds each setting before and after the change, such as old_domain and domain. A rotation writes two entries: keyring.rotate.start before it writes the key file, and keyring.rotate after it (reference/admin-api.md). idempotency is the SHA-256 of the idempotency key of the call. peer_uid and peer_pid name the user and the process that called through the socket.

Stop hopboxd

Section titled “Stop hopboxd”

Press Ctrl-C in the first terminal. hopboxd stops the units in the reverse order: the admin socket, the internal listener, the API, the leader election, the store, Postgres, and the metrics listener last. It removes /tmp/hb/admin.sock and exits with status 0. The next start keeps the cluster, the domain, and the key.

To start again from nothing, stop hopboxd, then remove the dirs ~/hopbox-dev and /tmp/hb.
