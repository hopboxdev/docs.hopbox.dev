Sign in the CLI, and make API keys and SSH keys

The console uses a session cookie. Every other client needs a credential of its own (CLI tokens, API keys, admin API keys, and SSH keys). The hopbox CLI signs in with a device flow and gets CLI tokens. Scripts use API keys. The hopbox Terraform provider uses an admin API key. SSH clients use SSH keys. This guide makes each of them on a laptop install, and calls the API with each one.

This guide calls the API with curl, so it shows each call that a client makes. Use the hopbox CLI does the same work with the hopbox CLI, and Use the console does it in a browser.

What you need

Section titled “What you need”
  • An install on a laptop with a domain and a signed-in instance admin, as at the end of First sign-in on a new install. This guide uses the API on 127.0.0.1:7080, the bootstrap config /tmp/hb/hopboxd.toml, and the domain example.com.
  • The shell function browser of that guide, which calls the API as the console does, with your session cookie.
  • curl, ssh-keygen, and python3 for the JSON.

Now be the person at the console. The page https://example.com/device takes the user code and looks it up with your session. Case and the dash do not matter:

The page shows this client to you. If it is not your own CLI, do not approve: someone else started it and sent you the code. If it is yours, approve with the start time that the page showed:

The approval needs a recent sign-in: you must have signed in within the last 10 minutes (Sessions, cookies, and sign-in links). The approval makes a CLI sign-in that can live longer than your session. So someone who takes over an old session cannot make one. If your sign-in is older, the call fails with permission_denied:

The code keeps waiting. Sign in again with a new login link, as in First sign-in on a new install. Print the link:

Put the part of the link after #token= in TOKEN. Then sign in with your old cookie, as a browser does. The new sign-in ends the old session and starts a new one (Sessions, cookies, and sign-in links). Take the new cookie, and approve again:

The console does the same for you. Its page /device asks you to sign in again, then shows the code again.

Wait 10 seconds, and poll again. The poll gets the CLI tokens, once:

A second poll fails with unauthenticated, because the device code works once. A code that nobody approves expires after 10 minutes.

Refresh the tokens

Section titled “Refresh the tokens”

Before the hour ends, the CLI trades its refresh token for new tokens. Each refresh token works once:

Now send the old refresh token again, as a thief with a copy of it does. Within 10 seconds of the refresh, the old token still works once, so that two CLI processes that refresh at the same time both succeed. So wait first:

The reuse ended the whole CLI sign-in, with every token of it. The log of hopboxd has a replaced CLI refresh token came back, so its sign-in ends, and the audit log has auth.end_cli_sign_in. Run the device flow again to get new tokens. A CLI ends its own sign-in with AuthService/SignOut and its access token. From the console, list your CLI sign-ins with AccountService/ListCLISignIns, and end one that is not yours with AccountService/EndCLISignIn.

Add an SSH key

Section titled “Add an SSH key”

Make a key, or use the one that you have. RSA keys need at least 3072 bits, so Ed25519 is the simple choice:

The fingerprint matches ssh-keygen -lf /tmp/hb/id_ed25519.pub. The comment became the name. A key works for one account only, so the same key on another account gets already_exists. The SSH front door finds your account by this key (Reach a machine over SSH).

Read the audit log

Section titled “Read the audit log”

Every step above is in the audit log of the install:

The newest entries come first. Root wrote admin_key.list, admin_key.register, and admin_key.create. Your session wrote api_key.revoke, ssh_key.add, api_key.create, and auth.approve_device. The CLI sign-in wrote auth.sign_in with the method device. anonymous wrote auth.end_cli_sign_in for the reused token, and auth.start_device_authorization. No entry holds a token, a key, or a device code (CLI tokens, API keys, admin API keys, and SSH keys).
