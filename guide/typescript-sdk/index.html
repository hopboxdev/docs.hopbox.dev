Call the API from TypeScript

The TypeScript SDK @hopbox/sdk is not on npm yet. You build it from the source of hopbox, which is not public yet. So today, only people with access to the source can follow this guide.

This guide calls the API of an install from a Node.js script with the TypeScript SDK. The script reads the install and the account, lists the machines, and runs a command in a machine. Then the guide copies a file in and out, and shows how the console opens a shell in a browser. TypeScript SDK has every function, option, and error.

The SDK wraps the generated client of each service with the same rules as the Go client of the hopbox CLI. It retries a call that failed with unavailable, resource_exhausted, or deadline_exceeded twice, after a short random wait, if a second run of the call does no harm. It puts an idempotency key on each create, so a retry never makes a second machine. Each error is a class of its own, such as NotFoundError, with the request ID of the server.

What you need

Section titled “What you need”
  • A checkout of the source of hopbox, with corepack pnpm install done.
  • Node.js 24 or later.
  • An account on an install, and an API key of your org in HOPBOX_API_KEY, in the form hbx_<key>. Make the key with hopbox api-key create, as in Use the hopbox CLI. This guide uses the install https://example.com, with a running machine box1.

See the retries

Section titled “See the retries”

Pass a logger to see each retry. console works:

Run the script against a port of your laptop where nothing listens, such as HOPBOX_URL=http://127.0.0.1:1. Each call that cannot reach the install fails with unavailable, so the client tries it 3 times. Before each retry, it logs retrying a call with the procedure, the code, and the wait. Then the script prints the error:

The request ID is empty, because the call never reached an install. The waits are random, up to 500 ms and then up to 1 s.

The client retries only a call that is safe to run again (TypeScript SDK). GetInstallInfo only reads, so it gets its retries after any of the three codes. A call that changes state and has no idempotency key, such as createInvitation, is different. A lost answer does not tell the client whether the install ran the call, and a second run sends a second invitation. So the client retries such a call only when its try surely did not reach the install. In Node.js, a refused connection is such a case. To see it, save this script as invite.mjs, and run it with the same HOPBOX_URL. The org ID does not matter, because the call never reaches an install:

node invite.mjs logs two retries, as above, and then fails with unavailable. An install refuses the call with the member key of this guide: with failed_precondition in a personal org, and with permission_denied in another org, where only an org admin or an org owner invites (the org API).

A browser cannot tell a refused connection from a lost answer, because fetch rejects both with a TypeError. So in a browser, the same call fails after one try. The install marks each refusal that changed nothing with the header Hopbox-Not-Run: 1, such as a rate limit, and each client retries such an answer.
